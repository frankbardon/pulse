# Guided analysis — Explain, Glossary and the jargon rule, Virtual skills

Per-topic slice of the guided-analysis reference (Explain, Glossary and the jargon rule, Virtual skills). Index (preamble + section map): `.claude/reference/guided-analysis.md` — load it first, then only the slice(s) your change touches.

## Explain (U22)

`Pulse.Explain(ctx, descriptor.ExplainRequest{Request | Composed | Chain | Facet | Sample | Response, Detail?})` says in plain words what a request will do (REQUEST mode, E3-S1) or what a response found (RESPONSE mode, E3-S2; Compose / Chain / Facet results E3-S3, see Result roots) — both fill the same result type. Types live in `descriptor/explain.go`; logic in the NO-EXECUTE `internal/guide/explain.go` (`TestGuideNoExecutionImports`); the facade (`explain.go`) only wires `guide.Checks`.

- **Input.** Exactly one request root, keyed by the request-template target spellings (`request`, `composed`, `chain`, `facet`, `sample`); none or several, or a `detail` other than `terse` (default) / `full`, is `SERVICE_VALIDATION` — checked before any cohort opens (`guide.ValidateExplainRequest`).
- **Output** (`ExplainResult`, fixed here for S2): `{mode, root, detail, summary, valid?, steps[]?, findings[], defaults_applied[]?, advisories[]?, refusals[]?, warnings[]?, sentences[]?, glossary_refs[]?, follow_ups[]?, caveats[]?}`. `findings` is always an array (empty in request mode); a finding is `{subject, operator?, verdict, strength_band?, convention?, numbers{}, multiplicity?{method, family, m}}` with the closed `Verdicts()` enum and `numbers` values `*float64` (an undefined figure is `null`). Terse = `summary` (one sentence) + the structured parts (`steps`, `findings`, `defaults_applied`, `advisories`, `refusals`, `caveats`); `full` adds `sentences` (summary, step texts, advisory messages), `glossary_refs` (the named operators' `Purpose.Glossary` terms the PRUNED ontology keeps) and `follow_ups` (their declared `FollowUps` through the same `keepAlternatives` Recommend uses), and appends each test / post-test / regression's `Assumptions` to `caveats` as `"OP: <assumption>"`. **Caveats stay in terse** — they say what was not checked and what predict refuses, which a reader must not lose (S2's mandatory many-tests caveat rides the same slot).
- **Steps.** One per slot, in the order the engine applies them: joins, filterers, features, attributes, windows, groups, aggregations, crosstab, tests, post_tests, regressions, matrices, overlays, then `weight` and `multiplicity` sentences. `slot` is the wire path, prefixed by the slot's place in its root (`requests[1].aggregations[0]`, `stages[0].request.groups[0]`); a Compose root adds its own `overlays[k]` / `multiplicity`, a chain its whole-chain overlays, a facet its field list, filters, additive fields, top-K, quantiles, histogram and overlays, a sample its row cap and label bindings. A step's `text` is a template over the slot's structure (`"Aggregation 1 runs AGG_SUM on `score`."`) plus the operator's scrubbed `Purpose.Plain`; the summary counts steps by role (`"This request reads `c.pulse` and runs 1 grouping and 2 aggregations."`). **Item fan-out (U41 E3-S4).** Feature, attribute and window steps describe the items that RUN: each request is expanded with the one `descx.ExpandRequestItems` (no derived-column limit — predict's check reports that), so a `for_each` item yields one step per combination, each keeping the WRITTEN slot (`windows[1]`) and naming its column (`, adding the column `x_ad30``), preceded once by a plain `<slot>.for_each` step stating the fan-out (count, axes, grid / zip); the summary counts expanded items. A `for_each` that does not expand is a caveat naming the code and its items are described as written (`internal/guide/explain_for_each.go`; `TestForEach_Explain`). Recommend needs no change: its drafts never carry `for_each` and a drafted window fans out as written (`TestForEach_Recommend`).
- **Predict.** A root naming a cohort is predicted IN-PROCESS with the facade's `predictOptions` (instance snapshot, defaults, suppression, the cohort's sidecar facts): `Request` → `descx.Predict`; `Composed` → `ValidateComposeWithOptions` with `SidecarLoader` wired (batch errors + every slot's advisories, prefixed) plus a per-slot `Predict` for each slot's inferred defaults; `Chain` → `ValidateChainWithOptions` plus a stage-0 `Predict` for its defaults (later stages' defaults resolve against the previous stage's output at run time — a caveat says so; a chain carries no advisories, as in predict); `Facet` → `ValidateFacetWithOptions`; `Sample` is never predicted. A single-file cohort is an open handle read for header + schema only (`openGuideCohort`, shared with bound Recommend; `TestExplain_FacadeReadsNoRecord`). An inferred operator fills its untyped step (`defaulted: true`, `"AGG_SUM is inferred for `score` from its type."`) and is listed in `defaults_applied` (predict's `DefaultApplied`, `path` prefixed `Requests/<i>` or `Stages/0/Request`). Predict's verdict is `valid` (nil when nothing was checked — no cohort, or a sample — with a leading "No cohort is named…" caveat); each predict error lands verbatim in `refusals` (`details.slot` names a Compose slot) and as a caveat naming ONLY its code — predict's message is engine prose, not an Explain template, and would not pass the prose lint. Each predict WARNING lands verbatim in `warnings` (U44 #309; the same `details.slot` rule, no caveat), once: a Compose slot's warning that the Compose check already reports located `details.request` is not repeated from the slot's own predict. A cohort that cannot be opened is `DATA_FILE`, a malformed header / schema `ENCODING_INVALID`.
- **Response mode** (E3-S2). `ExplainRequest.Response` (a Process `Response`) with `Request` as its optional companion — the request that produced it; any other request root beside a response is `SERVICE_VALIDATION`. `mode: response`, `root: response`; `valid`, `steps`, `defaults_applied`, `advisories`, `refusals`, `warnings` stay empty, and no cohort is opened. Logic: `internal/guide/explain_response.go`. One finding per test / post-test result (a nil `return`-skipped position is skipped), per regression (a model finding, then one per predictor coefficient — never `(intercept)`), per overlay layer, per matrix result and per aggregation slot. **Verdict** (closed `Verdicts()`): a test's p is evidence of a `difference` or an `association` by the family's class (`testClass` / `overlayClass`, held complete by `TestExplainResponse_ClassTablesComplete`; an extension is `association` when its Purpose serves `relationship` / `drivers`, else `difference`); a regression coefficient's is `evidence_of_effect` / `no_evidence_of_effect`; aggregations, matrices, model fits and descriptive overlay kinds are `descriptive`; an undefined p is `not_computable` — NaN in Go, and after a JSON round trip the `p_value: 0` + `reject_null: false` pair no defined p produces. The prose says "no evidence of a difference", never "no difference". **Alpha** is the result's own `TestResult.alpha` (never an assumed 0.05). When a correction ran the verdict reads `significant_adjusted` (an overlay: `summary.significant_adjusted`, or each cell's `payload.significant_adjusted`) and the finding names `multiplicity {method, family, m}`; the raw p never decides it. A regression and an UNCORRECTED overlay carry no alpha of their own: they are read against 0.05 and a caveat says so ("Regression p-values are raw…", "OVERLAY_X carries no alpha of its own…"). An overlay's p-values sit where its Interpretation's `Shared: "p-value"` field says (`summary.p_value`, `scalar`, `summary.statistic`, `cells.value`, or each series entry's summary); a per-cell / series layer is one finding with `tests` + `below_alpha` (or `below_alpha_adjusted`) and is evidence when any cell is. **Bands**: `strength_band` only from an Interpretation with bands, always with `convention` (the Interpretation's citation), via `descx.BandOf` (reads `|v|` under `Abs` and `max(v, 1/v)` under a registered SymmetricLog convention); a test bands its first banded effect size (the family's declared order), then `statistic`; a regression its `r2` / `adj_r2` / `pseudo_r2`; `MAT_CORRELATION` its strongest off-diagonal value. An unbanded effect size gets its number only. **Numbers** are keyed by Interpretation path (`statistic`, `p_value`, `alpha`, `df`, `p_adjusted`, `details.effect_size.<k>`, `summary.p_value`, `scalars.<k>`) or component key (`n`, `n_null`, `sum_weights`, `n_eff`, `n_weight_invalid`, `n_listwise_dropped`, `value`); an undefined figure is `null`. **Caveats** (terse too): ≥2 uncorrected p-values from tests, post-tests (not the self-controlling `TEST_TUKEY_HSD`) and overlay cells → a caveat citing `PULSE_ADVISORY_MANY_TESTS`, plus a separate remedy sentence naming `multiplicity` / `p_adjusted` that the prose scrub drops on an instance hiding the capability (the cited caveat survives); without the companion, a "Partial reading" note; absent Components (rows left out not reported), a `returned` marker, a `partial_cohort_reason`. **With the companion** each aggregation names its operator, its scrubbed `Purpose.Plain` and its weight (the slot's own, else the request's; a `null` slot is unweighted); **without it** an aggregation is its Components label and floor only (`n`, `n_null` as rows left out, `sum_weights` flagged as an unnamed weight) and the summary says "aggregated output of N rows across G groups" — never a guessed operator. The summary counts the parts, the run's records (`components.run`, else `metadata`) and how many inferential findings show evidence. Full detail adds one sentence per finding plus the `Run` floor sentence, glossary refs and follow-ups of every named operator, and the inferential operators' assumptions. A hidden operator is never named (the finding keeps its verdict, `operator` empty). Every response-mode finding carries `slot`, the wire path of the result it reads (`tests[0]`, `regressions[0].coefficients.hours`, `aggregations[0]` — an aggregation by its request slot).
- **Result roots** (E3-S3; `internal/guide/explain_results.go`). Exactly one result root — `response`, `composed_response` (`ComposedResponse`), `chain_response` (`ChainResponse`), `facet_result` (`FacetResult`) — with at most ITS OWN companion (`request` / `composed` / `chain` / `facet`); two result roots, or any other request root beside one, is `SERVICE_VALIDATION`; `root` echoes the result root's name. Each larger result reuses the Process-response reader under a SCOPE (sentence lead `"Request 2's test 1 (TEST_T) …"`, `"Stage 1's aggregation 1 …"`, `"Field `region`'s overlay 1 …"`, `"The batch's overlay 1 …"`) and a path prefix, sharing ONE reader so the many-tests caveat counts the WHOLE result: **Compose** — each slot `responses[i].…` with the batch request's `Requests[i]`, a per-slot sentence (`"Request 2 reports 1 test …"`) ahead of its findings, then the batch overlays (`overlays[k]`), each naming its `multiplicity {method, family: compose, m}`; the cross-slot count matches predict's per-slot + host-overlay advisories. **Chain** — each stage `stages[i].…` read with the response's echoed `normalized_request` FIRST (what the engine ran, defaults resolved), else the `chain` companion, so an echoed chain names its aggregations with no request supplied; `final` alone is read as the one stage; whole-chain overlays follow. **Facet** — one block per field (`fields.<name>`, the companion's field order then sorted): a descriptive finding (discrete: `distinct_count`, `top_count`, `truncated_at`, `null_count`; numeric: `count`, `min`, `max`, `mean`, `stddev`, `sum`, `percentiles.<k>`; a numeric field with no value is `not_computable`, `mean` null), then the overlay layers decorating it (tied by the companion spec's `params.field`, else the only field); then `additive.<name>` blocks and any layer no field could host (with a caveat when the companion is absent). Per-result caveats are scoped (`"Request 2's response carries no components …"`); an overlay layer's `warnings` become a caveat naming their CODES only (the messages are engine prose and stay in the slot), as do a facet's `warnings` (counted). The partial-reading caveat names the missing companion (`composed`, `chain` — "or run the chain with its request echoed" — `facet`).
- **Profiles + prose.** A step naming a hidden operator gets no `operator` and says the instance does not offer it (plus a caveat); every summary, step text, advisory message and caveat passes `ProseScrub.Text`; glossary refs and follow-ups come from the pruned ontology (`TestExplain_ProfileHidesOperators`, root `TestExplain_FacadeProfiled`). Every template passes `LintGuidanceText` (`TestExplain_ProseLint` over all five roots × both details; the binding golden-wide `TestExplainProseLint` below). Not an observed operation (`.claude/reference/observability.md`, Not operations).
- **Surfaces** (E3-S4). CLI `pulse explain --request F | --response F [--request F] [--root request|composed|chain|facet|sample] [--detail terse|full] [--json]` (`internal/cli/explain.go`, a thin adapter: `--root` names which root the files hold — default `request`; a `--response` file that is a `--json` envelope is unwrapped to `data`; `CLI_INPUT` for no file, a bad root, `sample` with a response or unreadable JSON; other refusals keep their own code) and MCP `pulse_explain` (`ExplainIn`: every root an OPEN object — the agent learns request shapes from the execute tools — re-encoded and decoded into its typed slot by `HandleExplain`; a root that does not decode is `SERVICE_VALIDATION` with `details.field`). **Undefined figures stay undefined on the way back in.** A result root (`response`, `composed_response`, `chain_response`, `facet_result`) is decoded through `internal/jsonfinite.Unmarshal` — `types.MarshalFinite`'s inverse: a JSON `null` in a non-pointer float slot is NaN, not the 0 plain `encoding/json` leaves — on both surfaces, so a `null` statistic, p-value or coefficient p reads `not_computable` with a `null` number rather than as a real 0 (a null coefficient p would otherwise read `evidence_of_effect`). Request roots decode with plain `encoding/json` (a null request float means unset). Both surfaces bind to the hideable feature `capability:explain` (Since 1.0.0, no dependency edge): hiding it unmounts the tool, drops the manifest `explain` command and the payload-schema roots `ExplainRequest` / `ExplainResult`; the facade stays callable. `ExplainRequest`'s own root slots follow their capabilities (`gatedSlots`), so an instance hiding compose has no `composed` / `composed_response` property and no `ComposedRequest` / `ComposedResponse` def through it (`TestExplain_HiddenFeatureSurfaces`, `TestRegister_ExplainFollowsItsFeature`); the closed `ExplainDetail` / `ExplainMode` / `ExplainRoot` / `Verdict` vocabularies are schema enums. Goldens `descriptor/testdata/explain.<family>.<terse|full>.<with|without>_request.json` for every family {test, regression, overlay, matrix, descriptive, compose, facet, chain}, plus request mode `explain.request.<detail>.json` over the Recommend fixture cohort (`TestExplainGolden`, `-update`); the result fixtures travel through the same JSON round trip the surfaces use (written by the wire rule, read back through `jsonfinite`), and `TestExplainGolden_NullFigureStaysUndefined` pins the null case. **`TestExplainProseLint`** (binding) runs `LintGuidanceText` over the template-built prose — `summary`, step texts, follow-up conditions, `sentences`, `caveats` — of every golden case, both as generated now (a non-compliant template fails before a golden moves) and as stored on disk, and requires every case's golden to exist; `refusals`, `warnings` and advisory messages carry verbatim engine text and are not linted.

## Glossary and the jargon rule

A `Jargon: true` term must be LINKED (listed in `Purpose.Glossary`) wherever one of its `Forms` appears in a `Plain` sentence. Matching is case-insensitive, word-boundary, longest match wins (`jargonTermsIn`; `TestJargonTermsIn_LongestMatchWordBoundary`). `pulse.Glossary()` returns the whole registry on every instance; the instance ontology prunes a term only when ≥1 operator cites it (`Purpose.Glossary`) and every citing operator is hidden, and the `glossary` virtual skill renders from that graph, dropping SeeAlso links into pruned terms.

## Virtual skills

`glossary` and `intents` are skills with no file, rendered as markdown from the registries (`RenderGlossarySkill` / `RenderIntentsSkill`, `internal/descriptor/guidance_skills.go`) and registered through `skills.RegisterVirtual` at init. Kind `reference` (`skills.KindReference`): no atomic family, no `##` set, no budget. They reach every skill surface — `pulse skills list|show`, `pulse_skills_list` / `pulse_skills_get`, the `pulse-skill://glossary` / `pulse-skill://intents` exact resources, manifest `skills[]` — and no feature profile hides them; on a profiled instance their BODIES render from the pruned ontology (`renderIntentsSkill` / `renderGlossarySkill` with the graph's keep filter, via `Discovery.Skill`), so a pruned intent or term is absent. `TestDiscovery_VirtualSkillsRenderPrunedGraph` and the root `TestGuidanceSkills_NeverPrunedByFeatureProfile` (served sections = surviving nodes) pin it. The stems are reserved (`skills.ReservedVirtualNames`; `TestVirtualSkillStemsNotEmbedded`). Mechanics: `.claude/reference/skill-pack.md` (List source of truth). Facade: `pulse.Glossary()` / `pulse.Intents()` return deep copies in declaration order.

**Skills for an intent (U23 E2-S3).** `pulse.SkillsForIntent(intent)` / `pulse_skills_list {intent}` (`InstanceSnapshot.SkillsForIntent`, `internal/descriptor/skills_for_intent.go`) rank the instance's skills for one intent, every edge read off the PRUNED ontology: tier 1 the skills the intent node is `documented_by` (the virtual `intents` skill); tier 2 the `kind: design` skills whose rendered `covers` names an operator serving the intent (`OperatorsServing`) or that operator's category prefix (`TEST` covers `TEST_T`), by name; tier 3 the atomic skills those operators are `documented_by`, by the operator's `Purpose.Level` (basic → intermediate → advanced; no Purpose / Level last — built-in registry, else `ExtensionsSnapshot.PurposeOf`), then name. Level is JOINED through the skill's `operator`, never stored on skill metadata. Each entry is the rendered metadata `Skills()` lists; an intent no operator serves (`lookup`; `flows` was one until U28) answers `intents` alone. The intent resolves through `InstanceSnapshot.checkIntent` — the ONE resolver example search shares — so an unknown or pruned intent is `PULSE_RECOMMEND_INTENT_UNKNOWN` with `details.valid` = the instance's intents. No intent: `pulse_skills_list` is `Skills()` byte-identically, and `Skills()` itself is unchanged. Pinned by `TestSkillsForIntent_Ranking` / `_NoServingOperator` / `_ProfilePruning` and `TestSkillsList_IntentArg` (`internal/mcp`). Not an observed operation (`.claude/reference/observability.md`, Not operations).

**Generated skill sections.** An atomic skill's `<!-- generated: use-when -->` / `<!-- generated: reading-the-output -->` markers render from the operator's `Purpose` / `Interpretation` at read time (`internal/descriptor/skill_sections.go`; contract: `.claude/reference/skill-pack.md` (Generated sections)). That is on-demand skill text, so `TestManifestGuidanceBudget` is unaffected; the glue text is held to the prose lint's text rules by `TestSkillSections_BuiltinsWithinCapsAndLint`.

**Generated reference (docgen).** `internal/docgen` renders the same registries into an instance-scoped Markdown tree: one catalog page per `PurposeSurfaces()` category (summary table Operator | In plain words | Answers questions like | Level | Instead, when…, then a detail block per operator under anchor `op-<lowercased name>`), a glossary page (anchor `term-<id>`) and every visible skill as `Discovery.Skill` serves it. It walks the PRUNED ontology: a hidden operator has no row, block, skill page or link; a not-for alternative whose target the prune removed is dropped; every Purpose / glossary prose string passes `ProseScrub.Text`. Glossary terms are kept by the virtual glossary skill's keep-function (owning operators), and a kept term's `Forms` are spellings rendered verbatim — never token-scrubbed (so "transition matrices" survives a matrices-hidden instance with its term). An extension operator without a `Purpose` renders "No guidance provided." plus its manifest description. Docs on disk are outside `TestManifestGuidanceBudget`. **Reading pages** (`reading.md` + `reading/<family>.md`): one Interpretation page per family — `test`, `regression`, `matrix`, `overlay`, `descriptive` (aggregator / attribute / filterer / grouper / window / feature / synth distribution) — each field rendering `Means`, `Bands` under the named `Convention`, `Sign` and `Caveats`, scrubbed like all prose; a field whose PATH names a hidden token (`p_adjusted` without `capability:multiplicity`) is dropped whole, and a family with no visible entry has no page. A shared rule set (the p-value reading) renders ONCE, at the top of the first page citing it (the Test page whenever a test is visible, anchor `shared-<key>`), and every citing field links there. `reading/components.md` documents the slot floors (`ComponentFloors()`), the weighted floor keys (`WeightFloorKeys()`, only when `capability:weighting` is offered), the mergeability classes and every visible operator's own `ComponentSchema` keys from the instance manifest. **Preserve markers:** hand-written prose inside a generated page sits between `<!-- docgen:preserve begin <id> -->` and `<!-- docgen:preserve end <id> -->` and is copied verbatim from a file EMBEDDED in `internal/docgen` (so an export outside the repo carries it); the Components intro's source of truth is `internal/docgen/components_intro.md` — edit it there, never in a rendered page. **Question pages** (U31): `questions.md` ("What can Pulse answer?": one row per guide — `Intent.Label` linked, the first `Sounds` phrasing — plus a mention of the utility intents, which get no guide) and `questions/<intent_id>.md`, one per analytic intent the instance keeps that a visible operator serves, titled by `Intent.Label`, in six parts: the question; pick your analysis (the intent's `Shapes`, then every visible serving operator grouped by category, basic first, with `Purpose.Plain` + Level); a worked story (the first story example whose FIRST `_meta.intents` entry is the intent and whose operators are all visible: request, the committed golden from `examples.StoryGolden` verbatim — docgen never executes — and `_meta.interpretation`); how to read (the story operators' Interpretation fields); pitfalls; next steps (the three guides sharing most serving operators, the intent's non-atomic skills plus the story operators' skills, and real CLI leaves gated on their capability). Hand prose lives in `internal/docgen/guides/<stem>.md` (`index` for the landing page), sections opened by whole `<!-- section <name> -->` lines — `intro` (landing), `question` and `pitfalls` (guides) — rendered in `guide-<intent>-<section>` / `questions-<section>` preserve spans and passed through `ProseScrub.Text` (verbatim on an instance hiding nothing it names); a missing file or section renders a generated fallback outside any span. `TestProse_EmbeddedFilesWellFormed` refuses an unknown stem or section, and question pages pass the same lint as reading pages (`TestRender_QuestionPagesLint`). Every reading page passes `LintGuidanceText` line by line (`TestRender_ReadingPagesLint`, with the registry allowlist's two shared p-value exemptions mirrored).
