# Byte layout — memory-mapped reads and atomic rewrites (unix and Windows)

Per-topic slice of the byte-layout reference (how a single-file cohort is mapped for a read, on which platforms, and what a mapping does to the atomic rewrites that replace a cohort). Index: `.claude/reference/byte-layout.md` — load it first, then only the slice(s) your change touches.

**Memory-mapped reads — platforms.** A single-file cohort on an fs that resolves a real on-disk path (`resolveRealPath`: `*afero.BasePathFs` over `OsFs`, the default `PULSE_DATA_DIR` shape, or any fs implementing `RealPath`) is read through `mmapFileBytes`: the streaming iterator maps it for the whole iteration and releases it on `Close`; the parallel decode maps it for the decode and releases it before the operation returns.

- **Platforms:** `mmap_unix.go` (darwin, linux, freebsd: `PROT_READ` / `MAP_SHARED` + `MADV_SEQUENTIAL`), `mmap_windows.go` (`CreateFileW` with `FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE`, `PAGE_READONLY` mapping; cleanup unmaps, then closes the section, then the file), `mmap_other.go` (every other GOOS) errors and the read falls back to `afero.ReadFile`. An empty file maps to nil with a no-op cleanup; a special file is refused and falls back.
- **Every mmap gate asks the build first:** `mappableRealPath` (`mmap_capability.go`) backs predict's `DecodeMappable`, `canParallelDecode` (bail reason `mmap unsupported on this platform`), the parallel dispatch pre-gate and the streaming iterator — so on an unmapped GOOS predict charges the serial arm the run takes (`TestMmapCapability_PredictMatchesRuntime`, which flips the capability on every OS). The build-tagged `mmapSupported` constant is the tests' only platform predicate — never a `runtime.GOOS` list.
- A mapped read is charged to `observe` `bytes_read` by `noteMapped` (no afero `Read` happens). Shard archives, sidecars, model files and everything else are never mapped.

**Pulse's own mappings never block its rewrites.** Every mapping ends with the operation that took it, and every atomic rewrite (temp file + fsync + rename over the target) MUST release its own source before its rename — Windows refuses a rename over an open file. A rewrite that renames over its still-open source works on unix and fails only on Windows, so a new rewriter must close its readers first (in-place filter-to-file uses `commitAfter` to release between finish and publish). Rename failures carry a coded error (`ENCODING_IO`, `SERVICE_RESOURCE`, or `PULSE_MODEL_WRITE_FAILED` for model / population / SEM saves). Gates: `TestMmapRewrite_AfterMap*` (`internal/integration/mmap_rewrite_test.go`, every OS) and `TestHeldHandle_InPlaceRewritesReleaseTheirSource` (an afero wrapper enforcing Windows' sharing rule on every OS) — add a case for any new rewrite. An ordinary `AddShard` renames nothing: it closes its read handle, then appends in place (`byte-layout/archive-append.md`). The managed-import TTL sweep keeps a cohort's sidecar when it cannot delete the cohort and retries next sweep, rather than orphaning it.

**A view another reader holds — the recorded decision.** While ANY other reader (another process, or an embedder's mapping or handle) holds a cohort, Windows refuses a rename over it ("Access is denied") whatever share mode that reader used, Pulse's own `FILE_SHARE_DELETE` included (measured: `TestMmapWindows_HeldViewOutcome`, `TestMmapHeldView_RewriteRefusedCoded*`).

- The rewrite FAILS with its coded rename error, the cohort byte-identical to its pre-rewrite file, its stage removed, the reader still seeing the old bytes; once released, the same rewrite succeeds.
- No retry or backoff (a view can be held indefinitely; the caller can retry knowing why), and no POSIX-rename path (it would bypass `afero.Fs`, and a foreign reader without `FILE_SHARE_DELETE` would still refuse it).
- A delete of a mapped cohort succeeds only when every opener allowed `FILE_SHARE_DELETE` (Pulse's views do, Go's `os.Open` does not). On unix a rename over or delete of a mapped file always succeeds and the view keeps the old inode; truncating a mapped file under a reader can `SIGBUS` it there (Windows refuses the truncation instead).
