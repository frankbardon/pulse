# Byte layout — memory-mapped reads and atomic rewrites (unix and Windows)

Per-topic slice of the byte-layout reference (how a single-file cohort is mapped for a read, on which platforms, and what a mapping does to the atomic rewrites that replace a cohort). Index (preamble + section map): `.claude/reference/byte-layout.md` — load it first, then only the slice(s) your change touches.

**Memory-mapped reads — platforms (U77 E2-S1).** A single-file cohort on an fs that resolves a real on-disk path (`resolveRealPath`: `*afero.BasePathFs` over `OsFs`, the default `PULSE_DATA_DIR` shape, or any fs implementing `RealPath`) is read through `mmapFileBytes`: the streaming iterator (`stream.go`) maps it for the whole iteration and `Close` releases it; the parallel decode (`buildParallelDecodeContext`) maps it for the decode and its cleanup releases it before the operation returns. `mmap_unix.go` (darwin, linux, freebsd: `unix.Mmap` `PROT_READ` / `MAP_SHARED` + `MADV_SEQUENTIAL`) and `mmap_windows.go` (`CreateFileW` with `FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE`, `CreateFileMappingW` `PAGE_READONLY`, `MapViewOfFile` `FILE_MAP_READ`; cleanup `UnmapViewOfFile`, then `CloseHandle` of the section, then the file) carry it; `mmap_other.go` (every other GOOS) returns an error and the read falls back to `afero.ReadFile`. **Every mmap gate asks the build first:** `mappableRealPath` (`mmap_capability.go`; `mmapCapable()` over `mmapSupported`, then `resolveRealPath`) backs predict's `DecodeMappable`, `canParallelDecode` (bail reason `mmap unsupported on this platform`), the parallel dispatch pre-gate, `buildParallelDecodeContext` and the streaming iterator — so on an unmapped GOOS predict charges the serial arm the run takes, never `parallel_decode` (pinned by `TestMmapCapability_PredictMatchesRuntime`, which flips the capability on every OS). An empty file maps to a nil slice with a no-op cleanup on both; a special file (Windows: anything not regular) is refused and falls back. A mapped read is charged to `observe` `bytes_read` by `noteMapped` (no afero `Read` happens). Shard archives are never mapped (`shardIter` reads through one afero handle), nor are sidecars, model files or anything else Pulse reads. The build-tagged `mmapSupported` constant is the tests' only platform predicate — never a `runtime.GOOS` list. Before U77 Windows read through the fallback, so the parallel-decode arm, the totals two-phase pre-pass and the `reduce` phase never ran there; output is identical, only the arm and its observability differ.

**Pulse's own mappings never block its rewrites.** Every mapping Pulse takes ends with the operation that took it, and every atomic rewrite (temp file + fsync + rename over the target) releases its own source before its rename. Audit (U77 E2-S1), each pinned by `TestMmapRewrite_AfterMap*` (`internal/integration/mmap_rewrite_test.go`, every OS) and `TestHeldHandle_InPlaceRewritesReleaseTheirSource` (`internal/service/held_handle_test.go`, an afero wrapper enforcing Windows' sharing rule on every OS): `WidenSetField` (closes the source, then renames; `ENCODING_IO`), `Dedup` in place (closes each pass's reader; `ENCODING_IO`), `Materialize` / `Rake` / `NewCohortBuilder` overwrite, `Materialize` in place (the scan iterator and exact-value reader close before the builder's `Close` renames; `ENCODING_IO`), `Import` / `import transfer` (`ENCODING_IO`), `FilterToFile` (`stagedStream` publish, `SERVICE_RESOURCE`) — **in place (`src == dst`, single file, archive, or an anchored shard over its own archive) it used to rename over its still-open source, which Windows refuses; the source is now released between finish and publish (`commitAfter`)** — `FilterToFileWithRequest` (its second rename, now `ENCODING_IO`; it was the one uncoded rename failure), `AddShard` / `RemoveShard` / `CompactShardArchive` (close the archive before publish; an ordinary `AddShard` renames nothing — it closes its read handle, then opens the archive for writing and appends in place, a refused write-open being `PULSE_SHARD_APPEND_REFUSED`, `byte-layout/archive-append.md`; `CreateShardArchive` only reads its sources; `SERVICE_RESOURCE`), index upkeep and `BuildIndex` (sidecars only; a cohort scan's view is released before any sidecar is written), `DropIndex` (`SERVICE_RESOURCE`), model / population / SEM file saves (`PULSE_MODEL_WRITE_FAILED`), and the managed-import `Drop` (now `SERVICE_RESOURCE`) / TTL sweep (a cohort it cannot delete keeps its sidecar and is retried by the next sweep, instead of being orphaned).

**A view another reader holds — the recorded decision (U77 E2-S1, owner decision #4).** Measured on the Windows CI runner (`TestMmapWindows_HeldViewOutcome`, `TestMmapHeldView_RewriteRefusedCoded*`): while ANY other reader — another process, or an embedder's own mapping or open handle — maps a cohort, Windows refuses a rename over it (`MoveFileEx`, which `os.Rename` and so every afero rename call: "Access is denied") whatever share mode that reader opened it with, Pulse's own `FILE_SHARE_DELETE` included. So the rewrite FAILS with its existing coded rename error (the codes above), the cohort byte-identical, its stage removed, and the reader's view still reading the old bytes; released, the same rewrite succeeds. No retry or backoff (a view can be held indefinitely, and the caller can retry knowing why), and no POSIX-rename path (it would bypass `afero.Fs`, and a foreign reader opened without `FILE_SHARE_DELETE` would still refuse it). A delete of a mapped cohort succeeds only when every opener allowed `FILE_SHARE_DELETE` — Pulse's views do, Go's `os.Open` does not — and the view keeps the old bytes. On unix a rename over or a delete of a mapped file always succeeds and the view keeps the old inode's bytes; truncating a mapped file under a reader can still `SIGBUS` it there (Windows refuses the truncation instead).
