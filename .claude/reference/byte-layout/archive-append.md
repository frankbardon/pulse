# Byte layout — `shard add` appends to the archive tail

Per-topic slice of the byte-layout reference (the in-place tail append an ordinary `shard add` takes, its Zip64 records, its concurrent-reader decision and its failure story). Index (preamble + section map): `.claude/reference/byte-layout.md` — load it first, then only the slice(s) your change touches. The archive layout itself is in `byte-layout/long-form-and-model-files.md`; the index upkeep the append keeps is in `byte-layout/archive-index.md`.

**Shard add tail append — in place (U73 #492).** An ORDINARY add — `mergeShard` returned no `rewrite` (no archive-level set rung widen, no constant-group promotion: every stored shard keeps its bytes; a dictionary that only GROWS is ordinary, stored shards' dictionaries stay canonical prefixes), every entry is store-only, and the tail is one the appender extends — writes nothing before the archive's old end. `Service.appendShard` (`internal/service/shard_append.go`) appends, at the old file length: the new shard's local entry, a refreshed `_schema.pulse` (aggregate, shard count, the dictionary union), then a NEW central directory, the zip64 end record + locator when needed, and the EOCD. The directory lists the new `_schema.pulse` FIRST, every stored shard's old record VERBATIM in archive order (local-header offsets, CRC32s, sizes and any zip64 extra stay valid: the bytes they point at never move), then the new shard — the entry order a create writes — and DROPS the superseded `_schema.pulse` record, so no reader ever sees two; the old directory, old EOCD and old `_schema.pulse` stay in the file as DEAD bytes no directory references (`DirectoryBytes` stays `size − max(entry data end)`, the live directory only; `CompactShardArchive` reclaims them and lands byte-identical on a create of the same shards — `TestShardAppend_AddAppendsInPlace`). Bytes written = new shard + `_schema.pulse` + the directory (O(shards)), whatever the archive's size (`TestShardAppend_WriteVolumeIsIndependentOfArchiveSize` counts them to the byte). No `.pulse` version byte or SHRD change: a reader of any earlier build reads the result. **The writer is hand-written** (`internal/encoding/archive_append.go`: `ReadArchiveDirectory`, `ArchiveAppender`, `CentralRecord`) because `zip.Writer` builds its directory only from entries it wrote; every byte is the one `zip.Writer.CreateHeader` + `Close` writes for the same store-only entry — local header with zeroed CRC/sizes, payload, data descriptor (flag `0x8`), the CP-437-safe UTF-8 flag rule — pinned byte-for-byte by `TestArchiveAppender_MatchesZipWriterBytes`, so an appended entry raw-copies (`CopyStoredEntry`) exactly like a rewritten one. **Zip64**, as `zip.Writer.Close` emits it: a record whose size or offset reaches 4 GiB carries both 32-bit size slots at `0xFFFFFFFF` and a 24-byte zip64 extra (uncompressed size, compressed size, offset), its offset slot `0xFFFFFFFF` past 4 GiB; a ≥ 4 GiB entry's data descriptor carries 64-bit sizes; a directory of ≥ 65535 records (the 65535-shard cap + `_schema.pulse` is 65536), or one larger or later than 4 GiB, adds the zip64 end record + locator with the EOCD at the sentinels (`TestArchiveAppender_Zip64Offsets`, `TestCentralRecord_Zip64SizesAndOffset` — synthetic sparse offsets — `TestArchiveAppender_RecordCountPastU16`, `TestShardAppend_AtTheShardCountLimit` (heavy)). **Which adds rewrite instead:** a widen or promotion (the staged rewrite + rename is what keeps a half-widened archive from ever being published, `TestShardAppend_ParityWithRewrite/set_rung_widens`); an archive holding a DEFLATED entry (the rewrite re-stores it); a tail `ReadArchiveDirectory` reports `*NotAppendableError` — data prepended to the archive (`directory_not_adjacent`), bytes after the EOCD (`bytes_after_eocd`), a multi-disk archive, a zip64 extensible data sector (`TestReadArchiveDirectory_Refusals`, `TestShardAppend_NotAppendableTailRewrites`); a malformed tail stays `PULSE_ARCHIVE_CORRUPT`. Parity: every appended archive's directory order, sizes, CRC32s and `_schema.pulse` equal a create of the same shards, warnings included (`TestShardAppend_ParityWithRewrite`); the shard-count cap answers before either path (`TestShardStream_ShardCountLimitRefused`). **Concurrent readers — owner decision:** an append assumes no concurrent WRITER, as every archive mutation does, and takes NO lock or lock file; a reader that opened the archive before the append keeps its OLD view — its parsed directory points only at bytes the append never touches — and reads every pre-append shard (`TestShardAppend_ReaderOpenedBeforeKeepsItsView`, real files); a reader opening after sees the new shard. The add closes its own read handle before opening the archive for writing (`os.O_WRONLY`, never truncating). **A write-open the platform refuses** — a read-only file or filesystem, on Windows another process holding the archive without write sharing — fails the add with `PULSE_SHARD_APPEND_REFUSED` (`details.reason` `open_for_write`, `details.cause`), nothing written: the archive, every sidecar and the index manifest byte-identical, no stage left (`TestShardAppend_WriteOpenRefusedIsCoded`); its fixup names `--rewrite` (the staged rewrite, which never opens the archive for writing). The same code with `archive_changed` refuses an archive whose length moved between the add's read and its write, closed untouched. **Failure and crash:** a write, flush or fsync error truncates the archive back to its old length — the old EOCD is the file's last record again — and returns the error (`TestShardArchiveAddCrashRecovery`); the next mutation still sweeps a crashed rewrite's `.pulse.tmp-*` stage. A CRASH mid-append is NOT covered by this path: the old EOCD may no longer sit in the last 64 KiB a zip reader searches, so the archive can be unopenable until the append journal (U73 E2-S2) truncates it back. **Index upkeep stays BUILD BEFORE PUBLISH:** before the archive is opened for writing, `stageAddUpkeep` scans the new shard from an in-memory TWIN archive (`appendUpkeepSource`: `_schema.pulse` + the new shard through the same appender, so the shard's name, size and CRC32 — its identity — are the ones the append records) and stages each sidecar, Bloom sidecar and the manifest; they are renamed only after the append is durable, with the mandatory `PULSE_SHARD_INDEXES_UPDATED` warning; the manifest's per-shard identity never involves the archive's own size or CRC, so every stored shard's sidecar stays fresh across the append (`TestShardAppend_IndexUpkeepAfterAppend`). An ordinary add emits no warning of its own (no index, no widen: no warning — the cheap append is the contract); the mandatory warnings of a widen, a promotion and index upkeep are unchanged.
