# Byte layout — shard set-width auto-widen, shard archives with parent groups, the sidecar point-lookup index and its manifest

Per-topic slice of the byte-layout reference (shard set-width auto-widen, shard archives with parent groups, the sidecar point-lookup index and its manifest). Index (preamble + section map): `.claude/reference/byte-layout.md` — load it first, then only the slice(s) your change touches.

**Shard set-width auto-widen.** A `pulse shard add` whose dictionary union outgrows a `set_*` field's declared bitmask does NOT refuse the shard: the field is promoted to the narrowest rung that holds the union, across the canonical `_schema.pulse` AND every shard payload already in the archive, and the merge then proceeds into a rung that fits. **A second, independent force triggers the identical promotion: the arriving shard DECLARING a different rung.** That is the case the field actually produces — a re-import of a new period infers the rung its own data needs, so a `set_u128` shard meets a `set_u64` archive with no dictionary overflow anywhere in sight, and the old behaviour refused it as `PULSE_SHARD_SCHEMA_MISMATCH` before the widen planner was ever consulted. The relaxation is ONE dimension wide and is implemented by ORDER rather than by loosening a validator: `PlanSetWidening` now runs BEFORE `ValidateStructuralCohesion` and reconciles the rungs, and cohesion then runs over the reconciled schemas as strictly as ever — which matters because `pulse shard verify` calls the same validator, and an archive whose shards really do carry different strides is a corruption signature that must stay fatal there. **The target rung is never narrower than either side declared.** A shard arriving at a NARROWER rung is promoted to the archive's rung and is the only payload rewritten; narrowing the archive to meet it would drop every selection above the target's ceiling, and would do so silently — the record still decodes, to a smaller, entirely plausible selection. `SetWidening.From != To` is the caller's test for "the archive moved"; equal means only the arriving shard did, and the mandatory warning's prose and its `details.archive_widened` both say which. **`CreateShardArchive` auto-widens on exactly the same conditions**, through the same planner and executor: refusing at seed while widening at add was an asymmetry with no defence, since the same two files produced an archive when fed one after the other and an error when fed together. It therefore returns a `*CreateShardArchiveResult` rather than a bare `error`, for the identical reason `AddShard` returns a result — a silent whole-archive rewrite is exactly the failure class this file exists to prevent, and the shards inside the archive are no longer byte-identical to the `.pulse` files the caller named. Refusing was the wrong trade — it forces a full re-import (re-read the source, re-infer, rebuild) to reach a layout a mechanical re-stride already produces, and the re-stride is strictly cheaper than the thing it would be avoiding. **But an expensive whole-archive rewrite that happens silently is exactly the failure class this file exists to prevent, so the `PULSE_SHARD_SET_WIDENED` warning is MANDATORY rather than advisory** — it names the field, the old rung, the new rung and the number of shards rewritten, and `Service.AddShard` returns an `*AddShardResult` rather than a bare `error` specifically so the warning has nowhere to be dropped. The planner is `encoding.PlanSetWidening`, which answers the question `MergeDictUnion` structurally cannot (nothing at the schema layer may perform an archive-wide byte rewrite); the executor is E4-S1's engine — `encoding.WidenSetFieldBytes` per shard payload and `encoding.WidenSchemaSetField` for the canonical block, which share ONE offset derivation (`widenFieldOffsets`) so the canonical schema block and every shard's own schema block describe the identical post-widen layout by construction rather than by agreement. A divergence there would not fail to open: it would decode every field after the widened one at the wrong offset, with the schema confidently describing a stride the records do not have. **A union above `set_u256` stays fatal `PULSE_SHARD_DICT_WIDTH_OVERFLOW`** — 256 is the hard ceiling and there is nowhere left to widen to; that is the one set-width overflow auto-widen does not remove. `PULSE_SHARD_DICT_DIVERGENCE` in `pulse shard verify` is untouched, and CATEGORICAL widths are untouched too: a categorical's width is fixed at folder creation by contract and its capacity is not a per-record bitmask the same rewrite widens. Atomicity is the whole safety argument, because concurrency here is caller-owned and no lock is added: the rebuilt archive is staged to a temp file beside the original, fsynced, and only then renamed over it (`service.atomicWrite`), so a mid-rewrite failure leaves the original byte-identical and openable at its old rung rather than half-widened. `aggregate_record_count` and `shard_count` in the SHRD trailer are recomputed from the widened payloads, so the trailer is correct after the re-stride, and the `archive.pulse#shard.pulse` anchor opens a widened shard as a one-shard cohort unchanged. Foresight is `VerifyShardArchive`'s `SetWidthHeadroom` (`pulse shard verify`, `--json` `set_width_headroom`): per set field, entries used, bitmask capacity, remaining headroom, and the rung a widen would promote to — empty `next_type` meaning the widest rung, where an overflow is fatal rather than widenable. The sidecar point-lookup index and the SPSS metadata sidecar are NOT updated by a widen; both invalidate themselves through their own size+mtime fingerprints on the next read, and rebuilding them is the caller's business. **That is a REPORTED fact rather than an unmentioned one**: the risk here was never stale data — a widen always changes the cohort's LENGTH, and a size mismatch is the one conclusive staleness verdict both fingerprints carry — it was silent BREAKAGE, a corpus that simply stopped answering lookups with nothing having said why. `pulse widen` therefore names every sidecar it invalidated and the exact command that rebuilds it (`data.invalidated_sidecars` on the `--json` arm, structured rather than prose; nothing at all on either arm when there are none). Discovery goes through each sidecar's own naming authority — `Pulse.ListIndexes` over the `cohort.pulse.indexes.json` manifest for indexes, `spss.SidecarPath` for the SPSS document — never a filename glob, because an index's filename is a HASH of its key tuple and the rebuild command needs the tuple back. **No automatic rebuild**, deliberately: it would attach unbounded work to a bounded metadata operation with no way for the caller to decline. `pulse dedup` reports the same way (`Pulse.Dedup`, above). Library surface: `Pulse.InvalidatedSidecars` / `pulse.StaleSidecar`. `pulse shard verify` uses the same `ValidateStructuralCohesion` and must keep refusing a genuinely mixed-stride archive; `PULSE_SHARD_SET_WIDENED` is mandatory because an expensive archive-wide re-stride that happens silently is indistinguishable from a cheap append. **Shard archives with parent groups — `0x02` shards.** Every shard of an archive is decoded with the CANONICAL schema (`shard_iter`, the parallel shard reducer, profile, filter-to-file), so a grouped archive has exactly ONE group layout — group count, kinds, members and key flags — and every shard's per-row indices address the canonical group dictionaries. `ValidateStructuralCohesion` therefore compares the group layout too (`encoding.ValidateGroupCohesion`, `details.dimension`): it decides the physical stride, and a `0x01` shard in a `0x02` archive, or the reverse, is `PULSE_SHARD_SCHEMA_MISMATCH` in `pulse shard verify`. Group dictionaries follow the append-only prefix rule byte for byte (`ValidateDictPrefixRule`: a stored shard's entries are the archive's first entries in the archive's order, else `PULSE_SHARD_DICT_DIVERGENCE`). **The merge** (`internal/service/shard_groups.go`, `mergeShard` — the ONE routine create and add share, so the same two files produce byte-identical archives either way, `TestShardGroups_CreateAndAddAgree`): (1) work on LOGICAL rows — the arrival is flattened (`encoding.FlattenCohortBytes`, byte-identical to its `0x01` original) and reconciled exactly as an ungrouped shard (set-rung plan BEFORE strict field cohesion, categorical union, remap), because every one of those speaks logical offsets; the remap keeps NULL placeholders (`RewriteShardCategoricalsKeepNulls`), because a null's bytes are part of an entry's identity and a remapped placeholder would make an identical `(key, null)` tuple a different entry — a spurious `PULSE_GROUP_MEMBER_NOT_CONSTANT` on a keyed group; (2) the ARCHIVE's layout wins: an ungrouped archive stores a grouped arrival as its `0x01` twin (byte-identical to adding that twin), a grouped archive re-encodes an arrival with another layout (or none) into its own — adopting the arrival's layout instead would turn an append into an archive-wide rewrite that can FAIL on data already accepted; (3) group dictionaries union-merge canonical-first — the `GroupEncoder` is SEEDED with the canonical dictionaries (`GroupEncoder.Seed`), so every stored shard's entries keep their indices, stored shards are untouched, and only the arrival is renumbered (no warning, exactly as a categorical union has none); a union past the u32 index space (`MaxGroupEntries`) is `PULSE_SHARD_DICT_WIDTH_OVERFLOW` naming the shard and `capacity`, never a wrap; (4) a CONSTANT group the arrival disagrees with is PROMOTED to an indexed group across the whole archive — every shard re-encoded with fresh dictionaries in archive order, each row gaining a 4-byte index — while a declared KEY the arrival violates (same key, different non-key member) is REFUSED with `PULSE_GROUP_MEMBER_NOT_CONSTANT` (`details.shard`, `details.field`), exactly as import refuses it: a key is a contract; (5) strict cohesion runs over the reconciled GROUPED schemas last. A set-rung widen of a grouped archive also re-encodes every shard (a member's rung moves the entry width) and is reported by `PULSE_SHARD_SET_WIDENED`. **Mandatory warning:** every layout change — `incoming_flattened`, `incoming_regrouped`, `constant_promoted` — emits `PULSE_SHARD_GROUPS_REWRITTEN` (`details.reason`, `archive_rewritten`, `shards_rewritten`, `records_rewritten`, `groups`) and a typed `GroupReconciliation` on `AddShardResult.Regrouped` / `CreateShardArchiveResult.Regrouped` (`data.regrouped` on the `--json` arm, present only when non-empty), for the reason `PULSE_SHARD_SET_WIDENED` exists. The rewrite is the same atomic temp + fsync + rename. **Foresight:** `VerifyShardArchive`'s `GroupIndexHeadroom` (`--json` `group_index_headroom`, grouped archives only): per group, entries, capacity (the u32 space; 1 for a constant group) and headroom — a constant group always reports 0, because its next distinct value promotes it archive-wide. **Readers:** the anchor form opens a stored grouped shard with its own schema (its dictionary is a prefix of the canonical one, so its indices are valid in it); filter-to-file copies physical rows by position and carries each shard's preamble; the parallel shard reducer hands each record its entry indices (`SetGroupIndices`) so the filter precompute engages on both archive arms; inspect's archive arm reports the CANONICAL groups over the archive-wide record count (ratio = total records ÷ canonical entries, header-only). `pulse dedup` still refuses an archive (Retro-dedup, above). Gates: `internal/service/shard_groups_test.go` (`TestShardGroups_*`), `internal/encoding/shard_groups_test.go`.

**Sidecar point-lookup index.** `Pulse.Lookup` / `pulse index build` / `pulse api lookup` are backed by a **separate file** next to the cohort — `cohort.pulse.<keyhash>.idx` — never the `.pulse` layout above. Format **v3** (own magic + version, distinct from `encoding.MagicBytes`/`FormatVersion`): 9-byte header (magic `PULSEIDX` + version `0x03`) → 32-byte SHA-256 source fingerprint → key-spec (ordered key columns + types) → `SourceSize` (u64) + `SourceModTime` (i64 Unix ns) → `u32 bucket_count` → fixed-width `bucket_count × u64` bucket-offset table → self-delimited bucket data (FNV-1a hash buckets → `[]uint64` row-id multimap). The fixed-width offset table makes one bucket directly addressable — a lookup hashes the key, seeks to its offset entry, seeks to that bucket's data, then seeks straight to each matched record via `RecordLocator`; never a full-cohort or full-index read (O(1) flat, measured ~5µs across 10k→1M rows vs. linear unindexed scan). **Read-path staleness has THREE outcomes, not two, and the middle one is the whole contract.** A **size** mismatch is an instant `PULSE_INDEX_STALE` with no hash, and it is CONCLUSIVE rather than merely cheap — the fingerprint covers the whole file, so a different length cannot produce the recorded digest. A full size+mtime **match** is served hash-free: that is the O(1) property the sidecar exists for. An **mtime that moved while the size held is NOT staleness** — it escalates to the sidecar's own SHA-256 (`service.classifyIndexFreshness`, shared by `Lookup` and `VerifyIndex` so the two cannot drift on which stat differences count as evidence) and refuses only if the content genuinely differs. Refusing on drift alone was wrong in the one direction that matters: `SourceModTime` is Unix NANOSECONDS, an S3 `LastModified` is whole SECONDS, and every copy, restore and cache hop truncates somewhere of its own choosing, so a cohort read through a bucket had its byte-identical index refused PERMANENTLY rather than transiently and point lookup could not work there at all (measured: a 2 ms truncation on an external drive, size identical, six trailing zeros on the mtime). The `encoding.Index` doc comment already promised the fingerprint as the authority for a stat MATCH; this applies the same authority to the one other case it can answer. **The escalation is memoised per `(cohort path, size, mtime)`** (`Service.fingerprints`, bounded at `cohortFingerprintCacheCap` 1024 with a clear-on-overflow flush), because bucket mtime drift is PERMANENT, not transient — without the memo the fix would trade a hard failure for an O(cohort) read on every lookup, silently losing the property the feature is built on, and a multi-GB cohort would hash per call. The memo assumes exactly what the existing stat fast path already assumes (same path + size + mtime ⇒ same bytes) and so adds no freshness gap. **`VerifyIndex` WRITES that memo and never READS it** — its whole job is the answer that does not rest on a stat pair, so serving it from a cache keyed on that pair would hollow it out, while a digest it just computed is as true as one `Lookup` computed. `verify` therefore always hashes when the size matches; its `stat_mismatch` reason is now a SIZE verdict, mtime drift lands on `fingerprint_match` / `fingerprint_mismatch` with the additive `VerifyIndexResult.ModTimeDrift` (and `--json` `modtime_drift`, `omitempty`) reporting that the stat pair disagreed and the hash overruled it. The residual gap is unchanged and still deliberate: an in-place edit preserving BOTH size and mtime passes `Lookup` and is caught only by `verify`.

**Sidecar index MANIFEST — `cohort.pulse.indexes.json` (`internal/encoding.IndexManifestSuffix`).** A THIRD file beside the cohort, JSON and not a `.pulse` layout, written by `pulse index build`. It exists because `SidecarIndexPath` derives an index's filename from a HASH OF ITS ORDERED KEY TUPLE, so **the file cannot be opened without already knowing the thing a caller is trying to learn**, and key order is significant so guessing is a permutation search. The tuple IS recorded inside the sidecar (`IndexMeta.Keys`), so on a local disk the escape is to glob `<cohort>.*.idx` and read each match — **but object storage cannot list a directory**, which is where cohorts are actually served from, so a bucket caller has neither the hash nor a listing and cannot discover an index at all. Document shape: `{format_version, kind, cohort, indexes:[{index_path, key_hash, keys:[{name,type}], distinct_keys, indexed_records}]}`, with `index_path` / `cohort` as BASENAMES so the document survives the corpus being moved or synced, and the counts recorded at build time **so a listing served from the manifest reads NO sidecar bucket table** — one GET plus one existence probe per entry, instead of downloading every index to answer "which indexes exist". `format_version` is the manifest's OWN (`"1"`), independent of both `encoding.FormatVersion` and `IndexFormatVersion`, so adding a field to it can never force a cohort or index rebuild. Wiring: `BuildIndex` upserts its entry (and SEEDS the document from the directory listing when creating it, best-effort, so the first build after an upgrade does not publish a manifest naming only itself); `DropIndex` prunes the entry, and prunes an ORPHANED entry as a successful drop rather than `PULSE_INDEX_MISSING` — that is the repair path, and without it a stale manifest could not be repaired by any command; `ListIndexes` reads the manifest FIRST and UNIONS any on-disk sidecar it does not name (so a pre-manifest sidecar does not vanish the day a manifest appears beside it), tolerating a failed directory listing only when the manifest answered. **An absent manifest is the ordinary pre-upgrade state and falls back to the directory listing; a manifest that EXISTS and cannot be parsed is `PULSE_INDEX_MANIFEST_INVALID`, never a silent degrade to that listing** — the degrade SUCCEEDS on a local disk and answers "this cohort has no indexes" on a bucket, which is precisely the backend-dependent divergence the manifest removes. A manifest naming a sidecar that is not present is `PULSE_INDEX_MANIFEST_STALE` rather than a skipped entry, because a listing reporting two indexes for a manifest claiming three is indistinguishable from a correct answer. It is one of Pulse's own `*.json` sidecars and therefore rides `isPulseSidecarName` — a `PULSE_LABEL_TABLES_DIR` / `PULSE_RANGE_TABLES_DIR` walk must skip it by suffix or `pulse.New` fails on a file Pulse wrote. `BuildIndexResult.ManifestPath` / `--json` `manifest_path` name it. `format_version` (the envelope's) does NOT move: nothing here is payload-reachable. **Keyable-type policy** (`processing.IsIndexKeyableFieldType`): ALLOW `u4`/`u8`/`u16`/`u32`/`u64`, `f32`/`f64` (raw bit-pattern equality — `-0.0`/NaN caveat), `date`, `datetime` (signed epoch seconds; literal resolves through `encoding.ParseDateTime`, never `ParseFloat`; exact within ±2^53 s, pre-1970 included), `decimal128` (exact mantissa, no float round-trip), `categorical_*` (dictionary ID), `packed_bool`. REJECT `set_*` (a multi-select bitmask has no single unambiguous equality value — use `FILTER_SET` instead). Single-file cohorts only: shard archives → `PULSE_INDEX_UNSUPPORTED_SHARDED` (the `archive.pulse#shard.pulse` anchor is a tested single-shard workaround). Equality-only, full-key required, composite-key order significant end to end. Coded errors: `PULSE_INDEX_MISSING`, `PULSE_INDEX_STALE`, `PULSE_INDEX_UNSUPPORTED_SHARDED`, `PULSE_INDEX_MANIFEST_INVALID`, `PULSE_INDEX_MANIFEST_STALE`, `PULSE_LOOKUP_NOT_FOUND`, `PULSE_LOOKUP_AMBIGUOUS`.
