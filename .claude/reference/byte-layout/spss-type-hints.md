# Byte layout — SPSS type hints (`@PulseType`)

Per-topic slice of the byte-layout reference (the record 7/18 Pulse type hint that lets a `.sav` round trip keep its field types). Index (preamble + section map): `.claude/reference/byte-layout.md` — load it first, then only the slice(s) your change touches.

**SPSS type hints — `@PulseType` (cohort-reshape E6-S2).** SPSS stores every numeric as a double, so before this a Pulse cohort exported to `.sav` and imported back read every `u4`–`u64`, `f32`, `packed_bool` and `decimal128` column as `f64`, and a `categorical_u16` / `_u32` as `categorical_u8`. The fix lives in the `.sav` ALONE — neither the `.pulse` format nor the metadata sidecar's schema moves (the sidecar's `pulse_type` was never the vehicle: a `.sav` travels without it). **Write side** (`internal/io/spss/type_hint.go`, `applyTypeHints`, called by `BuildDictionary` after the charset pass and name validation, so it keys on the final WIRE names): a record `7/18` variable attribute `@PulseType('<type>'\n)` — SPSS's own extension point for per-variable metadata, the `@` prefix hiding it from SPSS's Variable View; `<type>` is the field type's `String()`, or `decimal128(<precision>,<scale>)` — on every variable whose cohort type the plain re-import would NOT choose: an `EncodeNumeric` variable of `u4`/`u8`/`u16`/`u32`/`u64`/`f32`/`packed_bool`/`decimal128` that carries no value labels (a labelled integer binding re-imports categorical by design, so it gets none), and an `EncodeText` / `EncodeCategoricalCode` variable of `categorical_u16`/`_u32`. Nothing else is hinted — `f64`, `date`, `datetime`, `categorical_u8`, set members and vector elements already round-trip or are out of scope — so an export of a cohort without such a column, and every sidecar-path export of an SPSS-origin cohort nothing retyped, is byte-identical to before (`TestValueLabels_UnboundExportsAreByteIdentical` keeps its sidecar digest; the synthesised digest and `TestEmittedDictionary_HandVerified`'s walkthrough moved once, for the hint). The writer OWNS the attribute inside an otherwise verbatim source `7/18`: `parseVarAttributes` splits the payload PSPP's way (`name:` then `key(` values each up to `\n`, the last followed by `)`, sets joined by `/`, blank trailing bytes kept as a trailer), every existing `@PulseType` is dropped, the current hints are appended to the variable's set (or a new set), and the rest is re-emitted byte-for-byte — so a column retyped since import never keeps a stale hint; a source `7/18` the grammar cannot read stays verbatim and gains NO hint (rewriting bytes it cannot read would corrupt them). **Read side** (`typeHintsFrom` + `mapping.applyTypeHint`): the `7/18` payload is decoded in the file's charset and parsed the same way; a hint keys on the variable's long name, else its short name, case-insensitively; a file with no `@PulseType` (every third-party file) maps exactly as before (`TestTypeHint_ThirdPartyFilesImportUnchanged` pins two hint-free fixtures, one carrying ordinary `7/17` / `7/18` attributes, to their pre-hint cohort digests). A hint is NEVER taken on trust: a hinted plain numeric is checked value by value during the existing full scan (`columnStats.hintMisfit`) — integers must be whole and in range, `u64` strictly below 2^53 (2^53+1 rounds to 2^53, so a read-back 2^53 is ambiguous), `packed_bool` 0/1, `f32` exactly representable, `decimal128(p,s)` within `|v|·10^s < 2^50` (where a double's error stays under a quarter unit, so its shortest rendering IS the exported decimal) with at most `s` fraction and `p−s` integer digits; user-missing and system-missing values are nulls and are not checked. Restored cells render positionally (`typeHint.render` — never the shortest-`g` form, which spells 1e+06), so the shared import path parses them under the restored type; a decimal restores its precision and scale onto the schema field. Any value that does not fit, an unreadable hint, or a hint the variable's SPSS shape cannot carry (a numeric type on a string or value-labelled variable, a categorical rung its dictionary outgrows, a type on a date-formatted variable that differs from its mapping) leaves the plain mapping in place — the column's doubles kept, never rounded into the type — and raises ONE `PULSE_SPSS_TYPE_NOT_RESTORED` warning (`ImportReport.SourceWarnings`; details `variable`, `pulse_type`, and `value` for a misfit). The import's schema comes from the same `PulseSchema()` call predict reads, so import predict and run agree by construction. Pinned by `TestTypeHint_*` (`internal/io/spss`) and `TestMaterializeOutput_CategoricalCastSidecarRebuilt` (root: a Materialize cast to `u8` / `categorical_u16` keeps its types through `.sav`). Detail: `skills/spss-import-schema.md`, `skills/spss-export-fidelity.md`, `docs/src/cli/import-spss.md` (Pulse type hints).

**Set rungs, vector elements and inexact u64 (cohort-reshape E6-S4).** The import derives a multiple-dichotomy `set_*` at the NARROWEST rung with a bit per member (`iocore.SetTypeFor`), so a synthesised export of a 3-member `set_u16` used to come back `set_u8`. The set's FIRST member variable (bit 0, `EncodeSetMember`) now carries `@PulseType('<rung>')` whenever the cohort's rung differs from the narrowest; the members ARE the dictionary in bit order, so nothing else is needed, at every rung `set_u8`–`set_u256`. The read side CONSUMES every set-rung hint before the per-variable pass (`setTypeHints`): on the first member of a derived set whose member count fits the rung it widens the set column (widening a mask loses nothing); a rung with fewer bits than members, or a set hint on any other variable, keeps the narrowest rung and raises one `PULSE_SPSS_TYPE_NOT_RESTORED`; the member variable always maps as if unhinted. A sidecar-path export folds a derived set back into its source constituents and writes no set hint — an SPSS-origin derived set is already at its narrowest rung. **Vectors:** SPSS has no vector and the import never builds one, so a `vec_*` cannot round-trip; a `vec_f32`'s element variables carry `@PulseType('f32')` and come back `f32` (`vec_f64` elements need none). **Inexact u64:** past 2^53 a double cannot tell neighbouring integers apart, and the data encoder used to round such a value silently. `CaseValue.U64` now carries a `u64` column's exact word beside `Num`, and every value `> 2^53` (2^53 itself is exact) on an `EncodeNumeric` variable is counted: the export raises ONE `PULSE_SPSS_INTEGER_INEXACT` per variable on `TargetWarnings` (details `variable`, `cohort_field`, `count`, `first_row` 1-based, `value` the first one's exact decimal). Under Strict the first such value is the encode's error and nothing is written: `ExportJob.Strict` (set by the facade under `Options.Strict`) rides `CohortSource.Strict`; `ConvertJob.StrictRows` rides `ConvertSource.Strict`, handed over even for an unfaithful stream (Schema and Sidecar nil), so the row path's `Close` fails before it writes. Predict cannot read a record, so `ValidateCohort` lists the same code WITHOUT `count` / `first_row` for every `u64` `EncodeNumeric` variable — a risk, never a refusal; the run names the same code and variable when a value is that large. Pinned by `TestTypeHint_SetRungRoundTrips`, `TestTypeHint_SetHintTooNarrowOrMisplacedWarns`, `TestTypeHint_VectorF32ElementsComeBackF32`, `TestIntegerInexact_*` (`internal/io/spss`) and `TestExport_StrictRefusesAnInexactU64` (root).
