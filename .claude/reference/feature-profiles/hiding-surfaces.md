# Feature profiles — Manifest, payload schema and error hiding, instance-dependent wording, hard edges, validation codes

Per-topic slice of the feature-profiles reference (Manifest, payload schema and error hiding, instance-dependent wording, hard edges, validation codes). Index (preamble + section map): `.claude/reference/feature-profiles.md` — load it first, then only the slice(s) your change touches.

## Manifest hiding

**`Pulse.Manifest` describes only the instance** (`descx.BuildManifestForInstance(inst)`, `internal/descriptor/manifest_instance.go`; `pulse_manifest` inherits it through `p.Manifest`). `BuildManifest()` is the nil-instance wrapper the unprofiled CLI serves — the full registry — and `BuildManifestWithExtensions(snap)` the unscoped one. A profile-free instance's manifest is byte-identical to `BuildManifest()` (`TestManifest_DefaultInstanceIsFull`). Every manifest carries **`feature_set_digest`** (additive top-level field; `format_version` stays `"1.1"`): the instance's own digest, or for nil / unscoped the digest a profile-free `pulse.New` with the same extension operators computes (`descx.ReachedFeatureNames` over the running version — `SinceReached` moved to `internal/descriptor` so both sides share it). The default golden moved once, by that line only.

On a scoped instance the assembly keeps only what `inst.Enabled` offers: `components`, `tests` / `post_tests` (by `Family` — one row covers both tiers), `regressions`, `overlays`, `components_schemas`, `cohort_types[].compatible_*` (derived from the filtered tables), `extensions` (already visible-only). `commands` / `operations` filter through **`commandBindings`** (`features.go`, `CommandBinding{Command, Feature | Core | Ungated}` — `mcp`, `version` and `completion` are `Ungated`: they describe the binary; `TestCommandBindings_Complete` pins it to `commands()` / `operations()` both ways) and `mcp_tools` through `mcpToolBindings`. The `facet`, `process_chain`, `join`, `crosstab`, `export`, `import` blocks are **pointers, omitted** when `capability:facet` / `process_chain` / `joins` / `crosstab` / `export` / `import` is not enabled (a public `descriptor.Manifest` type change); inside a present block the operator lists are filtered, `import` / `export` formats keep only enabled `io_format:*`, and an import entry's `export` flag drops to false without `capability:export`. Without `capability:weighting` the aggregator table is read unstamped — no `weight_aware`, no weighted floor keys (`sum_weights` / `n_eff` / `n_weight_invalid`) in `components` or `components_schemas` (predict's per-slot `ComponentSchema` likewise) — and every extension entry's `weight_aware` is cleared (`TestManifest_WeightingHidden`). A `regressions` / `extensions.regressions` Param naming a hidden `RegressionSpec` slot key (`weight`, `save`, `multiplicity` — `gatedSlots`) is dropped, built-in and extension alike, as the payload schema drops the key (`hideRegressionSlotParams`, `TestManifest_RegressionSlotParamsFollowHiddenSlots`). Likewise a hidden MAT_SEM params surface (`capability:sem_meanstructure` / `capability:sem_groups` / `capability:sem_bootstrap` — its only prose token is `ci_level`, the other names being REG_RESAMPLE's too; `capability:sem_ordinal` — prose tokens the estimator names `dwls` / `wlsmv` and the scaled-test scalars, never the everyday `estimator` / `ordered`; `capability:sem_defined` owns model syntax only — its `:=` lines are `bad_params` and its one prose token is `PULSE_MATRIX_DEFINED_NONFINITE`) drops its Params and owned `output_keys` from the MAT_SEM entry (`hideSEMSurfaces`), its keys leave the params allowlist (`instanceBuiltinDecl`), and its wire tokens join the prose scrub (`semProseTokens`, beside `slotTokens`, which stays request-slot-only) — `.claude/reference/matrix-and-vectors/matrix-sem.md` (Predict, declared keys and feature profiles). `synth_distributions` is `[]` without `capability:synth`; likewise `extensions.label_tables` is `[]` without `capability:labels` and `extensions.range_tables` `[]` without `capability:range_tables` — a hidden capability's named tables are listed exactly as on an instance that registered none (`TestManifest_NamedTablesFollowTheirCapability`; `TestProfileHiddenNameSweep` registers one of each and treats a hidden capability's table names as hidden tokens).

**Prose scrub.** Descriptions, hints and rule lists name other operators (`GROUP_CATEGORY` points at `GROUP_SET_VALUE`, chain rejection rules list aggregators, tool descriptions name tools). After filtering, `scrubManifest` deep-copies the manifest by reflection — never writing the shared capability tables (`TestBuildManifestForInstance_ScopingLeavesTablesIntact`) — and, outside `skills`, the examples fields and the error lists, drops any `[]string` element or map key that IS a hidden token and every SENTENCE (split at `. `) of any other string that mentions one; a list element left empty is dropped. Tokens are hidden operator names, the MCP tools a hidden capability owns, and the **slot tokens** of every hidden slot-owning capability, matched as whole `[A-Za-z0-9_]` runs, so a family wildcard (`FILTER_SET_*`) or a longer name (`OVERLAY_PANEL_INDEX_VS_REF`) is not a hit. A sentence about an enabled operator that also names a hidden one goes too — the price of never leaking a name. Each string is redacted LINE BY LINE (`ProseScrub.Text`, the MCP scrub's own semantics), so a paragraph break never glues a kept sentence to a dropped one (`TestScrubManifest_LineAware`). Pinned per fixture by `TestManifest_FixturesNameNoHiddenFeature` (root).

**Slot tokens** (`slotTokens`, `internal/descriptor/features.go`, beside `requestSlotCapabilities`) map every capability whose visibility decides a `gatedSlots` key to the wire tokens its slots own: `capability:multiplicity` → `multiplicity`, `p_adjusted`, `significant_adjusted`; `capability:weighting` → `n_weight_invalid`, `weight_aware`; `capability:matrices` → `vectors`, `matrices`, `n_listwise_dropped`, `min_pair_n`, `max_pair_n`; `capability:crosstab` → `margin_aggregations`; `capability:crosstab_cells` → none (`cells` is everyday English and the crosstab's `Cells` matrix slot shares the spelling); `capability:joins`, `compose`, `process_chain`, `facet` → none. `hiddenProseNames` adds a hidden capability's tokens, so every surface the scrub serves — manifest strings, error fixups, MCP descriptions / schemas / prompts, skill metadata, the generated skill sections and docgen — drops each sentence naming one. Tokens are WIRE-specific: a slot key that is everyday English (`weight`, `joins`) or that another surface owns too (`crosstab`, the overlay hosts' shared `overlays`; `sum_weights` / `n_eff` are `AGG_WEIGHTED_MEAN`'s own component keys) stays out, so the scrub never over-drops; `Request.return` and the other ungated slots have no owning capability and no entry. A same-spelled slot elsewhere is exempt per sentence through `slotTokenHomonyms` (`pulse_lookup`'s duplicate-key `multiplicity`: a sentence naming `assert_unique` / `LookupMultiplicity` / `PULSE_LOOKUP_AMBIGUOUS` keeps it). The guidance lint's `SLOT-TOKEN` rule holds every built-in guidance sentence naming a token to the slot's topic (`.claude/reference/guided-analysis.md`). Pinned by `TestSlotTokens_EveryRequestSlotCapability` (every slot-owning capability — derived by probing `gatedSlots` — has an entry, possibly empty, and no other key does), `TestSlotTokens_Shape`, `TestHiddenProseNames_SlotTokens`, `TestProseScrub_SlotTokens` (`internal/descriptor`), the parity cases `TestProfileHiddenSlotTokenSweep` (root: manifest, skill metadata, generated sections and scrubbed Purpose / Interpretation prose on an everything-but-multiplicity instance) and `TestRegister_ProseNamesNoHiddenSlotToken` (`mcp/gosdk`: tool, schema and prompt prose before and after a re-bind, the lookup sentence kept). Not covered: the REGISTRATION-time reflected MCP input schemas still carry a hidden slot's property KEYS (structure, not prose; the bind-on-inspect rebind drops them).

**Skills and examples follow the instance's discovery prune**, not the prose scrub ("Discovery prune (ontology)"). **Not filtered here:** `error_codes` / `error_codes_count` / `error_domains` are filtered inside `assembleManifest` (see "Error hiding"). Named tables are still not features (no profile lists one), and the facade discovery methods `Pulse.LabelTables` / `RangeTables` / `ResolveLabel` are ungated like every facade method. **Resolution follows the capability too:** with `capability:labels` hidden a request `LabelBinding.Table` naming a registered table is `PULSE_LABEL_TABLE_UNKNOWN` exactly as an unregistered name — at the shared validation (`descx.ValidateLabels` takes the instance; predict passes `PredictOptions.Instance`, the service its snapshot) and at the resolver (`processing.lookupLabelTable` / `ExtensionRegistry.LookupLabelTable`) — and an `Options.AutoLabels` default naming one is not injected (`Service.labelTableRegistered`, as for any table the instance does not offer); with `capability:range_tables` hidden `ExtensionRegistry.LookupRangeTable` misses, so a `GROUP_DATE_RANGES` / `FILTER_DATE_RANGES` `table:` is `PULSE_RANGE_TABLE_UNKNOWN` (predict resolves no range table name). The engine spells the two capability names itself (`featureLabels` / `featureRangeTables`, pinned by `TestNamedTableFeatureNames`). `LookupTables` (the expr `lookup()` function) have no capability, so they always resolve. Pinned by `TestHiddenNamedTableParity` (hidden table == unregistered table on every entry point incl. `SampleWithRequest` and Predict, over the file fixtures plus two inline profiles) and `TestHiddenLabelsCapability_AutoLabelsNotInjected`. The MCP `labels` input-schema slot built by `BindOnInspect` (`internal/mcp/bind.go` `labelTableNames`) follows the capability too: absent when `capability:labels` is hidden, byte-identical to an instance with no label table (`TestBindForInstance_LabelsFollowCapability`).

## Payload schema hiding

**`Pulse.PayloadSchema() ([]byte, error)` serves the instance's schema** (`descx.PayloadSchemaForInstance(inst)` / panic-on-marshal twin `BuildPayloadSchemaForInstance`, `internal/descriptor/schema.go`). `BuildPayloadSchema()` is the nil-instance view — the full registry — and the published golden. On a scoped instance: the registry-backed enums (`AggregationType` … `TestType`, `OverlayKind`, `RegressionType`) keep only enabled names (a family with none is an empty `enum`), and each registered extension operator the instance keeps joins its category's enum (AGG / ATTR / FILTER / GROUP / WIN / FEAT / TEST / MAT / REG; `TestExtensions_PayloadSchemaEnumsCarryExtensions`) — so an instance with extensions is not byte-identical to the golden; the slots `HiddenSlotKeys` hides on each request root (`Request.crosstab` / `joins` / `overlays`, the `overlays` slot of `ComposedRequest` / `ChainRequest` / `FacetRequest`) are not properties; a root whose capability is hidden is not an entry point — `compose` → `ComposedRequest` / `ComposedResponse`, `process_chain` → `ChainRequest` / `ChainResponse`, `facet` → `FacetRequest` / `FacetResult`, `sample` → `SampleRequest`, `lookup` → `LookupRequest` / `LookupResult`, `recommend` → `RecommendRequest` / `RecommendResult`, `explain` → `ExplainRequest` / `ExplainResult` (whose own root slots follow their capabilities through `gatedSlots`: `composed` / `composed_response` ride compose, `chain` / `chain_response` process_chain, `facet` / `facet_result` facet, `sample` sample). `Request`, `Response` and `Envelope` are always present (`Response` keeps its result-side `crosstab` slot, its enums narrowed; each result root's `overlays` follows its request root's `overlays` gate — `Response` ↔ `Request`, `ComposedResponse` ↔ `ComposedRequest`, `ChainResponse` ↔ `ChainRequest`, `FacetResult` ↔ `FacetRequest` — so the `return` presets list no overlay path where no overlay can run, U35 #213). Defs are registered by walking from the surviving entries, so a def reachable only through something omitted is absent and no `$ref` dangles (`TestPayloadSchema_FixturesNameNoHiddenFeature` checks both directions per fixture). The root description names only the request roots present.

`$id` never changes. The root **`$comment`** is `"feature_set_digest: <digest>"` — the manifest's digest (`manifestDigest(inst)`), so a profile-free instance's schema (no extensions registered) is byte-identical to `BuildPayloadSchema()` and the default golden moved once, by that line. `pulse schema` routes through the default CLI instance (`newPulse` + `p.PayloadSchema()`); the `pulse://schema` MCP resource serves the mounted instance's `p.PayloadSchema()` (`mcp/gosdk` `registerSchemaResource`; `TestSchemaResource_ServesInstanceSchema`).

## Error hiding

`Pulse.ErrorLookup` / `ErrorsByDomain` / `ErrorsSearch` and the manifest `error_codes` / `error_codes_count` / `error_domains` list only codes the instance can raise (`descx.ErrorCodeVisible`, `ErrorLookup`, `ErrorsByDomain`, `ErrorsSearch`, `internal/descriptor/errors_instance.go`); `pulse_errors_lookup` routes through the facade. A hidden code looks up exactly like an unknown one; fixup templates are stripped of hidden whole tokens (a fully stripped fixup list becomes nil). The CLI `pulse errors lookup` stays full (the CLI is not profiled). Shown codes' `Message` is never stripped, so 19 messages were reworded to name only owning features (`TestErrorMessagesNameOnlyOwners`).

**The error-owner table is internal** (`internal/descriptor/error_owners.go`, `errorOwners map[errors.Code][]string`; `TestErrorOwners_Complete` pins it to `errors.AllCodes()`). A code is visible iff ANY owner is enabled, or its owner is the `shared` sentinel (listed on every instance, the empty one included). **A new error code MUST get an owner entry** (CLAUDE.md Update Demand). Rule of thumb: a code only one feature's path can raise is owned by it; a code reachable from a core path (open, inspect, predict, request decode, extension registration) or a request slot every host carries is `shared`. Contested classifications, decided: `GROUP_*` and `DEDUP_*` shared; `LABEL_*` shared except `PULSE_LABEL_TABLE_NOT_ENUMERABLE`; `SHARD_*` read codes shared; unknown-name codes (`*_UNKNOWN`, which a hidden name also raises) shared; `OVERLAY_*` / `TEST_*` / `REG_*` owned by their families; `*IMPORT_*` owned by `capability:import` + `capability:export` (Convert runs the import core); `LOOKUP_*` owned by the formula operators (`ATTR_FORMULA`, `FILTER_EXPRESSION`, `OVERLAY_FORMULA`); `RANGE` codes by `capability:range_tables` + the date-range operators; `PULSE_WEIGHT_INVALID_ROWS` / `PULSE_WEIGHT_UNSUPPORTED` by `capability:weighting` + `AGG_WEIGHTED_MEAN` (its ungated `weight_field` reaches both), `PULSE_EXTENSION_NOT_WEIGHT_AWARE` by `capability:weighting`. The `PULSE_FEATURE_PROFILE_*` codes are always shared.

## Instance-dependent wording

Refusal and hint prose that used to name built-ins as fixed text now depends on the instance; an instance with no profile is byte-identical to before. Changed: the zone-capable refusal (lists only enabled zone-capable operators), the `ATTR_RANK` → `WIN_RANK` hint (skipped when `WIN_RANK` is hidden, falling back to the generic unknown-attribute error), the pairwise `n_source` / `p_source` / `n_basis` advice, the facet-host overlay kind list, the `FEAT_TARGET_ENCODE` warning and the categorical / decimal suggestion reason fallback. Per-fixture manifest goldens include the skill list, so a skill edit moves them (`docs/src/internals/regenerating-goldens.md`).

**Runtime remedies.** The runtime refusals under `internal/processing` that recommend OTHER built-ins are swept the same way: the set-field refusals of the numeric aggregators / attributes / filterers / value groupers (`AGG_SET_*` / `AGG_COUNT`, `ATTR_SET_*`, `FILTER_SET_*`, `GROUP_SET_*`), the two-sample tests' too-many-groups advice (`TEST_ANOVA_F`, `TEST_CHISQ`, `FILTER_INCLUDE` / `FILTER_EXCLUDE`), `TEST_TUKEY_HSD`'s `TEST_ANOVA_F` pairing (advice, not an edge), the Welford pairwise kinds' `n_source` advice (the proportion kinds), the distinct-key `n_source` admitted list (`AGG_DISTINCT_SUM` / `AGG_DISTINCT_COUNT`, details `admitted_cell_aggregators` too) and the regression spec refusals' `REG_OLS` / `REG_GLM` pointers. Each clause is a **remedy** (`internal/processing/refusal_prose.go`, `regression.Remedies()`): a pure function of the offered predicate whose nil rendering is the historical literal, so the site builds its message from `remedy(nil)`. `ExtensionRegistry.ScopeRefusal(err)` swaps each default rendering found in a coded error on the chain for the instance's and drops hidden names from the `alternates` / `alternts` / `admitted_cell_aggregators` details lists; `Service.Process`, `Compose`, `ComposeParallel`, `ProcessChain`, `FacetSchema` and `SampleWithRequest` return through it (`Service.scopeRefusal`), which reaches factory-, test-, overlay-handler- and regression-time refusals without threading the instance through their signatures. A registry without a feature-set predicate returns the error untouched. **A new remedy must be added to `refusalRemedies()`** and its default must not contain another's (`TestRefusalRemedies_*`). A wrapper that formats its message at construction (`fmt.Errorf("...: %w")`) is NOT rewritten — scope before wrapping, as Compose does by calling the scoped `Process`. Hard-dependency names stay literal (`AGG_WELFORD` / `AGG_WEIGHTED_MEAN` for the pairwise kinds that read them, `GROUP_DATE` for `OVERLAY_YOY`, `REG_OLS` for `ATTR_REG_*`). Pinned by `TestProfileRuntimeRefusalSweep` (root: one targeted profile per clause, proving the unprofiled refusal names the recommendation and the profiled one keeps its code but names nothing hidden beyond the request's own tokens, then every fixture profile), `TestScopeRefusal_*` / `TestRefusalRemedies_*` (`internal/processing`).

## Hard edges

`capability:materialize` gates the SURFACES only — the `pulse_materialize` tool and the `pulse api materialize` leaf (manifest command `materialize`); the `Pulse.Materialize` facade stays ungated, as `Recommend` / `Explain` do, so the `PULSE_MATERIALIZE_*` codes stay `shared` in `error_owners.go`. A hidden operator inside a materialize request is refused exactly like a never-registered one (`Materialize` / `MCP/pulse_materialize` entry points of the parity harness; the `mcp-hosts` inline profile enables the capability so the MCP cells run).

`capability:rake` follows the same rule: it gates the `pulse_rake` tool and the `pulse rake` leaf (manifest command `rake`); the `Pulse.Rake` facade stays ungated, so every `PULSE_RAKE_*` code is `shared`. It has no dependency edge (raking reads records directly and runs no Request host). The shipped `survey-crosstab` profile lists it; `read-only-analyst` leaves it out, as a data-writing capability.

`capability:filter_to_file` hard-depends on `FILTER_EXPRESSION`: filter-to-file compiles every filterer into one filter expression, so a hidden `FILTER_EXPRESSION` would make every call fail.

## Validation codes and order

Three classes, run in order; validation **stops at the first failing class and reports EVERY instance of that class, sorted** (`TestFeatureProfile_ClassOrder`). All raised with their own code; prose and fixups in `errors/fixup_metadata.go`.

| Code | Class | Details |
|---|---|---|
| `PULSE_FEATURE_PROFILE_INVALID` | structural | `reason`: `both_options_set`, `file_unreadable`, `malformed_json` (incl. trailing data), `unknown_key`, `missing_features`, `duplicate_feature` (+ `duplicates`), `invalid_limits` (+ `limit`, `value`); `path` when a file was read. After the DEPENDENCY class (it needs the resolved set): `invalid_return` (+ `return_code`, `return`) |
| `PULSE_FEATURE_PROFILE_UNKNOWN` | name resolution | `unknown[]` of `{name, reason}`, plus `names`, `version`. Reasons: `unregistered`, `pattern` (`*`, `?`, `[` — never expanded; `TestProfileRejectsPatterns`), `wrong_kind` (+ `did_you_mean`, the one valid spelling), `core_surface`, `newer_than_running` (+ `since`) |
| `PULSE_FEATURE_PROFILE_DEPENDENCY` | dependencies | `unmet[]` of `{feature, requires_any_of}`, plus `features` |
