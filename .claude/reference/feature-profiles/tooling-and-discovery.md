# Feature profiles — Where a profile is read, example profiles, tooling, discovery prune, reference export, notes for U06

Per-topic slice of the feature-profiles reference (Where a profile is read, example profiles, tooling, discovery prune, reference export, notes for U06). Index (preamble + section map): `.claude/reference/feature-profiles.md` — load it first, then only the slice(s) your change touches.

## Where a profile is read

**`pulse.New` never reads the environment** (`TestFeatureProfile_NotReadFromEnv`): every CLI leaf calls it, and the CLI is not profiled. The env var is read only by `mcpserve.NewPulse(popts, opts)`, which `pulse mcp` calls. Precedence: `mcpserve.Options.FeatureProfileFile` (flag `--feature-profile`) > a profile already on `popts` > `PULSE_FEATURE_PROFILE`; the field plus a `popts` profile is `INVALID` `both_options_set`. The flag and env forms are host OS paths (absolute or cwd-relative, never under `DataDir`), read by `internal/profilefile.ReadOS` (shared with the `pulse features` leaves) — the one deliberate read outside the instance Fs, because they configure the process, not a cohort. `mcpserve.Serve` / `ServeStdio` ignore `FeatureProfileFile`: build through `NewPulse` or `pulse.New`. `mcpserve.Describe(p, opts)` reports the effective cohort-scan setting and loaded profile label, which the `pulse mcp` stderr notice prints.

**No runtime skill mentions feature profiles** — not `skills/session-bootstrap.md`, not any other. A served skill describing profiles tells an agent hidden features exist. This is the deliberate exception to the env-var row's session-bootstrap companion; embedder docs live in `docs/src/library/feature-profiles.md`.

## Example profiles

`examples/profiles/{minimal,survey-crosstab,read-only-analyst}.json` (repo root — NOT `internal/examples/`, the request example library) are the published examples, embedded by the root `//go:embed examples/profiles/*.json` (`example_feature_profiles.go`). `pulse.ExampleFeatureProfiles()` lists the names (file stem, sorted); `pulse.ExampleFeatureProfile(name)` returns a fresh value through the same strict decode as `ParseFeatureProfile`, and an unknown name is `INVALID` reason `unknown_example` {`name`, `examples`}. **Frozen: a published file is never edited in place** — a changed example ships under a new name (design decision: no live presets). File form: `profile`, `written_with` (the release it shipped in; every listed feature's `Since` reached), `features` only, 2-space indent, built-in names only, in canonical order — `descx.SortFeatureNames` (kind in `AllFeatureKinds` order, then operator category in table order, then table position; non-table names follow by name), the order a generated profile uses too. `read-only-analyst` is every built-in reached by its `written_with` minus `import` / `export` / `filter_to_file` / `dedup` / `widen` / `shard` / `index` / `synth` / `model_save` and every `io_format:*` (only import / export use one). Pinned by `TestExampleFeatureProfiles_*` / `TestExampleFeatureProfile_*` (root); the private fixtures under `descriptor/testdata/profiles/` stay test-only.

## Tooling (U06)

`feature_profile_tooling.go` — root functions that need no `*Pulse`; the `pulse features` CLI wraps them and holds no logic. Results are JSON-tagged plain strings (the feature model stays internal), list fields never `null`. Pinned by `TestInitFeatureProfile_*`, `TestCheckFeatureProfile_*`, `TestDiffFeatureProfile`, `TestDescribeFeatureProfile`, `TestFeatureProfileTooling_JSONShape` (root) and `TestProfileWrittenWith` (`internal/descriptor`).

- **One validation path.** `pulse.New` and `CheckFeatureProfile` share `validateExtensionUniverse` (`validateExtensions` → `probeExtensions` → `validateExtensionDependsOn`) and `validateFeatureProfile` (INVALID → UNKNOWN → DEPENDENCY). `TestCheckFeatureProfile_MatchesNew` asserts identical code, message and details per class; never fork either.
- **Offline check.** `FeatureProfileCheckOptions.Offline` adds each unresolved name matching `extensionNameRegex` (category not `SYNTH`, namespace not in `reservedExtensionNamespaces`, not a built-in row past the running version) to a COPY of the universe as an extension with no `DependsOn` (`withUnverified`): it satisfies dependency membership and still needs a request host. Each is reported in `Unverified` plus a warning coded `PULSE_FEATURE_PROFILE_UNKNOWN`, `reason` `unverified_extension` (no new code). Everything else stays an error.
- **`written_with` stamp.** `descx.ProfileWrittenWith(Version())`: the running release core (the `SinceReached` reduction), or, for a build with no core (`devel`, SHA, `0.0.0`), the newest `Since` in the table — so the stamp is always a release, matching the examples' literal `1.0.0`. Init output is sorted by `descx.SortFeatureNames` and re-checked before it is returned. `from` seeds from an example without adding extension names.
- **Diff `new`** = `!SinceReached(row.Since, written_with)`: an empty or core-less `written_with` reads as newest, so nothing is `new`; extension operators carry no `Since` and are never `new`. Unknown names reuse `featureUniverse.classify`. Tests inject rows through `lookupBuiltinFeature` + `listBuiltinFeatureNames`.
- **`return` is not rendered** by `DescribeFeatureProfile` / `pulse features show` (nor are `behaviour` and `limits` — the reports describe features); `CheckFeatureProfile` / `pulse features check` VALIDATE it through the shared `validateFeatureProfile`.
- Variadic `ext ...Extensions` is the optional `Options.Extensions` value; several values merge slice by slice (`mergeExtensions`).
- **CLI `pulse features {init,check,diff,show}`** (`internal/cli/features.go`): thin adapters, no extensions, no data dir; profile paths are host OS paths. `check` is always `Offline` and lifts the report's warnings onto the envelope; every leaf writes a fatal error through `codedErrorEnvelope` (own code in `errors[0]`, partial report kept in `data`) and then RETURNS it, so the process exits non-zero even under `--json` (unlike most leaves). Manifest `commands` carry the four, bound `Ungated` in `commandBindings`. Pinned by `TestFeatures*` (`internal/cli`) and `TestFeatures_InitThenCheck` (`cmd/pulse`).

## Discovery prune (ontology)

Skills and examples are discovery surfaces with no feature of their own: an instance shows one iff its node survives the instance's PRUNED skill ontology. The graph model (node kinds, IDs, edge sources) is `.claude/reference/skill-pack.md` (Skill ontology (U10)); this section is the prune and its invisibility contract.

`NewInstanceSnapshot` (so `pulse.New`) EAGERLY builds the instance ontology (`instanceOntology`, `internal/descriptor/ontology_instance.go`): `BaseOntology()` plus the visible extension operators (Purpose edges; an extension synth distribution requires `capability:synth`) and named tables (`table:<label|range|lookup>/<name>`; label → `capability:labels`, range → `capability:range_tables`), pruned by `pruneOntology` when the instance hides anything; a profile-free, extension-free instance shares the base graph BY POINTER. `inst.Ontology()` returns it and `inst.Discovery()` (`discovery.go`) is the skill / example view read off it — `fullDiscovery` (pass-through) when nothing is hidden, so profile-free output is byte-identical. Prune rules: an operator / capability node goes iff its feature is `Hidden`; a node that is not a feature goes when a capability it requires is hidden (synth distribution → `capability:synth`) or, for a REG spec modifier (`REG_RESAMPLE`, `REG_SELECTION`), when every regression is hidden — a feature node's flattened any-of `requires_capability` edges are never read (the resolved set is already dependency-closed); an MCP tool / table goes with a node it requires (core tools have none); an atomic skill goes with the operator or tool it documents, a topical skill when ANY `requires:` feature is hidden (AND); an example goes when an operator exemplifying it, a capability it requires (`_meta.capabilities` or a structural detector: facet, `crosstab`, `joins`, compose root, process-chain root) or an operator its description routes to is hidden — a skill's `## See` edge into it never prunes it; an intent goes when ≥1 operator serves it and all are hidden; a glossary term when ≥1 operator cites it and all are hidden (its SeeAlso edges go with it). Every edge touching a pruned node is dropped. There are no prose-token example rules any more: `TestExamples_EdgeCoverage` guarantees every operator named in an example body or description is an edge. Type skills stay; the virtual `intents` / `glossary` skills are never pruned but render from the pruned graph. Embedder skills (`Extensions.Skills`) are skill nodes too: an atomic one is no node when the profile hides its extension operator (dropped from the snapshot first), a topical one when a `requires:` entry is a hidden extension operator, and otherwise they prune like built-ins — so a hidden embedder skill reads as nonexistent on every surface (`TestExtensions_SkillsPrunedWithOperator`, `TestExtensionSkills_MCP`); a hide-nothing instance with embedder skills builds a `Discovery` that serves built-ins byte-identically. Embedder examples (`Extensions.Examples`) are example nodes the same way: no node when the profile hides an extension operator the example names anywhere (`ExtensionExample.ExtOperators`), and otherwise the example prune rule above, so a built-in operator or capability it uses, hidden, hides it too; `Discovery` merges the survivors into the searched library (`TestExtensions_ExamplesPrunedWithOperator`, `TestExtensionExamples_MCP`). Every surviving skill is RENDERED for the instance. Its listed METADATA goes through `ProseScrub` (description scrubbed; `applies_to` / `covers` / `examples_tags` entries naming a hidden token dropped — topical metadata included; a frontmatter description cannot hold a fence). Its BODY — atomic and topical alike — renders by its FEATURE FENCES against the pruned graph and, atomic only, its `## See` section by edge (E2-S1, `internal/descriptor/skill_render.go`; syntax and rules: `.claude/reference/skill-pack.md` (Feature fences)); markers are always stripped. The line-wise `ProseScrub` no longer touches a body — it cut table rows and code-fence lines — so prose outside a fence is served as written — which is why every feature name in a body must be fenced (`TestSkillsCoverFeatureFences`) and every served body is swept (`TestSkillsCoverProfileGet`, `TestProfileInvisibilityParity`, below). **Public facade (E1-S4):** `p.Ontology()` (a fresh deep copy of the pruned graph — never the full one), `p.Skills()` (`[]pulse.SkillMetadata`, rendered) and `p.Skill(name)` (rendered body; pruned == nonexistent) read it; they are ungated like every facade method — only the content is instance-scoped. `pulse_skills_list` / `pulse_skills_get` (`internal/mcp/handlers.go`) and the `pulse-skill://` enumeration and reader (`mcp/gosdk/resources.go`) call those two facade methods, `pulse_examples_*` call `p.ExamplesSearch` / `p.ExampleGet`, and the manifest `skills` (each description through the same `renderMetadata` pass, on a copy — the cached `sortedSkills` slice is never written), `examples_count` / `example_categories` / `example_tags` and top-level `intents[]` (`instanceIntentIDs`: the intent nodes that survived the prune) read the same view (`assembleManifest`; those fields are skipped by `scrubManifest`). Facade == MCP is pinned by `TestSkills_FacadeMCPParity` (`mcp/gosdk`), facade == ontology == manifest by `TestFacade_OntologySkillsAgree` and `TestManifestSkills_DescriptionsNameNoHidden` (root), the intents list by `TestManifestIntents_PrunedUnderProfile`. A pruned name reads exactly like a nonexistent one on every path. The CLI `pulse skills` / `pulse examples` leaves are unprofiled (admin tool). Pinned by `TestOntologyPrune_*`, `TestInstanceOntology_SharesAndExtends`, `TestDiscovery_*`, `TestRegister_Discovery*` and `TestProfileInvisibilityParity` (below). Cost: `BenchmarkNew_Ontology` (root; no gate).

**Hidden == nonexistent, per discovery surface.** `TestSkillsCoverProfileGet` (`mcp/gosdk/skills_profile_get_test.go`; a listed non-skippable gate) runs over every published example profile (`examples/profiles/*.json`) and every private fixture (`descriptor/testdata/profiles/*.json`). It derives the pruned skills and examples from the instance ONTOLOGY (full-graph node absent from `p.Ontology()`), independently of the lists under test, then pins: each is absent from every list (`p.Skills`, `pulse_skills_list`, the `pulse-skill://` enumeration, manifest `skills`; `p.ExamplesSearch`, `pulse_examples_search`, manifest `examples_count`) and from every search aimed at it (its name, tags, category and each operator it uses — facade and MCP); and an exact-name get — `p.Skill`, `p.ExampleGet`, `pulse_skills_get`, `pulse_examples_get`, a `pulse-skill://` read and the resource-template reader — answers byte-identically, after the name is substituted out, to a never-existing name. It also pins every SERVED body (no exemption, no report-only switch since U10 E4-S3): an atomic or topical body names no pruned skill stem or example, and a topical body no hidden operator or tool — bodies render by feature fence and atomic `## See` by edge, and a topical body's frontmatter `covers:` (served with it, unable to hold a fence) renders through the same `keepVisibleTokens` as the listed metadata (`Discovery.renderCovers`). Example names that are one word (`logistic`) double as taxonomy tags, so only compound (`-` / `_`) example names count as a body mention. A shipped profile that prunes no skill, or a profile set that prunes no example, fails as vacuous.

`TestProfileInvisibilityParity` (root `feature_parity_mcp_test.go`; the go-sdk client side is `feature_parity_mcp_bridge_test.go` in the external test package, because `mcp/gosdk` imports the root) runs over every published example profile, every private fixture and three inline profiles (`mcp-hosts`, the prompt-only `mcp-prompts`, and `mcp-intent-prompts` — every intent prompt over the minimal operators, so some intent prompts mount scrubbed and the rest are unmounted by the ontology prune and must read like never-registered ones). Operator arm: `runHiddenParityWith` driven through MCP tool calls (process, predict, compose slot and overlays, process-chain stages and overlays, facet-schema). Surface arm: tools/list before and after the bind-on-inspect rebind, prompts, resources and templates, `pulse://schema`, the cohort resource, `pulse-skill://` reads and the skills / examples / manifest / errors tools name no hidden feature, and each hidden tool, prompt, skill and example reads byte-identically (after name substitution) to a never-registered one. **Nothing is exempt** (since U10 E4-S3): every served skill body — atomic and topical — is swept like any other surface, so a body naming a hidden feature fails; a mention that must stay in prose is feature-fenced (`.claude/reference/skill-pack.md` (Fence coverage), bound by `TestSkillsCoverFeatureFences`). A new exemption is a deliberate edit to that file.

## Reference export (U21)

`p.ExportReference(fs, dir, ExportReferenceOptions{OmitSkills})` and `pulse docs export --out DIR [--feature-profile PATH] [--no-skills] [--json]` (`internal/docgen`, `internal/cli/docs.go`, `docs_export.go`) render the INSTANCE's operator catalog, reading pages, glossary and served skills from `InstanceSnapshot` and the pruned ontology: a hidden operator, tool, skill or capability slot token appears in no page (`TestProfileExportTreeSweep` over every example profile and private fixture, with `TestProfileRenderedSkillSweep` and `TestProfileHiddenSlotTokenSweep` for the rendered skill sections). `docs export` is a core, ungated CLI leaf (`commandBindings`); the CLI builds a default instance over an in-memory fs (no `PULSE_DATA_DIR`) and reads the profile from an OS path like `pulse mcp`. The `.pulse-docs-export` marker owns the directory: a non-empty directory without it is `PULSE_DOCS_EXPORT_DIR_NOT_EMPTY`, a marked one is overwritten and its stale files removed. Slot tokens (`slotTokens`, Manifest hiding) are the table the sweeps and `hiddenProseNames` share; `TestSlotTokens_EveryRequestSlotCapability` keeps it complete. The public book's tree is the profile-free export, committed. No runtime skill mentions any of this.

## Notes for U06

**Done in U05.** Extension operators omitted from a profile are hidden (dropped at `pulse.New`; embedder docs). `p.FeatureProfile()`, `p.FeatureSetDigest()` and `p.PayloadSchema()` exist. The MCP `pulse://schema` resource serves `p.PayloadSchema()` (profile-free: byte-identical to `BuildPayloadSchema()`; `TestSchemaResource_ServesInstanceSchema`), and MCP strict-decode location keys are the service's `request` / `stage` (formerly `request_index` / `stage_index` + `stage_name`; `TestCheckUnknownKeys*`). Runtime refusal text under `internal/processing` / `internal/service` is swept ("Instance-dependent wording", Runtime remedies). Malformed-request parity cells exist for every pre-lookup rule found ("Request-slot gate", Parity harness); U06 ran the harness over MCP (below). Design-doc amendments live in the roadmap (no single choke point; fixtures private; digest wording).

**Landed in U06 (MCP and tooling; the interim leaks U05 inherited).**

- **`BindOnInspect` rebinds tools by name**, bypassing any registration-time filter. Done: the rebind skips a tool the instance hides (`bindSessionTools`) and binds through `core.BindForInstance(schema, inst)` (`internal/mcp/bind.go`): every operator / test / overlay-kind enum keeps only `inst.Enabled` names plus the visible extensions (`enabledNames` in `mergeEnumNames`, `overlayKindEnumForFacade`), an enum filtered to nothing is OMITTED (the `enumStringField` convention, as the overlay `kind` already did), the labels slot follows `capability:labels`, and each root drops the slots `descx.HiddenSlotKeys` hides (`dropHiddenSlots`, as the payload schema does). Profile-free binds byte-identically (`TestBindForInstance_*`, `TestRegister_BindOnInspectScopesEnums`). The unbound registration-time input schemas are reflected and carry no name enum.
- **MCP prose is scrubbed.** Done: `descx.ProseScrub` (`internal/descriptor/prose_scrub.go`, `NewProseScrub(inst)`) exposes the manifest scrub — `hiddenProseNames` + `redactProse`, one token set, one sentence-drop semantics — to the MCP adapter: `Text` redacts line by line (a line left as a bare list / heading marker is dropped, the rest of its ordered list renumbered, blank runs collapsed) and `SchemaDescriptions` applies it to every string `description` keyword of a JSON Schema (byte-identical when nothing changes). `mcp/gosdk` applies it once at registration to tool descriptions and reflected input schemas (`registerTools`), prompt descriptions, argument descriptions and bodies (`registerPrompts`; the author-request question is user content, spliced unscrubbed), and per re-bind to bound descriptions and schemas (`bindSessionTools`). Prose that abbreviated operator lists (`AGG_SUM/AVG/...`) was reworded to full tokens in separate sentences so the whole-token scrub can see them (manifest goldens moved by those rewords only). Pinned by `TestRegister_ProseNamesNoHiddenFeature` (fixtures + a prompt-enabling and a dedup-only inline profile, before and after a re-bind) and `TestProseScrub_*`.
- **Prompts and skill resources take the `*Pulse`** (`registerPrompts`, `registerSkillResources` in `mcp/gosdk`). Prompts are filtered; skill resources route the enumeration AND the reader through the facade — `p.Skills()` / `p.Skill(name)` (`mcp/gosdk/resources.go`) — which read the skill prune ("Discovery prune (ontology)"). (`registerSchemaResource` took it in U05.)
- `SeriesOverlayRequest.Overlays` is method-level and ungated (by design: methods are ungated); `synth_fidelity.go` builds an unscoped processor for internal `TEST_KS` / `TEST_CHISQ` (audited, left).
- Pre-existing, unrelated: a second `Request.Groups` entry with an unknown type is silently ignored; the manifest's inner `format_version` is `"1.0"`.
- A manifest sentence about an enabled operator that also names a hidden one is dropped by the prose scrub (documented price).
- The profile-tooling CLI lives under `pulse features` (no collision with synth's `pulse profile create`); its library half is "Tooling (U06)".
- **Core tools and `RegisteredTools()` / `RegisteredPrompts()`.** Core-bound tools (`pulse_manifest`, `pulse_inspect`, `pulse_skills_*`, `pulse_examples_*`, `pulse_errors_lookup`) always mount. `gosdk.RegisteredTools()` / `RegisteredPrompts()` are GLOBAL canonical lists — they never reflect a profile; read the instance's own surface from `tools/list` or `p.Manifest`.
- **`pulse features` / the tooling functions** are the embedder half; the `check` extension caveat (CLI is offline, no extensions) is in "Tooling (U06)".
