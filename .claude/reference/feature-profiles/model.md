# Feature profiles — Naming, kinds, inventory, `Since`, dependency model, profile model, resolved feature set

Per-topic slice of the feature-profiles reference. Index (rules + section map): `.claude/reference/feature-profiles.md` — load it first, then only the slice(s) your change touches.

## Naming

The concept is a **feature profile**, never a bare "profile". "Profile" already belongs to synth data profiling (`Pulse.Profile`, `ProfileOptions`, `pulse profile create`, the `PULSE_PROFILE_*` codes). Every public name spells the concept out — `pulse.FeatureProfile*`, `Options.FeatureProfile` / `FeatureProfileFile`, `mcpserve.Options.FeatureProfileFile`, env `PULSE_FEATURE_PROFILE`, flag `pulse mcp --feature-profile`, codes `PULSE_FEATURE_PROFILE_INVALID` / `_UNKNOWN` / `_DEPENDENCY`. Never shorten any of them to `Profile`.

## Feature kinds and spelling

Four kinds (`descriptor.AllFeatureKinds()` in `internal/descriptor/features.go`). **Operators are spelled bare; every other kind is `<kind>:<name>`.** There are no aliases: one feature has exactly one spelling (`descx.FeatureName`).

| Kind | Spelling | Rows |
|---|---|---|
| `operator` | `AGG_SUM`, `TEST_T`, `OVERLAY_YOY` | every `types.All*Types()` entry. A `TEST_*` is ONE name covering both its row-test and post-test tiers |
| `capability` | `capability:process` | one row per approved capability in `builtinFeatures`; the code comment on each `capability(...)` row names the facade methods it owns |
| `io_format` | `io_format:csv` | one per `io.Formats()` entry; ONE name gates BOTH import and export |
| `mcp_extra` | `mcp_extra:cohort_resources` | the cohort-resource enumeration plus one row per registered MCP prompt (`prompt_bootstrap`, `prompt_author_request`, and one `prompt_<intent>` per ANALYTIC intent) |

Read and write siblings collapse into one capability: `capability:index` covers build / verify / list / drop, and `capability:shard` covers every shard-archive method.

## Inventory rules

- **`builtinFeatures` is THE table**, maintained by hand. `TestFeaturesHaveSince` fails on a registry entry (operator, I/O format, MCP prompt, approved capability) without exactly one row, on a row without a live registry entry, and pins `mcpToolBindings` to `toolmeta.Names()` in both directions.
- **Not features** (`TestFeatures_NonFeaturesAbsent`): synth distributions (`capability:synth` gates every one), field types (a cohort's schema is data), named tables, expr functions (the built-in `coef()` resolves only names `capability:compose_fits` binds, so hiding that capability leaves it nothing to read), and the behaviour switches.
- **Extension operators ARE features** (every operator category) but are not table rows and carry no `Since`. The resolvable universe is the table plus the instance's registered extension operators.
- **Core surfaces are always present and are NOT features** (`coreSurfaces`: `open`, `inspect`, `predict`, `count_records`, `manifest`, `payload_schema`, `skills`, `examples`, `errors_lookup`, `cohort_artifacts`). Listing one, bare or kind-prefixed, is `PULSE_FEATURE_PROFILE_UNKNOWN` reason `core_surface`.
- **MCP tool bindings** (`mcpToolBindings`) map every tool to exactly one feature or core surface. `gosdk.Register` mounts a core-bound tool always and a feature-bound one iff the instance enables the feature, so a hidden tool is never registered and calling it fails byte-identically to a nonexistent name. Prompts mount iff their `mcp_extra:prompt_*` feature is enabled; a generated intent prompt (`pulse-<intent-kebab>`; the tooling intents get none) ALSO needs its intent node to survive the instance's ontology prune — an intent whose every serving operator is hidden mounts no prompt although its feature is on. `gosdk.RegisteredTools()` / `RegisteredPrompts()` stay the GLOBAL canonical lists. Coverage gate: `TestSkillsCoverAllMCPPrompts` (analytic intent ↔ prompt bijection, a `docs/src/mcp/index.md` prompt-table row per prompt, and `skills/session-bootstrap.md` naming each hand-written prompt inside its own feature fence plus the `pulse-<intent>` family — never a concrete intent prompt, which a profile may hide).
- The table is internal on purpose: no public struct gains a field for it, so the manifest and public API goldens do not move.

## `Since`

Every row carries the release (major.minor.patch) that introduced it. Every built-in is `"1.0.0"` (`BuiltinFeatureSince`), and `TestFeaturesHaveSince` currently REQUIRES that: anything landing before the `v1.0.0` tag ships in 1.0.0, alpha and rc tags included. **The first feature added after `v1.0.0` gets the release that ships it — never back-dated — and that change must relax the gate's equality check to "parseable and ≤ the next release".** `ParseSince` accepts exactly `MAJOR.MINOR.PATCH`; `TestParseSince` pins it.

**Version compare.** A built-in row resolves only when the running build has reached its `Since` (`sinceReached`). The RUNNING version is reduced to its core: leading `v` dropped, everything from the first `-` or `+` cut — so `1.0.0-alpha.2` and a `git describe` build offer the `1.0.0` features. A running version with no usable core is treated as NEWEST: `devel`, `devel+<sha>`, a bare commit SHA, anything unparseable, and a `0.0.0` core (the Go pseudo-version of an untagged build). A row past the running version is `UNKNOWN` reason `newer_than_running` with `since`. `written_with` in the profile is never compared.

`pulse.Version()` (`internal/buildinfo`) is the running version: the ldflags value, else Pulse's OWN module version from build-info `Deps` (honouring a `replace`), never the embedder binary's `Main.Version` — otherwise an embedder's `v3.2.0` would unlock every future feature.

## Dependency model

`Feature.DependsOn` is an **AND of any-of groups**: for every group, at least one member must be enabled. Rows never spell it by hand — `withDependencies` derives it, in this order:

1. **Host group.** Non-overlay operators and the request-slot capabilities → any-of the request hosts `capability:process` / `compose` / `process_chain`. Process-only modes (`stream`, `watch`, `filter_to_file`, `materialize`) → `capability:process`. `capability:multiplicity` has NO dependency (its blocks also ride facet overlays, so no request-host group is right; `TestFeatureDependenciesResolve` pins `nil`). Intent prompts → `capability:recommend` AND `capability:explain` AND `capability:process` (the feature-bound tools the shared script calls; `TestFeatureProfile_IntentPromptNeedsItsTools`).
2. **Overlay hosts.** An overlay kind → any-of the hosts whose engine handler map lists it (`overlayHostKinds`); an extension overlay kind → any-of the hosts its handlers run on.
3. **Hard edges** (`hardEdges`) append ONE any-of group each, and **group edges** (`groupEdges`) append several ANDed groups for a row that needs more than one. Read the two tables in `features.go` for the current list; each entry's comment says why. Add an edge when a feature cannot run, or would leak a hidden name, without another one. Cases worth knowing because the reason is not obvious:
   - `capability:filter_to_file` → `FILTER_EXPRESSION`: filter-to-file compiles EVERY filterer, even a visible `FILTER_INCLUDE`, into one engine-internal `FILTER_EXPRESSION`. A profile hiding it would fail every run with an "unknown filter type" that leaks the hidden name, so the edge refuses that profile at `pulse.New` instead. There is deliberately no run-time exemption.
   - `OVERLAY_YOY` → `GROUP_DATE` (its series host must lead with a date grouper); the T / Z cell and versus-reference overlays → `AGG_WELFORD` (they read its triple).
   - `capability:models` and `capability:model_save` have wide any-of groups (every operator or capability that can read or write a fit, a population or an SEM fit), and `capability:models` / `capability:params` take the request hosts PLUS `capability:facet` (`modelsHosts`), because a facet filter's `coef()` / `params` read them too.
   - The MAT_SEM params surfaces (`capability:sem_*`) hang off `MAT_SEM` / `ATTR_SEM_SCORE`: `.claude/reference/matrix-and-vectors/matrix-sem.md` (Predict, declared keys and feature profiles).

`TEST_TUKEY_HSD` after `TEST_ANOVA_F` is deliberately NOT an edge: its inputs are plain params, so the pairing is advice.

**Gates.** `TestFeatureDependenciesResolve` (`internal/descriptor`): every member resolves, and the hard edges are pinned by name. `TestProfileDependenciesComplete` (`internal/processing`, because the descriptor cannot import the handler maps): (a) host groups present, (b) overlay host sets equal handler-map membership both ways, (c) a source scan — a file owning operator X that references operator Y needs an X→Y edge or a justified `dependencyScanAllowlist` entry. The scan sees identifiers, not semantics.

**Extension `DependsOn`.** Every operator registration has optional `DependsOn []string`; each entry is a single-name AND group added after the request-host group every extension operator gets. Every entry must resolve (a built-in feature or another registered extension) at EVERY `pulse.New`, profile or not — a typo fails at construction, as `PULSE_FEATURE_PROFILE_UNKNOWN` with `extension` and `category` on each entry. **A post-fit operator's host** is `capability:compose_post_fit` instead of the request hosts — it runs only in the Compose `post_fit` slot (`TestPostFit_HiddenCapability`). **Extension regressions meet the built-in REG_* groups:** `descx.ExtensionRegressionMeetsGroup` names the built-in features whose REG_* any-of group an enabled extension regression also satisfies (`ATTR_REG_PREDICT` and `capability:model_save` need a `Scorer`; `capability:compose_fits` takes any), and the resolver consults it on an unmet group; the static groups keep naming the built-ins (`TestFeatureProfile_ExtensionRegressionMeetsRegEdges`).

## The profile model

`pulse.FeatureProfile` mirrors the JSON file key for key: `profile` (free label), `written_with` (stored as-is, never validated), `features` (REQUIRED), `behaviour`, `return` and `limits` (each optional). Decode is strict (`DisallowUnknownFields`, nested objects included, trailing data refused): every other key — and an unknown key inside `behaviour` / `return` / `limits` — is refused (`unknown_key`). **A nil `Features` is invalid**; a Go embedder writes `[]string{}` for an empty profile, which is valid and offers no optional feature.

**Behaviour** switches OR into `Options`: `disable_defaults`, `disable_components`, `disable_projection` (also forces the deprecated `ProjectBufferedFields` off), `disable_cohort_scan`. A profile can turn a switch on; `Options` cannot turn it back off. `disable_cohort_scan` does nothing to the engine — `gosdk.Register` ORs it into `Config.DisableCohortScan` through the `internal/facadebridge.CohortScanDisabled` hook. A profile that omits `mcp_extra:cohort_resources` takes the same path: no startup walk, no `pulse://` enumeration, the template still registered so cohorts stay readable by URI; `mcpserve.Describe` folds both.

**`return`** (`types.Return`, the request block's shape) is the instance `return` default — NOT a feature (no `features.go` row; it never enters `feature_set_digest`). Precedence: a request `return` block REPLACES every instance layer; else `Options.DefaultReturn`; else the profile's `return`; else the library default `full` (identity). `pulse.New` installs the winner on the `InstanceSnapshot`, so predict and the runtime resolve through the same layer (`descx.EffectiveReturn`). It is validated against the profile's OWN resolved feature set after the dependency class (shared with `CheckFeatureProfile`): a bad preset / precision / path, or a path a hidden feature owns, is `INVALID` reason `invalid_return`, with the resolver's code under `return_code` and its details under `return`. `Options.DefaultReturn` is checked against the scoped snapshot too, but fails `New` with the resolver's own code (`PULSE_RETURN_INVALID` / `PULSE_RETURN_PATH_UNKNOWN`). A `data[*].<column>` path is not judged at `New` (no schema); the runtime warns `PULSE_RETURN_PATH_UNMATCHED` when it matches nothing. The `DisableComponents` shorthand fold: `.claude/reference/update-demand.md` (the `Request.Return` row). Pinned by `TestFeatureProfile_Return*` and `TestReturnDefaults_*`.

**`limits`** (`*FeatureProfileLimits`) is the PROFILE LAYER of the instance resource limits — behaviour, NOT a feature (never in `feature_set_digest`, `TestFeatureProfile_LimitsNotInDigest`). Keys are the snake_case `limits.Name`s, counts JSON `int64`, `request_timeout` a Go duration STRING (`"-1"` / `"unlimited"` → `Unlimited`; a JSON number is `malformed_json`). Encoding matches `Options.Limits`: absent / 0 → default, `-1` → unlimited, any other negative refused. Validated in the STRUCTURAL class (shared with `CheckFeatureProfile`); the first bad key in declaration order is `INVALID` reason `invalid_limits` {`limit`, `value` as written}. Resolution per field: non-zero `Options.Limits` > non-zero profile value > built-in default. Copied on decode and clone, so caller mutation never leaks. Not rendered by `DescribeFeatureProfile`. Pinned by `TestFeatureProfile_Limits*`.

**Sources.** `Options.FeatureProfile` (Go value, copied) XOR `Options.FeatureProfileFile` (read through the INSTANCE afero Fs, so relative to `Options.FS` / `DataDir`). Both set → `INVALID` `both_options_set`. `pulse.ParseFeatureProfile([]byte)` is the same strict decode, decode-only — names and dependencies are checked when the value reaches `pulse.New`, and those errors carry no `path` detail.

**Order in `pulse.New`:** `validateExtensions` → `probeExtensions` → `validateExtensionDependsOn` (against ALL registrations) → filesystem resolution → `resolveFeatureProfile` → `applyFeatureProfileBehaviour` → `resolveFeatureSet` → `withoutHiddenExtensions` → `service.New`, then the runtime extensions and the snapshot are built over the VISIBLE registrations only. `p.FeatureProfile()` returns a copy of the stored profile (`nil, false` without one).

## The resolved feature set

`pulse.New` computes the instance's feature set once (`feature_set.go`): the universe is every built-in row whose `Since` is reached plus every registered extension operator. With no profile the whole universe is enabled; a profile enables exactly its list and HIDES the rest. A hidden extension operator is never registered — dropped after `validateExtensionDependsOn`, so a `DependsOn` naming a hidden-but-registered extension still validates.

The set lives in `internal/descriptor.InstanceSnapshot` (`instance_snapshot.go`), installed with `Service.SetInstanceSnapshot`; it wraps the `*ExtensionsSnapshot`. `Enabled(name)` is membership in the resolved set; `Hidden(name)` is "resolvable here but not offered" — the predicate a native lookup site consults, since an unknown name already fails on its own. Both are O(1). A nil or unscoped snapshot (hand-wired services) enables everything, hides nothing and has an empty digest.

**`feature_set_digest`** (`p.FeatureSetDigest()`, `descx.FeatureSetDigest`) = `"fs1:" + sha256hex` over the sorted unique enabled names followed by the four EFFECTIVE behaviour switches (`behaviour:<switch>=<bool>`, fixed order, all newline-joined). Effective = the profile's `behaviour` ORed with `Options`; `disable_cohort_scan` comes from the profile alone. Every instance has one; it is unsalted so it keys caches across processes. Changing what it covers bumps the `fs1:` prefix. **Named tables are deliberately outside it**: `LookupTables` / `ReferenceVectors` / `LabelTables` / `RangeTables` are not features, so instances differing only in registered tables share a digest. `capability:labels` / `capability:range_tables` gate resolution only, and `capability:lookup_tables` drops every `LookupTables` registration at `pulse.New` (after validation — files still parse), so `lookup()` is undeclared on both sides.
