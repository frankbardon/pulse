## The contract

**Wide-set word order — `set_u128` / `set_u256`.** A wide set field's payload is a fixed-width bitmask of 16 or 32 bytes, read and written ONLY through `encoding.SetMask` and its wire API (`PutSetMask` / `SetMaskFromBytes`, `WriteSetMask` / `ReadSetMask`); the `uint64` value API `Read/WriteFieldValue` REFUSES both rungs with `ENCODING_TYPE_MISMATCH` rather than truncate to the low 64 bits. **The word order is normative: `words[0]` is bits 0–63 — the LOW 64 bits — then `words[1]` bits 64–127, `words[2]` bits 128–191, `words[3]` bits 192–255, laid down on the wire in that order (little-endian WORD order) with each word itself little-endian.** The payload is therefore exactly the little-endian byte image of the 128- or 256-bit integer, and **the low 8 bytes of a `set_u128` are byte-identical to a `set_u64` payload carrying the same selections** — the property that makes a narrow→wide rung promotion a pure append of zero bytes. Reverse either the word order or the intra-word byte order and every cohort written since the wide rungs landed decodes as a different, plausible-looking selection: no length changes, no checksum moves, nothing errors. Bit `i` ↔ dictionary entry `i` exactly as on the narrow rungs; an empty mask is a valid "no selection" distinct from null; nulls ride the per-record bitmap alone with no in-band sentinel, so a null row still carries (and every decoder still consumes) its full 16 or 32 payload bytes. A bit at or above `FieldType.MaxSetEntries()` is `ENCODING_INVALID` on write and, on the shard dict-remap rewrite path, `PULSE_SHARD_DICT_WIDTH_OVERFLOW`. Three places state this one contract and none may drift from the others: the `encoding.SetMask` doc comment (normative), this paragraph, and `skills/type-set-u128.md` / `skills/type-set-u256.md` (Bytes). In memory the hand-off type differs by rung and that difference is load-bearing: the narrow rungs (`set_u8`..`set_u64`) reach the decode wide map as a `uint64`, the wide rungs as a `SetMask` — a `uint64` there would carry only the low word. The `values` float64 echo for a wide rung is the low 64 bits and is DELIBERATELY lossy (two masks differing only above bit 63 echo the same number); it exists so a set field is never absent from the values map, and the `SetMask` is the authority. Detail: `skills/cohort-schema-design.md` (Field-type matrix (all 20), Width overflow).

**Shard set-width auto-widen.** A `pulse shard add` whose dictionary union outgrows a `set_*` field's declared bitmask does NOT refuse the shard: the field is promoted to the narrowest rung that holds the union, across the canonical `_schema.pulse` AND every shard payload already in the archive, and the merge then proceeds into a rung that fits. **A second, independent force triggers the identical promotion: the arriving shard DECLARING a different rung.** That is the case the field actually produces — a re-import of a new period infers the rung its own data needs, so a `set_u128` shard meets a `set_u64` archive with no dictionary overflow anywhere in sight, and the old behaviour refused it as `PULSE_SHARD_SCHEMA_MISMATCH` before the widen planner was ever consulted. The relaxation is ONE dimension wide and is implemented by ORDER rather than by loosening a validator: `PlanSetWidening` now runs BEFORE `ValidateStructuralCohesion` and reconciles the rungs, and cohesion then runs over the reconciled schemas as strictly as ever — which matters because `pulse shard verify` calls the same validator, and an archive whose shards really do carry different strides is a corruption signature that must stay fatal there. **The target rung is never narrower than either side declared.** A shard arriving at a NARROWER rung is promoted to the archive's rung and is the only payload rewritten; narrowing the archive to meet it would drop every selection above the target's ceiling, and would do so silently — the record still decodes, to a smaller, entirely plausible selection. `SetWidening.From != To` is the caller's test for "the archive moved"; equal means only the arriving shard did, and the mandatory warning's prose and its `details.archive_widened` both say which. **`CreateShardArchive` auto-widens on exactly the same conditions**, through the same planner and executor: refusing at seed while widening at add was an asymmetry with no defence, since the same two files produced an archive when fed one after the other and an error when fed together. It therefore returns a `*CreateShardArchiveResult` rather than a bare `error`, for the identical reason `AddShard` returns a result — a silent whole-archive rewrite is exactly the failure class this file exists to prevent, and the shards inside the archive are no longer byte-identical to the `.pulse` files the caller named. Refusing was the wrong trade — it forces a full re-import (re-read the source, re-infer, rebuild) to reach a layout a mechanical re-stride already produces, and the re-stride is strictly cheaper than the thing it would be avoiding. **But an expensive whole-archive rewrite that happens silently is exactly the failure class this file exists to prevent, so the `PULSE_SHARD_SET_WIDENED` warning is MANDATORY rather than advisory** — it names the field, the old rung, the new rung and the number of shards rewritten, and `Service.AddShard` returns an `*AddShardResult` rather than a bare `error` specifically so the warning has nowhere to be dropped. The planner is `encoding.PlanSetWidening`, which answers the question `MergeDictUnion` structurally cannot (nothing at the schema layer may perform an archive-wide byte rewrite); the executor is E4-S1's engine — `encoding.WidenSetFieldBytes` per shard payload and `encoding.WidenSchemaSetField` for the canonical block, which share ONE offset derivation (`widenFieldOffsets`) so the canonical schema block and every shard's own schema block describe the identical post-widen layout by construction rather than by agreement. A divergence there would not fail to open: it would decode every field after the widened one at the wrong offset, with the schema confidently describing a stride the records do not have. **A union above `set_u256` stays fatal `PULSE_SHARD_DICT_WIDTH_OVERFLOW`** — 256 is the hard ceiling and there is nowhere left to widen to; that is the one set-width overflow auto-widen does not remove. `PULSE_SHARD_DICT_DIVERGENCE` in `pulse shard verify` is untouched, and CATEGORICAL widths are untouched too: a categorical's width is fixed at folder creation by contract and its capacity is not a per-record bitmask the same rewrite widens. Atomicity is the whole safety argument, because concurrency here is caller-owned and no lock is added: the rebuilt archive is staged to a temp file beside the original, fsynced, and only then renamed over it (`service.atomicWrite`), so a mid-rewrite failure leaves the original byte-identical and openable at its old rung rather than half-widened. `aggregate_record_count` and `shard_count` in the SHRD trailer are recomputed from the widened payloads, so the trailer is correct after the re-stride, and the `archive.pulse#shard.pulse` anchor opens a widened shard as a one-shard cohort unchanged. Foresight is `VerifyShardArchive`'s `SetWidthHeadroom` (`pulse shard verify`, `--json` `set_width_headroom`): per set field, entries used, bitmask capacity, remaining headroom, and the rung a widen would promote to — empty `next_type` meaning the widest rung, where an overflow is fatal rather than widenable. The sidecar point-lookup index and the SPSS metadata sidecar are NOT updated by a widen; both invalidate themselves through their own size+mtime fingerprints on the next read, and rebuilding them is the caller's business. **That is a REPORTED fact rather than an unmentioned one**: the risk here was never stale data — a widen always changes the cohort's LENGTH, and a size mismatch is the one conclusive staleness verdict both fingerprints carry — it was silent BREAKAGE, a corpus that simply stopped answering lookups with nothing having said why. `pulse widen` therefore names every sidecar it invalidated and the exact command that rebuilds it (`data.invalidated_sidecars` on the `--json` arm, structured rather than prose; nothing at all on either arm when there are none). Discovery goes through each sidecar's own naming authority — `Pulse.ListIndexes` over the `cohort.pulse.indexes.json` manifest for indexes, `spss.SidecarPath` for the SPSS document — never a filename glob, because an index's filename is a HASH of its key tuple and the rebuild command needs the tuple back. **No automatic rebuild**, deliberately: it would attach unbounded work to a bounded metadata operation with no way for the caller to decline. Library surface: `Pulse.InvalidatedSidecars` / `pulse.StaleSidecar`. Detail: `skills/cohort-schema-design.md` (Sharded cohorts) + `docs/src/internals/managing-shard-archives.md`.

**Sidecar point-lookup index.** `Pulse.Lookup` / `pulse index build` / `pulse api lookup` are backed by a **separate file** next to the cohort — `cohort.pulse.<keyhash>.idx` — never the `.pulse` layout above. Format **v3** (own magic + version, distinct from `encoding.MagicBytes`/`FormatVersion`): 9-byte header (magic `PULSEIDX` + version `0x03`) → 32-byte SHA-256 source fingerprint → key-spec (ordered key columns + types) → `SourceSize` (u64) + `SourceModTime` (i64 Unix ns) → `u32 bucket_count` → fixed-width `bucket_count × u64` bucket-offset table → self-delimited bucket data (FNV-1a hash buckets → `[]uint64` row-id multimap). The fixed-width offset table makes one bucket directly addressable — a lookup hashes the key, seeks to its offset entry, seeks to that bucket's data, then seeks straight to each matched record via `RecordLocator`; never a full-cohort or full-index read (O(1) flat, measured ~5µs across 10k→1M rows vs. linear unindexed scan). **Read-path staleness has THREE outcomes, not two, and the middle one is the whole contract.** A **size** mismatch is an instant `PULSE_INDEX_STALE` with no hash, and it is CONCLUSIVE rather than merely cheap — the fingerprint covers the whole file, so a different length cannot produce the recorded digest. A full size+mtime **match** is served hash-free: that is the O(1) property the sidecar exists for. An **mtime that moved while the size held is NOT staleness** — it escalates to the sidecar's own SHA-256 (`service.classifyIndexFreshness`, shared by `Lookup` and `VerifyIndex` so the two cannot drift on which stat differences count as evidence) and refuses only if the content genuinely differs. Refusing on drift alone was wrong in the one direction that matters: `SourceModTime` is Unix NANOSECONDS, an S3 `LastModified` is whole SECONDS, and every copy, restore and cache hop truncates somewhere of its own choosing, so a cohort read through a bucket had its byte-identical index refused PERMANENTLY rather than transiently and point lookup could not work there at all (measured: a 2 ms truncation on an external drive, size identical, six trailing zeros on the mtime). The `encoding.Index` doc comment already promised the fingerprint as the authority for a stat MATCH; this applies the same authority to the one other case it can answer. **The escalation is memoised per `(cohort path, size, mtime)`** (`Service.fingerprints`, bounded at `cohortFingerprintCacheCap` 1024 with a clear-on-overflow flush), because bucket mtime drift is PERMANENT, not transient — without the memo the fix would trade a hard failure for an O(cohort) read on every lookup, silently losing the property the feature is built on, and a multi-GB cohort would hash per call. The memo assumes exactly what the existing stat fast path already assumes (same path + size + mtime ⇒ same bytes) and so adds no freshness gap. **`VerifyIndex` WRITES that memo and never READS it** — its whole job is the answer that does not rest on a stat pair, so serving it from a cache keyed on that pair would hollow it out, while a digest it just computed is as true as one `Lookup` computed. `verify` therefore always hashes when the size matches; its `stat_mismatch` reason is now a SIZE verdict, mtime drift lands on `fingerprint_match` / `fingerprint_mismatch` with the additive `VerifyIndexResult.ModTimeDrift` (and `--json` `modtime_drift`, `omitempty`) reporting that the stat pair disagreed and the hash overruled it. The residual gap is unchanged and still deliberate: an in-place edit preserving BOTH size and mtime passes `Lookup` and is caught only by `verify`.

**Sidecar index MANIFEST — `cohort.pulse.indexes.json` (`encoding.IndexManifestSuffix`).** A THIRD file beside the cohort, JSON and not a `.pulse` layout, written by `pulse index build`. It exists because `SidecarIndexPath` derives an index's filename from a HASH OF ITS ORDERED KEY TUPLE, so **the file cannot be opened without already knowing the thing a caller is trying to learn**, and key order is significant so guessing is a permutation search. The tuple IS recorded inside the sidecar (`IndexMeta.Keys`), so on a local disk the escape is to glob `<cohort>.*.idx` and read each match — **but object storage cannot list a directory**, which is where cohorts are actually served from, so a bucket caller has neither the hash nor a listing and cannot discover an index at all. Document shape: `{format_version, kind, cohort, indexes:[{index_path, key_hash, keys:[{name,type}], distinct_keys, indexed_records}]}`, with `index_path` / `cohort` as BASENAMES so the document survives the corpus being moved or synced, and the counts recorded at build time **so a listing served from the manifest reads NO sidecar bucket table** — one GET plus one existence probe per entry, instead of downloading every index to answer "which indexes exist". `format_version` is the manifest's OWN (`"1"`), independent of both `encoding.FormatVersion` and `IndexFormatVersion`, so adding a field to it can never force a cohort or index rebuild. Wiring: `BuildIndex` upserts its entry (and SEEDS the document from the directory listing when creating it, best-effort, so the first build after an upgrade does not publish a manifest naming only itself); `DropIndex` prunes the entry, and prunes an ORPHANED entry as a successful drop rather than `PULSE_INDEX_MISSING` — that is the repair path, and without it a stale manifest could not be repaired by any command; `ListIndexes` reads the manifest FIRST and UNIONS any on-disk sidecar it does not name (so a pre-manifest sidecar does not vanish the day a manifest appears beside it), tolerating a failed directory listing only when the manifest answered. **An absent manifest is the ordinary pre-upgrade state and falls back to the directory listing; a manifest that EXISTS and cannot be parsed is `PULSE_INDEX_MANIFEST_INVALID`, never a silent degrade to that listing** — the degrade SUCCEEDS on a local disk and answers "this cohort has no indexes" on a bucket, which is precisely the backend-dependent divergence the manifest removes. A manifest naming a sidecar that is not present is `PULSE_INDEX_MANIFEST_STALE` rather than a skipped entry, because a listing reporting two indexes for a manifest claiming three is indistinguishable from a correct answer. It is one of Pulse's own `*.json` sidecars and therefore rides `isPulseSidecarName` — a `PULSE_LABEL_TABLES_DIR` / `PULSE_RANGE_TABLES_DIR` walk must skip it by suffix or `pulse.New` fails on a file Pulse wrote. `BuildIndexResult.ManifestPath` / `--json` `manifest_path` name it. `format_version` (the envelope's) does NOT move: nothing here is payload-reachable. **Keyable-type policy** (`processing.IsIndexKeyableFieldType`): ALLOW `u4`/`u8`/`u16`/`u32`/`u64`, `f32`/`f64` (raw bit-pattern equality — `-0.0`/NaN caveat), `date`, `datetime` (epoch seconds; literal resolves through `encoding.ParseDateTime`, never `ParseFloat` — inherits `u64`'s >2^53 float-echo caveat, reachable only by a pre-1970 instant), `decimal128` (exact mantissa, no float round-trip), `categorical_*` (dictionary ID), `packed_bool`. REJECT `set_*` (a multi-select bitmask has no single unambiguous equality value — use `FILTER_SET` instead). Single-file cohorts only: shard archives → `PULSE_INDEX_UNSUPPORTED_SHARDED` (the `archive.pulse#shard.pulse` anchor is a tested single-shard workaround). Equality-only, full-key required, composite-key order significant end to end. Coded errors: `PULSE_INDEX_MISSING`, `PULSE_INDEX_STALE`, `PULSE_INDEX_UNSUPPORTED_SHARDED`, `PULSE_INDEX_MANIFEST_INVALID`, `PULSE_INDEX_MANIFEST_STALE`, `PULSE_LOOKUP_NOT_FOUND`, `PULSE_LOOKUP_AMBIGUOUS`. Detail: `skills/cohort-schema-design.md` (Sidecar index) + `skills/tool-lookup.md`.

**SPSS metadata sidecar.** An SPSS import writes a SECOND sidecar next to the cohort — `cohort.pulse.spss.json` (`spss.SidecarSuffix`, the `imports.Sidecar` "suffix appended to the cohort filename" convention; deliberately distinct from `imports.SidecarSuffix` `.meta.json`, which a managed import writes for the same cohort). JSON, not a `.pulse` layout. It holds every dictionary element the `.pulse` byte format has no slot for: measure levels, print/write format codes, records `7/17` file attributes and `7/18` variable attributes (kept distinct), record `6` documents, weight variable, compression bias, `nominal_case_size`, original short names, declared byte widths + `7/14` very-long-string segmentation, MR/MC set definitions, `7/5` variable sets, the source charset **in the file's own declared spelling**, product name, missing-value specs in all three shapes (discrete ≤3 / range / range-plus-one-discrete, raw 8-byte slots retained verbatim), and — the load-bearing payload — the `code ↔ label ↔ Pulse dictionary ID` triple per categorical column, since the cohort dictionary holds SPSS **codes** and this is the only place the **labels** live. Document shape: `{format_version, kind, fingerprint, payload}`. **`payload` is flat and self-contained** (no paths, no offsets, no external references) so it can be lifted verbatim into a future `.pulse` schema metadata block — that block is **deferred, not rejected** (it needs a `FormatVersion` `0x01` → `0x02` bump affecting every Pulse user), and this shape is what keeps the door open. `fingerprint` is the only file-bound part and a lift drops it: 32-byte SHA-256 + `SourceSize` (u64) + `SourceModTime` (i64 Unix ns) over the **`.pulse` cohort** (not the source `.sav`), mirroring the sidecar index's size+mtime staleness snapshot. Read-path policy, implemented at `spss.LoadSidecar(fs, cohortPath, spss.WriterOptions{})` (the write side's first act, reached from `pulse export spss`): **absent → warning** `PULSE_SPSS_SIDECAR_ABSENT` and the caller synthesises a default dictionary from the `.pulse` schema (a cohort that was never SPSS-derived correctly has none), **stale → error** `PULSE_SPSS_SIDECAR_STALE` (a stale dictionary over changed data produces a file that looks authoritative and is wrong — a refusal returns NO `SidecarResolution`, so there is no shape in which a caller reaches the stale document), **present-but-unreadable → error** `PULSE_SPSS_SIDECAR_INVALID` (foreign `kind`, unrecognised `format_version`, malformed digest, or a broken `multiple_response_sets[].fields` parallel array). The staleness check is a cheap O(1) size+mtime comparison with the same residual gap `PULSE_INDEX_STALE` has (a size- and mtime-preserving in-place edit) — but it is **no longer the same rule**: the index read path now treats an mtime that moved while the size held as inconclusive and escalates to the fingerprint, while this one still REFUSES there, so a `.sav` export of a cohort read through a filesystem that does not preserve nanosecond mtimes hits `PULSE_SPSS_SIDECAR_STALE` where a lookup would now succeed (`--ignore-sidecar` is the blunt escape). That asymmetry is not a considered position, only the untouched half: `Document.VerifyDigest` already exists and is the same authority the index escalates to. `Document.VerifyDigest` is the authoritative full SHA-256 recompute for a verify-style pass. `spss.WriterOptions{IgnoreSidecar: true}` (`--ignore-sidecar`) suppresses the sidecar READ entirely — not merely the staleness verdict — so a healthy sidecar is ignored too and an unreadable one cannot block; it downgrades both refusals to a `PULSE_SPSS_SIDECAR_IGNORED` warning on the same synthesise-a-default path, and never applies a stale dictionary. That warning deliberately does not report which refusal it silenced — skipping the read means nothing on that path knows. `MRSet.Fields` is additive under `omitempty` and `SidecarFormatVersion` did not move for it, so an ABSENT `fields` key means “written before the slot existed” and is back-filled by `Document.Normalise` from `variables[].short_name` (case-insensitive, first declaration wins), never rejected; a PRESENT one of the wrong length IS rejected. Written via `afero.Fs` + `encoding/json` through the optional `io.SidecarEmitter` interface, which `ImportJob.Run` calls after the cohort write; a source not implementing it yields a byte-identical import and no sidecar. Detail: `skills/spss-cohorts.md` (the metadata sidecar + the derived-column registry) + `docs/src/cli/import-spss.md` + `docs/src/internals/adding-io-format.md`.

**SPSS derived columns.** An SPSS import can produce a cohort WIDER than the source dictionary — count columns from the returned schema, never from the SPSS variable count. Two synthesised kinds, both **additive**: a `<var>_missing` `categorical_*` sibling immediately after every numeric variable declaring user-missing values (the null bitmap is one bit and cannot record *why*, so the reason must be materialised as data), and one `set_*` bitmask per multiple-DICHOTOMY response set immediately after its LAST constituent (never instead of the constituents — a bit cannot separate "not selected" from "not asked"). The asymmetry with the CATEGORICAL arm is deliberate and must not be "fixed": a categorical column already stores the SPSS code as a dictionary entry, so the code is preserved losslessly and a sibling would double the width of an all-categorical survey; those entries are FLAGGED instead (`variables[].categories[].missing` on the sidecar + one per-FILE `PULSE_SPSS_CATEGORICAL_USER_MISSING` diagnostic). `--spss-missing=null` / `spss.WithMissingMode` suppresses the numeric siblings only; the `set_*` column has no opt-out. Every synthesised column is registered on the sidecar's `payload.derived` (closed `kind` vocabulary — `spss.DerivedKinds()` / `spss.DerivedFoldFor`; a cohort that derived nothing writes `"derived": []`, never a missing key), so the export folds them mechanically rather than by name-matching. Detail: `skills/spss-cohorts.md`.

**SPSS export.** `pulse export spss -i cohort.pulse -o out.sav` (and `pulse convert x.csv out.sav`) writes `.sav`; `descriptor.importCapability()` carries `Export: true` for `spss` and `exportCapability()` its `warn_and_skip` overlay entry — `TestManifestImportCapability_ExportFlagMatchesExportBlock` fails if only one moves. Four per-command flags, one per `spss.WriterOptions` field: `--ignore-sidecar`, `--uncompressed`, `--charset`, `--sanitize-names`. The `.sav` writer is a **`pio.CohortWriter`**, the one optional writer interface that replaces the row loop rather than decorating it: `ExportJob.Run` calls `WriteCohort(ctx, CohortSource{FS, Path, Includes, Labelled})` after `SetPulseSchema` + `WriteHeader` and never calls `WriteRow`, because a `.sav` value is derived from a categorical's dictionary ID, a `set_*`'s mask bits and the null bitmap — all three erased by `formatFieldValue`'s rendering (a null and an empty string categorical become the same cell). The mask reaches the encoder as an `encoding.SetMask` at EVERY rung and never as a `uint64`: `readCohortCase` takes `set_u128` / `set_u256` through `encoding.ReadSetMask`, because `ReadFieldValue` refuses them, and a `uint64` there would carry a 206-option battery's low word alone — every member at or above bit 64 exporting as "not selected" in a perfectly well-formed `.sav`. A set member variable's bit is bounded against ITS OWN rung inside `NewDataEncoder`'s `checkColumns`, not on the per-case path, because a bound living per case is a refusal `ValidateCohort` cannot reach: predict would accept a cohort (a `set_u8` declaring ten dictionary entries) that the export fails on record 1. The derived multiple-dichotomy fold is keyed on `Derived.Kind` and is therefore width-blind by construction — a 206-constituent `set_u256` is dropped and its 206 constituents rebuilt exactly as a 3-constituent `set_u8` is — and the sidecar's `derived[].sources` records all 206 in BIT order, so dictionary ID `i` is constituent `i` at any width. Consequences: `ExportJob.Includes` / `Labels` are REFUSED with `PULSE_SPSS_EXPORT_UNSUPPORTED` rather than silently dropped, overlays are warn-and-skip, and a `convert` (no cohort exists) buffers rows and builds an intermediate in-memory cohort through the ordinary import path. Encode-side diagnostics ride the new `io.TargetWarningEmitter` optional interface onto `ExportReport.TargetWarnings` / `ConvertReport.TargetWarnings` (nil for every pre-existing adapter); the CLI re-reads them AFTER `Close`, because a writer that encodes at `Close` has raised none of them when the job builds its report. `PULSE_SPSS_EXPORT_UNSUPPORTED` was REPURPOSED, not retired — it now means "this cohort has no honest `.sav` form", matching E3-S2's treatment of `PULSE_SPSS_COMPRESSION_UNSUPPORTED`. Name policy: illegal names are `PULSE_SPSS_NAME_INVALID` / `_COLLISION` by default; `--sanitize-names` opts into a deterministic, collision-safe rewrite of the SYNTHESISED path only, reporting every rename as `PULSE_SPSS_NAME_SANITIZED`. Detail: `skills/spss-cohorts.md` (Writing `.sav`) + `skills/session-bootstrap.md` (Target-format CLI flags).

**SPSS convert carries the source through.** `pulse convert survey.sav out.sav` never builds a cohort on disk, so the `.sav` writer's ROW path rebuilds one in memory from the rendered text — and text is exactly where the two things a `.sav` is encoded FROM do not survive. Both now ride one channel, the optional `io.SourceAwareWriter` / `io.ConvertSource` pair (`SetConvertSource` before `WriteHeader`, type-asserted and otherwise a no-op, so every other adapter's convert output is byte-identical). **The DECLARED schema replaces inference on the rebuilt cohort**, because inference over a rendered `set_*` cell can only see the options somebody TICKED: a 206-member `set_u256` battery whose respondents chose eleven distinct options re-infers at a narrow rung and silently loses a dictionary entry per unticked member, and a value-labelled numeric loses its codes entirely — it re-derives as a STRING variable full of bare numerals, in a `.sav` that opens cleanly. **The source's metadata SIDECAR is written against the rebuilt cohort** (the source Reader's own `pio.SidecarEmitter`, re-fingerprinted by that call — the source's copy is fingerprinted over the SOURCE cohort and `LoadSidecar` would refuse it `PULSE_SPSS_SIDECAR_STALE`), which is what restores the `derived` registry: without it the writer synthesised a default dictionary, expanded the derived multiple-dichotomy column into member variables of its own, and every one collided with the constituent column already in the cohort — `PULSE_SPSS_NAME_COLLISION` refused EVERY multiple-dichotomy convert, at every width. The two are one mechanism because they fail together: a carried sidecar read against a re-inferred dictionary would attach each label to whichever code happened to appear first. Both are carried only when the emitted row stream is FAITHFUL to the schema — one cell per field, in field order, no `ConvertJob.Includes` projection and no label binding inserting or rewriting cells — since facts that do not describe the stream would bind a rebuilt cohort's columns to the wrong cells, which is the silent wrong answer rather than the loud one; an unfaithful stream carries nothing and the target infers exactly as before. `ConvertSource.Schema` is nil for a genuinely schema-less source (a CSV): there is nothing declared to preserve, inference stays the fallback, and `PULSE_SPSS_SIDECAR_ABSENT` still names the intermediate `converted-rows.pulse`. `format_version` does not move — `io.ConvertSource` is not payload-reachable. Detail: `skills/spss-cohorts.md` (Writing `.sav`) + `docs/src/internals/adding-io-format.md`.

**Export predict is target-aware.** `ExportJob.Predict` consults the target through the optional **`io.CohortValidator`** interface (`ValidateCohort(ctx, CohortSource) ([]*errors.CodedError, error)`), the write-side peer of `CohortWriter`; diagnostics land on the new `io.PredictReport.TargetWarnings` slot (symmetric with `ExportReport.TargetWarnings`). A Target that is nil or does not implement it is predicted EXACTLY as before — no extra read, no new failure mode (`TestExportJob_Predict_NonValidatingTargetUnchanged`). `spss.Writer` is the only implementer: `ValidateCohort` runs the writer's own non-data pass (`planCohort` — sidecar resolution, `BuildDictionary`, name policy, charset transcode, derived fold, `NewDataEncoder` column checks) and discards it, so a predicted refusal is the export's own check code-for-code, and it mutates nothing on the Writer. **Sound but INCOMPLETE by design:** anything needing a record (value width overflow, cell-text charset unencodability, a dictionary ID with no source code) is unreachable, and predict must NEVER refuse what the real export would accept — a false refusal is worse than silence. `pulse export predict` reads `--format` (writer built via `newWriterForFormat` against a MemMapFs + throwaway path, never `Close`d, so no file is created) and mounts the four `.sav` write flags, because `--sanitize-names` flips a `PULSE_SPSS_NAME_INVALID` refusal into a warning; with no `--format` behaviour is unchanged and the text output says the target was not checked. `format_version` stays `"1.1"` — `io.PredictReport` is not payload-reachable. Detail: `docs/src/internals/adding-io-format.md` + `docs/src/cli/export-spss.md`.

**Projected buffered decode.** Per-request field projection on the buffered decode iterator is **default-on** — it is output-transparent (same result payload, only faster and lighter per-record), so callers get the win with no flags. Opt out with `pulse.Options{DisableProjection: true}` or the `--no-project` CLI flag on `pulse api process` (v1: `pulse api process` only — `process-chain` / `compose` do not expose it yet). `pulse.Options.ProjectBufferedFields` is retained but deprecated: setting `true` is a harmless no-op; use `DisableProjection` to force full-record decode. Wiring at `pulse.go`: `svc.SetProjectBufferedFields(opts.ProjectBufferedFields || !opts.DisableProjection)`. `processing.NeededFields(req, schema, ext)` walks every request slot and returns a `FieldSet`; the iterator turns retained set into a cached `encoding.DecodePlan` via `Schema.BuildDecodePlan(retained)`. **A slot the walk misses, or a built-in whose `Params` name a field `addAggParamFields` does not know, fails SILENTLY** — the field is decoded onto no `Record`, `Record.NumericValue` answers `ok=false` on every row, and the operator reads a missing input rather than a broken request, so the request succeeds and publishes a confident zero with `n_null` equal to the full admitted count as the only signature. `Crosstab.MarginAggregations` is a walked slot (own `Field`, `Params` fields, and extension widening, exactly as `Crosstab.Cell`); `distinct_by` / `weight_field` / `numerator_field` / `denominator_field` are the aggregator params `addAggParamFields` covers, and a new one belongs there on the day the operator lands. Plan segments: `SkipBytes{N}` (one discard over N bytes) and `DecodeFields{Fields}`. Bit-packed runs stay grouped; null-bitmap whole-or-skip. Extension operators without `FieldInputs` widen retained set to `*`. Bench: ~7× speedup, ~14× fewer allocs on a 4-field projection of a 200-field cohort.
