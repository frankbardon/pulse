# Synthetic data — structural rules: the slot, the rule pass, `owns_nulls`, priority-0 claims, `set_expr` and the coercion matrix

Per-topic slice of the synthetic-data reference (structural rules: the slot, the rule pass, `owns_nulls`, priority-0 claims, `set_expr` and the coercion matrix). Index (preamble + section map): `.claude/reference/synthetic-data.md` — load it first, then only the slice(s) your change touches.

**Structural rules (`Spec.Rules`, additive + `omitempty`).** The slot for the class of fact no statistical summary can express, because it is not variation at all: a question block that is not ASKED of a respondent who failed a screener, a flag that is a band of another column. Reconstructed from marginals those come back as soft noise with a plausible rate and no gate — measured on the motivating cohort, a 50-field perception block whose real co-missingness is exact generated 22 stray rows in 40,000. Five slots per `RuleSpec` (`internal/synth/rules.go`): `when` (optional expr predicate; ABSENT MEANS EVERY ROW, which is not "never"), `set_null`, `set` (LITERAL values), `set_expr` (expression results) and `null_together` (one null decision across a block) — plus ONE MODIFIER, `owns_nulls`, which changes what a `set_null` MEANS for the fields it names rather than adding a sixth action (see the ownership paragraph below). **`set` and `set_expr` are SIBLING KEYS and must not be merged into one map with a `{"$expr": …}` marker**: one map leaves `{"set": {"region": "west"}}` undecidable between a categorical literal and a bare identifier, and two keys make the question impossible to ask. Rules apply in DECLARATION order, sequentially, LAST WRITE WINS, in one pass at the very END of the row (after the model stage), so an expression reads whatever the row holds when ITS RULE starts and a later rule may still change it. **They are deliberately NOT topologically sorted** — a sort would make the applied order implicit, and declaration order is the one ordering an author can read off the document. The pass consumes no RNG, so a spec declaring no rules is byte-identical to one written before the slot existed. The **standalone rules-file format is the `Spec.Rules` array itself**, so an inline declaration and a `--rules` file are the same JSON and the loader needs no translation layer. **Validation is EAGER — at spec parse, never at row time** (`validateRules`, reached from `validateSpec`, so `ParseSpec` / `Synth` / `SynthBytes` / `AugmentFromProfile` all gate): a rule naming a mistyped field or carrying an uncompilable expression is invisible at run time (the run succeeds and the gate is simply absent), which is the exact failure the slot exists to remove. Eight coded faults, one each: `PULSE_SYNTH_RULE_EMPTY` (no action slot), `_FIELD_UNKNOWN` (a slot names an undeclared field — AND an undeclared name inside `isnull("…")`, which is deliberately NOT `_EXPR_INVALID`: that expression COMPILES, since the builtin's signature is `func(string) bool`, so it is an unknown FIELD and widening "does not compile" to cover it would make one code mean two things; detected by `isnullUnknownField`, which PARSES the author's source rather than substring-matching it, and is applied to `compileConstraints` as well as `validateRules` because the two share one environment and `TestValidateRules_ExprEnvIsTheConstraintEnv` holds their verdicts equal), `_FIELD_NOT_NULLABLE` (`set_null` names a field the schema cannot record a null for — see the pass-runs-LAST paragraph for why `null_together` only warns), `_EXPR_INVALID` (`when` must additionally return bool), `_VALUE_INVALID` (the value a rule wants to write cannot be written — a `set` literal OR a `set_expr` result, since both go through one matrix; `details.slot` says which), `_CONFLICT` (one rule naming a field in two slots that disagree — there is no order to appeal to WITHIN a rule, so it is refused rather than arbitrated) `_BLOCK_INVALID` (`null_together` naming fewer than two DISTINCT fields) and `_OWNERSHIP_INVALID` (`owns_nulls` declared with an EMPTY `set_null` — the claim is scoped to that slot and to nothing else, so it has no referent; refused rather than ignored, because an ignored ownership claim is invisible: the fields keep the double-counted null rate the flag exists to remove and nothing in the run says the flag did nothing). A `when` that fails at RUN time keeps `PROCESSING_RUNTIME` and must NOT acquire a code of its own: the surviving causes are generic expr evaluation faults (an `isnull` argument that is only a string at run time, `int()` of a non-numeric string), identical in kind to a constraint's own failure, and the coded error already carries the rule index, the slot and the expression — the path IS still reachable, so the backstop is not dead code, but a code minted for it would describe a state nobody acts on differently. Every error carries the rule INDEX (`errors.DetailSynthRule`) and where one exists the slot (`errors.DetailSynthRuleSlot`) and field, because a rule has no name of its own and the index is the only handle back to the document. `when` and `set_expr` compile against the SAME environment `Spec.Constraints` uses (`rowExprEnv` / `rowExprOptions`, one builder shared) — a second hand-rolled env is what produced issue #258. Faults are reported in a fixed slot order with SORTED map keys, so a rule with two faults refuses the same one on every run rather than whichever key Go visited first. `format_version` does NOT move — `synth.Spec` lives in `synth/`, not `types/`. **The rule pass runs LAST, and that placement IS the semantics.** `drawRow`'s final act, after the model stage, is one pass over `Spec.Rules` (`internal/synth/rules_apply.go`, compiled once per Spec by `compileRules`). The semantics that buys are **`if gate then null else inferred`**: every field has already produced the value generation INFERS for the row — through its own sampler and through whatever model, conditional pair or correlation owns it — and a rule then masks or replaces it ONLY where its `when` selects, so a non-gated row keeps the inferred value untouched. Running the pass any earlier would hand the model the last word on its own target, so a `set_null` over a modelled field would be overwritten on every row and a `set` literal would survive only where no model bid. **The accepted consequence: a field a rule NULLS still contributed its DRAWN value to any model that used it as a PREDICTOR on that row.** The two-phase alternative (evaluate gates, then re-run the dependent stages with gated fields withheld) was considered and REJECTED — it doubles the stage surface and needs a rule↔model dependency order no document declares — and the single-phase reading is defensible on its own terms: the respondent's propensity existed, the question simply was not asked. A later reader will reach for two phases; this is why not to. Per-slot write semantics, which compose symmetrically under declaration order: `set_null` sets the null mask and LEAVES the drawn value in the row (the same shape `nullableSampler` produces, so `isnull()` and a later rule behave identically whether the null came from `null_rate` or from a rule; `writeFieldValueForField` writes the type's zero for every masked field, so nothing leaks to the wire), while `set` writes the value and CLEARS the mask (a rule stating a field's value is stating the field HAS one — leaving a drawn null would write 0 and the literal would silently vanish). A `set` literal is coerced to the row's Go shape ONCE at compile time through `constantRowValue` — the `constant` distribution's own coercion, reused, which is what turns a `set_*` target's JSON `["tv","radio"]` into the `map[string]bool` the row holds. The pass consumes NO RNG and allocates nothing per row. That is a statement about the PASS, and since E2-S2 it no longer implies the stronger one it used to be written as: a spec whose rule PRE-CLAIMS a field (see the paragraph below) retires that field's model, and a retired model stops consuming its own unconditional per-row normal, so the stream legitimately moves — for a reason a warning names, which is the whole difference between that and a determinism bug. A spec declaring no rules, and a spec whose rules claim nothing, are both byte-identical to pre-slot output. Every action slot is now live; `set_expr` has the coercion-matrix paragraph below and `null_together` the block paragraph after it. Two gotchas worth stating because both are silent: a `set_null` over a field NOT declared `"nullable": true` writes the type's zero as an ordinary value with no null bit (`encodeRow` writes the bitmap for nullable fields only) — the rule fires and the file cannot show it — so it is REFUSED at spec parse as `PULSE_SYNTH_RULE_FIELD_NOT_NULLABLE` rather than warned, because it is knowable from `FieldSpec.Nullable` and a warning capped at three examples per kind was three lines out of hundreds as the entire signal for a missing gate. **The refusal is keyed on WHAT THE SLOT CLAIMS, and `null_together` therefore keeps the warning**: `set_null` states the field IS null on a matching row, which a non-nullable field can never honour, while `null_together` states the members carry the GATE's decision — a decision that includes UN-nulling and may be "present" on every row. Do NOT "finish the job" by promoting `null_together` too: the gated-block idiom names a NEVER-NULL field first on purpose, so a refusal keyed on "any field a rule may null" refuses the most useful shape the layer has (falsified — it also breaks two E1 tests); and a `when` reads the row's PRE-ROUNDING float, so `== k` over a numeric reconstructed as a continuous distribution fires only on the draws landing exactly on `k` (for a clamped `normal`, the clamp's point mass) rather than on the whole wire-value-`k` bucket — comparisons (`>= 9`) are the well-behaved numeric form, and `packed_bool` is exact because its row value is exactly `1.0` / `0.0`. Rules reach GENERATED rows only: `AugmentFromProfile` calls `generate()` for its `_synthetic=true` partition and re-encodes the source records straight through, so a `synth from-profile --source` run never rewrites a real row. `format_version` does NOT move. **`owns_nulls`: a rule can be the field's ONLY source of absence, and it ZEROES the own draw rather than applying the residual.** `set_null` states WHICH rows a field is absent on and says NOTHING about how many, so each target's own `null_rate` kept firing beneath the gate. That rate is a MARGINAL the profiler captured — already inclusive of everything the gate removed — so the two composed as `g + (1−g)·r` and a gate that was exactly right about every gated row was wrong about the marginal. Measured on the motivating 122-field profile at 40,000 rows: a 50-field `{"when": "aware == 0"}` gate took `regard` from a captured 0.2526 to a generated 0.4369, and the five `*Aware` gates took `people` from 0.4273 to 0.7506 — every gated cell correct, every rate wrong. `RuleSpec.OwnsNulls` (`"owns_nulls": true`, `internal/synth/rules_ownership.go`) discards those fields' own null draw and lands all fifty on 0.2455, the gate's own firing rate, with the gate still exact on 491,200 of 491,200 gated cells. **The exactly-correct suppression would be the RESIDUAL `(r − g)/(1 − g)`, and it is not computable**: it needs `g`, the rule's FIRING PROBABILITY, and a `when` is an arbitrary predicate over a row — no Spec knows how often it will be true, and estimating it needs a generation pass whose own rows are drawn from the very rates being corrected, which would additionally make the answer depend on `RowCount`. So the flag zeroes the draw and the GAP IS MEASURED rather than guessed: `ownershipWarnings` counts each owned field's realised nulls over ACCEPTED rows (the same commit-per-accepted-row rule the firing counter uses) and reports any field whose realised rate misses its discarded `null_rate` by more than `nullOwnershipDivergenceThreshold` (0.02) AND `ownershipNoiseStdErrs` (2) standard errors — the both-terms rule `FidelityReport.Models` already applies, and dropping the noise term makes the line a coin toss on small runs (at 200 rows a CORRECT claim on a 0.25 field misses by 0.02 about half the time). One message covers both failures it can report — a gate explaining only part of the missingness, and a claim over a field the rule never nulls — because the number tells them apart and the remedy is the same three moves; it is an ATTENTION kind, bounded worst-first at 20 with a counted roll-up. **Where `g` IS knowable the residual is BOUNDED rather than unknown, and that is why `--suggest-rules` sets the flag on every gating candidate**: E3-S1 admits a (gate, target) pair only when the target is null on at least `gateHighNullRate` of gated rows and at most `gateLowNullRate` (0.02) of OPEN rows — and `P(null | open)` IS the residual — so every candidate detection can emit is within 0.02 of exact, the distance `nullRateDivergenceThreshold` already calls immaterial. **Suppression is a WRAPPER that discards the verdict (`ruleOwnedNullSampler`), never a rebuild without the nullable wrapper**: `nullableSampler` consumes one inner draw PLUS one `rng.Float64()` whatever the rate, so a rebuild would drop one draw per row per owned field and shift the whole seeded stream — measured against an un-owned run at one seed, the other 72 fields are cell-identical and the ONLY change is 381,351 null flags REMOVED on non-gated rows, 0 added, 0 values moved. **Ownership is a UNION, never a `resolveConflicts` claim**: `set_null` removes a value rather than supplying one and has never claimed a field away from its own generation (that is E2-S2's rule), and "two gates can each account for this field's absence" is a coherent statement needing no arbitration — two rules may own one field, the draw is suppressed once, either gate nulls it, and the divergence line names BOTH indices because editing one of two does not close the gap. **`null_together` already does this for its non-gate members, by COPY rather than by suppression**, so the gated-block idiom (name a never-null field first so the copy clears the block's own MCAR nulls, then supply the real gate with a `set_null`) is ownership obtained as a SIDE EFFECT; `owns_nulls` is the same statement said directly, on the rule that makes it true, and the two are byte-identical where they overlap. Do NOT conclude the block is retired: it alone expresses a co-missing block with NO gating field, where one member's own draw is the block's only source of absence — the four-field NPS block is exactly that, and without it comes back all-present on 45 of 40,000 rows. `format_version` does NOT move. **A rule that DETERMINES a field pre-claims it at priority 0.** `resolveConflicts` (`internal/synth/conflict.go`) already owns which stage may write a field; `Spec.Rules` now claims first, ahead of the linear-model pre-claim, because the rule pass runs LAST in `drawRow` and an unconditional write wins outright. Without it a modelled field a rule overwrites still gets its model compiled, its residual correlations drawn and — the reason this is not merely wasted work — **a `FidelityReport.Models` entry reporting a captured-versus-recovered coefficient delta for a value nothing kept**, with no slot on the report saying so. `BuildModelFidelity` asks generation's own compiler which models ran (`resolveConflicts` → `buildModelDrawers`), so the claim removes the work and the false report in one move. Everything downstream falls out of the existing machinery: the model loses with the ordinary `conditional relationship conflict: … is already claimed by structural rule N (set_expr); dropping linear model` wording, a conditional pair naming the field loses the same way, and the field stops being a residual-correlation participant with `buildResidualCorrelator`'s existing dropped-participant warning — no second phrasing was invented. **A whole-field claim SUBSUMES that field's `set_*` OPTIONS, and the containment is one-directional.** `claimTarget` is two-level — a whole field is `{field}`, a single set option is `{field, option}` — and those are different map keys, so `resolveConflicts.claimedBy` is the one place the relationship is expressed. Without it an unconditional rule writing a whole multi-select left the per-option set-set / set-categorical pair stages RUNNING and then discarded their work, and the fidelity report scored them: the wasted-stage-and-false-report class the priority-0 pre-claim exists to remove, silent, reachable from a hand-authored spec (no derived spec carries rules, and `--suggest-rules` targets `packed_bool`/`u4`). The other direction must stay false — a pair driving ONE option has said nothing about the field's others, so an option-level claim never reaches the whole field, or one pair would evict a rule or a model from the entire multi-select. A future per-option rule slot MUST key on `{field, option}`; `TestClaimTarget_OptionGranularity` guards both directions and `TestRuleClaims_NeverEmitsAnOptionTarget` fails the moment `ruleClaims` starts emitting option targets. **Which rules claim is the whole contract, and each of the four exclusions is SILENT if it is got backwards** (`internal/synth/rules_claim.go`): a rule carrying `when` writes only some rows, so claiming would strip the model from every row it never touches and leave a plausible bare marginal in its place; **`set_null` NEVER claims, at any conditionality** — it removes a value rather than supplying one, and `if gate then null else inferred` means the field's own model is exactly what produces the value the non-gated rows keep; `null_together` supplies no value either; and a **`set_expr` that READS ITS OWN TARGET does not determine the field, it transforms what generation produced** — the canonical instance is the documented pre-rounding remedy `{"when": "!isnull(nps)", "set_expr": {"nps": "round(nps)"}}`, and claiming there would leave the rounding applied to a bare marginal draw, making the documented fix for one silent fault cause a larger one (measured on the motivating profile: it strips `nps`'s model and all 54 of its residual correlations). The self-reference is detected on the PARSED expression, never by substring — a rule over `nps` must not be excluded by a mention of `nps_reason` — and an unparseable expression (unreachable past `validateRules`) answers "reads", the direction that cannot lose structure. The no-`when` restriction is sufficient rather than limiting because `set_expr` collapses the motivating three-band case into ONE unconditional rule. Measured on the motivating 122-field / 381,324-row profile: an unconditional `set_expr` over `promoter` takes the applied models from 55 to 54, drops its 54 residual-correlation pairs, and removes its `models` fidelity entry; a `set_null` over the same field changes none of the three. `format_version` does NOT move. **`set_expr` and THE COERCION MATRIX.** `set_expr` assigns the RESULT of an expression evaluated over the row, which is what collapses a derived-field relationship from several `when`-gated rules into one unconditional rule (`{"set_expr": {"promoter": "nps >= 9", "passive": "nps >= 7 && nps < 9", "detractor": "nps < 7"}}`) — and, because it carries no `when`, makes the target eligible for the E2-S2 pre-claim, so `promoter` is not modelled and correlated upstream only to be overwritten. It writes the value and CLEARS the null mask exactly as `set` does. An expression returns a Go shape and the target is one of the seventeen declarable field types, so **the matrix is the surface and a wrong cell is a silent wrong value** — a bool reaching a `u8` as a formatted string encodes as `0`, a computed category outside the declared domain adds a dictionary entry that looks like data, a `u4` taking 16 is masked to its low nibble and stored as `0`. There is exactly ONE matrix (`ruleValueFault`, `internal/synth/rules_coerce.go`) and the `set` literal path goes through it too; the row shape then comes from `constantRowValue`, the `constant` distribution's own coercion, so nothing here is a second conversion. The cells, by target CLASS (the three `sentinelFor` derives): a **scalar** (`u4` `u8` `u16` `u32` `u64` `f32` `f64` `date` `packed_bool` `decimal128`) takes a **bool as 1/0** or a **number**, range-checked against the same bounds a `set` literal obeys, and refuses a string; a **categorical_\*** takes a **string that is in the field's declared domain** (`weighted_categorical`'s `params.values`; a `regex` or `constant` field's domain is unbounded and any string is accepted, the same split the literal path makes) and refuses everything else; a **set_\*** takes a **selection** — a `map[string]bool` read straight off another set field, a list of declared option names, or `split()`'s `[]string` — and refuses scalars. **The one asymmetry with `set` is `decimal128` from a STRING, and it is a decision**: a `set` literal string is kept verbatim and parsed by `encoding.ParseDecimal128` (exact), while a `set_expr` string is REFUSED, because expr types every scalar field as the `float64` the row holds so anything computed already lost the digits, AND because a string left in the row for a field `rowExprEnv` typed `float64` makes the NEXT rule's `when` or `set_expr` over it fail at run time — issue #258's failure, now intermittent, firing only on the rows the earlier rule gated. Exactness lives in `set`; the refusal says so. **TWO TIMINGS, one code.** A fault the RETURN TYPE settles is refused at SPEC PARSE (`validateRuleExpr` reads expr's own inferred type off `prog.Node().Type()`; an `interface{}` type is expr saying it could not infer and defers whole), a fault only a VALUE settles — a number out of range, a computed category outside the domain — is refused at ROW time, and both are `PULSE_SYNTH_RULE_VALUE_INVALID` with `slot: "set_expr"`, the field, the expression and the value. The static side does NOT own a table: it probes the same matrix with the type's zero and refuses only on a TYPE fault, so a parse-time refusal cannot disagree with a run-time one. **INTRA-RULE ORDER IS UNOBSERVABLE — every expression in ONE rule, `when` included, reads the row as it stood BEFORE the rule ran, and the rule's writes all land afterwards (`UPDATE t SET a = b, b = a` swaps, and so does this).** That is E1-S4's answer to the question E1-S3 left open, and the alternative was rejected because the order it would expose is not one an author can SEE: a rule's slots are Go maps, JSON key order is gone after decode, and the surviving order is ALPHABETICAL — so renaming a column would silently change a number. Refusing intra-rule reads outright was the third option and also rejected: `{"set_expr": {"nps": "nps + 1"}}`, a field derived from its own drawn value, is the most natural thing an author writes. ACROSS rules nothing changed: sequential, last write wins, so a `set_expr` reading a field an EARLIER rule wrote sees the new value and one reading a field a LATER rule will write sees the old one. **The pre-rounding gotcha bites `set_expr` harder than `when`, because it is silent rather than merely surprising**: the row holds the sampler's float and the wire holds `round(f)`, so a three-band classification written straight off `nps` still sets exactly one flag per row and merely disagrees with the number printed beside it — measured on the motivating 122-field profile at 20,000 rows, 476 of 3,486 scored rows (13.7%). Normalise first, in an EARLIER rule (`{"when": "!isnull(nps)", "set_expr": {"nps": "round(nps)"}}`), which the snapshot rule makes mandatory: in the SAME rule the bands would still read the float. **`round`, not `int`, and the difference is invisible in the metric everyone checks** — both reach 100% band agreement, because an integer field is stored as `floor(v+0.5)` and `band(v) == band(floor(v))` for integer thresholds. `round(v)` moves the FLAGS onto the right side of the band edge; `int(v)` reaches the same agreement by moving the SCORE. Measured on the motivating profile at 40,000 rows: `round` moved `nps` on 0 rows and repaired 1,029 flag disagreements, while `int` moved it on 3,018 of 6,944 scored rows and repaired none — it buys agreement by dropping respondents a point. Same shape on a gate: `familiarity <= 1` fires on 1,843 rows raw, 2,739 behind `round()` with the column unchanged, and 3,824 behind `int()`. **And the `when` guard is not optional**, because a `set_expr` CLEARS the null mask: the ungated form writes a value on every row, so it un-nulls the field and takes any `null_together` block keyed on it along with it — measured, the four-field block goes from 6,944 present to 40,000 of 40,000. That normalisation rule reads its own target, so it does NOT pre-claim `nps` and the field keeps its model, pairs and residual correlations (see the pre-claim paragraph above). **The row environment's functions (U58)** are expr-lang's stock set minus `now()` (refused at spec validation, `PULSE_SYNTH_EXPR_NONDETERMINISTIC`: the wall clock breaks the `(spec, seed)` contract) plus `isnull` plus `exprenv.MathOptions` — the formula attribute's `sqrt` / `exp` / `log` / `log1p` / `pow` / `hill` / trig / `pi()` / `e()`, float `%` and `**` on `detmath`, TYPED so bad arity fails at parse — and NOTHING query-only (vectors, calendar, `total()`, params, embedder functions). A field named like a built-in follows the query side's PRECEDENCE, not a refusal: bare = the field (existing specs keep their bytes), calling a shadowed name is refused, and a bare built-in name no field declares (`pi` for `pi()`) is refused too, because expr-lang would otherwise compile it to a nil. `row` / `lag` are in that reserved set ahead of their stories (`internal/synth/row_expr_builtins.go`). **`row()` is the ACCEPTED-row ordinal, and `monotonic_from` counts the same way (U58 E2-S2).** `row()` (typed `func() int`) returns the 0-based ordinal of the row being drawn, stamped by `generate` on the constraint and rule hosts before EVERY attempt as the count already accepted, so a rejected attempt redraws at the SAME ordinal and the written cohort reads exactly `0..row_count-1` — `row() % 52 == 0 ? a : b` is a period reset with no drift under rejection. It reads a counter, never the RNG, so a spec without it is byte-identical. `monotonic_from` used to advance on every ATTEMPT and left one gap per rejected row; it now commits its step only after accept (`acceptCommitters`, looking through the null and rule-owned-null wrappers — a wrapper that hid the counter would freeze the column or restore the gaps SILENTLY), beside `ruleApplier.commitRow`. A spec that never rejects writes identical bytes; one combining `monotonic_from` with a rejecting constraint changes only that column. The `--suggest-rules` detectors only COMPILE candidates against this environment (to match the loader), never run one over captured records, so `row()` compiles there and has no record-index meaning to choose. `AugmentFromProfile` generates its partition with `generate`, so `row()` and `monotonic_from` count generated rows from 0, excluding the copied source rows. The pass still consumes NO RNG and allocates nothing per row of its own — each rule's evaluated results land in a buffer sized once at compile time. `format_version` does NOT move.
