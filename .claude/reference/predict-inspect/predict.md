## Predict

`internal/descriptor/predict.go` MUST NOT import `internal/service/` or `internal/processing/` — gated by `TestPredictNoExecutionImports`. Predict duplicates operator knowledge on purpose; reaching for the real implementation to validate params fails the gate.

`PredictResult.Streamable` mirrors the per-type `Streamable()` methods plus schema gates (decimal — built-in aggregators only; an extension aggregator on a `decimal128` field skips that gate, as `processing.canStream` does); an extension operator answers from its DECLARED registration flag on the `ExtensionsSnapshot` (attributes: `Mode`, whose `two_pass` also trips the two-pass combination gates), which is exactly what the runtime routes on. A request with no aggregation streams when it carries a matrix, a tier-1 test or a regression, and its `sizes` carry no `data` section (it emits no row; `execution-modes.md` (Streaming Process), U48 #336). Runtime parity is asserted against `processing.CanStreamRequest(req, schema)` by `TestPredict_Streamable_MatchesRuntime`, and for extension requests against `processing.CanStreamRequestWithExtensions(req, schema, exts)` by `TestExtensions_StreamabilityFollowsDeclaration`. `DefaultsApplied` is always computed, whatever the request.

`PredictResult.CrosstabFusable` (`crosstab_fusable`, `*bool`, nil ⇔ no crosstab spec or a slot refused before dispatch) + `CrosstabFusionReasons` (`omitempty`, every decline in rule order, short stable prose) sit beside `Streamable` and answer a different question: not "can this stream" but "will this instance run the crosstab on the fused in-decode arm" (identical output, `O(cells + margins)` memory). They come from `descriptor.CrosstabFusion` — the shared rule `crosstabfuse.Decide` (`internal/crosstabfuse`, a leaf importing only `types` + `encoding`, so predict reaches it without the engine) over the `ExtensionsSnapshot` + instance feature set — on the defaults-resolved request and the COHORT schema (what `service.processCrosstab` hands `processing.CanFuseCrosstab`). Instance-aware: `PredictOptions.DisableCrosstabFusion` (from `Options.DisableCrosstabFusion`) answers false with `CrosstabFusionDisabledReason`. `Predict` / `PredictBytes` only — Compose and ProcessChain validation do not report it. Not payload-schema-reachable (`PredictResult` is a `descriptor` type), so no golden moves. One sanctioned divergence: a keyable built-in grouper whose factory rejects its params (`GROUP_DATE` `component:"fortnight"`) — runtime declines, predict says true; the request errors on either answer. Gates: `TestStreamability_CrosstabFusionPredictMatchesRuntime`, `TestPredict_CrosstabFusableMatchesRuntime`.

`PredictResult.TimeZones` (`time_zones`, never nil) comes from the SAME pure resolver the runtime calls — `ResolveZones` in `internal/descriptor/zone_resolve.go`, which imports `internal/temporal` (allowed: it is a stdlib leaf, not the engine). Predict runs it on the defaults-resolved clone with `PredictOptions.DefaultTimeZone` / `ZoneLoader`, which the facade fills from the service, so a zone refusal is a predict error (`Valid=false`) exactly when runtime would refuse. A join resolves against the joined schema (`PredictOptions.SchemaLoader` reads the right cohort's header + schema; `internal/encoding.JoinedSchema` is the one rule both sides use), `PredictOptions.DisableDefaults` mirrors `Options.DisableDefaults`, and a slot still without a `Type` is reported with the runtime's own message. More than one `JoinSpec` is refused right after the header + schema read through `internal/descriptor.JoinCountRefusal`, the rule runtime `Process` applies first, so code, message and details `{count}` match; inside Compose / a chain both sides add the location (`details.request` / `details.stage`) through `RefusalAt`, as for a zone refusal. The chain validator's stage gate is `internal/mergegate.ChainRefusal`, the function the runtime calls, and a stage ≥1 carrying `Joins` is `PULSE_CHAIN_STAGE_JOIN` on both sides — detail: `execution-modes.md` (Time zones, ProcessChain).

`PredictResult.Weights` (`weights`, `omitempty`) comes from the SAME pure resolver the runtime calls — `ResolveWeights` in `internal/descriptor/weight_resolve.go` (slot `weight` → request `weight` → `PredictOptions.DefaultWeight`, which the facade fills from `Options.DefaultWeight` → none). It runs right AFTER the field-reference rule on both sides (the runtime folds it into `checkFieldRefs`; Compose / chain validators run it only when a slot's references pass, located through `RefusalAt`), against the joined schema for a join. One entry per weight-bearing slot `{slot, operator, field, kind, status, source}`; the key is omitted when neither the request, a slot, nor the instance names a weight, so an unweighted predict payload is unchanged. Contract: `.claude/reference/weighting.md` (Resolution order).

`PredictResult.PValues` (`p_values`, `*descriptor.PValueCount` `{total, uncorrected, basis, threshold}`, `omitempty`) answers "how many inferential p-values does this Request emit, and how many does no multiplicity block correct" — the trigger data for a multiple-comparison nudge (`descriptor.MultiplicityTriggerThreshold` = 10, echoed as `threshold`; the `PULSE_ADVISORY_MANY_TESTS` advisory reads `p_values` and that constant — see "Advisories" below). `internal/descriptor/predict_pvalues.go` (`countPValues`) reads only the request, the resolved `MultiplicityPlan` (`ResolveMultiplicity`, the same call the runtime makes) and the schema's dictionaries. Tests and post-tests count one each, `TEST_TUKEY_HSD` none (already family-wise); an `Inferential` overlay kind counts the p-values its payload carries, `uncorrected` being those no resolved block reaches; a `MAT_CORRELATION` / `MAT_PARTIAL_CORRELATION` under `params.inference` counts C(k, 2) per spec (k = its output axis, resolved by `resolveMatricesFor`), times the tier-1 bucket bound when grouped (a spec's own `multiplicity` block implies inference), corrected iff its `MultiplicityPlan.Matrices` entry is a member (gates `TestPredict_PValuesMatrixInference`, `TestPredict_MatrixManyTestsAdvisory`); the size model adds `auxiliary.p_adjusted` / `significant_adjusted` and the echo for a member (`TestPredict_ReturnSizes_MatrixMultiplicity`). `basis`, weakest wins: `exact`; `dictionary` (an axis is one `GROUP_CATEGORY` over a categorical or `packed_bool` field, so the cell count assumes every dictionary entry becomes a bucket — an over- or under-count when a filter empties some); `lower_bound` (an axis the schema cannot size counts as one). `Predict` / `PredictBytes` report it for a Request; Facet and Compose predict carry their own (see "Advisories", Roots); chain validation does not. Omitted when the request emits no p-value and when `capability:multiplicity` is hidden. `PredictResult` is a `descriptor` type, so no payload-schema golden moves. Gate: `TestPredict_PValues`, `TestPredict_PValuesFollowInstance`, `TestPredict_PValuesOmittedOnRefusal`, `TestMultiplicityTriggerThreshold`. Contract: `execution-modes.md` (Multiplicity).

**`PredictResult.Sizes`** (`sizes`, additive `omitempty`) is reported on EVERY single-cohort predict, with or without a `return` block — one `ResponseSectionSize {section, full_bytes, shaped_bytes, basis}` per top-level Response section the request produces (`data`, `metadata`, `tests`, `post_tests`, `regressions`, `matrices`, `crosstab`, `overlays`, `components`), in Response key order, from `internal/descriptor/predict_return_sizes.go`: each section is a tree mirroring its JSON shape, rows or cells × a bytes-per-value model; `full_bytes` is the tree's sum and `shaped_bytes` walks the SAME tree through the plan's `Visit`, so `shaped ≤ full` by construction and an excluded section is 0; with no effective plan (`ResolveReturn` nil) `shaped_bytes == full_bytes`, and a refused block withholds `sizes` entirely. Rows come from `EstimateGroups` (the MaxGroups bound: the product over every grouper, clamped to the record count unless a grouper fans out), crosstab cells from each axis's per-grouper key counts, matrices from `MatrixPredict.EstimatedBuckets` — each result its primary, vectors, scalars and **every `auxiliary` key its operator emits under the spec's resolved params at the runtime's shape** (`matrixAuxiliaryNodes`, reading the `vectors.Matrix` plans `predictMatrices` returns: pairwise `n` p × p; `params.inference`'s `p` / `ci_lower` / `ci_upper` p × p; `MAT_PCA` `eigenvectors` (+ `unrotated` under a rotation) p × k; `MAT_FACTOR` `unrotated` p × k and, oblique, `factor_correlation` k × k; `MAT_COLLINEARITY` `variance_decomposition` q × q, q = p + 1 uncentered; `MAT_DISTANCE` `centroids` (+ `centroids_standardized`) buckets × members, `pooled_covariance` under mahalanobis), so `return` include / exclude on `matrices[*].auxiliary[.key]` shapes them like any other node (`TestMatrixAuxiliaryNodes_PerOperator` — every sized key is declared in `OutputKeys.Auxiliary` — and `TestPredict_ReturnSizes_MatrixAuxiliary`). A section whose count depends on data — `BucketBasis` `unknown`, a join's open column set, a row-level output with no record count — is OMITTED, never guessed; `components` is sized only when computed (`componentsDisabled`). `basis` describes the count: `exact` (ungrouped aggregation row, ungrouped matrix), `upper_bound` (dictionary / include / boolean / quantile buckets, crosstab axes, a row-level output's record count) or `heuristic` (tests, regressions, overlays, metadata, components). The record count is derived from the file LENGTH (`deriveSingleFileRecordCount`, Inspect's own arm) for a single file and from the per-shard header peek for an archive (passed into `predictSingle`, since the canonical `_schema.pulse` has no records); `RecordCount` stays the archive-only figure it documents. Guidance only — no byte-accuracy gate. Chain validation reports no sizes. `PredictResult.Return` (`return`, the resolved plan — nil when no layer supplies a block) carries **`unresolved_includes`** (#217, additive `omitempty`) — the plan's Open include paths (through a map key or an open value) predict cannot resolve without data, less every `data[*].<column>` include it matches against a CLOSED output-column set (`returnOutputColumns`); at runtime each may match nothing, which a buffered run warns as `PULSE_RETURN_PATH_UNMATCHED` and a stream never reports (streams stay silent by design). `PredictResult` is a `descriptor` type, so no payload-schema or manifest golden moves; the API golden and the predict goldens (`sizes`) do. Gates: `TestPredict_Sizes_NoReturnBlock`, `TestPredict_ReturnSizes_ShapedNeverAboveFull`, `TestPredict_ReturnSizes_ExcludedReportZero`, `TestPredict_ReturnSizes_Basis`, `TestPredict_ReturnSizes_ArchiveRecordCount`, `TestPredict_ReturnUnresolvedIncludes`.

`PredictResult.Matrices` (`matrices`, `omitempty`) reports per matrix spec its shape, axis keys, labels, missing mode, encoding, estimated accumulator bytes, streamability, mergeability, a buffered (rank-method) spec's `row_buffer_bytes` and `pairwise_psd_risk` — read off the runtime's own resolver and the shared no-execute rules in `internal/vectors/matrix_rules.go`, which the engine's `PULSE_MATRIX_NOT_PSD` check also gates on. Long form: `matrix-and-vectors.md` (Predict bullet of the Matrix slot section).

**Field references are one rule, not a predict-only check.** Whether a name a slot references exists is `internal/descriptor.FieldRefRefusals` (`field_refs.go`), which the runtime calls too (first entry, via `FieldRefRefusal`) — so an unknown name is refused with one code, message and details on both sides, where the runtime used to read it as an all-null column and answer with wrong numbers. Predict reports every entry right after zone resolution, on the defaulted clone and the joined schema; the per-family validators (`validateFeatures`, `validateRequestFields`, `validateTests`, `validateRegressions`, `validateWindows`, `validateSort`, `validateCrosstab`) keep only the checks on fields the schema carries (types, orderability, decimal) and must NOT re-grow an existence check (window `order_by` orderability is NOT one of them any more: it is `IsOrderableType`, applied inside `FieldRefRefusals` so the runtime refuses what predict refuses — every type but `set_*`, following the runtime comparator: a categorical by dictionary LABEL, byte-wise, never by index, which shifts across imports and shards; `date` / `datetime` by signed epoch, pre-1970 first; `packed_bool` 0/1; `decimal128` by `Decimal128.Cmp`; nulls last; `TestWindowOrderBy_CategoricalOrdersByLabel`, `TestWindowOrderBy_OrderabilityPredictMatchesRuntime`) — a second copy is how the two sides drifted. The same walk refuses a derived name (attribute label, feature output, window label) that SHADOWS an available column, and an aggregation label that collides with a group field or another aggregation label in the output row, on both sides (`execution-modes.md`, Predict and the validators). Derived names follow the runtime's own naming and PIPELINE order (features → filterers → attributes → record consumers → output-row consumers); the walk is documented on the function. It also judges names inside params (the built-in `aggParamFieldKeys` / `postTestParamFieldKeys` tables) and an extension's `FieldInputs` declaration, which reaches the no-execute layer as `ExtensionsSnapshot.FieldInputs` — so predict takes the snapshot (`PredictOptions.Extensions`) and the service passes its own; `ValidateFacet` / `FacetSchema` apply its filterer half (`FacetFieldRefRefusals`). Join keys likewise: `internal/encoding.JoinKeysRefusals` is the one kind / OnPair rule (`PULSE_JOIN_FIELD_UNKNOWN {field, index}` and siblings), reported by predict right after the right schema loads and by `ValidateJoin`. Detail: `execution-modes.md` (Predict and the validators).

**Field-type acceptance is gated table-wide, with no ledger.** `TestFieldTypeAcceptance_PredictMatchesRuntime` (root `field_type_acceptance_test.go`) runs every registered operator — aggregators, attributes, features, groupers, windows, filterers, tests, regressions — over a cohort carrying one column of every field type, through `Process` and predict: the two accept exactly the same types, and where both refuse they raise the SAME code, once at predict (rule 3). A refusal raised after the type was accepted (too few rows or groups, a degenerate table, a rank-deficient design — `acceptanceDataOutcomes`) counts as acceptance; one raised BEFORE the type is judged (the weight resolver's `PULSE_WEIGHT_UNSUPPORTED` on `AGG_WEIGHTED_MEAN` over a decimal — `acceptancePrecedingOutcomes`) is matched as itself. Every refusal code the gate meets is in `acceptanceRefusalCodes`, each exercised; the former `knownTypeDivergence` ledger is deleted (TODO #198, U45 #313 delivered here). `TestFieldTypeSlots_PredictMatchesRuntime` extends it to the slots the templates leave alone (a test's `split_by` / `subject_field`, a contingency `cols`, `FEAT_TARGET_ENCODE`'s target, `FILTER_RANGE` under numeric bounds). **The accepted-types table, `internal/fieldaccept`, is the single source and the gate's third party**: a leaf (public `errors` / `encoding` / `types` only, so predict may import it) keyed operator → slot (`field`, `field2`, `target`, `predictor`, `split_by`, `subject_field`, `rows`, `cols`, `stratify`, `prediction_field`, `numerator_field`, `denominator_field`) → accepted types + code. Codes say what they mean: every "operator does not accept this type" refusal is `PULSE_FIELD_TYPE_UNSUPPORTED` (details `{type, slot, field, field_type, accepts_types}` where the table writes the message; a constructor that keeps a remedy message — the set guards — keeps its prose, so predict matches code and count, not words); a tier-1 numeric test's `field` / `field2` keeps `PULSE_TEST_FIELD_NOT_NUMERIC` / `PULSE_TEST_FIELD2_NOT_NUMERIC`; a "must be categorical" slot is never `*_NOT_NUMERIC`. **The decimal rule** runs before every row, as the runtime's decimal dispatch runs before any constructor: a `decimal128` primary field on a built-in aggregator outside `fieldaccept.DecimalAggregators()` is ONE `PULSE_AGG_NOT_MEANINGFUL_FOR_DECIMAL` error on both sides at every aggregation slot (crosstab cell and margin aggregations included, both arms) — no longer a predict warning; a hidden or never-registered name falls through to the unknown-type refusal; an extension aggregator is exempt. Predict reads the table in `validateFieldAcceptance` (aggregations, attributes, groups, filterers, crosstab axes / cell / margins, facet filterers; keyed on the operator's ROUTE), `validateFeatureSpec`, `validateOneTest`, `validateWindows`, `validateRegressions`, and — for `AGG_MAE` / `MAPE` / `RMSE`, `ATTR_CODE_IN`, `ATTR_DATE_PART`, which keep the runtime's refusal order — their own validators (`ownTypeValidator`). The manifest's `accepts_types` for a tabled slot IS `fieldaccept.TypeNames` (`TestCapabilities_AcceptsTypesMatchFieldAcceptTable`; no narrower allowance — only `FILTER_TRUE` / `FILTER_FALSE` are wider, their row judging strict mode only). The quantity readers (`ATTR_NORMALIZED` / `PERCENTILE` / `TSCORE` / `ZSCORE`, `GROUP_QUANTILE` / `RANGE` / `ROUNDED`, `FILTER_RANGE`) refuse a categorical — its echo is a dictionary index — and accept `decimal128` / `datetime` / `packed_bool`, whose figures equal an f64 twin's (`TestQuantityReaders_TypeVerdicts`). The numeric readers (the 16 arithmetic aggregators — `AGG_SUM` … `AGG_CI_UPPER`, wrapped by `numericReader` in the registry so every build path refuses — `AGG_RATIO`'s numerator / denominator, `FEAT_LOG` / `SQRT` / `BUCKETIZE`) refuse a categorical and a `set_*` the same way (E2-S4, `TestCategoricalNumericReaders_RuntimeRefusesPredictAgrees`); the counting aggregators (`AGG_COUNT` / `NULL_COUNT` / `MODE` / `MODE_COUNT` / `FREQUENCY` / `DISTINCT_COUNT`) keep reading it. `PULSE_AGG_NOT_MEANINGFUL_FOR_CATEGORICAL` survives only as the facet's numeric-statistic warning. Feature param refusals are the constructor's `PROCESSING_CONFIG` on both sides, in its order, first fault only (`TestFeatureParamRefusal_PredictMatchesRuntime`). An atomic skill's `Field` list for a tier-1 numeric test or a numeric reader is held to `TypeNames` (`TestAtomicSkillFieldTypesMatchFieldAcceptTable`). Only built-ins are tabled; a vector field is never refused here (`PULSE_VECTOR_FIELD_NOT_SCALAR` wins). An operator Type the instance never registered is `PROCESSING_CONFIG` "unknown <family> type: <name>" on both sides (`validateRegisteredOperators`). Predict stricter than a CORRECT runtime is a predict bug; a runtime computing a wrong number is refused through the table, never widened.

Debugging procedure: `docs/src/internals/debugging-predict.md`.

**Saved files are the one non-cohort read predict makes (`models`, `populations`).** A request's `models` and `populations` entries are read and decoded by predict through `PredictOptions.ModelLoader` (the runtime's own `Service.ReadModelFile`) at the point the runtime loads them, by the SAME leaf rules (`model.CheckRefs`, then `model.LoadFiles` — `internal/descriptor/predict_models.go` `predictModels`, Compose `loadComposeModels`, chain `loadChainModels`), so a bad entry is refused with the runtime's code, message and details (`TestModelLoad_PredictRuntimeParity_*`, `TestPopulationLoad_PredictRuntimeParity_*`). A loaded population enters predict's `FitCatalog` as a vector fit WITH its member labels (`model.CatalogWithLoaded`), so field-reference step 12 judges every `params.fit` name and kind against it; a name whose file failed to load is not ALSO reported `PULSE_MODEL_UNKNOWN` (`dropUnloadedUnknowns`). Still no record is read, and no decomposition is recomputed. Label alignment against the slot (`PULSE_VECTOR_REFERENCE_MISMATCH labels_differ`, `vectors.AlignFit` — the bind's own rule) is judged at step 12 for every fit whose labels the catalog knows: a loaded or registered population, and (U30 E2-S5) an in-batch Compose vector fit, whose labels `PredictCompose` resolves from the fit request's battery (`vectorFitAxis` → `composeFitCatalog`) before the slots are checked — the fits' own refusals are still reported after the slots'. Gates: `TestComposeVectorFits_PredictRuntimeParity` (label cases), `TestPopulationLoad_PredictRuntimeParity_Process`, `TestRegisteredPopulation_PredictRuntimeParity`.
