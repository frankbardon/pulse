## Auxiliary crosstab margin aggregations

When a request declares `crosstab.margin_aggregations`, the crosstab components carry AUXILIARY margin figures: `row_margin_aggregations[r]` / `column_margin_aggregations[c]` / `grand_total_aggregations`, one map per margin slot keyed by each auxiliary's effective label, each entry a `types.MarginAggregationFigure{value, present, components}`. `components` is the floor `{n, n_null}` over the ADMITTED records merged with the operator's own `ComponentSchema` keys, so an `AGG_DISTINCT_SUM` auxiliary's `distinct_count` is reachable per margin slot beside the scalar sum (two rendered sample-size rows for one scan). The figures sit BESIDE `row_margin_components`, never inside it: that map describes the cell aggregator's own margin on a different admission, and merging the key sets would put two differently-based figures under one roof.

**The admission rule: a record contributes to an auxiliary margin only if it contributed to a CELL.** Two exclusions follow:

- a record whose CELL FIELD is null (for a vector element cell — `params.element` on `AGG_VEC_*` — whose selected member is null; an element auxiliary's own floor counts its member too);
- a record whose AXIS KEY did not resolve (a null key, a null or empty `GROUP_SET_PER_ELEMENT` set, or a key a grouper `Include` excluded).

**The cell aggregator's own margins follow the axis half of the rule on both arms**: a record reaches a row, column or grand margin — and every normalize denominator, `normalize_level` / `normalize_within` included — only if it reached a cell, so column % is "% of those asked", not "% of everyone" (`TestCrosstab_OwnMarginsFollowCellAdmission`). The two differ on the cell field only: a null cell field reached its cell (as that cell's `n_null`), so it rides the cell margin's `n_null` and is absent from every auxiliary. That is deliberate: an auxiliary is a metric-scoped base the cells beside it divide into, so it must see the same records that carried a value. There is no knob. Getting it wrong is SILENT — every number renders plausibly and only the base is wrong.

**`present` is load-bearing and is not a zero value.** A slot that admitted no record carries `present: false` and no `value` key, because an aggregator over an empty set has no defined output and a fabricated `0` is indistinguishable from a real one; its `components` still carry the floor (`n = 0`). All three figure maps are `omitempty` and ride the DISPLAY flags (`margins.rows` / `.columns` / `.grand`), matching the cell's own margin counts, so a margin computed only as a normalize denominator stays off the wire on both arms.

**Allocation and emission ask different questions; the gap is warned, not closed.** Both arms allocate auxiliary accumulators on `NeedsRowMargin` / `NeedsColumnMargin` / `NeedsGrandMargin` (display OR normalize), so the normalize-only shape accumulates every auxiliary and emits none. `CrosstabSpec.MarginAggregationsObserved` — behind the `PULSE_CROSSTAB_MARGIN_AGG_UNOBSERVED` predict warning — therefore reads the DISPLAY flags directly, not the `Needs*Margin` trio (those answer the cell's question). Keep that predicate and the emission gate stating one rule; drift shows up as a request that quietly does the work and returns none of it. An auxiliary is never a denominator.

Allocation also rides the compute plan: when `components.crosstab` or its `*_margin_aggregations` figures are not computed (a `return` exclusion or the closed DisableComponents gate), neither arm accumulates an auxiliary. Refusals stay ungated: both arms probe-construct every declared auxiliary, so an unknown operator or a misconfigured auxiliary is refused whatever the plan and whether or not a margin is requested, and the refusal is predict's (`TestCrosstabMarginAgg_RefusalIndependentOfMargins`). A request declaring no auxiliary emits none of the three maps and is byte-identical (`TestCrosstab_MarginAggregationsInertAtRequestSurface`).

Implementation detail for the buffered arm (why admission is computed from the axis partitions, not the cell buckets): Implementation notes, `notes-and-undefined.md`.

## Multi-measure crosstabs

`CrosstabSpec.Cells` (`cells`, mutually exclusive with `cell`) folds a MEASURE dimension into the row axis. **Each measure is computed exactly as the single-cell crosstab `MeasureSpec(i)` would be** — its own cells, margins, normalize denominators, auxiliary margins and components over the same axis partitions — and only then folded. Nothing is pooled across measures (`TestCrosstabCells_EachMeasureIsItsSingleCellCrosstab`); the fused arm runs one state per measure in lockstep over one scan (`TestCrosstabCells_FusedMatchesBuffered`).

- **Matrix.** `RowHeader` gains `{_measure, MEASURE}` (`types.CrosstabMeasureField` / `CrosstabMeasureType`); spec row r, measure m sits at payload row r*M+m, its key the row key plus the measure label; `MatrixPayload.CellLabels[i]` names row i's measure and `CellLabel` is `""`. Row margins fold with the rows. Column margins and the grand total are per measure: the single-measure `ColumnMargins` / `GrandTotal` stay empty and the figures move to `MatrixPayload.Measures[m]` (`CrosstabMeasureMargins`).
- **Components.** Every row-indexed `CrosstabComponents` slot folds like the matrix; the column-margin and grand-total counterparts move to `CrosstabComponents.Measures[m]`. Auxiliary figures are evaluated per measure and the admission rule holds per measure unchanged: **a record reaches an auxiliary margin only if it reached a CELL.**
- **Long shape.** Each measure's rows (margin rows included), then the next measure's, every row stamped `_measure`; post-test rows likewise.
- **Overlays.** Only `OVERLAY_PAIRWISE_*` runs, once per measure through one shared accumulator (pairs never cross measures). Every other request overlay, and any Compose overlay reading such a slot, is refused with `PULSE_OVERLAY_REF_INCOMPATIBLE_WITH_SHAPE`, reason `multi_measure_host` — predict, runtime and the Compose arm alike (`overlayhost.MeasureHostRefusal`). A moment kind refuses a measure whose cells carry no Welford triple (or, for `OVERLAY_PAIRWISE_WEIGHTED_TWO_MEANS_Z`, no weighted moments) ALONE: its folded rows are null cells and a `PULSE_OVERLAY_REF_INCOMPATIBLE_WITH_SHAPE` warning carries `measure`, `measure_index`, `cell_type`, `reason`; the layer refuses only when every measure is refused.
- **Absent = byte-identical.** `cell_labels`, `measures` and `components.crosstab.measures` are `omitempty`; gated by `capability:crosstab_cells`.

## Opt-out and the Compose surface

**Opt-out.** `pulse.Options.DisableComponents` (engine default) and `types.Request.DisableComponents *bool` (`nil` inherits). Disabled leaves `Response.Components` `nil` and the wire byte-identical to the Components-free form; `format_version` does not move. The gate sits at each execution path's emission block, so component construction is skipped, not built and discarded. CLI: `--no-components` on `pulse api process` / `process-chain` / `compose`; ProcessStream's `.Components()` returns `nil`; each Compose slot carries its own override. MCP tools do not surface the knob. **`return` interplay:** an engine `DisableComponents` sticks — a request `return` never re-opens the compute gate; only the request's own explicit `disable_components: false` does. Whenever the gate is closed and some `return` layer exists, the effective selection also excludes `components`; with no `return` the opt-out is the compute gate alone (no `returned` marker). The rule lives in `descx.EffectiveDisableComponents` / `EffectiveReturn`; contract: `update-demand.md` (the `Request.Return` row).

**Compute plan.** `processing.ComputePlan` carries one flag per computable part (each `components.*` sub-part, the matrix slot and its finalize-only sub-parts, and per-entry overlay / test / post-test masks, whole-slot regressions). `Service.resolveComputePlan` resolves it ONCE before dispatch and the plan rides the dispatch context to every seam; read the struct for the flag list. The rules:

- A part is computed iff the `return` plan keeps it or something below it. A skipped part is never built (absent from the Go response too); a kept part is byte-identical to the `return`-absent run's (`TestReturnKeptNumberInvariant`). Work counters in `processing.WorkStats()` prove the skip (`TestReturnSkipsComputation*`).
- **Vetoes.** A kept request overlay that reads its host's components (`descx.OverlayReadsHostComponents`) keeps `components.crosstab`: the pairwise family always; the floor-scaling kinds and `OVERLAY_FISHER_EXACT_CELL` only when the cell is WEIGHTED (`descx.CrosstabCellWeightBasis`), since over an unweighted cell they read the matrix payload alone. A prior-period test kind over a grouped Process keeps `components.aggregations` + groups instead. A Compose slot named by a Compose overlay keeps what `Service.composeSlotVetoes` resolves per slot — weight-basis aware; the per-kind audit table is the doc comment on `composeOverlaySlotVeto`. The strongest veto over a slot wins. A wrong floor-kind rule trips the `PROCESSING_INTERNAL` fold backstop (`composeOverlayFloorsPresent`). Chain overlays read data and the crosstab payload only, so they veto nothing; each chain stage runs under its own plan.
- The closed DisableComponents gate drops every sub-part, veto or not. The facade still prunes a vetoed-but-excluded part at serialization.
- **Arm choice reads the ORIGINAL request** (merge gate, `canStream`, crosstab fusion, `PULSE_CHAIN_NOT_MERGEABLE`), so a selection never moves a request onto another arm.
- **Crosstab.** `components.crosstab` off builds no cell / margin component maps on any arm; auxiliary figures off accumulate nothing per record. Registry resolution and probe construction of auxiliaries stay ahead of both gates.
- **Matrices.** No veto. A run accumulates `Request.Matrices` iff it computes the slot or `components.matrices`; each sub-part (`auxiliary`, `scalars`, `vectors`) renders only under its own flag — `standard` drops `auxiliary` except a spec's requested inference keys (`matrix-and-vectors.md` Inference bullet), `minimal` also drops `scalars` and `vectors`. `Request.Vectors` unreferenced warnings are request-derived and always raised.
- **Overlays** follow the selection PER LAYER. An excluded layer that a resolved multiplicity family claims still folds, so `m` and every kept `p_adjusted` match the full run. A skipped layer runs no handler and raises no refusal or warning (predict stays the validator) and stops vetoing; when another layer is computed its position holds a zero `OverlayLayer` (the fold aligns by index). `payload` + `summary` are one unit. Compose-host overlays follow the Compose-level `return` whole.
- **Tests and post-tests** follow the selection PER ENTRY with the same multiplicity veto; a skipped position holds nil when another entry is computed. **Regressions** follow it WHOLE with no veto. A skipped entry or fit raises nothing.

**Compose surface (v1.1).** `ComposedResponse.Responses[i].Components` carries the per-slot block exactly as a buffered `Process` would; the Compose-overlay fold treats it read-only. Compose-host fold diagnostics ride `ComposedResponse.Overlays[i].Warnings` (`omitempty`, shared with the chain-host barrier; `skills/overlay-system.md` (Per-layer warnings)), so overlay-free Compose responses stay byte-identical (`TestComposedResponse_OverlayFreeByteIdentical`). Each slot's `return` and components gate apply per slot; the fold reads a slot's components BEFORE pruning, so a slot `return` alone never starves a Compose-host overlay. The closed DisableComponents gate does: a kind that reads a slot's components is refused rather than folded empty — `PULSE_OVERLAY_COMPONENTS_REQUIRED` (reason `components_disabled`) or the hidden-floor `PROCESSING_CONFIG` (`weighting.md`), predict and runtime alike.

**Compose envelope.** `pulse api compose --json` puts a `ComposedResponse` OBJECT in `data` — `responses` (one per `ComposedRequest.Requests` slot, input order) and `overlays` (one per Compose overlay spec, omitted when none). Each slot's `return` shapes `responses[i]`; `ComposedRequest.Return` (`overlays…` paths only) shapes the layers after the fold and stamps `returned`. `--stream` bypasses the envelope and emits per-row `{"index", "row"}` NDJSON, so Compose overlays surface only in non-streaming mode (`skills/streaming-and-watching.md` (Compose streaming vs. overlays)). Change rows: `update-demand.md` (the `ComposedResponse` row).

**Slot label echo.** Each `responses[i]` carries `label` (`omitempty`): the slot's final label, caller-supplied or the synthesized `request_<i+1>`, stamped after the slot runs on both orchestrators (sweep slots carry their expanded label). It is an ordinary `return` path kept by `standard` and `minimal`. A standalone `Process` never sets it.

The Compose-only slots below share three rules: absent = byte-identical on the wire and under `Hash()`; each is PINNED outside the `overlays…`-only Compose `return` (always emitted, never rounded — the pin keys live in `types/return_shape.go`); each writes one terminal line under `--stream`.

**Sweep.** `ComposedRequest.Sweep` adds no response slot: it expands (`internal/sweep.Expand`) into ordinary slots appended after the explicit `Requests` (grid: first axis slowest). `--echo-request` fills `ComposedResponse.NormalizedRequest` with the expanded slots. MCP `pulse_compose` fills the `standard` `return` default into a sweep body that sets none. `sweep.rank` adds `ComposedResponse.Ranking` (`[]RankEntry{label, value, rank, slot, axes}`, sweep slots only); `rank.profile` adds `RankingProfile` (computed over the full ranking before `top`; never moves the derived seed). A sampling sweep (`random` / `lhs`) adds `SweepSeed` (`sweep_seed`, the effective seed: the pinned `rng_seed`, else derived from the spec), gated with `capability:compose_sweep`. Prose: `skills/compose-sweeps.md`.

**Banner.** `ComposedRequest.Banner` (`capability:compose_banner`) expands (sweep first) into one crosstab slot per section × block — Total first, then the groups — labelled `<section>:<block>`, appended after the explicit and sweep slots. It adds `ComposedResponse.Banner`, stitched after every fold from the still-unshaped slots (a slot `return` trims the wire, never the stitch). Each section copies its slots' cells side by side (rows = union in first-seen order); a record reaches a block's margin only if it reached a CELL of that block. `letters[]` re-letters each column-scope banner overlay banner-wide; the Total slot never receives banner overlays. A section's own `overlays` replace the banner-level ones on its group slots; base `labels` ride only the slots grouping by the bound field (else every slot, warning `PULSE_LABEL_NOT_APPLIED`). Prose: `skills/compose-banner.md`.

**Fits.** `ComposedRequest.Fits` adds `ComposedResponse.Fits`, a `map[string]*FitResult` keyed by fit name: a regression fit's result exactly as that fit request alone would put in `Response.Regressions[0]` (written as the bare `RegressionResult` object), or a vector fit's `{"vector": VectorFitResult}` (covariance M2*/(N* − 1) on the fit's basis; undefined cells `null`). The `vector` key discriminates (`FitResult` `oneOf` in the payload schema). Pinned because a slot that scores against the fit reads those figures. `--stream` writes them only under `--stream-fits` / `ComposeStreamOptions.TerminalFits`. Hidden with `capability:compose_fits`. Pre-pass wiring: `.claude/reference/execution-modes.md` (Compose fits). **Batch warnings.** `ComposedResponse.Warnings` carries diagnostics no slot owns (a fit save's `PULSE_MODEL_OVERWRITTEN`, `details.fit`); every `warnings` slot is a keep path, so it needs no pin. Model file: `.claude/reference/byte-layout.md` (Model file).

**Optimize.** `ComposedRequest.Optimize` (`capability:compose_optimize`) adds `ComposedResponse.Optimizations` (declaration order), solved once after the fits, before any slot, reading no record. Conventions: `marginal` = d objective / d variable; `multiplier` is the shadow price in the objective's OWN direction (for a budget `eq`, the gain per extra unit, equal to every free variable's marginal); `starts_agreeing` counts converged starts within 10 × tolerance × max(1, |f*|) of the best. Flat optima are accurate to about sqrt(tolerance) in x. **Fails alone:** `PULSE_OPTIMIZE_NOT_CONVERGED` / `_INFEASIBLE`, or `coef()` of a failed fit, keeps `{name, direction, error}` and warns `PULSE_SLOT_FAILED` (`slot_kind` `optimizations`); Strict fails the batch with the block's code; any other fault is fatal. Prose: `skills/compose-optimize.md`; rules and gates: `update-demand/compose-optimize.md`.

**Post-fit.** `ComposedRequest.PostFit` (`capability:compose_post_fit`) adds `ComposedResponse.PostFit` (`post_fit`, `[]PostFitResult {label, type, scalars, tables, error}`, declaration order); a `return` path naming it is `PULSE_RETURN_INVALID`; NaN → `null`. **Fails alone:** an operator error or a named failed fit keeps `{label, type, error}` and warns `PULSE_SLOT_FAILED` (`slot_kind` `post_fit`); Strict fails the batch; an output off its declaration is the fatal `PULSE_EXTENSION_POSTFIT_OUTPUT_MISMATCH`. Contract: `.claude/reference/architecture/extension-models.md` (Extension models).
