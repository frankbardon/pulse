# Execution modes — full prose

CLAUDE.md keeps one-line pointers; this file is the in-depth wiring detail per mode. Skill docs are the canonical longform — this file is the "everything tightly cross-referenced in one place" view for engine work.

## Mode index

Relocated from CLAUDE.md "Execution modes (pointers)" at U16 E1-S2 (CLAUDE.md keeps only the pointer). One line per mode: identity, knob, named skill; the sections below carry the wiring.

- **Streaming Process** (`pulse.ProcessStream`, `--stream`) — four orchestrator modes; the forced-buffered list is `skills/streaming-and-watching.md`.
- **Projected buffered decode** — default-on, output-transparent; `Options{DisableProjection}` / `--no-project`.
- **Parallel Compose** (`pulse.ComposeParallel`, `--parallel N`) — `ComposeOptions{MaxWorkers, PerRequestTimeout, FailFast}`; post-slot overlay fold at `internal/service/compose_overlay.go`. `skills/compose-requests.md`.
- **Parallel shards** (`Options.ShardWorkers`) / **parallel buffered Process** (`Options.DecodeWorkers`) — mergeable-only via the engine's internal `CanMergeRequest`, orthogonal to each other. `skills/cohort-schema-design.md`.
- **ProcessChain** (`pulse.ProcessChain`) — source-rooted linear chain, mergeable-only at v1, dual-slot overlays. `skills/process-chain.md`.
- **Pushdown hash join** (`Request.Joins`) — v1 is exactly one inner join per Request. `skills/join-design.md`.
- **Crosstab / fused crosstab** (`Request.Crosstab`; fusion rule `crosstabfuse.Decide` in `internal/crosstabfuse`, shared by `CanFuseCrosstab` and predict) — composed row×column grid whose margins recompute from raw rows, plus an in-decode streaming arm. `skills/crosstab-guide.md`.
- **Facet endpoints** — simple (`pulse.Facet`) + rich (`pulse.FacetSchema`); four FACET-host overlay kinds ride `FacetRequest.Overlays`. `skills/facet-design.md`.
- **Filter precompute** (grouped cohorts) — a filter over ONE group's members is evaluated once per dictionary entry, per-row otherwise. `execution-modes.md`.
- **Point lookup** (`pulse.Lookup`) — O(1) key-exact rows via a prebuilt sidecar index; single-file cohorts, equality-only, full-key. `skills/tool-lookup.md`.
- **Overlays** (`Request.Overlays`, `Response.Overlays`) — additive post-result decorations keyed to host coordinates that **never mutate the base payload**. `skills/overlay-system.md`.
- **Matrices** (`Request.Vectors` + `Request.Matrices`, `Response.Matrices`) — whole-set matrix operators (`MAT_*`) over virtual vectors, folded into per-block `linalg.CoMoment`s through the `BlockMerger` opt-in and emitted at finalize (streaming: terminal flush). `skills/op-mat-covariance.md`; contract `.claude/reference/matrix-and-vectors.md`.

## Streaming Process

`pulse.ProcessStream`, `pulse api process --stream`. Four orchestrator modes — single-pass, grouped, two-pass attributes (Welford-Pébaÿ), streaming features. Forced-buffered: median/percentile/zscore aggregators, `ATTR_PERCENTILE`, `GROUP_QUANTILE`/`GROUP_DATE`, window operators, built-in decimal paths (a `Streamable` extension aggregator streams a `decimal128` target — `UpdateRow` reads `DecimalValue`), tier-1 tests with groupers/features/two-pass, all tier-2 tests. NDJSON one row per line. See `skills/streaming-and-watching.md`.

Response shaping (`return`) wraps the finished iterator at the facade (`Pulse.ProcessStream` → `returnshape.NewRowIter`; `ProcessStreamResult` goes through it): every row is a deep-cloned, pruned copy equal to the buffered shaped `data` element (an excluded `data` yields NO rows, so `ProcessStreamResult` emits no chunks); Components / Metadata are shaped COPIES, so the run keeps accumulating an excluded slot — except an excluded Components sub-part, which the compute plan never builds (see the Compute plan paragraph of `.claude/reference/response-components.md`); an excluded `components` is absent from every chunk, a kept one carries the plan so mid-stream chunks are rounded too; the `returned` marker rides the terminal chunk only (`StreamChunk.Returned`, iterator `Returned()`). Precision is wire-only — rows stay float64 and the shaped iterator's `MarshalRow` writes them (the `api process --stream` writer); `api compose --stream` writes each slot's already-pruned rows through `returnshape.MarshalRow`. A stream has no warnings slot, so `PULSE_RETURN_PATH_UNMATCHED` surfaces only on buffered responses; streams stay silent by design, and predict lists the Open includes it cannot resolve without data as `return.unresolved_includes` (#217, `predict-inspect.md` (Predict)). `return` participates in `Request.Hash`. No effective block ⇒ the service iterator untouched, byte-identical.

**Extension operators route on their DECLARED `Streamable` flag** (aggregators, groupers, attributes, tier-1 row tests; features on the returned value). `Streamable:false` runs buffered even when the value is online-capable; predict reads the same declaration. Merging follows the declarations too (`processing.CanMergeRequestWithExtensions`): an extension aggregator or grouper (single-key or fan-out) merges iff its registration declares `Mergeable` (probe-validated — `PULSE_EXTENSION_MERGEABLE_MISMATCH`), decimal128 targets included; extension filterers and `row_local` attributes merge as row-local operators; `two_pass` / `buffered` attributes, features, windows and tests never merge, so shard / decode parallelism runs those requests serially. A merged grouper folds its components state through `extend.MergeableGrouper.MergeState` (a no-op when it emits no components), and both reducers sum the (record, bucket) assignment count into `GroupedTail.Assignments` so a bucket-less grouper's `{total_n, n_null}` floor matches the serial exit. Fused crosstab: an extension AXIS grouper fuses iff it DECLARES `Streamable` (single-key; the adapter synthesizes the engine-only `KeyFor` from `KeyForRow` + the bound `Group.Field`) or `FansOut` — both probe-validated, so the declaration guarantees the keying sibling. **Deliberate change (cohort-facade E4-S1):** the gate used to probe the constructed grouper's interface, so `Streamable:false` + `KeyForRow` fused; it now runs buffered (output identical, only peak heap differs), because the no-execute predict arm can read only the declaration and both arms run one rule (`internal/crosstabfuse`). A built-in answers from the static keyability table, which still admits `GROUP_DATE`. a `two_pass` extension attribute declines fusion exactly like the built-in two-pass set (`ExtensionRegistry.TwoPassAttributes`), and an extension CELL aggregator fuses only when its registration declares a fusable `MarginReducibility` (summable / mean_reducible / independent; requires `Mergeable`, probe-validated — `PULSE_EXTENSION_MARGIN_REDUCIBILITY_MISMATCH`), read through `ExtensionRegistry.AggregatorMarginReducibility` (undeclared reads as recompute → buffered); the class gates admission only, since the fused walk feeds every margin its own accumulator. Detail: `.claude/reference/architecture.md` (Extension surface).

**Two-pass attributes run in DECLARED order on every scan.** The buffered arm runs `req.Attributes` one after another over the filtered set, so attribute i sees the final per-row output of every attribute before it. `processStreamingTwoPass` reproduces that with a pass plan (`internal/processing/two_pass_plan.go`): each two-pass attribute gets a prepass LAYER — 0 when its inputs (followed back through row-locals) are source fields, else one more than the deepest two-pass attribute it reads. Scan L evaluates, in declared order, only the attributes a layer-L `PrePass` depends on, folding each layer-L `PrePass` at its own declared position; then that layer `Finalize`s and `iter.Reset()` rewinds. The last scan emits every attribute in declared order and folds the aggregations. Filters gate every scan; row counts and filter counters are taken on scan 0 only. Inputs come from `Field`, `Target`, `Predictors`, every identifier in an `ATTR_FORMULA` expression and, for an extension, its `FieldInputs` hook — an extension WITHOUT one (or an unparsable formula) is assumed to read every earlier attribute, which is correct but may add scans. Cost: a request whose two-pass attributes read only source fields keeps the historical two scans byte-for-byte; a two-pass fed by a row-local re-evaluates that row-local in the prepass (`BenchmarkProcessor_StreamingTwoPass`, 200K rows arm64: independent 62 ms unchanged, formula-fed 67 → 94 ms, two dependent layers 84 → 153 ms — the earlier figures were wrong answers). Before this, the prepass saw no attribute output at all and emission ran two-pass before row-local, so `ATTR_FORMULA x` → `ATTR_ZSCORE x` gave `AGG_MAX(zx) = 0` streaming against 1.689 buffered. Shard and decode-worker reducers never take two-pass requests (not mergeable), so the serial iterators carry this path; `ProcessStream` wraps `Process`. Gates: `TestTwoPassOrder_*`, `TestTwoPass_DeclaredOrder_*`.

## Projected buffered decode

Per-request field projection on the buffered decode iterator is **default-on** — output-transparent (byte-identical result, only faster and lighter per record). Opt out with `pulse.Options{DisableProjection: true}` or the `--no-project` CLI flag on `pulse api process` (v1: `pulse api process` only; `process-chain` / `compose` do not expose it yet). `pulse.Options.ProjectBufferedFields` is retained but deprecated — a harmless no-op; use `DisableProjection` to force full-record decode. Wiring: `svc.SetProjectBufferedFields(opts.ProjectBufferedFields || !opts.DisableProjection)`. `processing.NeededFields(req, schema, ext)` walks every request slot — Aggregations, Attributes (incl. expr-AST identifiers via `expr-lang/expr/parser` + `expr-lang/expr/ast` for `ATTR_FORMULA` / `FILTER_EXPRESSION`), Filterers, Groups, Windows, Features, Tests, Regressions, Sort.Field, and the whole Crosstab block (Rows, Columns, Cell, **MarginAggregations**). It also reads the built-in `Params` that NAME a field but do not live on the operator struct (`addAggParamFields`: `distinct_by`, `weight_field`, `numerator_field`, `denominator_field`; plus `stratify` / `target` on the two feature ops). A missed slot or a missed param is SILENT — the field is decoded onto no `Record`, `NumericValue` answers `ok=false` on every row, and the operator publishes a confident zero with `n_null` equal to the full admitted count. The iterator turns the retained set into an `encoding.DecodePlan` via `internal/encoding.BuildDecodePlan(schema, retained)`(retained)` (cached per-iterator); per-record hot path walks the plan via `RecordReader.ReadRecordReusedWithPlan` on BOTH arms — the reuse arm into one reused `Record`, the buffered arm into a FRESH `Record` per row (the map decoder `ReadRecordWithWidePlan` survives only as the defensive projection-without-plan fallback and for non-iterator callers). Plan segments: `SkipBytes{N}` (one `Seek` / `io.CopyN` discarding N bytes, coalescing contiguous unprojected non-bit-packed runs) and `DecodeFields{Fields, Indices}` — `Indices[k]` is the schema position of `Fields[k]`, recorded by the builder's own walk. **Index-keyed reuse.** The reuse decoders write through `encoding.IndexedReusableRecord` (`SetNumericAt` / `SetNullFieldAt` / `SetWideFieldAt`, keyed by position in `Schema.Fields`) whenever the record implements it — `*processing.Record` does — and fall back to the name-keyed `encoding.ReusableRecord` through an allocation-free shim otherwise; a record implementing both is always driven index-keyed. The position is never looked up by name: the full-stride path counts it during its schema walk, the plan path reads `DecodeFields.Indices`, the bitmap uses the bit index. A hand-built `DecodeFields` without `Indices` still decodes (positions recovered on a slow path; a field absent from the reader's schema is `ENCODING_INVALID`). The index is only meaningful against the schema the `RecordReader` was built with — the stream and shard iterators build record and reader over the same schema. **Positional `Record`.** `processing.Record` stores values, null marks and wide values positionally (a `[]float64`, three presence bit-planes — has-value / null / has-wide — and sparse wide slots for decimal128 / `set_*` fields only), so an absent (projected-out) field stays distinguishable from a present zero. Name → slot resolution goes through a `recordLayout` built once per binding: the full layout is cached per schema under a WEAK key (dropped when the schema is collected) and shared by every record over it; a projected layout (`processing.BindRecords(schema, keep)`, built once per iterator / parallel-decode context) stores only the retained fields densely, so a buffered projected record costs O(retained), not O(schema width). A name with no slot — attribute labels, feature/window outputs, a schema field outside the projection — lands in lazily-allocated overflow maps with the former map semantics. The map-taking constructors (`NewRecord*`) convert on entry and do not alias the caller's maps; they are the slow path. Invariants a later change must keep: `ClearForRow` clears the null and has-wide planes (not values) — on the reuse arm it now runs only when run-skip cannot keep the previous row (below) — a `SetNumericAt` position outside a projected layout falls back to the overflow side by name, and `Record.*At` positions are valid only for a record built over the reader's schema (full layout) or a projection of it (a position past the schema panics rather than landing on another field). **Run-skip.** On the reuse arm the decoders skip rewriting fields whose on-wire bytes repeat the previous row — a cohort sorted by its parent key repeats the whole parent block across that parent's child rows. Self-activating: no declaration, no metadata, no format change, and the buffered arm (a fresh `Record` per row) never takes it. The contract is split: the READER (`internal/encoding/reader_runskip.go`) keeps the previous row's bytes (the whole stride on the full path; on the plan path the ASSEMBLED row — every `DecodeFields` group read into one buffer before decoding, which also puts the bitmap in hand first) and passes keep=true to `encoding.RunSkipRecord.BeginRunRow(token, keep)` only when that baseline was decoded, successfully, under the same decode shape (full, or the same `*DecodePlan` — `keep` must stay fixed per plan), into the same record; the RECORD answers true only when the token is the reader that began its previous row, it has the full identity layout (projected and duplicate-name layouts always refuse), and no schema field was written since by anything but that reader's `*At` writes — every name-keyed schema-field mutator (`Set`, `SetNull`, `SetWide`, attribute injection onto a schema name, the name-keyed `SetNumeric`/`SetNullField`/`SetWideField`, `copyStateInto`'s target, a wide value that fell to the overflow side) calls `resetRun()`, and `ClearForRow` zeroes the owner. Off-schema writes (attribute labels, feature outputs) do NOT withdraw the record. A kept row clears only the overflow null/wide marks and the `AllValues` cache; the field walk compares value bytes only (8 bytes at a time over runs of narrow fields) and rewrites a changed field in full; `settleNulls` then visits the fields null on either row, re-signalling null, or clearing it and restoring the value (`ClearNullAt`). Result: after every row the record is identical, accessor for accessor, to a full decode — sorted and scattered, full and plan, across `Reset` two-pass rescans and shard boundaries (a new reader per shard, so the first row of each shard repopulates everything). Backoff: comparing costs a mispredicted branch per field on data that does not repeat, so the reader tallies rewrites over every 32 kept rows and, when more than half the fields changed, decodes the next 1024 rows without comparing before probing again. Bench (`BenchmarkJoinShape_RunSkip`, synthetic 95-field 12.5x-fanout join, 100K rows, in-memory payload, arm64): sorted full-stride 783 → 500 ns/row (1.57x), sorted 4-field projection 117 → 96; scattered full 860 → 754 and projection 114 → 100 — both gains on scattered data come from caching the per-reader stride layout (`strideLayout`, formerly recomputed per row), and the run-skip mechanism itself costs +1.8–2.6% there against a same-commit decode that never compares (without the backoff it was +40–50%). Field-level continuation on that fixture: 0.71 sorted, 0.21 scattered. Gates: `TestJoinShapeRunSkip_WorkCounts` (`make test`, deterministic COUNTS through a counting record on a 5,000-row sorted/scattered pair — sorted keeps every row after the first and writes 1 − continuation of a full decode's values; scattered compares ≤ 5% of rows and never writes more than a full decode, the structural net-loss bound) and `BenchmarkJoinShape_RunSkip` (`-bench` only, against a same-commit no-compare arm on the production record: sorted full ≥ 1.15x, measured 1.31–1.34x arm64 / 1.40–1.42x amd64-under-Rosetta; sorted 4-field projection ≥ 1.00x, measured 1.03–1.06x / 1.09x — two of its four fields change almost every row, write fraction 0.45, just under the backoff's 50% trip; scattered REPORTED, not gated: full 0.97–0.99x on both arches, projection break-even). Against the true pre-run-skip commit the scattered decode is still faster (stride-layout cache), so the loss is relative to the same-commit no-compare decode only. **Grouped (`0x02`) reuse decode.** Over a parent-grouped cohort the reuse decoders do not expand rows (`internal/encoding/group_decode.go`; the logical-stream expansion stays for the map decoders and whole-row consumers — byte-layout.md, Parent groups). The physical row is read whole (one `io.ReadFull` of the physical stride, even under a plan — it is small), every group index bounds-checked, and fields are written at their LOGICAL positions. The decode shape (full, or one plan, keyed by `*DecodePlan` identity exactly as run-skip keys it) is compiled once into a selection: row fields taking a value write, row fields surfacing a null (the plan's bitmap segment surfaces every nullable field `keep` accepts), and per group the members taking each. Plain records (`ClearForRow`) and fresh buffered records get every selected field written. A `RunSkipRecord` gets `BeginRunRow(token, prevValid && sameSink && samePlan)` — the backoff does NOT gate keeping, because an unchanged group index is a certain hit; it only decides whether ROW fields are byte-compared (compare → rewrite changed, as run-skip) or rewritten wholesale this row, with the null settle honouring which it did. A retained group whose index equals the committed row's is skipped outright; a changed one writes its value members from the entry cache, then re-signals null / `ClearNullAt` from the new and old entries' null bits. Entry cache per group, budget `groupEntryCacheBudget` (8 MiB per reader per decode shape, split across value-writing groups, allocated on first changed index): WHOLE mode when the whole dictionary fits (every value member's float64 + decoded `Decimal128`, slot = entry), else DECIMALS mode (only decimal members, direct-mapped — decimal decode is the one expensive member decode; caching cheap members in a thrashing table measured SLOWER than decoding them), else none. Work-count gate (`make test`): `TestGroupedDecode_MemberWriteCounts` — member value writes == Σ changes × members exactly, a row with no index change takes zero member-field writes, sorted ≈ 1.3 member writes/row of 14 members, fresh records decode each entry once (fills == distinct entries); correctness: `TestGroupedDecode_CacheModesMatchFlat` (every cache mode × sorted/scattered × full/plans × fresh/run-skip × backoff on/off), `TestGroupedDecode_RunSkipRowFields`, `TestGroupedDecode_ProjectionSkipsUnretainedGroups`, `TestGroupedDecode_InterleavedPaths`, `TestGroupedDecode_PositionalRecordParity` (production `Record`). Bench `BenchmarkGroupedDecode_ParentWidth` (arm64, 60K rows, 29-field child block, 12.5x fanout, parent 10/40/80 fields; ns/row 0x01 → 0x02): reuse sorted full 444→379, 543→433, 722→520; reuse scattered full 483→481, 1225→649, 2223→1006; buffered full sorted 553→464, 1241→723, 2138→997; 4-field projection flat at ~58 (reuse sorted), ~80 (reuse scattered), ~130 (buffered) for every width vs 145–345 on 0x01. Before this (expansion, E3-S2) 0x02 was 3–30% SLOWER than 0x01 on every arm. Remaining width dependence is inherent: a changed entry must reach the record (scattered ≈ every row), a fresh buffered record takes every retained member, and in sorted order each entry is decoded once on first touch. Past the budget (DECIMALS mode, thrashing) scattered w80 measured 2005 ns/row at a 1 MiB budget — still under 0x01's 2223, the cost of bounded memory. **Typed wide storage.** Wide values live UNBOXED — a lazily allocated `[]encoding.Decimal128`, and set-mask words (1 per narrow rung, 2 for `set_u128`, 4 for `set_u256`) stored bit-for-bit in the spare CAPACITY of the value slice past its length (so a set costs no extra allocation or slice header; every range over the values sees only the slots) — and the reuse decoders hand set masks over through the optional `encoding.TypedSetRecord` (`SetNarrowSetAt` / `SetWideSetAt`), so decoding a set field allocates nothing (boxing a mask ≥ 256 or any `SetMask` into `any` cost one heap allocation per set field per row; `BenchmarkCrosstabWideSetFanout` buffered 100K rows: peak heap 63.3 → 53.0 MB, 3 fewer allocs per row). `WideValue` still returns the stored dynamic type exactly (`Decimal128` / `uint64` / `SetMask`); a value a slot cannot hold typed AND exactly (another dynamic type, a mask past the rung) stays boxed on the overflow side — never truncated. Decimal128 needs no typed twin: a single-pointer struct boxes for free; its decode cost is `big.Int` / `big.Float` work, not boxing. **Null drops the wide value.** `SetNullField` / `SetNullFieldAt` (the decoder's bitmap-null signal) clear the wide value as the map decoder's `delete` did, so a later `Set` on a decoded-null field never resurfaces the decoded mask or decimal; public `SetNull` keeps its documented asymmetry. **Duplicate field names** (nothing on import rejects a repeated column) share ONE slot per name, whose metadata is the first occurrence (`Schema.Field(name)`): the last occurrence decoded wins the value and wide value, a null on any occurrence marks the name null — exactly the former map-key behaviour. Bench (`BenchmarkBufferedRecordFootprint`, synthetic 95 fields × 200K rows): retained heap 3.99 KiB → 1.04 KiB per buffered record full-decode, 408 → 144 B under a 4-field projection; buffered decode 4.1 µs → 1.1 µs per record. Bit-packed grouping: any contiguous `u4`/`packed_bool` run stays grouped — if any member retained the whole group becomes one `DecodeFields` (unretained still decoded to keep cursor aligned, map writes suppressed); otherwise the run folds into one `SkipBytes{K}`. Null-bitmap whole-or-skip: bitmap decoded once when any nullable field retained; else single `SkipBytes{N: Schema.BitmapByteSize()}`. Extension operators without `FieldInputs` widen retained set to `*` (full-coverage plan). Bench: synth 200-field × 100K-row Process drops from ~1.07s to ~155ms (~7×, 14× fewer allocs) on a 4-field projection. Detail: this file (above) is the projection/decode-plan home; `docs/src/internals/extension-points.md` (FieldInputs hook) carries the extension side, and CLAUDE.md "Byte-layout invariants" (Projected buffered decode) the contract summary. `skills/cohort-schema-design.md` deliberately carries NO decode-plan section — it is the schema-authoring surface, and a projection section there would push an already-over-budget skill further over for prose that belongs beside the execution modes.

## Parallel Compose

`pulse.ComposeParallel`, `pulse api compose --parallel N`. Bounded worker pool over `ComposedRequest`. Order-preserving by slot index. `ComposeOptions{MaxWorkers, PerRequestTimeout, FailFast}` (FailFast defaults true).

Post-slot-barrier Compose-overlay fold (`internal/service/compose_overlay.go` ⇒ `processing.ApplyComposeOverlaysWithRequests` in `internal/processing/overlay_compose_dispatch.go`; the bare `ApplyComposeOverlays` is the nil-requests, nil-extensions delegate kept for embedders): the orchestrator invokes `s.applyComposeOverlays(ctx, req, requests, responses)` once every slot has produced a finalised `*Response` and BEFORE the response is returned. Operates EXCLUSIVELY on `*Response` objects; per-slot `Responses[i].Overlays` is left UNTOUCHED.

FailFast handling: when `FailFast=true` (default) AND any slot fails, the orchestrator returns the first observed error WITHOUT invoking the overlay hook. FailFast=false routes slot failures through `SERVICE_INTERNAL` which also skips the hook. Empty / nil `req.Overlays` short-circuits with no allocation (overlay-free Compose JSON is byte-identical to a request that omits the slot entirely).

Per-kind handlers replace the chassis stub (`applyComposeStub`) for every Compose-only kind that has shipped. The six crosstab-shape COMPOSE handlers (`OVERLAY_INDEX_VS_REF`, `OVERLAY_DELTA_VS_REF`, `OVERLAY_PROP_Z_CELL`, `OVERLAY_T_CELL`, `OVERLAY_CHISQ_VS_REF`, `OVERLAY_RANK`) are wired today; remaining Compose-only kinds dispatch through the chassis stub until their handler lands. All buffered — streamable subset is empty across COMPOSE by construction.

Request-shape gates on the COMPOSE host. Everything else in this fold reads `*Response` only, but `internal/processing/overlay_compose_partition.go` needs the AUTHORED request: the `OVERLAY_PROP_Z_PANEL` within-prefix slab gate turns on each slot's declared `Crosstab.Rows` grouper types, and a materialised `MatrixPayload` carries its row KEYS but never the grouper that produced them — a fan-out row axis is invisible downstream of execution. So `service.(*Service).applyComposeOverlays` passes the per-slot requests and the `*ExtensionRegistry` into `ApplyComposeOverlaysWithRequests`, and the gate runs per spec INSIDE the dispatch loop (after reference/target resolution, before the key-set and schema walk — mirroring predict's Gate 3b position) rather than in the handler, because the `composeOverlayHandler` signature must stay `(spec, reference, targets, refIdx, targetIdxs)`. The gate declines whenever an earlier refusal is due, so the cap still fires first. An embedder calling the bare `ApplyComposeOverlays` gets no request-shape gate — the documented counterpart of the exported `ApplyOverlaysWithExtensions` bypass on the MATRIX host.

Response shaping (`return`) never runs inside the service: `Service.ComposeResolved` / `ComposeParallelResolved` hand the facade the label- and defaults-resolved slot clones, and `Pulse.Compose` / `ComposeParallel` apply each slot's plan plus the Compose-level `ComposedRequest.Return` (top-level overlays only) via `returnshape.ApplyComposed` AFTER the overlay and multiplicity folds — so every layer reads unshaped slots and serial ≡ parallel. What a slot's selection skips COMPUTING is decided per slot, where the whole `ComposedRequest` is in hand: a slot a Compose overlay names (reference or target) keeps every Components sub-part (`composeSlotVetoes`), an unnamed slot skips what it excludes — the Compute plan paragraph of `.claude/reference/response-components.md`. Contract row: `update-demand.md` (Return).

Slot label resolution: `applyComposeLabelDefaults` synthesises `request_<index+1>` for empty `Request.Label`; `ApplyComposeOverlays` builds a `Label → Index` lookup. The dedicated error codes `PULSE_OVERLAY_REFERENCE_UNKNOWN` and `PULSE_OVERLAY_TARGET_UNKNOWN` are pending — the chassis currently falls back to `PULSE_OVERLAY_REF_UNKNOWN` with a `which` Detail. See `skills/compose-requests.md`.

## Parallel shards

`pulse.Options.ShardWorkers`, default `0` ⇒ `runtime.NumCPU()`. An explicit `1` forces serial. Both concurrency knobs (`ShardWorkers` here, `DecodeWorkers` under Parallel buffered Process) are orthogonal to each other and reject negatives at `pulse.New()` (relocated from CLAUDE.md "Build / Env" Knobs at U18 E1-S2). Bounded per-shard worker pool inside `Process` when cohort is a shard archive. Reducer engages only when every operator is mergeable per `processing.CanMergeRequestWithExtensions` (built-ins per type with non-decimal targets, extension aggregators per their `Mergeable` declaration; no windows/features/regressions/tests/two-pass). The per-row order is filter → row-local attributes → floor and `Run.NullRecords` tallies, on both reducers and the serial grouped path, so a primary field that is an attribute label is read after it lands. Non-mergeable falls through to serial `shardIter`. Associative+commutative byte-equal vs serial; Welford within ULP via Chan-Welford. Surface: `internal/service/shard_reduce.go`, `processing.MergeableAggregator`, `types.AggregationType.Mergeable()`. See `skills/cohort-schema-design.md` (Sharded) + `skills/cohort-sharding.md`.

**`Response.Components` is part of that parity, not an exception to it.** Both reducers share `shardPartial` / `mergeShardPartials` / `finalizeMergedPartial`, and `shardPartial` carries per-slot floor tallies (`aggFloor`, `processing.SlotFloor`; per bucket `groupFloors` on a grouped partial) and `processing.FilterPassCounters` alongside the operator state, all folded slot-wise on merge. The per-operator `Operator` map is read off the MERGED aggregator — the arms fold operator STATE, so no components-level merge exists or is needed, and the `Mergeable` / `Partial` / `None` classes need no second gate here because `CanMergeRequest` already refused anything whose state cannot fold. Emitted: `Aggregations` (grouped: cohort-wide slot floors + per-bucket `groups[]`, built by the shared grouped tail), `Filterers`, `Run`, and `Groupers`: each worker builds its own grouper instance, and those instances' live bucket state folds through `processing.MergeableGrouper` (implemented by exactly the `GroupType.Mergeable()` set), so the merged grouper's `Components()` is the serial one's. **The grouped arm has no emission tail of its own** — it hands the merged buckets and grouper to `processing.FinalizeGroupedStream`, the tail the serial streaming-grouped path uses (row order incl. include order, `Request.Sort`, Components, SERIES overlays), and keys records through `processing.GroupKeyer` (multi-key fan-out for `GROUP_SET_PER_ELEMENT`). A private copy of that tail used to drop `Sort`, `Overlays`, include order and `Groupers`, and refused `GROUP_SET_PER_ELEMENT` outright. `Run.ShardCount` is the archive's shard count on BOTH arms — the serial exit stamps it in `Service.Process` (`stampShardCount`) because the processing layer has no shard concept. Counting presence for the floor goes through `processing.FieldPresent`, never `Record.NumericValue`, or a set column reads as entirely null. Parity gates: `TestShardWorkers_AggregationComponentsParity`, `TestShardWorkers_FiltererComponentsParity`, `TestDecodeWorkers_ComponentsParity`, `TestShardWorkers_ComponentsParity_GroupedAndFlatArchives` (whole `{data, components, overlays}` document, flat + grouped `0x02` archives), `TestDecodeWorkers_GroupedAnswersParity`, `TestMergeableGrouper_MergedComponentsEqualSerial`.

**Resource limits on the grouped paths (U19).** `MaxGroups` is counted at every bucket mint — O(1) per NEW key, never per row — and a breach raises `PULSE_LIMIT_EXCEEDED` (`limits.Check`) with no partial result: the serial streaming-grouped mint (`processStreamingGrouped`), the buffered path once `Grouper.Group` returns (one check on the partition size), `GroupedMatrices.bucket` (built with the run's limits by `BuildGroupedMatrices`), each parallel partition's `foldGroupedRow`, and the MERGED key count in `mergeShardPartials` (every partition can sit under the limit while their union does not). `newProcessor` installs `Service.Limits()` through `Processor.SetLimits`; both parallel reducers bypass it, so `newShardPartial` takes the limits explicitly. A partition never holds more keys than the run, so a local trip is a sound early abort; the parallel `observed` is therefore the count AT BREACH (≥ configured + 1) and is not reproducible across worker counts — parity compares `{code, limit, configured}` only. Facet bounds each faceted field's distinct values the same way (rich categorical / boolean accumulators, base and additive; the simple facet's numeric stream) — the simple facet's categorical fast path returns the resident dictionary and mints nothing, so it is not counted. Gates: `TestMaxGroups_ProcessorPaths`, `TestMaxGroups_GroupedMatricesMint`, `TestMaxGroups_ParallelShardPartition`, `TestMaxGroups_ParallelShardRuns`, `TestMaxGroups_ParallelDecode`, `TestMaxGroups_GroupedMatrixRun`, `TestMaxGroups_PartitionMatricesCarryLimits`, `TestMaxGroups_Facet`, `TestMaxGroups_FacetBool`.

## Parallel buffered Process

`pulse.Options.DecodeWorkers`, default `0` ⇒ `runtime.NumCPU()`. Bounded per-segment worker pool inside `Process` for single-file (non-shard) cohorts. Engages only when `service.canParallelDecode` accepts — `DecodeWorkers != 1`, `recordCount >= service.parallelDecodeRecordThreshold` (currently `100_000`), single-file (sharded routes through `ShardWorkers`), `resolveRealPath` succeeds (mmap available), `processing.CanMergeRequestWithExtensions(req, schema, exts)` is true. Ineligible falls through to serial `scanIter`. Components parity is the ShardWorkers paragraph above verbatim — same `shardPartial`, same merge, same emission set; `ShardCount` stays 0 because a single-file run is not a shard run.

Crosstab is intentionally NOT exercised today — `validateCrosstabSpec` requires `req.Aggregations` empty so crosstab requests always fail `CanMergeRequest`. This infrastructure benefits future non-crosstab buffered Process calls.

Segments stride-aligned at record boundaries over the mmap'd record region AND block-aligned: every boundary is a multiple of `linalg.MergeBlockSize` (4096 records; `blockAlignedSegments` spreads the ceil(N/4096) blocks evenly, the ragged tail lands in the last segment, and workers beyond the block count get an empty segment that never reaches its factory), and `DecodeCallbackFactory(workerIdx, startRecord, recordCount)` hands each worker its segment's ABSOLUTE start record so a block-keyed reducer can key row `startRecord+i` to block `(startRecord+i)/4096` and fold blocks through `linalg.MergeTree`; same `DecodeFields`/`SkipBytes` plan shared read-only across workers; each worker owns a `shardPartial`; partials fold in worker-index order via `mergeShardPartials` + `finalizeMergedPartial`. Byte-equal vs serial; Welford within ULP via Chan-Welford. Surface: `internal/service/parallel_decode.go`, `internal/service/parallel_reduce.go`. See "Mode index" (Parallel shards / parallel buffered Process) below for the knob, and CLAUDE.md "Build / Env" (Knobs) for the threshold; the mechanics above are the detail home.

## Blocked merge (`processing.BlockMerger`)

The opt-in for a reducer whose answer must be BIT-identical under every concurrency knob, not merely within ULP. Surface: `internal/processing/block_merge.go`; the one built-in user is the U16 matrix slot (`MAT_*`, below — no extension operator can opt in), and every other reducer keeps the `MergeOnline` path above untouched.

- **Positions.** Every record source stamps the row's merge-block position on the `Record` (`SetMergePosition(shard, record)` → `MergeBlock() (BlockKey, bool)`; packed into the Record's padding, size stays 96 bytes): the serial single-file iterator (`streamingIterator`, shard 0, absolute record index), the serial archive iterator (`shardIter`, the shard's archive index + in-shard record index, restarting per shard), the parallel-decode workers (shard 0, `segment start + offset`) and the per-shard reducer (`processOneShard`, same keys as `shardIter`). `BlockKey{Shard, Block}` with `Block = record / linalg.MergeBlockSize` (4096).
- **State.** A `BlockMerger` is an `OnlineAggregator` whose state is a `*BlockCoMoments` — one `linalg.CoMoment` per block that saw a row, rows folded in record order. A record no source stamped (join output, a chain stage, a test harness) is refused `PROCESSING_INTERNAL` rather than guessed at.
- **Merge.** `mergeShardPartials` (both parallel arms, ungrouped slots and grouped buckets) moves the other partition's blocks in via `processing.MergeBlockMerger` → `BlockCoMoments.Absorb` — a disjoint union, so partition order cannot reach the bits; a key on both sides means a block was split across partitions and is `PROCESSING_INTERNAL`.
- **Tree.** At `Finalize` the reducer calls `BlockCoMoments.Tree`: `linalg.MergeTree` over each shard's blocks in block order, then `linalg.MergeTree` over the per-shard roots in shard order. A block no row reached has no entry (absence is data-determined); no blocks ⇒ an empty accumulator. Serial, any `DecodeWorkers` and any `ShardWorkers` count therefore produce the same bits on every architecture (the kernels are FMA-free).
- **Matrix slots.** `Request.Matrices` state is not an aggregator: each partition (`shardPartial`, both arms) carries a `*processing.MatrixSlots` (`mats`, the `aggs` analogue, nil without matrices; a grouped partition carries per-bucket `*processing.GroupedMatrices` in `groupedMats` instead, fed per key by `foldGroupedRow`, merged key by key and rendered by the grouped tail in the final, `Request.Sort`-applied Data order — `.claude/reference/matrix-and-vectors.md`) built off the STAMPED request by `processing.BuildMatrixSlots`, folds every filter-passing row after the universal floor (`processOneShard` / the decode callback), merges in `mergeShardPartials` via `MatrixSlots.Merge` (slot-wise `MergeBlockMerger`, so the same disjoint union), and `finalizeMergedPartial` sets `Response.Matrices` from `MatrixSlots.Finalize` on every arm. The merge gate admits it: `mergegate.MergeRefusal` waives the at-least-one-aggregator rule for a request carrying matrices, and requires every `MatrixType.Mergeable()` (manifest `matrices[].mergeable`); a grouped request carrying matrices merges per bucket under the ordinary grouper rule. `ChainRefusal` still strips `matrices` before the rule. `Run.NullRecords` stays 0 for a matrix-only request on every arm (no aggregator or grouper names a primary field). Gate: `TestMatrixCovariance_WorkerInvariant` (`internal/service/matrix_merge_invariance_test.go`) — every real `MAT_*` registration (`MAT_COVARIANCE`, `MAT_CORRELATION`) under the same cohorts and knobs as the vehicle gate below, matrix-only and beside an aggregation, weighted and unweighted, bitwise over every cell and the determinant plus warnings and `Components.Run`; `TestMatrixOnly_RunComponents`.
- **Caveat.** A multi-shard archive and the single file holding the same rows cut blocks at different places, so they agree to rounding but may differ in the last bits; a ONE-shard archive equals its single-file twin bit for bit.
- **Gate.** `TestCoMomentMergeTree_WorkerInvariant` (`internal/service/comoment_merge_tree_test.go`) drives a `_test.go`-only CoMoment reducer through the real dispatch (registered on `Service.SetExtensions`; no registry, manifest or skill entry): serial vs `DecodeWorkers` 2/3/7/8 on 102,400- and 105,177-record cohorts, serial vs `ShardWorkers` 2/3/8 on an 8-shard archive, listwise/pairwise × weighted/unweighted — bitwise over N, invalid-weight count, W, means and every pair's count, weight and M2. Unit gates: `TestBlockCoMoments_*`, `TestRecordMergePosition*`.

## Filter precompute (grouped cohorts)

Over a parent-grouped (`0x02`) cohort a filter whose every input field is a member of ONE group has at most `entry_count` distinct answers, whatever the row count or order. `internal/processing/filter_precompute.go` evaluates it once per dictionary ENTRY into a two-bit-per-entry verdict table (unknown / fail / pass / per-row) and turns each row's verdict into a bit test on the row's entry index. On the effort's reference shape that is ~109K evaluations instead of ~1.4M. Derived at read time, never persisted; opt-out process-wide with `processing.SetFilterPrecompute(false)` (benchmarks / A-B only — it changes speed, never a result). Diagnostics: `processing.FilterPrecomputeStats()` (tables built, entry evaluations, table bytes, ineligible pairs) — only table builds and entry evaluations touch its atomics, never the per-row path.

**Seam.** The wrap is at the `FilterFunc`: `Processor.buildFilterFuncs` and `processing.BuildFilters` wrap each ELIGIBLE filterer (grouped build schema only; an ungrouped schema gets the builder's `FilterFunc` back unchanged, so a `0x01` cohort pays nothing). `applyFilterPass` is untouched, so `{n_in, n_out, n_null_input}` are the per-row counts by construction: `n_in` / `n_out` follow the verdict, and `n_null_input` still reads the record's own null state (`Record.IsNull`, now one name resolution instead of three). **The entry index** reaches the record through `encoding.GroupIndexRecord` (`SetGroupIndices(schema, idx)`), called by the grouped reuse decoder after every row on the full, plan, plain-sink and run-skip paths (`nil` for a plan that decodes nothing). `*processing.Record` stores the indices bit-exactly in the tail of `vals` past the set-mask words (`recordLayout.nGroups`; no allocation, none at all for an ungrouped schema) and reports them through `Record.GroupIndex(g)` only while valid: `ClearForRow` and `resetRun` — every schema-field mutation that is not a decode write — withdraw them, and indices addressing another schema than the record's own (by identity; the decoder passes the GROUPED schema, not its `Logical()` view) are refused. A feature or attribute rewriting a member's name therefore sends that row per-row, never to a stale verdict.

**Eligibility** (`precomputeInputs`, then per record schema `precomputeGroup`): every built-in filterer on its `Field`; `FILTER_EXPRESSION` when its AST's free identifiers are all fields and every call is pure — expr-lang built-ins except `now()`, the set built-ins, and `lookup()` only when every lookup table is a static `Rows` map. Embedder `ExprFunctions` (even one shadowing a built-in), `let` names, `$env` and off-schema columns disqualify. Extension filterers never qualify — a registration declares no purity and `FieldInputs` does not prove statelessness. Inputs must resolve to unique field names in ONE group: a group member mixed with a row field, or two groups, stays per-row (the verdict space is the product; there is no small table). **Evaluation is lazy**: an entry is evaluated the first time a row carrying it reaches the filter, so the work is the DISTINCT entries reached — never more than the per-row count, even behind a selective earlier slot. An entry whose evaluation ERRORS is marked per-row and re-evaluated on each of its rows, so an error surfaces on exactly the row the per-row path raises it on, and never when no such row gets there. Per-entry evaluation decodes only the filter's input members (`internal/encoding.NewGroupEntryDecoder(schema, g, fields)`), not the whole entry.

**Arms.** Routed: streaming Process (reuse record), buffered and projected Process (fresh record per row through `ReadRecordReusedWithPlan`), fused crosstab and buffered crosstab, parallel buffered Process (one `FilterFunc` set — and so one verdict table — per worker; bounded by workers × entries), Compose (per slot), ProcessChain stage 0, `FacetSchema`, and `FilterToFile` (its map decode forwards `RecordReader.GroupIndex` into `Record.SetGroupIndices`; `TestGroupedCohort_FilterToFilePrecompute`). Per-row fallback (correct, not precomputed): every other map-decode consumer — `Lookup`, the shard reducer, the projection-without-plan fallback — plus joined records (`Request.Joins`), ProcessChain stages ≥ 1 (synthesised ungrouped cohorts) and any extension filterer. Shard archives refuse grouped shards today; the tables are keyed by the record's schema pointer (the shard's own dictionary), so grouped shards need no change here beyond the decoder handing over that shard's schema. Gates: `TestFilterPrecompute_ParityEveryFilterer` (all built-in filterers, both reuse arms, verdicts + components vs per-row and vs `0x01`, evaluation count = distinct entries, ≥10x at 12x fanout), `TestGroupedCohort_FilterPrecomputeParity` (facade arms, exact entry-evaluation counts), `TestFilterPrecompute_ParallelDecode`, `TestGroupedDecode_ReportsGroupIndices`, `TestRecord_GroupIndexWithdrawnByEveryMutator`. Bench: `BenchmarkFilterPrecompute` (`internal/service/`).

## Compile-once expressions (`FILTER_EXPRESSION`, `ATTR_FORMULA`)

Both compile their expr-lang program ONCE per build (`internal/processing/expr_program.go`), never per row. **Prototype**: every schema field declared with the Go type `Record.AllValues` gives it (`exprValueType` — float64; string for a dictionary categorical; `[]string` for a dictionary set; `Decimal128` / `uint64` / `SetMask` otherwise), so build-time type checking equals the old per-row check on a row with every field present — same program, same results, same `PROCESSING_RUNTIME` "compiling … expression" error, now raised by `BuildFilters` / `buildFilterFuncs` / the attribute build (`bindAttribute` → `prepare`) before any row. A name the schema cannot declare (feature output, earlier attribute label) DEFERS the compile to the first record, against prototype + that record — the old first-row env — then caches it. **Env**: per row, only the named fields (`Record.exprValue`, pinned to `AllValues` by `TestRecord_ExprValueMatchesAllValues`) in a pooled map; `$env`, a deferred compile, or a record already carrying its `AllValues` map take the whole map. **Null**: a null field is absent → reads as nil. Rows with every referenced field present run the typed program; a null-input row runs an untyped twin (every name `any`, compiled lazily once) so nil follows expr-lang's nil rules uniformly (`== nil` true, `==` false, `!=` true, `in` false, `??` substitutes; ordering / arithmetic / nil-rejecting functions error). `FILTER_EXPRESSION` reads a null-input evaluation error (or nil result) as UNKNOWN → row dropped; `ATTR_FORMULA` raises it ("evaluating formula expression"). `now()` still evaluates per row. **Concurrency**: `*vm.Program` is immutable and `expr.Run` builds a VM per call; the lazy compiles sit behind a mutex + atomic publish. Gates: `TestExprProgram_CompilesOncePerBuild` (`processing.ExprCompileCount` deltas independent of row count), `TestExprProgram_MatchesPerRowCompile` (per-row-compile oracle), `TestExprValueType_MatchesAllValues` (every field type × every decode path), `TestExprFilter_NullSemantics`, `TestExprProgram_ConcurrentRuns` (`-race`). Bench `BenchmarkExprCompileOnce` (95-field join fixture, 100K rows): filter pass ~8.7 µs → ~0.14 µs/row, end to end ~24 → ~2.1 µs/row (0x01), ~24 → ~1.1 (0x02).

## ProcessChain

`pulse.ProcessChain`, `pulse_process_chain`, `pulse api process-chain`. Source-rooted linear chain. Stage 0 against `ChainRequest.Cohort`; subsequent stages receive prior `Response.Data` as synthesised in-memory cohort (grouper keys → categorical_u32, aggregator outputs → f64). Mergeable-only at v1: every stage passes `internal/mergegate.ChainRefusal` — the merge rule `CanMergeRequestWithExtensions` delegates to (`mergegate.MergeRefusal`: mergeable aggregators / groupers, streamable filterers, row-local attributes, no built-in aggregator over `decimal128`) — every mergeable built-in emits one f64 per row, so `AGG_MODE` (categorical: the dictionary index, not the label), `AGG_MODE_COUNT` and `AGG_FREQUENCY` are admitted. The runtime calls it as `processing.ChainRefusal` over the `ExtensionRegistry`, `ValidateChainWithExtensions` over the `ExtensionsSnapshot` (`ValidateChain` is extension-blind and flags a `Mergeable` extension aggregator the runtime admits), so both refuse with one `PULSE_CHAIN_NOT_MERGEABLE "chain stage is not mergeable: <reason>" {stage_index, stage_name}` (`TestChainGate_ValidatorMatchesRuntime`). Both sides gate each stage after smart defaults (see Time zones → Predict and the validators). **Only stage 0 may join:** a later stage's `Joins` (which the runtime used to drop silently) is `PULSE_CHAIN_STAGE_JOIN {count, stage, stage_name}` (`mergegate.StageJoinRefusal`), raised first in that stage — before its defaults, zones and gate — on both sides (`TestChainStageJoin_RefusedBothSides`). Failures: `PULSE_CHAIN_NOT_MERGEABLE`, `PULSE_CHAIN_STAGE_JOIN`, `PULSE_CHAIN_EMPTY`. Predict equivalent: `descriptor.ValidateChain`. Surface: `types/chain.go`, `internal/processing/chain.go`, `internal/service/chain.go`, `internal/descriptor/chain.go`, `internal/descriptor/capabilities_chain.go`.

Response shaping: each stage's `return` resolves up front beside its multiplicity (`details.stage`) and is APPLIED by `Pulse.ProcessChain` (`returnshape.ApplyChain`) only after the whole chain and its overlay barrier finished — a stage excluding `data` still feeds the next stage; `Final` aliases the last stage, so it follows that stage's plan. No chain-level block. Each stage also COMPUTES under its own plan (stage 0 inside `Process`, every later stage via the plan `processChain` puts on the `runChainStage` context); a chain overlay reads stage data and crosstab payloads only, so it vetoes no skip.

Dual-slot overlay design: per-stage overlays ride `ChainRequest.Stages[i].Request.Overlays`; whole-chain overlays ride `ChainRequest.Overlays []*ChainOverlaySpec` and produce `ChainResponse.Overlays []*OverlayLayer` after every stage finalises. `ChainOverlaySpec` carries `Ref StageRef` + `Target StageRef`. Whole-chain barrier: `service.applyChainOverlays` runs after the stage loop, dispatching through `processing.ApplyChainOverlays`. Per-stage `Stages[i].Overlays` is left UNTOUCHED. The dedicated error codes `PULSE_OVERLAY_TARGET_UNKNOWN`, `PULSE_OVERLAY_REFERENCE_UNKNOWN`, and `PULSE_OVERLAY_CHAIN_STAGE_SHAPE_DIVERGENT` are pending follow-ups. See `skills/process-chain.md`.

## Pushdown hash join

`Request.Joins []*JoinSpec`. v1 = exactly one inner join per Request (`PULSE_JOIN_TOO_MANY` — one rule, `internal/descriptor.JoinCountRefusal`, applied by runtime `Process` before its crosstab / join dispatch and by predict and the validators; `PULSE_JOIN_KIND_NOT_IMPLEMENTED`); in-memory build (no spill; `PULSE_JOIN_SPILL_DIR` + `PULSE_JOIN_MAX_MEMORY_BYTES` reserved), bounded by `Options.Limits.MaxJoinBuildRows`: `openJoinStream` reads the right side's header-only count (`Service.CountRecords`) after the join-key rule and refuses `PULSE_LIMIT_EXCEEDED` before the build decodes a record, with an in-loop decode-count backstop; predict grades the same count `certain` (`predict-inspect.md`). Both join hosts hand `openJoinStream` a `preflight` hook that runs their defaults, zones, field references and limits pre-flight on the joined schema (`processing.JoinedSchema`) AFTER the join-key rule and the `MaxJoinBuildRows` check and BEFORE the build decodes a record — so an unknown field or a `MaxEstimatedMemory` breach costs no decode on either side (the build side was decoded first until U19 E2-S3). `MaxEstimatedMemory` reads the left header count plus the right one the build check reads (counted once when either limit is set, never under both defaults); the memory model assumes at most one right match per left row for the joined rows a buffered arm holds. `JoinedSchema(left,right,spec)` produces `left.Fields + right.Fields` with optional `spec.As` prefix; non-prefixed collisions → `PULSE_JOIN_FIELD_COLLISION`. Key compatibility (`internal/encoding.JoinKeyTypesCompatible`, inside the one join-key rule `JoinKeysRefusals` — see Predict and the validators): identical types match; categorical of any width match; unsigned-int/float/date numeric family interchangeable; decimal128 rejects cross-type. `decimal128` keys compare on their **exact 128-bit mantissa bytes**, not the `Float64(scale)` echo — otherwise two decimals closer than float64's spacing share a key; safe to special-case because `decimal128` is admitted only against `decimal128`. **Known limit:** a `u64` key above 2^53 rides the `float64` echo the rest of the numeric family uses, so two ids rounding to one float join as equal — unfixed, it needs the whole unsigned-int/float/date family renormalised together (relocated from `skills/join-design.md` for budget).

**Crosstab over a join.** `Request.Crosstab` with its one `JoinSpec` crosstabs the JOINED row stream. `Service.processCrosstab` branches to `processCrosstabWithJoin` before opening the cohort; it builds the identical stream `processWithJoin` consumes (the shared `Service.openJoinStream` — right side materialised + hashed, left wrapped in `HashJoinIterator`), applies defaults / zones / labels against the joined schema, materialises the joined records and runs the buffered `RunCrosstab`. Consequences: axes and cell may name `As`-prefixed right fields; an unmatched left row reaches no cell, margin, auxiliary or Components count; a 1:N right match counts once per joined row everywhere (`CellCounts`, margin counts, `GrandTotalCount`, `IncludedRecords`). Always buffered — `CanFuseCrosstab` declines any `req.Joins` (`"joins force buffered"`, checked before every other rule because the gate is handed the LEFT schema), so `FusedCrosstabState.AssertCanFuse`'s join guard stays an unreachable invariant; the crosstab projection and parallel segment decode are single-cohort optimisations and do not apply. Predict already validates the crosstab against the joined schema (`predictJoinedSchema`), so predict and runtime agree. Before E4-S5 the fused arm returned `PROCESSING_INTERNAL` "gate should have rejected" and the buffered arm silently crosstabbed the bare LEFT cohort (unmatched rows included, a right-side axis field bucketed as null). Gates: `TestCrosstabJoin_HonoursJoinOnBothArms` + `TestCrosstabJoin_LeftOnlyAxesStillJoin` (`internal/service`, against an independent non-crosstab join expectation and hand-computed figures, fused-enabled and -disabled), `TestCrosstabJoin_PredictAndRuntimeAgree` (root), `TestCanFuseCrosstab_JoinsForceBuffered`.

Surface: `types/join.go`, `internal/processing/join.go`, `internal/service/join.go`, `internal/descriptor/join.go`, `internal/descriptor/capabilities_join.go`. See `skills/join-design.md`.

## Crosstab

`Request.Crosstab`, `Response.Crosstab`. Composes existing groupers + aggregators across a row × column axis grid; reshape, margin recompute, normalization layered on top. Multi-grouper axes recursively partitioned. Margins always recomputed from raw rows for correctness — `AGG_MEDIAN` row margin equals the standalone single-axis median, NOT the median of cell medians. Per-aggregator classification at `AggregationType.MarginReducibility` (`summable` / `mean_reducible` / `independent` / `recompute`; `independent` = the operator keeps its own row/column/grand accumulator, so the margin — a union, not a cell sum — is exact after one pass and the fused gate admits it). `shape: matrix` (default) populates `Response.Crosstab.Matrix`; `shape: long` emits tuple rows on `Response.Data` with margin rows tagged `_margin=row|column|grand`. Inherently buffered except `shape=long` + no margins + `normalize=none`.

Normalization layering: `normalize_level` truncates the same axis as `normalize`; `normalize_within` fixes a prefix of the OPPOSITE axis. Both compose.

Auxiliary margin-only aggregations (`margin_aggregations`) are computed by `processing.(*Processor).computeAuxMargins` (`internal/processing/crosstab_margin_agg.go`) alongside the cell aggregator's own three margin blocks, and MUST match what the fused walk accumulates for the same request — dispatch picks the arm on request shape and nothing in `Response` reports which ran. The admission rule is the same one stated under Fused crosstab: a record contributes to an auxiliary only if it contributed to a CELL, so a null cell field and an axis key an `Include` excluded are absent from every auxiliary slot while the cell's own margin loops beside them still count both. The buffered implementation resolves each axis's membership ONCE into pointer sets and then walks each margin slot on its own axis — deliberately NOT the `(rkey, ckey)` cell buckets, which are admitted-by-construction but would fold a record into a ROW auxiliary once per COLUMN it landed in, M times under a `GROUP_SET_PER_ELEMENT` fan-out, where fused folds it once per distinct row key. Each slot's admitted subset is shared across the auxiliaries in it and rides `runCellAggregation`, so the `{n, n_null}` floor is over ADMITTED records and decimal128 dispatch comes for free; a slot admitting nothing carries no figure at all, mirroring the fused path's unconstructed accumulator. An auxiliary naming an unknown operator is refused up front, matching `NewFusedCrosstabState` — AHEAD of the compute plan's `AuxMargins` gate, past which `computeAuxMargins` returns nil and evaluates nothing when the figures are not computed. Partial-depth and cross-axis margins get no auxiliary on either path: those are normalization denominators, and an auxiliary is never a denominator. `TestCrosstab_BufferedAuxMarginMatchesFused` drives one request down both arms.

A crosstab carrying a `JoinSpec` runs over the joined row stream, always buffered — see Pushdown hash join (Crosstab over a join).

Buffered record set automatically projected via `service.applyCrosstabProjection` (extends `processing.NeededFields` to walk `Crosstab.Rows/Columns/Cell` + `req.Labels[].Field` + `AGG_WEIGHTED_MEAN/RATIO` Cell.Params); wide-cohort crosstab cost is `O(|referenced|)` not `O(|schema|)`; forced on regardless of `opts.DisableProjection`. Capability: `Manifest.Crosstab`. Predict gate: `descriptor.validateCrosstab`. See `skills/crosstab-guide.md`.

**Resource limits on the crosstab arms (U19).** `MaxCrosstabCells` bounds the grid, rows × columns of observed composite axis keys, and a breach raises `PULSE_LIMIT_EXCEEDED` (`limits.Check`) with no partial result. The buffered arm (`RunCrosstab`) checks once, right after the two `PartitionByAxis` calls and BEFORE the `rows*cols` per-cell map preallocations. The fused arm checks in `internRowKey` / `internColKey` on the PROSPECTIVE product (`(len(rowKeys)+1)*len(colKeys)` / `len(rowKeys)*(len(colKeys)+1)`) before any dense slice grows; `RunCrosstabFused` installs the processor's limits through `FusedCrosstabState.setLimits`, and a state built without them enforces nothing. Both arms see the same final grid, so the same request trips with the same `{code, limit, configured}` on either; `observed` is the final grid on buffered and the first product past the limit on fused. The joined crosstab is buffered, so it trips in `RunCrosstab` over the joined rows. Predict grades the Cartesian upper bound `EstimateCrosstabCells` (each axis the product of its positions' `EstimateGroups` bounds, clamped by the header record count unless a position fans out) as `possible` only — so the pre-flight never refuses on it. Gates: `TestMaxCrosstabCells_Arms`, `TestLimits_MaxCrosstabCells_BothArms`, `TestLimits_MaxCrosstabCells_JoinedCrosstab`, `TestEstimateCrosstabCells`.

## Fused crosstab

`processing.CanFuseCrosstab` (a thin adapter over the shared rule `crosstabfuse.Decide` in the no-execute leaf `internal/crosstabfuse`), `processing.FusedCrosstabState`, `processing.StreamableGrouper.KeyFor`, `processing.MultiKeyStreamingGrouper.KeysForRow`. In-decode streaming alternative to the buffered Crosstab orchestrator. When the gate accepts, `service.processCrosstab` short-circuits `materializeRecords` + recursive `PartitionByAxis` and drives a single streaming pass that interns row/col composite axis keys on first sight and folds each filter-passing record into the matching cell / row-margin / column-margin / grand-margin / cross-axis-margin online aggregator. Memory drops from `O(filtered records)` to `O(cells + margins)`.

Gate composition (`CanFuseCrosstab`): mergeable + non-recompute scalar cell aggregator (both read through the registry — `IsMergeable` / `AggregatorMarginReducibility` — so an extension cell answers with its DECLARED `Mergeable` / `MarginReducibility`); every row/col grouper is KEYABLE — a built-in per the static `crosstabfuse` keyability table (pinned against the constructed instances by `TestBuiltinGrouperKeyableMatchesRegistry`), an extension per its DECLARED `Streamable || FansOut`; the runtime facts adapter additionally declines a grouper whose factory fails to construct — and keying means one of the two per-record interfaces: `StreamableGrouper.KeyFor` (one bucket per record: CATEGORY/RANGE/ROUNDED/DATE/SET_VALUE — `GROUP_DATE` is admitted here even though `GroupType.Streamable()` is false at the Process layer) or `MultiKeyStreamingGrouper.KeysForRow` (N buckets per record: `GROUP_SET_PER_ELEMENT`); no tests; no features; no two-pass attribute (the built-in set or a `two_pass` extension — the fused walk never runs a `PrePass`, so admitting one values every row against empty stats; `AssertCanFuse` echoes it); no `ATTR_FORMULA`; no `FILTER_EXPRESSION`; no decimal128 cell field on a BUILT-IN cell (an extension cell reads decimals through `DecimalValue` and fuses on its declarations); no extension operator without `FieldInputs` hook; every `margin_aggregations` entry mergeable (extension: declared `Mergeable`) and, for a built-in, non-decimal (an auxiliary rides the same per-record `UpdateRow` walk, so it must be online — declining sends the request to buffered rather than dropping the auxiliary, which would return a margin with the requested figure silently missing). An auxiliary's `MarginReducibility` is deliberately NOT consulted: the classification answers "can this aggregator's margin be derived from its CELLS", a question an auxiliary does not have — it has none, and both paths give it its own row / column / grand accumulator fed record by record, so every auxiliary is `independent` in role whatever its declared class. `GROUP_QUANTILE` implements neither keying interface and is the only grouper that forces buffered.

**Predict reports the decision.** `PredictResult.CrosstabFusable` (`*bool`, nil ⇔ no crosstab) + `CrosstabFusionReasons` (every decline, rule order) come from `descriptor.CrosstabFusion` — the same `crosstabfuse.Decide` over the `ExtensionsSnapshot` + instance feature set — on the defaults-resolved request and the cohort schema; `PredictOptions.DisableCrosstabFusion` (filled from `Options.DisableCrosstabFusion`) answers false with `CrosstabFusionDisabledReason`. `Predict` / `PredictBytes` only, not Compose / ProcessChain validation. A name the feature profile hides answers as never-registered on both arms — the name-keyed `ATTR_FORMULA` / `FILTER_EXPRESSION` bails consult `Facts.Hidden` — so the answer cannot reveal a hidden operator (`TestHiddenOperatorMalformedParity`, `TestDecide_HiddenNameKeyedBails`). **One sanctioned divergence:** a keyable built-in grouper whose factory rejects its params (e.g. `GROUP_DATE` `component:"fortnight"`) — runtime declines (construction fails → buffered → coded error), predict says fusable from the static table; the request errors on either answer. Gates: `TestStreamability_CrosstabFusionPredictMatchesRuntime` (rule parity, both instances), `TestPredict_CrosstabFusableMatchesRuntime` (end to end through the facade, incl. the disable knob).

`Request.Overlays` is explicitly NOT an exclusion. Overlays decorate a finalised response and consume no records, so `RunCrosstabFused` folds them after `state.Finalize()` through the same `processing.applyOverlaysToResponse` hook the buffered exit calls — cells, `Components`, `Overlays` and `Warnings` are byte-identical across arms. `types.OverlayStreamability` is unchanged (every kind still `false`): a post-`Finalize` fold is not an in-pass computation. The surviving reason an overlay-carrying crosstab may still buffer is the CELL-AGGREGATOR arm — `AGG_WELFORD` is non-mergeable, so `OVERLAY_PAIRWISE_WELCH_T` / `OVERLAY_PAIRWISE_TWO_MEANS_Z` (which read its `{n, mean, variance}` triple off `CellComponents`) stay buffered; `TestCrosstabWelfordCell_StaysBufferedWithCorrectOverlays` pins it. `OVERLAY_PAIRWISE_PROP_Z` and `OVERLAY_PAIRWISE_WEIGHTED_TWO_MEANS_Z` (which reads the mergeable cell's `{weighted_mean, m2_weighted, sum_weights, sum_weights_sq}` moments) over an `AGG_WEIGHTED_MEAN` cell fuse.

Multi-key axis routing: `fusedAxisKeyer.derive` returns the cartesian product of each position's key set plus deduped per-depth prefix sets, so one record updates every accumulator the buffered path would touch, exactly once per distinct key at that depth. Fan-out is legal at any axis position, on either or both axes, several positions per axis. Consequence (deliberate, mirrors buffered): margins are NON-ADDITIVE under fan-out — a record selecting 3 labels counts 3× across row margins but once in the grand margin, so row margins do not sum to the grand total.

`normalize_level` denominators gate on PREFIX depth, not full-axis resolution: the buffered denominator is `PartitionByAxis(spec.Rows[:level+1], filtered)`, which never looks past `level`, so a record whose DEEPER axis positions are null still feeds it. Fused now matches. Releases before this alignment returned a different `normalize_level` denominator on the fused arm whenever a nullable grouper sat ahead of the level — a numbers-changing fix, not a no-op.

Auxiliary margin accumulation (`FusedCrosstabState.rowMarginAux` / `colMarginAux` / `grandMarginAux`, one `auxMarginAccumulator` per declared auxiliary per occupied slot, instance built on first admission) observes a DIFFERENT record admission from the cell's own margins beside it, and that is the point of the slot: a record contributes to an auxiliary only if it contributed to a CELL. Three exclusions follow — a null cell field, an unresolved row key (including one a grouper `Include` excluded, which surfaces as `ErrGrouperKeyNull`), and an unresolved column key. The cell aggregator's own margins are untouched and still count every filter-passing record with a non-null axis key on that axis: measured, a `rows=[brand]` crosstab returns byte-identical column margins with a two-brand `Include` and with none at all. Reusing that for an auxiliary would make the figure cohort-wide and metric-agnostic. Getting it wrong is SILENT — every number still renders, the base is merely wrong. Slots are allocated only for the margins the spec asks for, and nothing at all when `margin_aggregations` is absent — or when the compute plan drops the figures (`FusedCrosstabState.setCompute` forgets the auxiliaries before `Update`; construction already resolved them against the registry). The figures are accumulated and held; they surface on `Response.Components` (`crosstab.margin_aggregations`, response-components.md) unless a `return` drops them.

Axis-key nullity is per-axis: a record with non-null row key + null col key still updates the row margin and the grand margin. Cells only land at intersections where both axes resolved. Margins recompute from raw rows so byte-for-byte equivalent to buffered RunCrosstab. Map-valued cell aggregators paired with `normalize != none` are rejected (`PULSE_CROSSTAB_NORMALIZE_MAP_VALUED`). Disable via internal `disableCrosstabFusion` toggle.

Perf: synth 200-field × 100K-row bench ~0.51 × buffered (~47% faster); canonical 1M-row real-cohort bench 2.57s vs buffered crosstab baseline 3.82s (~32% faster). **Quote peak heap, never `B/op`.** The combined fan-out + overlay bench (`BenchmarkCrosstabSetFanoutOverlay`) measures `peak-heap-MB` 8.8× / 18.6× / 20.8× better on fused at 25k / 100k / 400k rows, while `B/op` moves only ~30% — `B/op` is cumulative bytes allocated and cannot see retention, so quoting it alone understates the win by ~20×. `allocs/op` is HIGHER on fused (the fan-out keyer builds a key tuple per fanned key); expected, not a regression. See `skills/crosstab-guide.md` (Fused mergeable path) + `skills/grouper-design.md` (Fused crosstab eligibility).

## Overlays

`Request.Overlays []*OverlaySpec`, `Response.Overlays []*OverlayLayer`. Additive post-result decorations attached to an already-computed base result. ## Multiplicity

`multiplicity {method, family, alpha}` (`types.Multiplicity`; slots on `Request`, `Test`, `OverlaySpec`, `ComposeOverlaySpec`, `ComposedRequest`; engine default `Options.DefaultMultiplicity`) corrects the p-values of tests, post-tests and inferential overlays. Methods `none|bonferroni|holm|bh|by` live in the leaf `internal/processing/multiplicity` (pure `[]float64 → []float64`, R `p.adjust` parity, BY to 1e-13, NaN excluded from `m`, ties by original position, capped at 1). Families `layer|row|column|request|compose`. ONE resolver, `ResolveMultiplicity` / `ResolveComposeMultiplicity` / `ResolveFacetMultiplicity` (`internal/descriptor/multiplicity_resolve.go`, schema-free), serves runtime AND predict, so refusals are identical (`PULSE_MULTIPLICITY_INVALID` / `_CONFLICT`). Precedence per key: slot → request → `ComposedRequest` → `Options` → none; an inherited family a surface does not offer takes the surface default, only an explicit one is refused; `row` / `column` need a MATRIX payload kind, `compose` exists only inside Compose, `request` is refused on a Compose-host overlay and `request` / `compose` on a facet overlay; an explicit block on a descriptive overlay is accepted and inert; an explicit non-`none` block on `TEST_TUKEY_HSD` is refused, an inherited one skipped.

**Wire outputs (relocated from CLAUDE.md "Output Format Contract" at U18 E1-S1).** An absent block is byte-identical and `format_version` stays `"1.1"`. The correction adds BESIDE the raw p, which never moves: `TestResult` / `OverlaySummary` gain `p_adjusted` + `significant_adjusted`, `OverlayPayload` gains the matching `p_adjusted` / `significant_adjusted` matrices, and each corrected surface echoes `multiplicity {method, family, alpha, m}` (`types.AppliedMultiplicity`). A NaN p is excluded from `m` and its `p_adjusted` is `null`.

Fold sites (raw p never written; every output additive `omitempty`):

- **Process** — `foldRequestMultiplicity` (`internal/service/multiplicity_fold.go`) after `processDispatch` returns, so every arm (serial buffered / streaming, fused and buffered crosstab, join, shard, parallel decode, `ProcessStream`) corrects in one place. Overlay half: `multiplicity_overlay.go`, the `overlayPSites` table (one entry per `Inferential` kind, `TestOverlayPSites_CoverEveryInferentialKind`).
- **Compose** — `foldComposeMultiplicity`, run by BOTH `compose` and `composeParallel` after the slots and the Compose-host overlays finish; collection is slot-index then spec order, never completion order, so serial == parallel byte for byte. Non-compose families stay per slot (scope `requests[i]/`), `compose` pools every slot and Compose-host layer. `--stream` emits slot rows only (no corrections); a failed slot errors the batch before the barrier, so a `compose` family never folds over partial members.
- **ProcessChain** — each stage folds its own plan (stage 0 in `Service.process`, later stages in `runChainStage`); one `request` family per stage, never spanning stages; the whole-chain `ChainOverlaySpec` has no slot. The v1 stage gate refuses tests and crosstab, so no gate-passing stage reaches a p-site yet.
- **Facet** — `applyFacetOverlays` folds each spec's layers alone under `ResolveFacetMultiplicity`.
- **Excluded members still fold** — a `return` that excludes overlays skips every layer EXCEPT a family member (`multiplicityVetoes`; Compose-host layers whole under any member), so `m` and every kept `p_adjusted` match the full run (`TestReturnSkipsOverlays_MultiplicityVeto`). Tests / post-tests reuse it per entry (E3-S2, `TestReturnSkipsTests_MultiplicityVeto`); regressions are outside the pool and skip whole.

`row` / `column` are coordinate-based on the layer's own MATRIX (pairwise rows are the compared groups); a panel cell's vector elements each join their cell's family; the layer echo carries `m_per`. Extension `TEST_*` operators join like built-ins. Feature `capability:multiplicity`. Skill: `skills/multiplicity-correction.md`; update-demand row: Multiplicity.

## Time zones

Long form of CLAUDE.md's "Date-family field types" zone clause. Storage stays UTC epoch; a zone is a request-time configuration that is resolved, validated, echoed and — on a `datetime` field of a zone-aware operator — applied: the instant is read on its LOCAL calendar day. It is refused wherever it would otherwise be silently ignored (a derived field).

**One home for date math.** Epoch-day, calendar and zone math lives in `internal/temporal` (a leaf over stdlib + `errors`; it must not import `encoding`). The public `encoding` date helpers (`ParseDate`, `ParseDateTime`, `FormatDateTime`, `DateTimeToDay`, `SecondsPerDay`) keep their frozen signatures and forward into it. `internal/processing/date_field.go` remains the OPERATOR-boundary adapter: a `datetime` (epoch seconds) is day-truncated exactly once there — toward the past, never rounding (`1969-12-31T23:59:59Z` is UTC day −1, not day 0) — by `DateTimeToDay` when no zone applies, or by `temporal.LocalDay` in the slot's resolved non-UTC zone (`resolveDateField` decides once at construction, `dateField.epochDay` per record; a nil zone is exactly the zone-free path, so UTC / absent costs nothing) — and everything downstream speaks epoch days. `GROUP_DATE`, `GROUP_DATE_RANGES` and `FILTER_DATE_RANGES` read the zone there, so `GROUP_DATE` keys and `period_start` / `period_end` are local calendar labels with no format change and range literals are local days. `TestNoZoneMathOutsideTemporal` (root `zone_math_gate_test.go`, `go/ast`) fails on the int literal `86400`, any `SecondsPerDay` reference, `time.LoadLocation` / `LoadLocationFromTZData` / `FixedZone` / `Local`, a dot-import of `time`, or a `time/tzdata` import anywhere outside `internal/temporal`; the sole allow-list entry is the `encoding.SecondsPerDay` re-export declaration. `.In(` is deliberately not banned — with every means of obtaining a non-UTC location banned, only `time.UTC` can reach it.

**`Zone`.** `temporal.LoadZone(name)` accepts exactly `UTC` (the `temporal.UTC` sentinel) or an IANA `Area/Location` name (contains `/`, each segment opens with an ASCII upper-case letter) with an exact, case-sensitive entry in Pulse's own embedded `internal/temporal/zoneinfo.zip` (release `temporal.TZDataVersion`, hash-pinned by `TestTZDataVersion_MatchesEmbeddedZip`; refresh with `make tzdata`). `$ZONEINFO`, host zoneinfo and `time/tzdata` are never consulted, so acceptance and offsets are host-independent (`TestLoadZone_IgnoresHostZoneinfo`). `EST`, `EST5EDT`, `GMT`, `Local`, `""` and offset strings (`+05:00`) are `PULSE_TIMEZONE_UNKNOWN` with the name under `details.tz`. Offset lookup is allocation-free, amortized O(1): a transition table built from `Time.ZoneBounds` over 1900–2100, binary search plus a last-span cache, `time.In` fallback outside the window. `LocalDay`, `LocalMidnightUTC` and `LocalParts` are the primitives zone-aware operators consume. `(*Zone).IsUTC()` is true for the sentinel and every fixed-zero-offset zone (`Etc/UTC`, `Etc/GMT`, `Etc/Zulu`, `Etc/UCT`, `Etc/GMT-0`). A per-instance `temporal.Cache` (built in `pulse.New`) memoises loads so a request does not rebuild a transition table.

**Wire.** `Request.TimeZone` / `FacetRequest.TimeZone` (`time_zone`) and per-slot `TimeZone` (`tz`) on `types.Group`, `Filterer`, `Attribute`, `Feature` — all additive `omitempty`, `format_version` stays `"1.1"`. `ComposedRequest` / `ChainRequest` carry no zone of their own (each inner `Request` does); `SampleRequest` has none. `pulse.Options.DefaultTimeZone` (`""` = UTC) is validated at `pulse.New` (unknown → `PULSE_TIMEZONE_UNKNOWN`) and a non-UTC default is ACCEPTED there (it applies wherever it resolves onto a `datetime` slot). No env var and no CLI default-zone flag (decided in U14); `skills/time-zones.md` is the agent-facing form.

**Capability.** `internal/descriptor/capabilities_zone.go` is the single declaration table (`ZoneCapabilityOf` / `IsZoneCapable`), projected onto the manifest `zone` key of an operator entry (`descriptor.Operator.Zone`) or an overlay kind entry (`descriptor.OverlayCapability.Zone`): `capable` on `GROUP_DATE`, `GROUP_DATE_RANGES`, `FILTER_DATE_RANGES`, `ATTR_DATE_PART`, `FEAT_DATE_FEATURES`; `following` on `OVERLAY_YOY` (no `tz` slot — it inherits its host grouper's zone, because a disagreeing overlay zone would be meaningless); absent everywhere else. Extension operators are never zone-capable. Windows are excluded (no time-based window exists).

**Resolution.** `internal/descriptor/zone_resolve.go` — `ResolveZones(req, schema, defaultZone, load)` / `ResolveFacetZones` — is pure, never mutates the request, and is the ONE pass both runtime and predict call, so they accept and refuse identically. Precedence per zone-capable slot: slot `tz` → request `time_zone` → `Options.DefaultTimeZone` → `UTC`. Refusal order:

1. unknown `time_zone` / default zone → `PULSE_TIMEZONE_UNKNOWN {tz}` — even with no zone-capable slot;
2. explicit `tz` on a non-capable operator (built-in or extension) → `PROCESSING_CONFIG {slot, operator, tz}`;
3. explicit `tz` on a field present in the schema that is not `datetime` (a calendar `date`, or the epoch-day count `GROUP_DATE` tolerates) — even `"UTC"` → `PROCESSING_CONFIG {slot, operator, tz, field, field_type}` (`TestDateFieldRejectsTZ`);
4. unknown slot `tz` → `PULSE_TIMEZONE_UNKNOWN {slot, tz}`;
5. a non-UTC-equivalent zone resolving onto a field ABSENT from the schema (a derived or chain-synthesised column; a JOINED column is in the joined schema and resolves by its own type) → `PROCESSING_CONFIG {slot, operator, tz}`, message "… a zone cannot be applied to a derived field …" — the operators read an absent field as epoch DAYS, so the zone would be silently ignored (`TestTimeZone_DerivedFieldRefusedEveryMode`). Onto a `datetime` schema field it is ACCEPTED and applied (`TestTimeZone_LocalDayEveryMode`).

A slot with an EMPTY operator `Type` (defaults disabled, or no default rule fits) is skipped — it is a type error, reported by operator construction (`PROCESSING_CONFIG "unknown group type: "` and siblings) with or without a `tz`, never as a zone-capability refusal. A NIL schema (only a validator with no cohort schema in reach) skips rules 3 and 5, so a schema-less check never refuses what the schema-holding runtime accepts.

An INHERITED zone on a non-`datetime` field is not applied and echoes `tz: null`. `ATTR_DATE_PART` / `FEAT_DATE_FEATURES` accept `date` and `datetime`: over a `datetime` they read the resolved zone's wall clock (`temporal.LocalParts`; part / column `hour` is `datetime`-only, and FEAT `dow` stays Sunday = 0, never following `week_start`), over a `date` an explicit `tz` is refused (rule 3) and an inherited one is never applied. Their field rules are read once, by `internal/datepart` (ATTR) and the predict feature check, so predict and runtime refuse alike. A UTC-equivalent zone is never refused and output is byte-identical to no zone (`TestUTCZoneIsIdentity`); the echo keeps the caller's spelling. Slot paths: `filterers[i]`, `features[i]`, `attributes[i]`, `groups[i]`, `crosstab.rows[i]`, `crosstab.columns[i]`, walked in that order.

**Call sites (one per mode).** `Service.SetTimeZones` is installed at `pulse.New`; the service resolves once per Request after `applyDefaults` in the Process main arm, `processCrosstab`, `processWithJoin` (against the joined schema), `ProcessChain` (every stage, BEFORE the chain gate — stage 0 explicitly against the cohort schema, unless it carries a join, which resolves inside Process), and `FacetSchema`. `ProcessStream`, `Compose` and `ComposeParallel` inherit through Process. **Applying the zone.** The operator factories see only `(slot, schema)`, so each mode hands its arm `descx.ZonedRequest(req, zones, loader)` (`ZonedFacetRequest` for facet; `Service.zoned`) right after its last caller-visible mutation (auto labels): a shallow copy whose slots that INHERITED a non-UTC zone are copies carrying it in `tz` — or `req` itself when there is none (zone-free and UTC requests run the unchanged object). An explicit slot `tz` is already on the slot; an inherited zone on a `date` field resolved to null and is never written. Every arm built from it — buffered, streaming, fused crosstab and its gate probe, parallel decode, shard reduce, chain stages ≥1 — sees the zone with no further plumbing; the factory loads the name through a process-wide `temporal.Cache` in `internal/processing` (zones are immutable and built from the one embedded tz database). The caller's request is never written, so the request echo, `Request.Hash` / `ComposedRequest.Hash` and the Compose echo show it as written (`TestTimeZone_ZoneWriteLeavesCallerRequestPristine`). **Location:** a Compose refusal keeps its message prefix `request N:` and adds `details.request` (0-based slot) on the serial and the `FailFast` parallel path (`FailFast=false` still aggregates into `SERVICE_INTERNAL`); a chain refusal adds `details.stage` (0-based). Both are copies of the resolver's coded error, so the code survives `errors.As` and the CLI envelope (`TestTimeZone_RefusalCarriesLocation`, `TestAPI_TimeZoneRefusalKeepsItsCode`). The service marks a **located refusal** where it is raised (`locatedRefusal` in `internal/service/located.go`, unwrapping to the coded error; `locate` copies it through `descx.RefusalAt`) — the zone refusals and the join-count refusal — so only those gain a location; the validators call `RefusalAt` at the same points, so the location matches. `FilterToFileWithRequest` refuses any filterer `tz` (`PROCESSING_CONFIG {operator, tz}`).

**Predict and the validators.** Predict resolves on the defaults-resolved clone (`PredictOptions.DefaultTimeZone` / `ZoneLoader`, which the facade fills from the service) and echoes `PredictResult.TimeZones` — `"time_zones": [{slot, operator, field_type (omitempty), tz (string|null), source}]`, `source` ∈ `slot|request|options|default` (`descriptor.ZoneSource*`), never nil, zone-capable slots only (`OVERLAY_YOY` not listed); a refusal is a predict error (`Valid=false`). For a single `JoinSpec` predict reads the right cohort's header + schema through `PredictOptions.SchemaLoader` (the facade passes the runtime's own `Service.Open`) and validates the whole request against `internal/encoding.JoinedSchema` — the one join-schema rule `processing.JoinedSchema` delegates to — so a joined `date` field echoes `tz: null`, a joined `datetime` echoes its zone and a name in neither schema refuses exactly as runtime does (`TestTimeZone_JoinPredictMatchesRuntime`). `PredictOptions.DisableDefaults` (facade: `Options.DisableDefaults`) validates the request as written; `DefaultsApplied` then lists what WOULD apply. Predict reports any top-level slot still without a `Type` with the runtime's own `PROCESSING_CONFIG` message (`validateOperatorTypes`; `TestTimeZone_DisableDefaultsSameErrorBothSides`). `ValidateComposeWithOptions`, `ValidateChainWithOptions` and `ValidateFacetWithOptions` run the same pass (defaults on a clone unless disabled, then `ResolveZones` / `ResolveFacetZones`) and record each refusal with the runtime's code, message and details, location included; Compose reads each slot's schema through `SchemaLoader` and resolves schema-less without one (`TestTimeZone_ValidatorsMatchRuntime`). `ValidateChain*` also runs the chain gate, the field checks and the next stage's synthesised schema (whose `<TYPE>_<field>` labels embed a defaulted Type) on each stage AFTER the shared `ResolveDefaults` pass against its input schema — the cohort's for stage 0, even when it joins — unless `DisableDefaults`, exactly as the runtime's `applyDefaults` does; the echoed request stays as written (`TestChainDefaults_ValidatorMatchesRuntime`). The gate is the shared `internal/mergegate.ChainRefusal` on both sides (see ProcessChain), so code, message and details `{stage_index, stage_name}` match. **Join count.** `internal/descriptor.JoinCountRefusal` is the one v1 rule — more than one `JoinSpec` → `PULSE_JOIN_TOO_MANY "v1 supports exactly one JoinSpec per Request" {count}`. Runtime `Process` applies it first (after the cohort check, before the crosstab and join dispatch, so a crosstab is covered too); predict right after the header + schema read, before the joined schema and defaults; the Compose validator per slot before that slot's zones; the chain validator on stage 0 after the gate and before its joined-schema zones (a joined stage 0 resolves zones inside Process). It is a located refusal: inside Compose it gains `details.request` (serial and `FailFast` parallel), on chain stage 0 `details.stage`; predict and a single `Process` add none (`TestJoinTooMany_PredictAndValidatorsMatchRuntime`, `TestJoinTooMany_LocatedInsideComposeAndChain`). Chain stages ≥1 never reach it: their `Joins` is `PULSE_CHAIN_STAGE_JOIN` first. **Join keys.** `internal/encoding.JoinKeysRefusals(left, right, spec)` is the one kind / OnPair rule, in runtime order: no OnPair (`PULSE_JOIN_KEYS_EMPTY`), a kind other than inner, then per pair a blank side, an unknown left then right key (`PULSE_JOIN_FIELD_UNKNOWN {field, index}`), incompatible key types (`PULSE_JOIN_TYPE_MISMATCH`, the set-key sentence `JoinKeySetRejection`). The service applies it as soon as both cohorts are open — before the right side is decoded — as a located refusal, and `NewHashJoinIterator` re-applies it; predict reports every entry once `SchemaLoader` reads the right schema, `ValidateJoin` the same; the Compose slot validator and the chain stage-0 validator report it located and stop there (it precedes zones and field references). **Field references.** `internal/descriptor.FieldRefRefusals(req, schema, snap)` is the one unknown-name rule. Every execution mode calls `Service.checkFieldRefs` (its first entry, `FieldRefRefusal`) right after `resolveZones`, against the schema the request executes over — the cohort's in `Process` / `processCrosstab` (both crosstab arms, so fused and buffered agree), the joined schema in `processWithJoin` / `processCrosstabWithJoin`, the synthesised stage schema on chain stages ≥1 (after the gate); ProcessStream, Compose and chain stage 0 reach it through `Process`; `FacetSchema` applies its filterer half (`FacetFieldRefRefusals`, against the cohort schema) right after `resolveFacetZones`, so a FACET-host overlay request is covered, and `ValidateFacet` reports every entry at that point (`TestFieldRefs_FacetFiltererRefusedLikeValidator`). `FilterToFileWithRequest` with structured `Filterers` applies the filterer half too (`Service.FilterToFileFilterers`, against the cohort schema — the canonical one for an archive — before the translated expression compiles; `TestFilterToFile_FilterersRefusedLikeProcess`). It is a located refusal (`details.request` / `details.stage`). Predict reports every entry after zones; `validateComposeSlots` after the slot's zones on the defaulted slot; `ValidateChain*` after the gate, against the joined schema for a joined stage 0 (defaults re-applied against it, as `processWithJoin` does) — none once an earlier located refusal on that slot / stage fired. The walk is PIPELINE order: features see the schema and earlier features' outputs (`Field`, `FEAT_TARGET_ENCODE` `params.target`, `FEAT_TRAIN_TEST_SPLIT` `params.stratify`); filterers see features but NOT attribute labels (attributes run after filters); each attribute sees earlier attributes' labels (`ATTR_FORMULA` may omit `Field`; `ATTR_REG_*` judge `Target` / `Predictors`); tier-1 tests, regressions, groups, aggregations and crosstab rows / columns / cell / `margin_aggregations` see every attribute label; windows (order_by, partition_by, and `Field` only on a value-bearing operator), sort and post-tests see the OUTPUT row columns — group fields + aggregation labels (`<TYPE>_<field>` with a defaulted Type), or the record columns when there are neither, plus earlier windows' labels (sort / post-tests see all) — a window `order_by` key that is a schema field is also judged by `IsOrderableType` (every type but `set_*`, the types the window comparator orders by value; `PULSE_WINDOW_INVALID "window[i]: order_by field F is not orderable (type T)"` on both sides, `TestWindowOrderBy_OrderabilityPredictMatchesRuntime`); a crosstab's post-tests run over cell rows and are not judged. An extension feature (outputs unnameable without executing) opens the set for everything after it. **Shadowing.** A derived column whose name is already available at its producer's point — an attribute label (or default label) equal to a schema field, feature output or earlier attribute label; a feature output equal to a schema field or earlier output; a window label equal to an output-row column or earlier window label — is refused `SERVICE_VALIDATION` `"attribute label <l> shadows an existing field"` `{label, attribute}` / `"feature <TYPE> output <l> shadows an existing field"` `{label, feature}` / `"window[i] label <l> shadows an existing column"` `{window_index, label, type}`. Writing it overwrote the column in place, and the arms disagreed (buffered `applyAttributes` kept a nullable field's null mark through `injectValue`, the streaming orchestrator cleared it with `Set`); no documented request relied on the overwrite, so both sides refuse (`TestLabelShadow_RefusedOnEverySide`). It supersedes predict's former warning-level window label collision. A name only an extension feature might produce is not judged. Aggregation labels are judged too (Output namespace, below). **Names inside params** are judged at the operator's own pipeline point: the built-in aggregation params (`aggParamFieldKeys` — `AGG_WEIGHTED_MEAN` `weight_field`, `AGG_RATIO` `numerator_field` / `denominator_field`, `AGG_DISTINCT_SUM` `distinct_by`, on every aggregation slot including crosstab cell and `margin_aggregations`; message `"<slot> <TYPE>: params.<key> references unknown field <f>"`, details `{field, param, aggregation|role}`), the post-test output-column params (`TEST_ANOVA_F` / `TEST_ANOVA_WELCH` `n_col` / `variance_col`, an explicit `TEST_TUKEY_HSD` `n_column`), and an extension's own declaration — `ExtensionsSnapshot.FieldInputs` carries every registration's `FieldInputs` hook (the projection hook, keyed `<category>|<name>`; row tests only), the service passes its snapshot to the rule so both sides call the same hook with the slot's `Params` (`nil` for a filterer) and refuse `"<category> <NAME>: FieldInputs references unknown field <f>"` with `field_inputs: true`; a hook that panics is undeclared (nothing judged), an extension without one is not judged (`TestFieldRefs_ParamFieldsRefusedLikePredict`, `TestFieldRefs_ExtensionFieldInputsJudged`, `TestFieldRefRefusals_ParamsAndFieldInputs`). Empty names are refused where the slot requires one (aggregation, group, attribute but `ATTR_FORMULA`, regression predictor, every built-in filterer but `FILTER_EXPRESSION` — an extension filterer's `Field` is its own business), even after an extension feature opened the set, with the slot's unknown-field message naming `""` (`TestFieldRefs_EmptyFilterFieldRefusedLikePredict`). Gates: `TestFieldRefs_*`, `TestJoinKeys_UnknownKeyRefusedLikeRuntime`, `TestFieldRefRefusals_*`, `TestJoinKeysRefusals_*`.

**Output namespace.** An aggregation label (explicit, or `<TYPE>_<field>` with a defaulted Type) equal to a group field or to an earlier aggregation's label is refused the same way — `"aggregation[i] label <l> collides with group[j] field <l>"` `{label, aggregation_index, aggregation, group_index, group}` / `"aggregation[i] label <l> collides with aggregation[j] label <l>"` `{label, aggregation_index, aggregation, other_aggregation_index, other_aggregation}` — because an output row holds one value per name: the group key is written after the aggregations (the aggregation vanished) and a duplicate label kept only the last figure, on every arm (`TestOutputNamespace_CollisionRefusedOnEverySide`, `TestOutputNamespace_DistinctNamesAccepted`, located inside Compose and on every chain stage, the final one included — `ChainOutputSchema`'s own `PROCESSING_CONFIG` collision only ever saw a non-final stage and is now unreachable behind it). A label equal to the field it reads or to an attribute label is not a collision (neither is an output column); a crosstab's top-level labels are not judged (its output is the cell grid, whose cell / `margin_aggregations` labels `MarginAggregationFaults` already keeps distinct). Tests and regressions emit slices, not row columns, so their labels cannot collide.

## Date-family field types

**Date-family field types.** `GROUP_DATE`, `GROUP_DATE_RANGES` and `FILTER_DATE_RANGES` accept BOTH temporal types — `date` (epoch days, `int32`) and `datetime` (epoch seconds, `int64`). Past the operator boundary (`internal/processing/date_field.go`) everything speaks epoch DAYS: a `datetime` is day-truncated once there, toward the past, naive UTC (`1969-12-31T23:59:59Z` is day −1). **All epoch-day / calendar / zone math lives in `internal/temporal`** (`encoding` forwards); `TestNoZoneMathOutsideTemporal` bans `86400` / zone loading elsewhere. `GROUP_DATE_RANGES` / `FILTER_DATE_RANGES` reject any other field type with `PROCESSING_CONFIG`; `GROUP_DATE` stays non-validating and reads a non-temporal `Field` as an epoch-day count — except `component: hour`, the one sub-day bucket, which reads the local epoch HOUR (`temporal.LocalHour`; key `YYYY-MM-DDTHH`, the skipped DST hour has no bucket and the repeated one is ONE) and refuses any field that is not a `datetime` schema field. `week_start` (`week` only, default `monday` = ISO `YYYY-Www`) keys any other start by the week's first local date. Both params are read once, by `internal/dategroup`, for the factory and predict alike. `ATTR_DATE_PART` / `FEAT_DATE_FEATURES` also take both types (see Time zones). **Zones:** request `time_zone` and slot `tz` (manifest `zone: capable` operators) resolve slot → request → `Options.DefaultTimeZone` → UTC; a `datetime` is read on its local day in that zone, and non-UTC on a derived field is `PROCESSING_CONFIG`. See `execution-modes.md` (Time zones).

- **Crosstab** (`Request.Crosstab`, `Response.Crosstab`) — composed row×column grid; margins recompute from raw rows; `normalize_level` / `normalize_within` compose. `AggregationType.MarginReducibility` classifies each cell aggregator into FOUR classes — `summable` / `mean_reducible` / `independent` / `recompute` — surfaced as `crosstab.*_aggregators` in the manifest. `independent` (`AGG_DISTINCT_COUNT`, `AGG_DISTINCT_SUM`, `AGG_MODE_COUNT`) means the operator keeps its OWN row/column/grand accumulator: the margin is the union across cells (for `AGG_MODE_COUNT`, the modal count of the margin's own rows), never their sum, and is exact after one pass — so the fused gate ADMITS it. Re-labelling those `recompute` because "a distinct count is not a sum of cells" changes no number and silently costs fusion. `CrosstabSpec.MarginAggregations` (`margin_aggregations`, additive + `omitempty`) carries AUXILIARY aggregations evaluated into the row/column/grand margin accumulators ONLY, never into a cell — `Cell` is a single `*Aggregation`, so this is how a second figure (canonically an unweighted respondent base beside a weighted metric) rides one request instead of a whole second scan. Effective labels (`Label`, else `TYPE_field`) must be unique across the slot AND distinct from `CellLabel`, because margin components are keyed by label. Structural detection is SHARED — `types.CrosstabSpec.MarginAggregationFaults` is called by both `processing.validateCrosstabSpec` and `descriptor.validateCrosstab`, so predict and execution cannot drift on WHICH specs they refuse; only the coded rendering differs. An auxiliary observes the SAME record admission as the cell aggregator (a record contributes only if it contributed to a cell) — deliberately unlike the cell's own margins, and deliberately not configurable. BOTH execution arms implement it and they must AGREE: dispatch picks fused or buffered on request SHAPE and nothing in `Response` reports which ran, so an auxiliary present on one arm only moves a sample-size figure for reasons a caller cannot see or ask about — and `AGG_WELFORD` / `AGG_MEDIAN` force buffered by construction, which is the arm two BERA stat-test families land on. The buffered half is `processing.(*Processor).computeAuxMargins` (`internal/processing/crosstab_margin_agg.go`): it resolves each axis's membership ONCE into pointer sets and narrows each margin slot's own routed bucket, deliberately NOT walking the `(rkey, ckey)` cell buckets — those are admitted by construction but would fold a record into a ROW auxiliary once per COLUMN it landed in, M times under a `GROUP_SET_PER_ELEMENT` fan-out, which is precisely the axis this slot exists to serve and the one shape where the two arms could silently disagree. A slot admitting no record carries no figure on either arm, never a fabricated 0. `TestCrosstab_BufferedAuxMarginMatchesFused` drives one request down both. The figures surface on `Response.Components.Crosstab` as `row_margin_aggregations` / `column_margin_aggregations` / `grand_total_aggregations` — see the `Response.Components` section above for the shape, the presence semantics and the display-flag gate, and `TestCrosstabAuxMargin_WireFiguresAgreeAcrossPaths` for the cross-arm byte comparison at that surface. A row weight weights cells, every margin and every auxiliary off each slot's own resolved weight on both arms (counts stay raw; a `weight: null` auxiliary is the unweighted base): `.claude/reference/weighting.md` (Crosstab). See `skills/crosstab-guide.md`.
- **Fused crosstab** (`processing.CanFuseCrosstab`, `processing.StreamableGrouper.KeyFor`, `processing.MultiKeyStreamingGrouper.KeysForRow`) — in-decode streaming alternative; ~30–47% faster on benches, and `peak-heap-MB` 8.8× / 18.6× / 20.8× better than buffered at 25k / 100k / 400k rows. **Quote peak heap, never `B/op`** — `B/op` is cumulative bytes allocated, cannot see retention, and understates the win by ~20×; fused `allocs/op` is deliberately HIGHER. Axis groupers may implement EITHER per-record keying interface, so `GROUP_SET_PER_ELEMENT` fan-out axes fuse at any position, on either or both axes; `GROUP_QUANTILE` implements neither and is the only grouper forcing buffered. `Request.Overlays` does NOT force buffered: `RunCrosstabFused` folds layers after `state.Finalize()` through the same `applyOverlaysToResponse` hook the buffered exit calls, byte-identical across arms, and `types.OverlayStreamability` stays all-`false` because a post-`Finalize` fold is not an in-pass computation. The surviving reason an overlay-carrying crosstab may still buffer is the cell-aggregator arm — `AGG_WELFORD` is non-mergeable, so `OVERLAY_PAIRWISE_WELCH_T` / `OVERLAY_PAIRWISE_TWO_MEANS_Z` stay buffered while `OVERLAY_PAIRWISE_PROP_Z` / `OVERLAY_PAIRWISE_WEIGHTED_TWO_MEANS_Z` over a mergeable `AGG_WEIGHTED_MEAN` cell fuse. Fan-out margins are non-additive on BOTH arms (a 3-label record counts 3× across row margins, once in the grand margin) — deliberate. `CrosstabSpec.MarginAggregations` gets the SAME two gate checks the cell gets — mergeable (an auxiliary rides the same per-record `UpdateRow` walk, so it must be online) and non-decimal — and declining sends the request to buffered rather than DROPPING the auxiliary, which would return a margin with the requested figure silently missing. Its `MarginReducibility` is deliberately NOT consulted: that classification answers "can this aggregator's margin be derived from its CELLS", which an auxiliary does not have — both paths give it its own row/column/grand accumulator fed record by record, so every auxiliary is `independent` in role whatever its declared class, and requiring a class would decline fusion for a request the fused walk computes exactly. The fused walk accumulates auxiliaries in `rowMarginAux` / `colMarginAux` / `grandMarginAux` beside the cell's own margin slices, under the admission rule above — a record reaches an auxiliary ONLY if it reached a cell, so a null cell field and an `Include`-excluded axis key are both absent from it while the cell's own margins still count them. Getting that wrong is SILENT: every number still renders, the base is merely cohort-wide instead of metric-scoped. Slots allocate only for the margins the spec asks for, and nothing at all when the slot is absent. A weight never moves the fusion answer, and every fused accumulator class is built off the stamped (weighted) spec — fused equals buffered weighted too (`weighting.md` "Crosstab"). See `skills/crosstab-guide.md` (Fused mergeable path) + `skills/grouper-design.md` + `.claude/reference/execution-modes.md`.
- **Facet endpoints** — simple (`pulse.Facet`) + rich (`pulse.FacetSchema`); four FACET-host overlay kinds (`OVERLAY_INDEX_VS_POP` / `OVERLAY_ZSCORE_VS_POP` / `OVERLAY_CHISQ_VS_POP` / `OVERLAY_KS_VS_POP`) ride `FacetRequest.Overlays`. FACET-host wiring is the FacetSchema-buffered-exit hook at `service.applyFacetOverlays`. See `skills/facet-design.md`.

Single-file cohorts only; equality-only, full-key required. See "Byte-layout invariants" above (Sidecar point-lookup index) + `skills/cohort-schema-design.md` + `skills/tool-lookup.md`.

## Labeled date ranges

Relocated verbatim from CLAUDE.md (Smart defaults). `GROUP_DATE_RANGES` (explicit-only) and `FILTER_DATE_RANGES` share one compiled `{label, start, end}` model (`daterange.Compile`): inline `ranges` XOR a named `table:` (`RangeTable`). Structured ranges ride the additive `omitempty` `types.Filterer.Params` slot — `format_version` stays `"1.1"`. **Zones:** range literals are LOCAL calendar days in the slot's resolved zone (Time zones); over a `datetime` the record side is floored to its local day by `temporal.LocalDay` and matched on day numbers, so the compiled model is zone-free. A `RangeTable` is calendar-only — no table-level `tz` — and follows the referencing slot's zone exactly like inline `ranges`. Proven by `TestTimeZone_DateRangeBoundsAreLocalDays` + `TestTimeZone_DateRangesLocalDayEveryArm`. Skills: `skills/op-group-date-ranges.md`, `skills/op-filter-date-ranges.md`.
