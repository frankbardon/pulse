## Parallel Compose

`pulse.ComposeParallel`, `pulse api compose --parallel N`. Bounded worker pool over `ComposedRequest`. Order-preserving by slot index. `ComposeOptions{MaxWorkers, PerRequestTimeout, FailFast}` (FailFast defaults true).

Post-slot-barrier Compose-overlay fold (`internal/service/compose_overlay.go` ⇒ `processing.ApplyComposeOverlaysWithRequests` in `internal/processing/overlay_compose_dispatch.go`; the bare `ApplyComposeOverlays` is the nil-requests, nil-extensions delegate kept for embedders): the orchestrator invokes `s.applyComposeOverlays(ctx, req, requests, responses)` once every slot has produced a finalised `*Response` and BEFORE the response is returned. Operates EXCLUSIVELY on `*Response` objects; per-slot `Responses[i].Overlays` is left UNTOUCHED.

FailFast handling: when `FailFast=true` (default) AND any slot fails, the orchestrator returns the first observed error WITHOUT invoking the overlay hook. FailFast=false routes slot failures through `SERVICE_INTERNAL` which also skips the hook. Empty / nil `req.Overlays` short-circuits with no allocation (overlay-free Compose JSON is byte-identical to a request that omits the slot entirely).

Per-kind handlers replace the chassis stub (`applyComposeStub`) for every Compose-only kind that has shipped. The six crosstab-shape COMPOSE handlers (`OVERLAY_INDEX_VS_REF`, `OVERLAY_DELTA_VS_REF`, `OVERLAY_PROP_Z_CELL`, `OVERLAY_T_CELL`, `OVERLAY_CHISQ_VS_REF`, `OVERLAY_RANK`) are wired today; remaining Compose-only kinds dispatch through the chassis stub until their handler lands. All buffered — streamable subset is empty across COMPOSE by construction.

Request-shape gates on the COMPOSE host. Everything else in this fold reads `*Response` only, but `internal/processing/overlay_compose_partition.go` needs the AUTHORED request: the `OVERLAY_PROP_Z_PANEL` within-prefix slab gate turns on each slot's declared `Crosstab.Rows` grouper types, and a materialised `MatrixPayload` carries its row KEYS but never the grouper that produced them — a fan-out row axis is invisible downstream of execution. So `service.(*Service).applyComposeOverlays` passes the per-slot requests and the `*ExtensionRegistry` into `ApplyComposeOverlaysWithRequests`, and the gate runs per spec INSIDE the dispatch loop (after reference/target resolution, before the key-set and schema walk — mirroring predict's Gate 3b position) rather than in the handler, because the `composeOverlayHandler` signature must stay `(spec, reference, targets, refIdx, targetIdxs)`. The gate declines whenever an earlier refusal is due, so the cap still fires first. An embedder calling the bare `ApplyComposeOverlays` gets no request-shape gate — the documented counterpart of the exported `ApplyOverlaysWithExtensions` bypass on the MATRIX host.

Response shaping (`return`) never runs inside the service: `Service.ComposeResolved` / `ComposeParallelResolved` hand the facade the label- and defaults-resolved slot clones, and `Pulse.Compose` / `ComposeParallel` apply each slot's plan plus the Compose-level `ComposedRequest.Return` (top-level overlays only) via `returnshape.ApplyComposed` AFTER the overlay and multiplicity folds — so every layer reads unshaped slots and serial ≡ parallel. What a slot's selection skips COMPUTING is decided per slot, where the whole `ComposedRequest` is in hand: a slot a Compose overlay names (reference or target) keeps the Components its overlays read (`Service.composeSlotVetoes`: every sub-part, except that the floor kinds `OVERLAY_PROP_Z_CELL` / `_PANEL` / `OVERLAY_CHISQ_VS_REF` keep `components.crosstab` only over a weighted slot and nothing over an unweighted one, #221), an unnamed slot skips what it excludes — the Compute plan paragraph of `.claude/reference/response-components.md`. Contract row: `update-demand/payload-and-return.md` (`Request.Return` row).

Slot label resolution: `applyComposeLabelDefaults` synthesises `request_<index+1>` for empty `Request.Label`; `ApplyComposeOverlays` builds a `Label → Index` lookup. The dedicated error codes `PULSE_OVERLAY_REFERENCE_UNKNOWN` and `PULSE_OVERLAY_TARGET_UNKNOWN` are pending — the chassis currently falls back to `PULSE_OVERLAY_REF_UNKNOWN` with a `which` Detail. See `skills/compose-requests.md`.

## Compose banner

`ComposedRequest.Banner` (`types.BannerSpec`, `capability:compose_banner`, hard dependencies `capability:compose` + `capability:crosstab`) is Compose sugar, not an engine mode: `internal/banner.ExpandCompose` (shared with `PredictCompose`) runs the sweep expansion, then appends one crosstab slot per section × block (Total — a no-column crosstab — first, then each group), each a deep copy of the base request with the section's filterers appended, its rows / `cell` / `cells` replacing the base crosstab's, the group's columns, the base `labels` scoped to the bindings the slot's rows / columns group by (`scopeLabels`; a binding grouped by no slot stays everywhere) and, on group slots only, the section's own overlays — which REPLACE the banner-level ones — else the banner overlays. Every slot runs as an ordinary slot (N scans of the cohort; `ComposeParallel` overlaps them — measured by `BenchmarkComposeBanner`), under the rank veto so the stitch reads it unshaped. After the multiplicity barrier fold (letters already refreshed), `applyComposeBanner` (`internal/service/compose_banner.go`) builds `ComposedResponse.Banner` on both orchestrators. Contract: `.claude/reference/response-components.md` (Opt-out and the Compose surface); skill `skills/compose-banner.md`.

## Compose base

`ComposedRequest.Base` (`capability:compose_base`, hard dependency `capability:compose`; library-gaps E6-S1) is Compose sugar, not an engine mode: a `types.Request` partial merged copy-on-write into every EXPLICIT slot by `banner.MergeBase` (`internal/banner/base.go`), called first inside `banner.ExpandCompose` — so serial Compose, `ComposeParallel` and `PredictCompose` judge the same merged slots, and everything downstream (the slot gate, the top-level params inheritance `descx.InheritComposeParams`, the sweep and banner expansion, `resultcall.CatalogOf` for `result()`, each slot's item `for_each` expansion in `Service.process` / predict) sees the base items as the slot's own. Never applied to the sweep body, the banner slots or a fit request; no per-slot opt-out. Rules, walked by reflection over `types.Request` so a new list slot (or a new item kind gaining `for_each`, library-gaps E7) inherits them with no edit: `label` is never merged (a set base `label` is `PULSE_COMPOSE_BASE_COLLISION` reason `base_label`); a map (`params`) merges key-wise, the slot's key winning — precedence slot > base > top-level `params`; a list carries the base items first, then the slot's own, and a base item whose `label` / `name` / `as` equals one of the slot's own in the SAME list is reason `label_collision` (details `request`, `slot`, `list`, `label`; unlabelled items are not compared — a duplicate DEFAULT label falls to that list's own duplicate rule); any other slot (a string, a pointer) takes the base's only when the slot leaves it zero. Each slot gets its own JSON deep copy of the base items (the banner base request's technique), so a slot's in-place rewrites (smart defaults, item fan-out) never reach a sibling or the caller; the input is never mutated. The effective request carries no `base`, so `NormalizedRequest` and predict's echo show the merged slots; predict's `result.request` keeps the batch as written. A set `base` on an instance hiding `capability:compose_base` is an unknown field before the merge (`setSlots`, both sides); a base item a profile hides is refused on the merged slot, located `details.request`. Also merged by Explain (`internal/guide`), walked once at `base` by the request-reads walker, and the MCP `return` default lands on the base instead of each slot. Tests: `TestMergeBase_*`, `TestExpandCompose_MergesBaseBeforeSweepAndBanner`, `TestComposeBase_*`, `TestPulseCompose_RunsBase`. Contract row: `update-demand/compose-expansion.md`; skill `skills/compose-requests.md`.

## Item fan-out (`for_each`)

A `for_each {axes, mode}` on a window, feature, attribute, aggregation or matrix item is expanded by ONE function, `sweep.ExpandItems` (import-fenced `internal/sweep`, reusing the compose sweep's `forEachCombination`, `variablesFor` and `template.RenderJSON`), wrapped with the `MaxDerivedColumns` then `MaxExpandedItems` preflight (`sweep.Counts`) by `descx.ExpandRequestItems`. Every request host calls it right after the slot gate and before anything else reads the item lists: `Service.process` (so `Process`, `ProcessStream`, every serial and parallel Compose slot and chain stage 0), `Service.materialize` (before the materialize gates, so every expanded item becomes a column), `Service.ProcessChain` (every stage, located `details.stage`), and predict (`Predict`, each Compose slot, each chain stage). The runtime rewrites `req.Features` / `Attributes` / `Windows` / `Aggregations` / `Matrices` IN PLACE — as smart defaults resolve in place — so the request echo shows the expanded lists and a second run is a no-op; predict expands a clone. Order: an aggregation `for_each` where no fan-out runs (a crosstab `cell` / `cells` / `margin_aggregations` entry, so a banner cell too) is refused first (reason `position_unsupported`, never silently ignored); then structural and reference checks over every for_each item (expansion order: features, attributes, windows, then aggregations and matrices, so an aggregation may read a `{{ch}}_lag` column a window fan-out adds), then the limits — `MaxDerivedColumns` over plain + expanded column items (`sweep.DerivedCount`), `MaxExpandedItems` over the aggregation and matrix items the fan-outs ADD, plain ones never counted (`sweep.ExpandedCount`; a later kind sums `sweep.FanOutCount`) — then rendering (grid first axis slowest; zip lockstep) and a strict decode per item. `[]MatrixSpec` is a value slice (`expandValues`); each rendered matrix needs its own `name`, a repeat falls to the matrix duplicate-name refusal. The `result()` catalog (`descx.ResultCatalog`) catalogs each slot's expanded aggregation labels (`resultItemsExpanded`), and a `base` item's `for_each` expands per slot after the merge. A sweep body carrying a for_each on any of the five lists is refused (`nested_in_sweep`) by `sweep.Expand` before its placeholder scan. **Optimize blocks (E7-S2)** fan out at the Compose level, not per slot: `sweep.ExpandOptimize`, called in `banner.ExpandCompose` right after `MergeBase` (so before the sweep's `MaxComposeSlots` preflight, `OptimizeRefusal`, the `result()` catalog and its pre-phase, serial, parallel and predict alike), runs the same axis and reference rules over the block nested as `{"optimize":[block]}` (an objective / constraint / bound `{{axis}}` is `PULSE_FOR_EACH_EXPR_SPLICE`), requires an axis in `name` (`name_without_axis`), checks `MaxExpandedItems` over the blocks it adds (once per call, apart from the slots') and renders each combination with a strict decode. A typed field takes a whole `{"$var"}` value: `OptimizeSpec.UnmarshalJSON` keeps such a block as written for the render (a marker without a for_each stays a decode error); a marker standing for a whole list or a list entry is refused before render, `PULSE_FOR_EACH_INVALID` `marker_position` (`sweep.checkOptimizeMarkers`, the schemas' rule read off `types.OptimizeSpec`; a free-form `inline` body admits one anywhere). A set block for_each opens the pre-expansion slot gate (`OptimizeHasForEach`); the echo (`NormalizedRequest`, predict's normalized batch) carries the expanded blocks, predict's `Request` the block as written. **Never inside an expression (U58 E4-G1):** an `{{axis}}` token in an `internal/exprslots` expression slot is refused by the reference scan, before the limit and any rendering — `PULSE_FOR_EACH_EXPR_SPLICE` (the item scanned nested under its list key, so `features[].params.fit_on` matches) and, for a compose sweep's request or overlays, `PULSE_SWEEP_EXPR_SPLICE`; details `field`, `placeholder`, `slot`. The slot list also covers an embedder extension's `Expression`-flagged params (slot `extension_param`, U79 E1-S5): the instance's visible flagged keys ride `sweep.Options.ExprParams` from the service and from predict (`.claude/reference/architecture/extension-surface.md`). Both ride the ONE expansion, so predict refuses identically (`TestExprSplice_PredictRuntimeParity`); the template-side twin is `PULSE_TEMPLATE_EXPR_SPLICE` (`.claude/reference/request-templating.md`). `Request.Hash` hashes the request as written (the `for_each` key is `omitempty`, so a for_each-free request hashes byte-identically); the hash of the expanded request equals its hand-expanded twin's.
