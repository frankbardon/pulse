## Parallel Compose

`pulse.ComposeParallel`, `pulse api compose --parallel N`. Bounded worker pool over `ComposedRequest`. Order-preserving by slot index. `ComposeOptions{MaxWorkers, PerRequestTimeout, FailFast}` (FailFast defaults true).

Post-slot-barrier Compose-overlay fold (`internal/service/compose_overlay.go` ⇒ `processing.ApplyComposeOverlaysWithRequests` in `internal/processing/overlay_compose_dispatch.go`; the bare `ApplyComposeOverlays` is the nil-requests, nil-extensions delegate kept for embedders): the orchestrator invokes `s.applyComposeOverlays(ctx, req, requests, responses)` once every slot has produced a finalised `*Response` and BEFORE the response is returned. Operates EXCLUSIVELY on `*Response` objects; per-slot `Responses[i].Overlays` is left UNTOUCHED.

FailFast handling: when `FailFast=true` (default) AND any slot fails, the orchestrator returns the first observed error WITHOUT invoking the overlay hook. FailFast=false routes slot failures through `SERVICE_INTERNAL` which also skips the hook. Empty / nil `req.Overlays` short-circuits with no allocation (overlay-free Compose JSON is byte-identical to a request that omits the slot entirely).

Per-kind handlers replace the chassis stub (`applyComposeStub`) for every Compose-only kind that has shipped. The six crosstab-shape COMPOSE handlers (`OVERLAY_INDEX_VS_REF`, `OVERLAY_DELTA_VS_REF`, `OVERLAY_PROP_Z_CELL`, `OVERLAY_T_CELL`, `OVERLAY_CHISQ_VS_REF`, `OVERLAY_RANK`) are wired today; remaining Compose-only kinds dispatch through the chassis stub until their handler lands. All buffered — streamable subset is empty across COMPOSE by construction.

Request-shape gates on the COMPOSE host. Everything else in this fold reads `*Response` only, but `internal/processing/overlay_compose_partition.go` needs the AUTHORED request: the `OVERLAY_PROP_Z_PANEL` within-prefix slab gate turns on each slot's declared `Crosstab.Rows` grouper types, and a materialised `MatrixPayload` carries its row KEYS but never the grouper that produced them — a fan-out row axis is invisible downstream of execution. So `service.(*Service).applyComposeOverlays` passes the per-slot requests and the `*ExtensionRegistry` into `ApplyComposeOverlaysWithRequests`, and the gate runs per spec INSIDE the dispatch loop (after reference/target resolution, before the key-set and schema walk — mirroring predict's Gate 3b position) rather than in the handler, because the `composeOverlayHandler` signature must stay `(spec, reference, targets, refIdx, targetIdxs)`. The gate declines whenever an earlier refusal is due, so the cap still fires first. An embedder calling the bare `ApplyComposeOverlays` gets no request-shape gate — the documented counterpart of the exported `ApplyOverlaysWithExtensions` bypass on the MATRIX host.

Response shaping (`return`) never runs inside the service: `Service.ComposeResolved` / `ComposeParallelResolved` hand the facade the label- and defaults-resolved slot clones, and `Pulse.Compose` / `ComposeParallel` apply each slot's plan plus the Compose-level `ComposedRequest.Return` (top-level overlays only) via `returnshape.ApplyComposed` AFTER the overlay and multiplicity folds — so every layer reads unshaped slots and serial ≡ parallel. What a slot's selection skips COMPUTING is decided per slot, where the whole `ComposedRequest` is in hand: a slot a Compose overlay names (reference or target) keeps the Components its overlays read (`Service.composeSlotVetoes`: every sub-part, except that the floor kinds `OVERLAY_PROP_Z_CELL` / `_PANEL` / `OVERLAY_CHISQ_VS_REF` keep `components.crosstab` only over a weighted slot and nothing over an unweighted one, #221), an unnamed slot skips what it excludes — the Compute plan paragraph of `.claude/reference/response-components.md`. Contract row: `update-demand/payload-and-return.md` (`Request.Return` row).

Slot label resolution: `applyComposeLabelDefaults` synthesises `request_<index+1>` for empty `Request.Label`; `ApplyComposeOverlays` builds a `Label → Index` lookup. The dedicated error codes `PULSE_OVERLAY_REFERENCE_UNKNOWN` and `PULSE_OVERLAY_TARGET_UNKNOWN` are pending — the chassis currently falls back to `PULSE_OVERLAY_REF_UNKNOWN` with a `which` Detail. See `skills/compose-requests.md`.

## Compose banner

`ComposedRequest.Banner` (`types.BannerSpec`, `capability:compose_banner`, hard dependencies `capability:compose` + `capability:crosstab`) is Compose sugar, not an engine mode: `internal/banner.ExpandCompose` (shared with `PredictCompose`) runs the sweep expansion, then appends one crosstab slot per section × block (Total — a no-column crosstab — first, then each group), each a deep copy of the base request with the section's filterers appended, its rows / `cell` / `cells` replacing the base crosstab's, the group's columns, the base `labels` scoped to the bindings the slot's rows / columns group by (`scopeLabels`; a binding grouped by no slot stays everywhere) and, on group slots only, the section's own overlays — which REPLACE the banner-level ones — else the banner overlays. Every slot runs as an ordinary slot (N scans of the cohort; `ComposeParallel` overlaps them — measured by `BenchmarkComposeBanner`), under the rank veto so the stitch reads it unshaped. After the multiplicity barrier fold (letters already refreshed), `applyComposeBanner` (`internal/service/compose_banner.go`) builds `ComposedResponse.Banner` on both orchestrators. Contract: `.claude/reference/response-components.md` (Opt-out and the Compose surface); skill `skills/compose-banner.md`.

## Item fan-out (`for_each`)

A `for_each {axes, mode}` on a window, feature or attribute item is expanded by ONE function, `sweep.ExpandItems` (import-fenced `internal/sweep`, reusing the compose sweep's `forEachCombination`, `variablesFor` and `template.RenderJSON`), wrapped with the `MaxDerivedColumns` preflight by `descx.ExpandRequestItems`. Every request host calls it right after the slot gate and before anything else reads the item lists: `Service.process` (so `Process`, `ProcessStream`, every serial and parallel Compose slot and chain stage 0), `Service.materialize` (before the materialize gates, so every expanded item becomes a column), `Service.ProcessChain` (every stage, located `details.stage`), and predict (`Predict`, each Compose slot, each chain stage). The runtime rewrites `req.Features` / `Attributes` / `Windows` IN PLACE — as smart defaults resolve in place — so the request echo shows the expanded lists and a second run is a no-op; predict expands a clone. Order: structural and reference checks over every for_each item (pipeline order: features, attributes, windows), then the limit over plain + expanded items, then rendering (grid first axis slowest; zip lockstep) and a strict decode per item. A sweep body carrying a for_each is refused (`nested_in_sweep`) by `sweep.Expand` before its placeholder scan. **Never inside an expression (U58 E4-G1):** an `{{axis}}` token in an `internal/exprslots` expression slot is refused by the reference scan, before the limit and any rendering — `PULSE_FOR_EACH_EXPR_SPLICE` (the item scanned nested under its list key, so `features[].params.fit_on` matches) and, for a compose sweep's request or overlays, `PULSE_SWEEP_EXPR_SPLICE`; details `field`, `placeholder`, `slot`. The slot list also covers an embedder extension's `Expression`-flagged params (slot `extension_param`, U79 E1-S5): the instance's visible flagged keys ride `sweep.Options.ExprParams` from the service and from predict (`.claude/reference/architecture/extension-surface.md`). Both ride the ONE expansion, so predict refuses identically (`TestExprSplice_PredictRuntimeParity`); the template-side twin is `PULSE_TEMPLATE_EXPR_SPLICE` (`.claude/reference/request-templating.md`). `Request.Hash` hashes the request as written (the `for_each` key is `omitempty`, so a for_each-free request hashes byte-identically); the hash of the expanded request equals its hand-expanded twin's.
