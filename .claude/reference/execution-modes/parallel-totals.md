## Two-phase `total()`

**Two-phase `total()` (U51 E3-S1, #399; grouped and multi-layer U74 E3-S1 / E3-S2, #494).** A total-bearing `ATTR_FORMULA` is not row-local, yet both reducers run it when `mergegate.ParallelTotals` admits it: every `total()` formula of a request with no `Crosstab` (and no nil attribute slot) — grouped too (the cohort-wide total publishes before any grouper reads a row), and in any pre-pass layer of the serial two-pass plan (`twoPassPlan`: a formula whose input reads, directly or through row-local slots, an earlier `total()` formula's label sits one layer deeper; an `ATTR_REG_PREDICT`, fit-referenced or extension slot without `FieldInputs` reads every earlier one). The request's other attributes are judged as ever: a non-row-local one keeps it serial. Phase 1 (`internal/service/totals_prepass.go`) is one parallel pre-pass per layer (`processing.TotalsPrepassLayers`, `prepassLayers`), in order, over the same partitions — shards on the per-shard arm, the block-aligned segments on the decode arm — under the layer's own projection (`processing.TotalsPrepassRequest(req, exts, layer)`: filters, weights, zones, the stages a layer-L `total()` argument reads — an earlier layer's formula among them whole — and each layer-L formula reduced to its arguments — never a field only a formula's row expression or an aggregation reads; `TestTotalsPrepass_ProjectionNarrowsToTotalInputs`, `TestTotalsPrepass_MultiLayerProjectsPerLayer`): each worker builds a `processing.TotalsPrepass` for layer L with every earlier layer's published values bound (`PublishTotals`; a missing one is `PROCESSING_INTERNAL`, never a 0) and folds its filter-passing rows (the stages a layer-L argument reads, in declared order, then each layer-L formula's `PrePass` — the serial layer-L scan's record state), the workers' states merge through `MergeableTotals.PartialTotals` / `AbsorbTotals` (binned `reprosum` sums, integer counts — order-free, so the merged totals are the serial pre-pass bits) and `Publish` finalizes them beside the earlier layers' values (the next layer's prior; after the last, everything phase 2 binds). Phase 2 is the ordinary reduce: `buildRowLocalAttrSpecs` binds each partition's formula through `PublishedTotals.Bind` → `PublishTotals` before its first row (an unbound one refuses, never reads 0). Predict follows the shared gate (`ShardFanOut` / `DecodeFanOut`: `TestShardFanOut_PredictMatchesRuntime`, `TestDecodeFanOut_PredictMatchesRuntime`) and `PULSE_ADVISORY_EXTRA_PASS` stays one added scan per formula (each sits in one layer). Gates: the bit-exactness family `TestBitExact_Archive` / `TestBitExact_Heavy` (DecodeWorkers 2/3/7/8, ShardWorkers 2/3/8 on a scattered nine-shard archive, each parallel cell required to fan out, == the serial bits; plain, weighted, filtered share-over-label, matrix-beside, grouped and three-layer (ungrouped and grouped) `formula_total*` shapes), `TestParallelTotals`, `TestTotalsPrepass_*` (`_MultiLayerPartitionMergeEqualsSerial`: any partition, layer by layer, == the serial buffered bits), `TestFormulaTotal_PartitionedRouting`, the fan-out parity tests' multi-layer shapes.

## ProcessChain stages

**A chain stage runs `total()` two-phase too (U74 E3-S3, #494).** `mergegate.ChainRefusal` is `MergeRefusal` (crosstab first, matrices stripped) with the same `ParallelTotals` admission, so a `total()` stage passes wherever a Process request would merge — grouped, any layer — and a refused one (beside a two-pass attribute, …) keeps `PULSE_CHAIN_NOT_MERGEABLE` with that attribute's reason; the chain validator calls the same rule, so runtime and predict-chain agree per stage (`TestChainGate_ValidatorMatchesRuntime`). **Stage 0** runs `Process`, so it takes the arms above: two-phase on the per-shard / parallel-decode arm when it fans out, the serial two-pass plan otherwise. **A later stage** never fans out (one in-memory input); a `total()`-bearing one with rows (`chainStageTwoPhase`) runs the same two phases over the previous stage's rows as ONE partition (`internal/service/chain_totals.go`: `runChainStageTotals`, `chainTotalsSource`): phase 1 is `prepassLayers` over the `processing.ChainRowIterator` (rewound per layer), phase 2 the partition reduce (`reducePartitions`, the source-agnostic core of `reduceParallelBuffered`, `partitionSource{prepass, scan}`) with every formula bound before its first row. The rows stay lazy — the serial processor buffers a grouped `total()` stage (two-pass beside groups routes buffered), one record a row — and the stage reports the `streaming` arm; the answer is the serial processor's whole response byte for byte (`TestChainStageTotals_MatchesSerialProcessor`: ungrouped, grouped, three layers grouped). A stage with an empty input, or no `total()`, keeps `runChainStage`. Gates: `TestBitExact_ChainTotals` (three stages — grouped, three layers over a forwarded key with a frequency weight, ungrouped — ShardWorkers 1/2/3/8 on the scattered archive ≡ the single file's serial chain, stage by stage, bitwise; stage 0 on `shard_parallel`, later stages `streaming`), `TestBitExact_ChainTotalsDecode` (heavy: DecodeWorkers 2/3/7/8, stage 0 `parallel_decode`), `TestChainTotals_PeakMemoryNotWorseThanSerial` / `TestChainStageTotals_PeakMemoryNotWorseThanSerial` (heavy: the chain's and a later stage's peak heap not above the serial run's; a stage-0 grouping whose key count nears the row count is the per-shard reducer's own trade — a partial of every group per worker — as on Process).
