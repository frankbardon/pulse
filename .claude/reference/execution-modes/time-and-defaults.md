# Execution modes — time zones, date-family types, labeled date ranges, smart defaults

Per-topic slice of the execution-modes reference. Index (Mode index + section map): `.claude/reference/execution-modes.md` — load it first, then only the slice(s) your engine work touches. Agent-facing form: `skills/time-zones.md`.

## Time zones

Storage stays UTC epoch. A zone is request-time configuration that is resolved, validated, echoed and — on a `datetime` field of a zone-aware operator — applied: the instant is read on its LOCAL calendar day. It is refused wherever it would otherwise be silently ignored (a derived field).

**One home for date math.** Epoch-day, calendar and zone math lives in `internal/temporal` (a leaf over stdlib + `errors`; it must not import `encoding`). The public `encoding` date helpers keep their frozen signatures and forward into it. `internal/processing/date_field.go` is the OPERATOR-boundary adapter: a `datetime` (epoch seconds) is day-truncated exactly once there — toward the past, never rounding (`1969-12-31T23:59:59Z` is UTC day −1, not day 0) — by `DateTimeToDay` when no zone applies, or by `temporal.LocalDay` in the slot's resolved non-UTC zone (decided once at construction; a nil zone is exactly the zone-free path, so UTC / absent costs nothing). Everything downstream speaks epoch days, so `GROUP_DATE` keys and `period_start` / `period_end` are local calendar labels with no format change and range literals are local days. `TestNoZoneMathOutsideTemporal` (`go/ast`) fails on the int literal `86400`, any `SecondsPerDay` reference, `time.LoadLocation` / `LoadLocationFromTZData` / `FixedZone` / `Local`, a dot-import of `time`, or a `time/tzdata` import anywhere outside `internal/temporal` (sole allow-list entry: the `encoding.SecondsPerDay` re-export). `.In(` is deliberately not banned — with every means of obtaining a non-UTC location banned, only `time.UTC` can reach it.

**`Zone`.** `temporal.LoadZone(name)` accepts exactly `UTC` or an IANA `Area/Location` name (contains `/`, each segment opens with an ASCII upper-case letter) with an exact, case-sensitive entry in Pulse's own embedded `internal/temporal/zoneinfo.zip` (release `temporal.TZDataVersion`, hash-pinned; refresh with `make tzdata`). `$ZONEINFO`, host zoneinfo and `time/tzdata` are never consulted, so acceptance and offsets are host-independent. `EST`, `EST5EDT`, `GMT`, `Local`, `""` and offset strings (`+05:00`) are `PULSE_TIMEZONE_UNKNOWN` with the name under `details.tz`. Offset lookup is allocation-free, amortized O(1) (a transition table over 1900–2100, `time.In` fallback outside it). `LocalDay`, `LocalMidnightUTC` and `LocalParts` are the primitives operators consume. `(*Zone).IsUTC()` is true for the sentinel and every fixed-zero-offset zone (`Etc/UTC`, `Etc/GMT`, …). A per-instance `temporal.Cache` memoises loads.

**Wire.** `Request.TimeZone` / `FacetRequest.TimeZone` (`time_zone`) and per-slot `TimeZone` (`tz`) on `types.Group`, `Filterer`, `Attribute`, `Feature` — all additive `omitempty`, `format_version` stays `"1.1"`. `ComposedRequest` / `ChainRequest` carry no zone of their own (each inner `Request` does); `SampleRequest` has none. `pulse.Options.DefaultTimeZone` (`""` = UTC) is validated at `pulse.New` (unknown → `PULSE_TIMEZONE_UNKNOWN`); a non-UTC default is accepted and applies wherever it resolves onto a `datetime` slot. There is no env var and no CLI default-zone flag.

**Capability.** `internal/descriptor/capabilities_zone.go` is the single declaration table (`ZoneCapabilityOf` / `IsZoneCapable`), projected onto the manifest `zone` key of an operator or overlay entry: `capable` on the date groupers / filter, `ATTR_DATE_PART` and `FEAT_DATE_FEATURES`; `following` on `OVERLAY_YOY` (no `tz` slot — it inherits its host grouper's zone, since a disagreeing overlay zone would be meaningless); absent everywhere else. Extension operators are never zone-capable; windows are excluded.

**Resolution.** `internal/descriptor/zone_resolve.go` — `ResolveZones` / `ResolveFacetZones`, wrapped by the service in `internal/service/zones.go` — is pure, never mutates the request, and is the ONE pass both runtime and predict call, so they accept and refuse identically. Precedence per zone-capable slot: slot `tz` → slot `tz_field` → `time_zone_field` → request `time_zone` → cohort default zone field → `Options.DefaultTimeZone` → `UTC`. Refusal order:

1. unknown `time_zone` / default zone → `PULSE_TIMEZONE_UNKNOWN {tz}` — even with no zone-capable slot;
2. explicit `tz` on a non-capable operator (built-in or extension) → `PROCESSING_CONFIG {slot, operator, tz}`;
3. explicit `tz` on a schema field that is not `datetime` (a calendar `date`, or the epoch-day count `GROUP_DATE` tolerates) — even `"UTC"` → `PROCESSING_CONFIG {slot, operator, tz, field, field_type}`;
4. unknown slot `tz` → `PULSE_TIMEZONE_UNKNOWN {slot, tz}`;
5. a non-UTC-equivalent zone resolving onto a field ABSENT from the schema (a derived or chain-synthesised column; a JOINED column is in the joined schema and resolves by its own type) → `PROCESSING_CONFIG {slot, operator, tz}`, "… a zone cannot be applied to a derived field …" — the operators read an absent field as epoch DAYS, so the zone would be silently ignored.

**Per-row zones and the cohort default zone field.** `tz_field` / `time_zone_field` and a cohort's declared default zone field: `execution-modes/per-row-zones.md`.

- A slot with an EMPTY operator `Type` is skipped — it is a type error reported by operator construction (`PROCESSING_CONFIG "unknown group type: "` and siblings), never a zone refusal. A NIL schema (a validator with no cohort schema in reach) skips rules 3 and 5, so a schema-less check never refuses what the runtime accepts.
- An INHERITED zone on a non-`datetime` field is not applied and echoes `tz: null`. A UTC-equivalent zone is never refused and output is byte-identical to no zone (`TestUTCZoneIsIdentity`); the echo keeps the caller's spelling.
- `ATTR_DATE_PART` / `FEAT_DATE_FEATURES` accept `date` and `datetime`. Over a `datetime` they read the resolved zone's wall clock (`hour` is `datetime`-only; ATTR `iso_weekday` / FEAT `dow` are ISO 1..7, Monday = 1, the local day, never following `week_start`); over a `date` an explicit `tz` is refused (rule 3) and an inherited one never applied. A null source cell is null, never `0`, in every mode. Their field rules are read once (`internal/datepart` and the predict feature check), so predict and runtime refuse alike.
- Slot paths, walked in this order: `filterers[i]`, `features[i]`, `attributes[i]`, `groups[i]`, `crosstab.rows[i]`, `crosstab.columns[i]`, then each `MAT_DISTANCE` `matrices[i].params.between` (a grouper slot inside params — `matrix-and-vectors.md`).

**Call sites.** The service resolves once per Request after smart defaults, in every executing mode (Process, crosstab, join — against the joined schema — every chain stage BEFORE the chain gate, FacetSchema, Materialize) and once per predicate in the `FilterToFile*` family. Streaming and Compose inherit through Process. Every public executing entry point is pinned by `TestTimeZone_DefaultZoneReachesEveryEntryPoint`; grep `resolveZones` in `internal/service` before adding an entry point. Sample, Lookup, Dedup, BuildIndex and CountRecords run no filter or expression.

- **FilterToFile.** A synthetic `Request{Filterers, TimeZone}` goes through the same resolution (unknown zone → `PULSE_TIMEZONE_UNKNOWN` up front), so `to_day()` reads the request zone, else `Options.DefaultTimeZone`. Structured filterers are resolved against the canonical schema before hashing or reuse, so every zone refusal is Process's own with the request's slot indices. The resolved non-UTC zone and the applied per-slot zones join the dedup hash — otherwise two requests differing only by zone would share a file.
- **Applying the zone.** The operator factories see only `(slot, schema)`, so each mode hands its arm `descx.ZonedRequest(req, zones, loader)` right after its last caller-visible mutation (auto labels): a shallow copy whose slots that INHERITED a non-UTC zone carry it in `tz` — or `req` itself when there is none. Every arm built from it (buffered, streaming, fused crosstab and its gate probe, parallel decode, shard reduce, chain stages) sees the zone with no further plumbing. The caller's request is never written, so the echo and `Request.Hash` show it as written.
- **Location.** A Compose refusal keeps its prefix `request N:` and adds `details.request` (0-based) on the serial and fail-fast parallel path (`CollectErrors` aggregates into `SERVICE_INTERNAL`); a chain refusal adds `details.stage`. Both are copies of the coded error, so the code survives `errors.As` and the CLI envelope. Only refusals the service marks as **located** where they are raised (`internal/service/located.go`) gain a location; the validators locate at the same points.

**Predict and the validators.** Predict resolves on the defaults-resolved clone (`PredictOptions.DefaultTimeZone` / `ZoneLoader`, filled from the service) and echoes `PredictResult.TimeZones` — `[{slot, operator, field_type (omitempty), tz (string|null), tz_field (omitempty), source}]`, `source` one of the `descriptor.ZoneSource*` constants, never nil, zone-capable slots only; a refusal is a predict error (`Valid=false`).

- **Joins in predict.** For a single `JoinSpec` predict reads the right cohort's header + schema through `PredictOptions.SchemaLoader` and validates the whole request against `encoding.JoinedSchema` — the one join-schema rule the runtime delegates to.
- **Defaults off.** `PredictOptions.DisableDefaults` validates the request as written; `DefaultsApplied` still lists what WOULD apply. A top-level slot still without a `Type` gets the runtime's own `PROCESSING_CONFIG` message.
- **The validators.** `ValidateComposeWithOptions`, `ValidateChainWithOptions` and `ValidateFacetWithOptions` run the same pass (defaults on a clone unless disabled, then zone resolution) and record each refusal with the runtime's code, message and details, location included. The chain validator also runs the chain gate, the field checks and the next stage's synthesised schema on each stage after defaults against its input schema — exactly as the runtime does. The gate is the shared `mergegate.ChainRefusal` on both sides (see ProcessChain).
- **Join count.** `descriptor.JoinCountRefusal` is the one rule — more than one `JoinSpec` → `PULSE_JOIN_TOO_MANY "v1 supports exactly one JoinSpec per Request" {count}`. Runtime applies it first (before the crosstab and join dispatch, so a crosstab is covered too); predict right after the header + schema read; the Compose validator per slot before that slot's zones; the chain validator on stage 0. It is a located refusal. Chain stages ≥ 1 never reach it: their `Joins` is `PULSE_CHAIN_STAGE_JOIN` first.
- **Join keys.** `encoding.JoinKeysRefusals(left, right, spec)` is the one kind / OnPair rule, in runtime order: no OnPair (`PULSE_JOIN_KEYS_EMPTY`), a kind other than inner, then per pair a blank side, an unknown left then right key (`PULSE_JOIN_FIELD_UNKNOWN {field, index}`), incompatible key types (`PULSE_JOIN_TYPE_MISMATCH`). The service applies it as soon as both cohorts are open — before the right side is decoded — as a located refusal; predict reports every entry once the right schema is read.
- **Field references.** `descriptor.FieldRefRefusals(req, schema, snap)` is the one unknown-name rule, called by every execution mode right after zone resolution, against the schema the request executes over (cohort, joined, or synthesised chain-stage schema; FacetSchema and FilterToFile apply its filterer half). It is a located refusal. The walk is PIPELINE order and is documented on the function and in `.claude/reference/predict-inspect/predict.md` (Field references are one rule, not a predict-only check): features see the schema and earlier features; filterers see features but NOT attribute labels (save a before-filters `ATTR_PREVIOUS_STATE` label); attributes see earlier attributes; record consumers see every attribute label; windows, sort and post-tests see the OUTPUT row columns. A window `order_by` key that is a schema field must be orderable (`IsOrderableType`: every type but `set_*`). An extension feature opens the set for everything after it.
- **Shadowing.** A derived column whose name is already available at its producer's point (an attribute label equal to a schema field, feature output or earlier label; a feature output equal to a schema field or earlier output; a window label equal to an output-row column or earlier window label) is refused `SERVICE_VALIDATION` — `"attribute label <l> shadows an existing field"` `{label, attribute}`, `"feature <TYPE> output <l> shadows an existing field"` `{label, feature}`, `"window[i] label <l> shadows an existing column"` `{window_index, label, type}`. Writing it overwrote the column in place and the arms disagreed on its null mark, so both sides refuse. A name only an extension feature might produce is not judged.
- **Names inside params** are judged at the operator's own pipeline point: the built-in aggregation params that name a field (every aggregation slot, crosstab cell and margins included; `"<slot> <TYPE>: params.<key> references unknown field <f>"`, details `{field, param, aggregation|role}`), the post-test output-column params, and an extension's `FieldInputs` hook (`"<category> <NAME>: FieldInputs references unknown field <f>"`, `field_inputs: true`; a hook that panics is undeclared). Empty names are refused where the slot requires one, even after an extension feature opened the set.

**Output namespace.** An aggregation label (explicit, or `<TYPE>_<field>` with a defaulted Type) equal to a group field or to an earlier aggregation's label is refused — `"aggregation[i] label <l> collides with group[j] field <l>"` `{label, aggregation_index, aggregation, group_index, group}` / `"aggregation[i] label <l> collides with aggregation[j] label <l>"` `{label, aggregation_index, aggregation, other_aggregation_index, other_aggregation}` — because an output row holds one value per name: the group key would silently overwrite the aggregation, and a duplicate label keep only the last figure. Located inside Compose and on every chain stage. A label equal to the field it reads or to an attribute label is not a collision; a crosstab's top-level labels are not judged (its cell / margin labels are kept distinct by `MarginAggregationFaults`). Tests and regressions emit slices, not row columns, so their labels cannot collide.

## Date-family field types

**Date-family field types.** `GROUP_DATE`, `GROUP_DATE_RANGES` and `FILTER_DATE_RANGES` accept BOTH temporal types — `date` (epoch days, `int32`) and `datetime` (epoch seconds, `int64`). Past the operator boundary everything speaks epoch DAYS (see One home for date math). `GROUP_DATE_RANGES` / `FILTER_DATE_RANGES` reject any other field type with `PROCESSING_CONFIG`. `GROUP_DATE` stays non-validating and reads a non-temporal `Field` as an epoch-day count — except `component: hour`, the one sub-day bucket, which reads the local epoch HOUR (key `YYYY-MM-DDTHH`; the skipped DST hour has no bucket and the repeated one is ONE) and refuses any field that is not a `datetime` schema field. `week_start` (`week` only, default `monday` = ISO `YYYY-Www`) keys any other start by the week's first local date. Both params are read once, by `internal/dategroup`, for the factory and predict alike. Zones: see Time zones above.

## Labeled date ranges

`GROUP_DATE_RANGES` (explicit-only) and `FILTER_DATE_RANGES` share one compiled `{label, start, end}` model (`daterange.Compile`): inline `ranges` XOR a named `table:` (`RangeTable`). Structured ranges ride the additive `omitempty` `types.Filterer.Params` slot. **Zones:** range literals are LOCAL calendar days in the slot's resolved zone; over a `datetime` the record side is floored to its local day and matched on day numbers, so the compiled model is zone-free. A `RangeTable` is calendar-only — no table-level `tz` — and follows the referencing slot's zone exactly like inline `ranges`. Skills: `skills/op-group-date-ranges.md`, `skills/op-filter-date-ranges.md`.

**Typed tables.** A `RangeTable` is typed by its bounds — ISO strings a date table (`Ranges`), numbers a numeric one (`NumericRanges`, half-open `[start, end)`) read only by `GROUP_NUMERIC_RANGES`; either side naming the other kind is `PULSE_RANGE_TABLE_KIND_MISMATCH`, which predict raises too.

## Smart defaults

When a request slot names a field but omits `Type`, the engine infers an operator from the schema type. The rules are `defaultRules` in `internal/descriptor/defaults.go` — one row per field type naming its aggregation and grouper default (an empty aggregation means explicit only, as for `date` / `datetime`), plus the grouper params a default fills (`defaultRangeInterval`, `defaultDateComponent`). A field type with no row takes no default. Agent-facing tables: `skills/aggregation-design.md` and `skills/grouper-design.md` (Smart defaults).

- Defaults apply only when `Field` is set and `Type` is empty. They never override an explicit `Type` / `metric`, never cross categories (a grouper default never fills an aggregation slot), and never fill tests, filterers, attributes, windows or features. `Field.Nullable` never changes the inferred operator.
- The crosstab cell — and each measure of `crosstab.cells` — is an aggregation slot and takes the aggregation default (`DefaultApplied.Path` `["Crosstab", "Cell", "Type"]` / `["Crosstab", "Cells", i, "Type"]`). Each crosstab `rows` / `columns` axis grouper is a grouper slot and takes the grouper default plus its params; a banner's section rows and group columns expand into those axes, so they default too. Under `DisableDefaults` a typeless axis is `PROCESSING_CONFIG` `unknown group type: ` on both sides.
- Disable via `pulse.Options{DisableDefaults: true}` or `--no-defaults`. Predict always computes `DefaultsApplied`.
- **Previous-state output columns.** An `ATTR_PREVIOUS_STATE` output label reads as its state field for the aggregation, grouper and crosstab-cell slots, so an untyped slot naming it takes the state field's default (`GROUP_CATEGORY` / `AGG_MODE_COUNT`) on predict and at runtime alike; its `mode_value` is the dictionary index.

**Metric defaults.** A metric-taking matrix slot (`vectors.MatrixMetricConsumer` — `MAT_DISTANCE`) that reads a `kind`-declared vector BY NAME and names no `params.metric` (absent or `null`) gets the kind's default for its consumer (`metric.DefaultFor`: the kind's table default when the consumer accepts it, else the first accepted metric suiting the kind, never a poor fit; under `MAT_DISTANCE` `standardize` the non-negative-domain metrics are skipped). The pass rewrites the slot's `Params` on a COPY of the `Matrices` slice and reports `DefaultApplied{Path: ["Matrices", i, "Params", "metric"], Field: <vector>, Type: <metric>, Category: "metric"}`, the reason naming a fallback. It honours `DisableDefaults` and a hidden operator like every other default, and never fills an inline-`fields` slot or a kind-free vector (`MAT_DISTANCE` then keeps its implicit `euclidean`). Runtime and predict run the same pass, so the metric predict reports is the one executed. Kind table: `matrix-and-vectors.md` (Virtual vectors).
