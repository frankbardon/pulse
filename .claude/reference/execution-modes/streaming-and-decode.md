# Execution modes — streaming, projection, parallel decode, cancellation, timeout

Per-topic slice of the execution-modes reference. Index (Mode index + section map): `.claude/reference/execution-modes.md` — load it first, then only the slice(s) your engine work touches.

## Streaming Process

`pulse.ProcessStream`, `pulse api process --stream`. Four orchestrator modes — single-pass, grouped, two-pass attributes (Welford-Pébaÿ), streaming features. Forced-buffered: median/percentile/zscore aggregators, `ATTR_PERCENTILE`, `ATTR_PREVIOUS_STATE` (orders every record of a subject; never merge-gate row-local), `GROUP_QUANTILE`/`GROUP_DATE`/`GROUP_KMEANS`, window operators, built-in decimal paths (a `Streamable` extension aggregator streams a `decimal128` target — `UpdateRow` reads `DecimalValue`), tier-1 tests with groupers/features/two-pass, all tier-2 tests, a buffered matrix spec (`types.MatrixSpec.Streamable()` false — a rank method; `matrix-and-vectors.md`, Matrix slot). NDJSON one row per line. See `skills/streaming-and-watching.md`.

**No-aggregation work streams (U48 #336).** A request with no aggregation streams when it carries a matrix, a tier-1 test or a regression (`processing.hasStreamingWork`; predict `computeStreamable` and `mergegate.MergeRefusal` change with it — a tests- or regression-only request is refused a merge for its tests / regressions, never for a missing aggregator); every other gate still applies. Tests beside a streamable regression stream too (U48 E3-S3): the ungrouped scan folds each filter-passing record into both in the buffered arm's record order and finalizes tests before regressions, so a whole readout (SRM check, lifts, regression adjustment, one `request`-family correction) is ONE streaming request; a grouper, feature or two-pass attribute beside a regression still buffers. Such a request emits no `data` row on either arm, so `ProcessStream` yields no row and `ProcessStreamResult` sends no chunk, only the `StreamCompleted` terminator (`TotalRows` 0) — its results ride `Response.Tests` / `Regressions` / `Matrices`, and a regression's multiplicity fold still runs on the finished response. Predict sizes no `data` section for it (`dataRows` is 0 exact for any ungrouped, aggregation-free, window-free request) and costs memory on the streaming arm. A request with none of that work (empty; filters, attributes or features only) stays buffered. Gates: `TestNoAggregationRequests_StreamAndMatchBuffered` (whole response byte-identical to the forced-buffered arm), `TestPredict_Streamable_NoAggregationWork`, `TestExperimentStreaming_NoAggregationChunkShape`, `TestExperimentReadout_OneRequestStreams` (the readout as one request, weighted and unweighted, ≡ forced-buffered and ≡ the Compose oracle).

Response shaping (`return`) wraps the finished iterator at the facade (`Pulse.ProcessStream` → `returnshape.NewRowIter`; `ProcessStreamResult` goes through it): every row is a deep-cloned, pruned copy equal to the buffered shaped `data` element (an excluded `data` yields NO rows, so `ProcessStreamResult` emits no chunks); Components / Metadata are shaped COPIES, so the run keeps accumulating an excluded slot — except an excluded Components sub-part, which the compute plan never builds (see the Compute plan paragraph of `.claude/reference/response-components.md`); an excluded `components` is absent from every chunk, a kept one carries the plan so mid-stream chunks are rounded too; the `returned` marker rides the terminal chunk only (`StreamChunk.Returned`, iterator `Returned()`). Precision is wire-only — rows stay float64 and the shaped iterator's `MarshalRow` writes them (the `api process --stream` writer); `api compose --stream` writes each slot's already-pruned rows through `returnshape.MarshalRow`. Run-time warnings reach a stream through the iterator's `Warnings()` / `StreamTerminator.Warnings` and the CLI's trailing `{"warnings":[...]}` NDJSON record (`.claude/reference/response-components.md` (Run-time warnings in the envelope and the stream)); `PULSE_RETURN_PATH_UNMATCHED` is raised by the buffered shaping pass only, so a stream never reports it, and predict lists the Open includes it cannot resolve without data as `return.unresolved_includes` (#217, `predict-inspect.md` (Predict)). `return` participates in `Request.Hash`. No effective block ⇒ the service iterator untouched, byte-identical.

**Extension operators route on their DECLARED `Streamable` flag** (aggregators, groupers, attributes, tier-1 row tests; features on the returned value). `Streamable:false` runs buffered even when the value is online-capable; predict reads the same declaration. Merging follows the declarations too (`processing.CanMergeRequestWithExtensions`): an extension aggregator or grouper (single-key or fan-out) merges iff its registration declares `Mergeable` (probe-validated — `PULSE_EXTENSION_MERGEABLE_MISMATCH`), decimal128 targets included; extension filterers and `row_local` attributes merge as row-local operators; `two_pass` / `buffered` attributes, features, windows and tests never merge, so shard / decode parallelism runs those requests serially. A merged grouper folds its components state through `extend.MergeableGrouper.MergeState` (a no-op when it emits no components), and both reducers sum the (record, bucket) assignment count into `GroupedTail.Assignments` so a bucket-less grouper's `{total_n, n_null}` floor matches the serial exit. Fused crosstab: an extension AXIS grouper fuses iff it DECLARES `Streamable` (single-key; the adapter synthesizes the engine-only `KeyFor` from `KeyForRow` + the bound `Group.Field`) or `FansOut` — both probe-validated, so the declaration guarantees the keying sibling. **Deliberate change (cohort-facade E4-S1):** the gate used to probe the constructed grouper's interface, so `Streamable:false` + `KeyForRow` fused; it now runs buffered (output identical, only peak heap differs), because the no-execute predict arm can read only the declaration and both arms run one rule (`internal/crosstabfuse`). A built-in answers from the static keyability table, which still admits `GROUP_DATE`. a `two_pass` extension attribute declines fusion exactly like the built-in two-pass set (`ExtensionRegistry.TwoPassAttributes`), and an extension CELL aggregator fuses only when its registration declares a fusable `MarginReducibility` (summable / mean_reducible / independent; requires `Mergeable`, probe-validated — `PULSE_EXTENSION_MARGIN_REDUCIBILITY_MISMATCH`), read through `ExtensionRegistry.AggregatorMarginReducibility` (undeclared reads as recompute → buffered); the class gates admission only, since the fused walk feeds every margin its own accumulator. Detail: `.claude/reference/architecture.md` (Extension surface).

**Two-pass attributes run in DECLARED order on every scan.** The buffered arm runs `req.Attributes` one after another over the filtered set, so attribute i sees the final per-row output of every attribute before it. `processStreamingTwoPass` reproduces that with a pass plan (`internal/processing/two_pass_plan.go`): each two-pass attribute gets a prepass LAYER — 0 when its inputs (followed back through row-locals) are source fields, else one more than the deepest two-pass attribute it reads. Scan L evaluates, in declared order, only the attributes a layer-L `PrePass` depends on, folding each layer-L `PrePass` at its own declared position; then that layer `Finalize`s and `iter.Reset()` rewinds. The last scan emits every attribute in declared order and folds the aggregations. Filters gate every scan; row counts and filter counters are taken on scan 0 only. Inputs come from `Field`, `Target`, `Predictors`, a vector attribute's resolved `Fields` and its `params.fit_on` filterers' columns (field + expression identifiers — a `fit_on` on an earlier attribute's label puts the fitted attribute on a later layer), every identifier in an `ATTR_FORMULA` expression and, for an extension, its `FieldInputs` hook — an extension WITHOUT one (or an unparsable formula) is assumed to read every earlier attribute, which is correct but may add scans. Cost: a request whose two-pass attributes read only source fields keeps the historical two scans byte-for-byte; a two-pass fed by a row-local re-evaluates that row-local in the prepass (`BenchmarkProcessor_StreamingTwoPass`, 200K rows arm64: independent 62 ms unchanged, formula-fed 67 → 94 ms, two dependent layers 84 → 153 ms — the earlier figures were wrong answers). Before this, the prepass saw no attribute output at all and emission ran two-pass before row-local, so `ATTR_FORMULA x` → `ATTR_ZSCORE x` gave `AGG_MAX(zx) = 0` streaming against 1.689 buffered. Shard and decode-worker reducers never take two-pass requests (not mergeable), so the serial iterators carry this path; `ProcessStream` wraps `Process`. An `ATTR_FORMULA` calling `total(expr)` is a two-pass attribute (`internal/totalcall.Contains`; its prepass sums the argument over filtered rows, nulls skipped — Σw·x under a frequency weight on the slot, a probability weight refused (`weighting.AttributeClassOf`, survey-tables E1-S3)): it streams alone, buffers with groups/features, and shard / decode-worker / chain paths decline it as above. The fitted vector attributes (`ATTR_MAHALANOBIS`, `ATTR_PC_SCORE`, `ATTR_FACTOR_SCORE`, `matrix-and-vectors.md` (Virtual vectors)) are two-pass the same way: a cohort-wide co-moment fit over the filtered rows `fit_on` admits, never per group (grouped / feature requests buffer), every filtered row scored — unless bound to a prebuilt fit by `params.fit`, which makes the slot ROW-LOCAL (Vector fits, below); their fit warnings ride `Response.Warnings` on every arm (`AttributeWarnings`); a row-local attribute's warnings (`ATTR_SCALE_SCORE`'s out-of-range tally) ride the single-pass streaming and fused crosstab arms too, first and in declared order (`prependRowLocalWarnings`). Gates: `TestTwoPassOrder_*`, `TestTwoPass_DeclaredOrder_*`, `TestFormulaTotal_*`, `TestMahalanobis_*`, `TestPCScore_*`, `TestFactorScore_*`. Two-pass-ness is PER SLOT, never by type alone: an `ATTR_FORMULA` calling `total(expr)` and an `ATTR_VEC_DISTANCE` over `std_euclidean` / `mahalanobis` (`vectors.ComparisonFitted`; `attrRequiresTwoPassIn` reads a kind default off `Request.Vectors`, the crosstab fusion rule through `Facts.AttributeSlotTwoPass`) take the two-pass drive; the same type over a row-local metric streams in one pass, and any fitted slot bound to a prebuilt fit (`vectors.FitBound`) is row-local whatever its type.

## Projected buffered decode

Per-request field projection on the buffered decode iterator is **default-on** — output-transparent (byte-identical result, only faster and lighter per record). Opt out with `pulse.Options{DisableProjection: true}` or the `--no-project` CLI flag on `pulse api process` (v1: `pulse api process` only; `process-chain` / `compose` do not expose it yet). `pulse.Options.ProjectBufferedFields` is retained but deprecated — a harmless no-op; use `DisableProjection` to force full-record decode. Wiring: `svc.SetProjectBufferedFields(opts.ProjectBufferedFields || !opts.DisableProjection)`. `processing.NeededFields(req, schema, ext)` walks every request slot — Aggregations, Attributes (incl. expr-AST identifiers via `expr-lang/expr/parser` + `expr-lang/expr/ast` for `ATTR_FORMULA` / `FILTER_EXPRESSION`), Filterers, Groups, Windows, Features, Tests, Regressions, Sort.Field, and the whole Crosstab block (Rows, Columns, Cell, **MarginAggregations**). It also reads the built-in `Params` that NAME a field but do not live on the operator struct (`addAggParamFields`: `distinct_by`, `weight_field`, `numerator_field`, `denominator_field`; plus `stratify` / `target` on the two feature ops). A missed slot or a missed param is SILENT — the field is decoded onto no `Record`, `NumericValue` answers `ok=false` on every row, and the operator publishes a confident zero with `n_null` equal to the full admitted count. The iterator turns the retained set into an `encoding.DecodePlan` via `internal/encoding.BuildDecodePlan(schema, retained)`(retained)` (cached per-iterator); per-record hot path walks the plan via `RecordReader.ReadRecordReusedWithPlan` on BOTH arms — the reuse arm into one reused `Record`, the buffered arm into a FRESH `Record` per row (the map decoder `ReadRecordWithWidePlan` survives only as the defensive projection-without-plan fallback and for non-iterator callers). Plan segments: `SkipBytes{N}` (one `Seek` / `io.CopyN` discarding N bytes, coalescing contiguous unprojected non-bit-packed runs) and `DecodeFields{Fields, Indices}` — `Indices[k]` is the schema position of `Fields[k]`, recorded by the builder's own walk. **Index-keyed reuse.** The reuse decoders write through `encoding.IndexedReusableRecord` (`SetNumericAt` / `SetNullFieldAt` / `SetWideFieldAt`, keyed by position in `Schema.Fields`) whenever the record implements it — `*processing.Record` does — and fall back to the name-keyed `encoding.ReusableRecord` through an allocation-free shim otherwise; a record implementing both is always driven index-keyed. The position is never looked up by name: the full-stride path counts it during its schema walk, the plan path reads `DecodeFields.Indices`, the bitmap uses the bit index. A hand-built `DecodeFields` without `Indices` still decodes (positions recovered on a slow path; a field absent from the reader's schema is `ENCODING_INVALID`). The index is only meaningful against the schema the `RecordReader` was built with — the stream and shard iterators build record and reader over the same schema. **Positional `Record`.** `processing.Record` stores values, null marks and wide values positionally (a `[]float64`, three presence bit-planes — has-value / null / has-wide — and sparse wide slots for decimal128 / `set_*` fields only), so an absent (projected-out) field stays distinguishable from a present zero. Name → slot resolution goes through a `recordLayout` built once per binding: the full layout is cached per schema under a WEAK key (dropped when the schema is collected) and shared by every record over it; a projected layout (`processing.BindRecords(schema, keep)`, built once per iterator / parallel-decode context) stores only the retained fields densely, so a buffered projected record costs O(retained), not O(schema width). A name with no slot — attribute labels, feature/window outputs, a schema field outside the projection — lands in lazily-allocated overflow maps with the former map semantics. The map-taking constructors (`NewRecord*`) convert on entry and do not alias the caller's maps; they are the slow path. Invariants a later change must keep: `ClearForRow` clears the null and has-wide planes (not values) — on the reuse arm it now runs only when run-skip cannot keep the previous row (below) — a `SetNumericAt` position outside a projected layout falls back to the overflow side by name, and `Record.*At` positions are valid only for a record built over the reader's schema (full layout) or a projection of it (a position past the schema panics rather than landing on another field). **Run-skip.** On the reuse arm the decoders skip rewriting fields whose on-wire bytes repeat the previous row — a cohort sorted by its parent key repeats the whole parent block across that parent's child rows. Self-activating: no declaration, no metadata, no format change, and the buffered arm (a fresh `Record` per row) never takes it. The contract is split: the READER (`internal/encoding/reader_runskip.go`) keeps the previous row's bytes (the whole stride on the full path; on the plan path the ASSEMBLED row — every `DecodeFields` group read into one buffer before decoding, which also puts the bitmap in hand first) and passes keep=true to `encoding.RunSkipRecord.BeginRunRow(token, keep)` only when that baseline was decoded, successfully, under the same decode shape (full, or the same `*DecodePlan` — `keep` must stay fixed per plan), into the same record; the RECORD answers true only when the token is the reader that began its previous row, it has the full identity layout (projected and duplicate-name layouts always refuse), and no schema field was written since by anything but that reader's `*At` writes — every name-keyed schema-field mutator (`Set`, `SetNull`, `SetWide`, attribute injection onto a schema name, the name-keyed `SetNumeric`/`SetNullField`/`SetWideField`, `copyStateInto`'s target, a wide value that fell to the overflow side) calls `resetRun()`, and `ClearForRow` zeroes the owner. Off-schema writes (attribute labels, feature outputs) do NOT withdraw the record. A kept row clears only the overflow null/wide marks and the `AllValues` cache; the field walk compares value bytes only (8 bytes at a time over runs of narrow fields) and rewrites a changed field in full; `settleNulls` then visits the fields null on either row, re-signalling null, or clearing it and restoring the value (`ClearNullAt`). Result: after every row the record is identical, accessor for accessor, to a full decode — sorted and scattered, full and plan, across `Reset` two-pass rescans and shard boundaries (a new reader per shard, so the first row of each shard repopulates everything). Backoff: comparing costs a mispredicted branch per field on data that does not repeat, so the reader tallies rewrites over every 32 kept rows and, when more than half the fields changed, decodes the next 1024 rows without comparing before probing again. Bench (`BenchmarkJoinShape_RunSkip`, synthetic 95-field 12.5x-fanout join, 100K rows, in-memory payload, arm64): sorted full-stride 783 → 500 ns/row (1.57x), sorted 4-field projection 117 → 96; scattered full 860 → 754 and projection 114 → 100 — both gains on scattered data come from caching the per-reader stride layout (`strideLayout`, formerly recomputed per row), and the run-skip mechanism itself costs +1.8–2.6% there against a same-commit decode that never compares (without the backoff it was +40–50%). Field-level continuation on that fixture: 0.71 sorted, 0.21 scattered. Gates: `TestJoinShapeRunSkip_WorkCounts` (`make test`, deterministic COUNTS through a counting record on a 5,000-row sorted/scattered pair — sorted keeps every row after the first and writes 1 − continuation of a full decode's values; scattered compares ≤ 5% of rows and never writes more than a full decode, the structural net-loss bound) and `BenchmarkJoinShape_RunSkip` (`-bench` only, against a same-commit no-compare arm on the production record: sorted full ≥ 1.15x, measured 1.31–1.34x arm64 / 1.40–1.42x amd64-under-Rosetta; sorted 4-field projection ≥ 1.00x, measured 1.03–1.06x / 1.09x — two of its four fields change almost every row, write fraction 0.45, just under the backoff's 50% trip; scattered REPORTED, not gated: full 0.97–0.99x on both arches, projection break-even). Against the true pre-run-skip commit the scattered decode is still faster (stride-layout cache), so the loss is relative to the same-commit no-compare decode only. **Grouped (`0x02`) reuse decode.** Over a parent-grouped cohort the reuse decoders do not expand rows (`internal/encoding/group_decode.go`; the logical-stream expansion stays for the map decoders and whole-row consumers — byte-layout.md, Parent groups). The physical row is read whole (one `io.ReadFull` of the physical stride, even under a plan — it is small), every group index bounds-checked, and fields are written at their LOGICAL positions. The decode shape (full, or one plan, keyed by `*DecodePlan` identity exactly as run-skip keys it) is compiled once into a selection: row fields taking a value write, row fields surfacing a null (the plan's bitmap segment surfaces every nullable field `keep` accepts), and per group the members taking each. Plain records (`ClearForRow`) and fresh buffered records get every selected field written. A `RunSkipRecord` gets `BeginRunRow(token, prevValid && sameSink && samePlan)` — the backoff does NOT gate keeping, because an unchanged group index is a certain hit; it only decides whether ROW fields are byte-compared (compare → rewrite changed, as run-skip) or rewritten wholesale this row, with the null settle honouring which it did. A retained group whose index equals the committed row's is skipped outright; a changed one writes its value members from the entry cache, then re-signals null / `ClearNullAt` from the new and old entries' null bits. Entry cache per group, budget `groupEntryCacheBudget` (8 MiB per reader per decode shape, split across value-writing groups, allocated on first changed index): WHOLE mode when the whole dictionary fits (every value member's float64 + decoded `Decimal128`, slot = entry), else DECIMALS mode (only decimal members, direct-mapped — decimal decode is the one expensive member decode; caching cheap members in a thrashing table measured SLOWER than decoding them), else none. Work-count gate (`make test`): `TestGroupedDecode_MemberWriteCounts` — member value writes == Σ changes × members exactly, a row with no index change takes zero member-field writes, sorted ≈ 1.3 member writes/row of 14 members, fresh records decode each entry once (fills == distinct entries); correctness: `TestGroupedDecode_CacheModesMatchFlat` (every cache mode × sorted/scattered × full/plans × fresh/run-skip × backoff on/off), `TestGroupedDecode_RunSkipRowFields`, `TestGroupedDecode_ProjectionSkipsUnretainedGroups`, `TestGroupedDecode_InterleavedPaths`, `TestGroupedDecode_PositionalRecordParity` (production `Record`). Bench `BenchmarkGroupedDecode_ParentWidth` (arm64, 60K rows, 29-field child block, 12.5x fanout, parent 10/40/80 fields; ns/row 0x01 → 0x02): reuse sorted full 444→379, 543→433, 722→520; reuse scattered full 483→481, 1225→649, 2223→1006; buffered full sorted 553→464, 1241→723, 2138→997; 4-field projection flat at ~58 (reuse sorted), ~80 (reuse scattered), ~130 (buffered) for every width vs 145–345 on 0x01. Before this (expansion, E3-S2) 0x02 was 3–30% SLOWER than 0x01 on every arm. Remaining width dependence is inherent: a changed entry must reach the record (scattered ≈ every row), a fresh buffered record takes every retained member, and in sorted order each entry is decoded once on first touch. Past the budget (DECIMALS mode, thrashing) scattered w80 measured 2005 ns/row at a 1 MiB budget — still under 0x01's 2223, the cost of bounded memory. **Typed wide storage.** Wide values live UNBOXED — a lazily allocated `[]encoding.Decimal128`, and set-mask words (1 per narrow rung, 2 for `set_u128`, 4 for `set_u256`) stored bit-for-bit in the spare CAPACITY of the value slice past its length (so a set costs no extra allocation or slice header; every range over the values sees only the slots) — and the reuse decoders hand set masks over through the optional `encoding.TypedSetRecord` (`SetNarrowSetAt` / `SetWideSetAt`), so decoding a set field allocates nothing (boxing a mask ≥ 256 or any `SetMask` into `any` cost one heap allocation per set field per row; `BenchmarkCrosstabWideSetFanout` buffered 100K rows: peak heap 63.3 → 53.0 MB, 3 fewer allocs per row). `WideValue` still returns the stored dynamic type exactly (`Decimal128` / `uint64` / `SetMask`); a value a slot cannot hold typed AND exactly (another dynamic type, a mask past the rung) stays boxed on the overflow side — never truncated. Decimal128 needs no typed twin: a single-pointer struct boxes for free; its decode cost is `big.Int` / `big.Float` work, not boxing. **Null drops the wide value.** `SetNullField` / `SetNullFieldAt` (the decoder's bitmap-null signal) clear the wide value as the map decoder's `delete` did, so a later `Set` on a decoded-null field never resurfaces the decoded mask or decimal; public `SetNull` keeps its documented asymmetry. **Duplicate field names** (nothing on import rejects a repeated column) share ONE slot per name, whose metadata is the first occurrence (`Schema.Field(name)`): the last occurrence decoded wins the value and wide value, a null on any occurrence marks the name null — exactly the former map-key behaviour. Bench (`BenchmarkBufferedRecordFootprint`, synthetic 95 fields × 200K rows): retained heap 3.99 KiB → 1.04 KiB per buffered record full-decode, 408 → 144 B under a 4-field projection; buffered decode 4.1 µs → 1.1 µs per record. Bit-packed grouping: any contiguous `u4`/`packed_bool` run stays grouped — if any member retained the whole group becomes one `DecodeFields` (unretained still decoded to keep cursor aligned, map writes suppressed); otherwise the run folds into one `SkipBytes{K}`. Null-bitmap whole-or-skip: bitmap decoded once when any nullable field retained; else single `SkipBytes{N: Schema.BitmapByteSize()}`. Extension operators without `FieldInputs` widen retained set to `*` (full-coverage plan). **Windowed record rows retain the full row.** A windows-only request (windows, no group, no aggregation, no crosstab) emits the filtered records themselves as rows, each the FULL record plus the window columns, so `NeededFields` widens to `*` for exactly that shape (`windowsEmitRecordRows`) and gives up the projection win there; a window beside a group, an aggregation or a crosstab rides aggregated rows and still projects (`TestWindowRecordRows_ProjectionTransparent`, every `WIN_*`, single file and shard archive). Bench: synth 200-field × 100K-row Process drops from ~1.07s to ~155ms (~7×, 14× fewer allocs) on a 4-field projection. Detail: this file (above) is the projection/decode-plan home; `docs/src/internals/extension-points.md` (FieldInputs hook) carries the extension side, and CLAUDE.md "Byte-layout invariants" (Projected buffered decode) the contract summary. `skills/cohort-schema-design.md` deliberately carries NO decode-plan section — it is the schema-authoring surface, and a projection section there would push an already-over-budget skill further over for prose that belongs beside the execution modes.

## Parallel buffered Process

`pulse.Options.DecodeWorkers`, default `0` ⇒ `runtime.NumCPU()`. Bounded per-segment worker pool inside `Process` for single-file (non-shard) cohorts. Engages only when `service.canParallelDecode` accepts — `DecodeWorkers != 1`, `recordCount >= service.parallelDecodeRecordThreshold` (currently `100_000`), single-file (sharded routes through `ShardWorkers`), `resolveRealPath` succeeds (mmap available), `processing.CanMergeRequestWithExtensions(req, schema, exts)` is true. Ineligible falls through to serial `scanIter`. Components parity is the ShardWorkers paragraph above verbatim — same `shardPartial`, same merge, same emission set; `ShardCount` stays 0 because a single-file run is not a shard run.

Crosstab is intentionally NOT exercised today — `validateCrosstabSpec` requires `req.Aggregations` empty so crosstab requests always fail `CanMergeRequest`. This infrastructure benefits future non-crosstab buffered Process calls.

Segments stride-aligned at record boundaries over the mmap'd record region AND block-aligned: every boundary is a multiple of `linalg.MergeBlockSize` (4096 records; `blockAlignedSegments` spreads the ceil(N/4096) blocks evenly, the ragged tail lands in the last segment, and workers beyond the block count get an empty segment that never reaches its factory), and `DecodeCallbackFactory(workerIdx, startRecord, recordCount)` hands each worker its segment's ABSOLUTE start record so a block-keyed reducer can key row `startRecord+i` to block `(startRecord+i)/4096` and fold blocks through `linalg.MergeTree`; same `DecodeFields`/`SkipBytes` plan shared read-only across workers; each worker owns a `shardPartial`; partials fold in worker-index order via `mergeShardPartials` + `finalizeMergedPartial`. Byte-equal vs serial; Welford within ULP via Chan-Welford. Surface: `internal/service/parallel_decode.go`, `internal/service/parallel_reduce.go`. See "Mode index" (Parallel shards / parallel buffered Process) below for the knob, and CLAUDE.md "Build / Env" (Knobs) for the threshold; the mechanics above are the detail home.

## Cooperative cancellation (ctx polling)

Every SERIAL per-record loop polls the caller's ctx through `processing.CtxPoller` (`internal/processing/ctxpoll.go`): `Poll()` reads `ctx.Err()` on the first row and then once every `processing.CtxPollInterval` (4,096) rows — a counter mask, inlined, no allocation — so a pre-cancelled ctx stops the loop before its first fold and a mid-run cancel within 4,096 rows. The polled loops: the buffered materialize loop in `Processor.Process`; the serial streaming scans `processStreaming` / `processStreamingGrouped` / `processStreamingTwoPass` (feature pre-pass, every two-pass layer scan and the emission scan included); the fused crosstab loop `RunCrosstabFused`; the buffered crosstab drain `service.materializeRecords` (serial decode AND the joined crosstab's `HashJoinIterator` drain); and the join build loop in `service.openJoinStream`. One poller per function, so a multi-pass scan keeps one cadence across `Reset`. **The ctx error is returned UNCHANGED** — `context.Canceled` / `context.DeadlineExceeded` itself, never a coded error and never wrapped; mapping an INNER deadline (`RequestTimeout`) to `PULSE_LIMIT_EXCEEDED` is the entry point's job via `context.Cause`, not the loop's. The parallel arms already poll on their own: `parallelDecodeMmap` and the per-shard reduce read `ctx.Err()` every record. The facet scans (`Service.Facet`'s numeric stream, `FacetSchema`'s accumulator pass) poll too. Not polled: the in-memory passes `processRecords` runs over an already-materialized slice. Tests: `TestCtxPoll_CancelStopsEveryLoop`, `TestCtxPoll_PreCancelledStopsAtFirstRow`, `TestCtxPoller_Cadence` (`internal/processing/ctxpoll_test.go`); `TestCtxPoll_MaterializeRecords`, `TestCtxPoll_BufferedCrosstabCancelled`, `TestCtxPoll_JoinBuildCancelled` (`internal/service/ctx_poll_test.go`). A new serial per-record loop adds a poll and a case to those tables. Consequence for FailFast `ComposeParallel`: a still-running sibling now stops with `context.Canceled`, so the reported error is the lowest-index failure that is NOT a sibling cancellation (`failFastWinner`, `internal/service/compose_parallel.go`; `TestFailFastWinner`) — a caller-done ctx keeps the plain lowest-index failure. A ctx done before every slot LAUNCHED, with no slot error, returns the ctx error — never a "successful" response with unrun `nil` slots.

## Request timeout (`Limits.RequestTimeout`)

An inner deadline on one top-level call, applied by `Service.BoundRequest` (`internal/service/request_timeout.go`) through `context.WithTimeoutCause` at every entry: `Process`, `ProcessStream` (via its `Process`), `Facet`, `FacetSchema`, `Compose` / `ComposeParallel` (the WHOLE call) and `ProcessChain` (the whole call); the facade's `ProcessStreamResult` bounds its run AND its drain. Default unlimited ⇒ the caller's ctx untouched, no deadline. A nested entry bounds again with the same duration, starting later, so `WithTimeoutCause` keeps the outer deadline and cause — the outermost call owns the budget. The loops stop on it like any ctx (section above); each entry then maps through `MapRequestTimeout(ctx, err)`: ONLY when `context.Cause` is the RequestTimeout cause does the error become a bare `PULSE_LIMIT_EXCEEDED` `{limit: request_timeout, configured, observed: elapsed ns}` (no partial result; never slot- or stage-located). A caller's own deadline or cancel passes through as `context.DeadlineExceeded` / `context.Canceled` — `WithTimeoutCause` under an earlier parent deadline keeps the parent's cause — and so does `ComposeOptions.PerRequestTimeout`, the unchanged per-slot knob. `ProcessStreamResult`: a trip during the buffered run returns the coded error up front; one mid-stream ends `StreamErrored` with it (`StreamCancelled` stays the caller's).
