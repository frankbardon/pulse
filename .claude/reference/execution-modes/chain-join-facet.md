# Execution modes — ProcessChain, pushdown hash join, facet endpoints

Per-topic slice of the execution-modes reference. Index (Mode index + section map): `.claude/reference/execution-modes.md` — load it first, then only the slice(s) your engine work touches.

## ProcessChain

`pulse.ProcessChain`, `pulse_process_chain`, `pulse api process-chain`. Source-rooted linear chain: stage 0 runs against `ChainRequest.Cohort`; each later stage receives the prior `Response.Data` as a synthesised in-memory cohort (grouper keys → `categorical_u32`, aggregator outputs → `f64`). Skill: `skills/process-chain.md`.

**The synthesised schema is ONE builder, `vectors.ChainStageSchema(req, in, kinds)`.** Runtime, predict (`stage_schemas`), the code-column walk and the whole-chain overlay all call it with the stage's OWN input schema (stage 0: the gate schema; later: the one synthesised before it), because an expanding vector aggregation (`params.expand`) writes no label column, only `<label>[<elem>]` element columns.

- An expanding slot on a feeding stage is admitted; a non-expanding array-valued (`array_valued`) or non-scalar (`non_scalar`) one is refused (`mergegate.StageArrayValuedRefusal`). A later stage naming the bare label is an unknown field on both sides. A `fields` entry naming a schema field exactly is that literal even with `[` in it.
- An aggregation column colliding with an earlier one is `PROCESSING_CONFIG {column, aggregation_index, aggregation}` from the shared builder.
- **Lazy rows.** A later stage reads the previous rows through `processing.ChainRowIterator`: every categorical key resolves up front in row order, and each record is built when the scan reaches its row and never kept (materializing them all held one record per row for the whole stage — `TestGroupMemory_ChainRowIteratorHoldsNoRecords`). The iterator reads a NaN f64 cell (an unanswered element, any undefined figure) as NULL, so the next stage's `n_null` counts it.

**Mergeable-only.** Every stage passes `internal/mergegate.ChainRefusal` — the same rule as `mergegate.MergeRefusal` (mergeable aggregators / groupers, streamable filterers, row-local attributes, no built-in aggregator over `decimal128`; `total()` admitted two-phase — `execution-modes/parallel-totals.md` (ProcessChain stages)). Every mergeable built-in emits one f64 per row, so `AGG_MODE` (categorical: the dictionary index, not the label), `AGG_MODE_COUNT` and `AGG_FREQUENCY` are admitted. Runtime and predict call it over the same extension registry, so both refuse with one `PULSE_CHAIN_NOT_MERGEABLE "chain stage is not mergeable: <reason>" {stage_index, stage_name}` (`TestChainGate_ValidatorMatchesRuntime`; a nil extension snapshot in predict is extension-blind). Both sides gate each stage after smart defaults (see Time zones → Predict and the validators).

**A forwarded code is judged as the code it is.** Stage 0 refuses a numeric reader over a categorical field, but a later stage's synthesised schema types the forwarded column `f64` — so without this rule `AGG_SUM` over an upstream `AGG_MODE`-over-categorical column silently summed dictionary indexes. `descriptor.ChainStageCodeReaderRefusals` judges each aggregator slot (`field` and the params slots the field-accept table rows) naming a column in the stage's `ChainCodeColumns` as the type it is a code of: `PULSE_FIELD_TYPE_UNSUPPORTED`, the field-accept details + `forwarded_code: true`, located `details.stage`, right after the limits pre-flight on both sides. The allowlist is the field-accept table's: a categorical code is refused by every row refusing a categorical (MIN / MAX too); a `packed_bool` code stays legal for SUM / AVERAGE (a 0/1 mean is a proportion); COUNT / NULL_COUNT stay legal; extension aggregators are untabled, but one declaring `EmitsInputValue` forwards code-ness like `AGG_MODE`. Smart defaults stay schema-typed: an untyped slot over a forwarded code defaults to `AGG_SUM` and is refused.

**A joined stage 0 resolves its defaults and runs its gate against the JOINED schema** (the right side's header only; falling back to the bare cohort when the right side does not open or the join collides, so Process raises the join's own refusal). Against the bare cohort, an untyped aggregation over a right-side field would stay untyped and be refused as not mergeable.

**Only stage 0 may join.** A later stage's `Joins` is `PULSE_CHAIN_STAGE_JOIN {count, stage, stage_name}` (`mergegate.StageJoinRefusal`), raised first in that stage on both sides.

**No stage may carry `Request.Crosstab`.** `mergegate.ChainRefusal` refuses it first, whatever else the stage carries — `PULSE_CHAIN_NOT_MERGEABLE` with reason `mergegate.CrosstabStageReason` — because a crosstab answers a matrix, never the rows the next stage reads. So no ProcessChain reaches the whole-chain overlay MATRIX arm or a MATRIX-vs-SERIES `PULSE_OVERLAY_CHAIN_STAGE_SHAPE_DIVERGENT`; that code stays for caller-built responses through `processing.ApplyChainOverlays`.

**A stage's own `Request.Overlays`** is judged up front by `descriptor.ChainStageOverlayRefusal` on both sides — `.claude/reference/execution-modes/overlays-matrix-kinds.md` (Spec refusals — one rule per host).

**A stage's label bindings apply on every stage.** A later stage's `labels` are judged over the synthesised stage schema (after the limits pre-flight) and applied to the stage's rows — the stage-0 path. A forwarded group key is `categorical_u32` there, so it relabels; an aggregation output (f64) is `PULSE_LABEL_FIELD_NOT_CATEGORICAL`. A replace-mode binding on a feeding stage rewrites the key values the next stage reads.

- **Auto labels (`Options.AutoLabels`) are injected on EVERY stage**, over the synthesised schema, so a forwarded categorical key is labelled like stage 0's (augment: the raw key gets its `<field>_label` sibling). A `replace` default is NOT re-injected on a key an earlier stage already bound in `replace`: those values are labels already and a second pass only misses (`PULSE_LABEL_LOOKUP_MISS`).
- A caller binding that reaches no surface of a stage's response warns `PULSE_LABEL_NOT_APPLIED` on that stage (`skills/label-display.md`).

Every coded refusal a stage raises is located `details.stage`, and predict-chain runs the request body per stage (`.claude/reference/predict-inspect/inspect-and-roots.md`; `TestChainPredict_StageBodyMatchesRuntime`). Failures: `PULSE_CHAIN_NOT_MERGEABLE`, `PULSE_CHAIN_STAGE_JOIN`, `PULSE_CHAIN_EMPTY`. Predict: `descriptor.ValidateChainWithOptions`; it checks `MaxChainStages` right after the empty check and reports every stage's limit findings located `details.stage` — stage ≥ 1 never a certain memory finding (`.claude/reference/predict-inspect/limits.md`).

**Response shaping.** Each stage's `return` resolves up front beside its multiplicity and is APPLIED by `Pulse.ProcessChain` only after the whole chain and its overlay barrier finished — a stage excluding `data` still feeds the next stage; `Final` aliases the last stage, so it follows that stage's plan. No chain-level block. Each stage also COMPUTES under its own plan; a chain overlay reads stage data and crosstab payloads only, so it vetoes no skip.

**Dual-slot overlays.** Per-stage overlays ride `Stages[i].Request.Overlays`; whole-chain overlays ride `ChainRequest.Overlays []*ChainOverlaySpec` (`Ref StageRef` + `Target StageRef`) and produce `ChainResponse.Overlays` after every stage finalises, through `processing.ApplyChainOverlays`; per-stage overlays are left untouched. An unresolved Target / Ref stage is a fatal `PULSE_OVERLAY_TARGET_UNKNOWN` / `PULSE_OVERLAY_REFERENCE_UNKNOWN` (one rule, `overlayhost.ResolveStageRef`, both sides). `PULSE_OVERLAY_CHAIN_STAGE_SHAPE_DIVERGENT` is warning-class on BOTH predict-chain (envelope warning, the chain stays `Valid`) and runtime (empty layer plus one `OverlayLayer.Warnings` entry), never escalated by `Strict` at runtime.

## Pushdown hash join

`Request.Joins []*JoinSpec`. Exactly one inner join per Request: `PULSE_JOIN_TOO_MANY` (one rule, `descriptor.JoinCountRefusal`, runtime and predict) and `PULSE_JOIN_KIND_NOT_IMPLEMENTED`. Skill: `skills/join-design.md`.

- **In-memory build** (no spill), bounded by `Options.Limits.MaxJoinBuildRows`: the right side's header-only count is read after the join-key rule and refused `PULSE_LIMIT_EXCEEDED` before the build decodes a record, with an in-loop decode-count backstop; predict grades the same count `certain` (`predict-inspect.md`).
- **Preflight before the build.** Both join hosts hand `openJoinStream` a `preflight` hook that runs defaults, zones, field references and limits on the joined schema AFTER the join-key rule and the build-row check and BEFORE the build decodes a record, so an unknown field or a `MaxEstimatedMemory` breach costs no decode. `MaxEstimatedMemory` reads the left plus the right header count; the memory model assumes at most one right match per left row.
- **Schema.** `JoinedSchema(left, right, spec)` is `left.Fields + right.Fields` with optional `spec.As` prefix; non-prefixed collisions → `PULSE_JOIN_FIELD_COLLISION`.
- **Key compatibility** (`encoding.JoinKeyTypesCompatible`, inside the one join-key rule): identical types match; categorical of any width match; the unsigned-int / float / date numeric family is interchangeable; `decimal128` matches only `decimal128`.
- **`decimal128` keys compare on their exact 128-bit mantissa bytes**, not the `Float64(scale)` echo — otherwise two decimals closer than float64's spacing silently share a key.
- **Exact `u64` join keys.** A `u64` column keys on its EXACT stored word, formatted with `FormatUint` only at or above 2^53; below it the float echo is exact and the key text stays `FormatFloat`'s, so smaller keys are byte-identical. Every left-side iterator kind and the right-side build copy carry the exact word. `u64` ↔ `f32` / `f64` is REFUSED (`PULSE_JOIN_TYPE_MISMATCH`, `details.reason` `"u64_float_key"`) — exact or nothing, since a float holds no exact integer above 2^53.

**Crosstab over a join.** `Request.Crosstab` with its one `JoinSpec` crosstabs the JOINED row stream: the service builds the same stream the plain join consumes, applies defaults / zones / labels against the joined schema, materialises the joined records and runs the buffered crosstab. Axes and cell may name `As`-prefixed right fields; an unmatched left row reaches no cell, margin, auxiliary or Components count; a 1:N right match counts once per joined row everywhere. **Always buffered:** `CanFuseCrosstab` declines any `req.Joins` (`"joins force buffered"`) before every other rule, because the gate is handed the LEFT schema; the crosstab projection and parallel segment decode are single-cohort optimisations and do not apply. Predict validates against the joined schema, so predict and runtime agree (`TestCrosstabJoin_HonoursJoinOnBothArms`).

## Facet endpoints

`pulse.Facet(ctx, path, field)` — simple distinct values (categorical fast path through the dictionary; numeric streams the file). `pulse.FacetSchema(ctx, *FacetRequest)` — rich multi-field: counts (sorted desc by count, ties asc by value), null tallies, Welford numeric stats, optional `NumericPercentiles` (forces a buffered per-field sort), `IncludeHistogram` with caller-supplied `HistogramRange` (single-pass), `DiscreteTopK` (`TruncatedAt` warning), `AdditiveFields` contribution counts, and `FacetRequest.Overlays` (the FACET-host kinds). CLI `pulse api facet` uses the simple shape for one `--field` and no other option; `--request`, a second `--field` or any rich-only flag selects `FacetSchema` (`internal/cli/api.go`). Skill: `skills/facet-design.md`.

- **Overlays.** Dispatch runs at the buffered `FacetSchema` exit, attaching layers to `FacetResult.Overlays` in spec order, and recurses `FacetSchema` against `Ref.Population.Cohort` for the population view (strips filterers / labels / additive; cycle-safe). `FacetSchema` is structurally buffered, so even the streamable FACET kinds run there. The Ref / Scope / Level contract (`overlayhost.FacetSpecRefusal`) and the per-kind host-arm gate (`overlayhost.FacetHostArmRefusal`) are one rule on both sides, judged before the population runs.
- **Field types.** `descx.FacetFieldTypeRefusal` is one rule for predict and `FacetSchema` (before the scan): a `set_*`, `vec_*` or `datetime` faceted or additive field is `SERVICE_VALIDATION` "facet does not support field type <type>". `packed_bool` values are `"1"` / `"0"` (Sample's spelling) on both endpoints. The simple `Facet` lists a `set_*` field's dictionary (no scan) and refuses a `vec_*` field (`descx.FacetTypeUnsupported`).
- **Resource limits.** `FacetSchema` runs `descx.FacetLimitRefusal` right after the field-reference pass: a set `MaxEstimatedMemory` below `EstimateFacetMemory` (one bucket per `Fields` + `AdditiveFields` entry, per-value state for a dictionary-less field, doubled under `numeric_percentiles`) refuses before the scan. The simple `Facet` runs the same pre-flight on its streamed (numeric) path; its categorical fast path reads no record, so it has none. `PredictFacet` reports `FacetLimitFindings` — a `possible` `MaxGroups` bound (the largest faceted field's dictionary size, 2 for `packed_bool`, a labelled integer-coded field's code range, clamped by the header count) and the `certain` memory estimate; the pre-flight refuses with the first certain one.
- **Labelled integer codes.** An augment label binding on a `u4`–`u32` faceted field (`descx.FacetCodedField`, one rule for predict and runtime) routes it through the categorical accumulator: discrete per-code counts keyed by the decimal code, the categorical order / `DiscreteTopK` / `MaxGroups`, a `<field>_label` sibling; percentiles / histogram warn not-meaningful; the population facet inherits the choice for its one field; KS is refused. Unbound stays numeric.
