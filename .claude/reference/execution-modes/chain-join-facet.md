# Execution modes — ProcessChain, pushdown hash join, facet endpoints

Per-topic slice of the execution-modes reference. Index (Mode index + section map): `.claude/reference/execution-modes.md` — load it first, then only the slice(s) your engine work touches.

## ProcessChain

`pulse.ProcessChain`, `pulse_process_chain`, `pulse api process-chain`. Source-rooted linear chain. Stage 0 against `ChainRequest.Cohort`; subsequent stages receive prior `Response.Data` as synthesised in-memory cohort (grouper keys → categorical_u32, aggregator outputs → f64). **The synthesised schema is ONE builder, `vectors.ChainStageSchema(req, in, kinds)`** — runtime `processing.ChainOutputSchema`, predict `synthChainSchema` / `chainPredictedOutputFields` (`stage_schemas`), the code-column walk (`ChainCodeColumns`' `next(req, in)`) and the whole-chain overlay's `ChainStageInputSchema` all call it with the stage's OWN input schema (stage 0: the gate schema; later: the one synthesised before it, threaded as `priorIn`), because an expanding vector aggregation (`params.expand`) writes no label column, only `<label>[<elem>]` element columns whose members resolve there (U30 E4-S3). `mergegate.StageArrayValuedRefusal` therefore admits an expanding slot on a feeding stage (`vectors.AggregationExpands`) and still refuses a non-expanding array-valued (`array_valued`) or non-scalar (`non_scalar`) one; a later stage naming the bare label is an unknown field on both sides. `RecordsFromChainRows` reads a NaN f64 cell (an unanswered element, any undefined figure) as NULL — the wire's `null` — so the next stage's `n_null` counts it. A `fields` entry naming a schema field exactly is that literal even with `[` in it, so a later stage's vector over `m[b1]` resolves (and re-resolves after the slot rewrite). An aggregation column colliding with an earlier one is `PROCESSING_CONFIG {column, aggregation_index, aggregation}` from the shared builder on both sides (unreachable past the field-ref walk's `SERVICE_VALIDATION` output-label collision today). Gates: `TestChain_ElementColumnsFeedNextStage`, `TestChain_ElementColumnRefusalsParity`, `TestChain_ElementColumnsThroughThreeStages`, `TestStageArrayValuedRefusal`, `TestChainStageSchema`, `TestRecordsFromChainRows_NaNIsNull`, `TestResolveSpec_ExactFieldNameBeatsGlob`. Mergeable-only at v1: every stage passes `internal/mergegate.ChainRefusal` — the merge rule `CanMergeRequestWithExtensions` delegates to (`mergegate.MergeRefusal`: mergeable aggregators / groupers, streamable filterers, row-local attributes, no built-in aggregator over `decimal128`) — every mergeable built-in emits one f64 per row, so `AGG_MODE` (categorical: the dictionary index, not the label), `AGG_MODE_COUNT` and `AGG_FREQUENCY` are admitted. The runtime calls it as `processing.ChainRefusal` over the `ExtensionRegistry`, `ValidateChainWithExtensions` over the `ExtensionsSnapshot` (`ValidateChain` is extension-blind and flags a `Mergeable` extension aggregator the runtime admits), so both refuse with one `PULSE_CHAIN_NOT_MERGEABLE "chain stage is not mergeable: <reason>" {stage_index, stage_name}` (`TestChainGate_ValidatorMatchesRuntime`). Both sides gate each stage after smart defaults (see Time zones → Predict and the validators). **A joined stage 0 resolves its defaults and runs its gate against the JOINED schema** (`Service.chainStage0Schema` / predict's `joinedDefaultsSchema`: the right side's header only, falling back to the bare cohort when the right side does not open or the join collides, so Process raises the join's own refusal) — the schema Process executes it against. Before U46 E4-S6 both sides defaulted against the bare cohort: an untyped aggregation over a right-side field stayed untyped, the gate refused it `PULSE_CHAIN_NOT_MERGEABLE` ("aggregator  is not mergeable"), and neither the next stage nor a whole-chain overlay could name its `TYPE_field` label (`TestChainSeriesOverlay_JoinedStageDefaultedLabel`). **Only stage 0 may join:** a later stage's `Joins` (which the runtime used to drop silently) is `PULSE_CHAIN_STAGE_JOIN {count, stage, stage_name}` (`mergegate.StageJoinRefusal`), raised first in that stage — before its defaults, zones and gate — on both sides (`TestChainStageJoin_RefusedBothSides`). **No stage may carry `Request.Crosstab`** (U30 E7-S4): `mergegate.ChainRefusal` refuses it first, whatever else the stage carries, `PULSE_CHAIN_NOT_MERGEABLE` with reason `mergegate.CrosstabStageReason` and the usual `{stage_index, stage_name}`, on both sides — a crosstab answers a matrix, never the rows the next stage reads. Before, a later stage beside aggregations dropped the crosstab and its overlays silently, a stage 0 beside aggregations hit Process's `PULSE_CROSSTAB_CONFLICTS_WITH_GROUPS` predict-chain never raised, and a crosstab-only stage was refused as "no aggregator" (`TestChainStage_CrosstabRefusedBothSides`). So no ProcessChain reaches the whole-chain overlay MATRIX arm (a stage whose response carries a crosstab matrix; `OVERLAY_INDEX_VS_STAGE` / `_DELTA_VS_STAGE` matrix payloads) or a MATRIX-vs-SERIES `PULSE_OVERLAY_CHAIN_STAGE_SHAPE_DIVERGENT`: that code stays, unreachable through the public `ProcessChain` surface, for a future crosstab-stage feature (owner, U30 E7-S5; reachable only through `processing.ApplyChainOverlays` over caller-built responses). **A stage's own `Request.Overlays`** is judged up front by `descriptor.ChainStageOverlayRefusal` on both sides (wrong slot, wrong shape, the shared Ref / Scope rule — on a SCALAR stage every Process kind, U30 E7-S5; located by `details.stage`) — `.claude/reference/execution-modes/overlays-matrix-kinds.md` (Spec refusals — one rule per host). **A stage's label bindings apply on every stage (U35 E3-S2, #201c / #254):** a later stage's `labels` used to be dropped silently (an unknown table ran clean); `runChainStageChild` now judges them over the synthesised stage schema (`validateProcessLabels`, after the limits pre-flight) and applies them to the stage's rows (`buildAndApplyLabels`) — the stage-0 binding path. A forwarded group key is `categorical_u32` there, so it relabels; an aggregation output (f64) is `PULSE_LABEL_FIELD_NOT_CATEGORICAL`, as on stage 0 — no binding kind needed a refusal. A replace-mode binding on a feeding stage rewrites the key values the next stage reads (as stage 0's always did). **Auto labels (`Options.AutoLabels`) are injected on EVERY stage (U44 #460, owner kept "every stage"):** `runChainStageChild` calls `applyAutoLabels` over the synthesised schema before `validateProcessLabels`, so a forwarded categorical key is labelled like stage 0's (augment: the raw forwarded key gets its `<field>_label` sibling). Replace mode is pinned: a `replace` default is NOT re-injected on a key an earlier stage already bound in `replace` (explicit or injected) — `chainAutoLabelFields` drops it from the stage's `restrictTo` set — because those forwarded values are labels already and a second pass only misses (`PULSE_LABEL_LOOKUP_MISS`); results are unchanged (`TestChain_AutoLabelsEveryStage`). A caller binding that reaches no surface of a stage's response warns `PULSE_LABEL_NOT_APPLIED` on that stage (the Process rule; `skills/label-display.md`). Every coded refusal a stage raises is located `details.stage` (`locate`), and predict-chain runs the request body per stage (`.claude/reference/predict-inspect/inspect-and-roots.md`); gates `TestChain_StageLabelsApplied`, `TestChainPredict_StageBodyMatchesRuntime`. Failures: `PULSE_CHAIN_NOT_MERGEABLE`, `PULSE_CHAIN_STAGE_JOIN`, `PULSE_CHAIN_EMPTY`. Predict equivalent: `descriptor.ValidateChain`; it checks `MaxChainStages` right after the empty check and reports every stage's limit findings located `details.stage` — stage ≥ 1 never a certain memory finding (U35 E7-S1, `.claude/reference/predict-inspect/limits.md`). Surface: `types/chain.go`, `internal/processing/chain.go`, `internal/service/chain.go`, `internal/descriptor/chain.go`, `internal/descriptor/capabilities_chain.go`.

Response shaping: each stage's `return` resolves up front beside its multiplicity (`details.stage`) and is APPLIED by `Pulse.ProcessChain` (`returnshape.ApplyChain`) only after the whole chain and its overlay barrier finished — a stage excluding `data` still feeds the next stage; `Final` aliases the last stage, so it follows that stage's plan. No chain-level block. Each stage also COMPUTES under its own plan (stage 0 inside `Process`, every later stage via the plan `processChain` puts on the `runChainStage` context); a chain overlay reads stage data and crosstab payloads only, so it vetoes no skip.

Dual-slot overlay design: per-stage overlays ride `ChainRequest.Stages[i].Request.Overlays`; whole-chain overlays ride `ChainRequest.Overlays []*ChainOverlaySpec` and produce `ChainResponse.Overlays []*OverlayLayer` after every stage finalises. `ChainOverlaySpec` carries `Ref StageRef` + `Target StageRef`. Whole-chain barrier: `service.applyChainOverlays` runs after the stage loop, dispatching through `processing.ApplyChainOverlays`. Per-stage `Stages[i].Overlays` is left UNTOUCHED. The dedicated codes are live: `PULSE_OVERLAY_TARGET_UNKNOWN` / `PULSE_OVERLAY_REFERENCE_UNKNOWN` are fatal coded errors for an unresolved Target / Ref stage (one rule, `overlayhost.ResolveStageRef`, on both sides: Index and Name both set, neither on a Ref, out of range, unknown name), and `PULSE_OVERLAY_CHAIN_STAGE_SHAPE_DIVERGENT` is warning-class on BOTH predict-chain (envelope warning, the chain stays `Valid`) and runtime (empty layer plus one `OverlayLayer.Warnings` entry), never escalated by `Strict` (U46 E4-S9). See `skills/process-chain.md`.

## Pushdown hash join

`Request.Joins []*JoinSpec`. v1 = exactly one inner join per Request (`PULSE_JOIN_TOO_MANY` — one rule, `internal/descriptor.JoinCountRefusal`, applied by runtime `Process` before its crosstab / join dispatch and by predict and the validators; `PULSE_JOIN_KIND_NOT_IMPLEMENTED`); in-memory build (no spill; `PULSE_JOIN_SPILL_DIR` + `PULSE_JOIN_MAX_MEMORY_BYTES` reserved), bounded by `Options.Limits.MaxJoinBuildRows`: `openJoinStream` reads the right side's header-only count (`Service.CountRecords`) after the join-key rule and refuses `PULSE_LIMIT_EXCEEDED` before the build decodes a record, with an in-loop decode-count backstop; predict grades the same count `certain` (`predict-inspect.md`). Both join hosts hand `openJoinStream` a `preflight` hook that runs their defaults, zones, field references and limits pre-flight on the joined schema (`processing.JoinedSchema`) AFTER the join-key rule and the `MaxJoinBuildRows` check and BEFORE the build decodes a record — so an unknown field or a `MaxEstimatedMemory` breach costs no decode on either side (the build side was decoded first until U19 E2-S3). `MaxEstimatedMemory` reads the left header count plus the right one the build check reads (counted once when either limit is set, never under both defaults); the memory model assumes at most one right match per left row for the joined rows a buffered arm holds. `JoinedSchema(left,right,spec)` produces `left.Fields + right.Fields` with optional `spec.As` prefix; non-prefixed collisions → `PULSE_JOIN_FIELD_COLLISION`. Key compatibility (`internal/encoding.JoinKeyTypesCompatible`, inside the one join-key rule `JoinKeysRefusals` — see Predict and the validators): identical types match; categorical of any width match; unsigned-int/float/date numeric family interchangeable; decimal128 rejects cross-type. `decimal128` keys compare on their **exact 128-bit mantissa bytes**, not the `Float64(scale)` echo — otherwise two decimals closer than float64's spacing share a key; safe to special-case because `decimal128` is admitted only against `decimal128`. **Known limit:** a `u64` key above 2^53 rides the `float64` echo the rest of the numeric family uses, so two ids rounding to one float join as equal — unfixed, it needs the whole unsigned-int/float/date family renormalised together (relocated from `skills/join-design.md` for budget).

**Crosstab over a join.** `Request.Crosstab` with its one `JoinSpec` crosstabs the JOINED row stream. `Service.processCrosstab` branches to `processCrosstabWithJoin` before opening the cohort; it builds the identical stream `processWithJoin` consumes (the shared `Service.openJoinStream` — right side materialised + hashed, left wrapped in `HashJoinIterator`), applies defaults / zones / labels against the joined schema, materialises the joined records and runs the buffered `RunCrosstab`. Consequences: axes and cell may name `As`-prefixed right fields; an unmatched left row reaches no cell, margin, auxiliary or Components count; a 1:N right match counts once per joined row everywhere (`CellCounts`, margin counts, `GrandTotalCount`, `IncludedRecords`). Always buffered — `CanFuseCrosstab` declines any `req.Joins` (`"joins force buffered"`, checked before every other rule because the gate is handed the LEFT schema), so `FusedCrosstabState.AssertCanFuse`'s join guard stays an unreachable invariant; the crosstab projection and parallel segment decode are single-cohort optimisations and do not apply. Predict already validates the crosstab against the joined schema (`predictJoinedSchema`), so predict and runtime agree. Before E4-S5 the fused arm returned `PROCESSING_INTERNAL` "gate should have rejected" and the buffered arm silently crosstabbed the bare LEFT cohort (unmatched rows included, a right-side axis field bucketed as null). Gates: `TestCrosstabJoin_HonoursJoinOnBothArms` + `TestCrosstabJoin_LeftOnlyAxesStillJoin` (`internal/service`, against an independent non-crosstab join expectation and hand-computed figures, fused-enabled and -disabled), `TestCrosstabJoin_PredictAndRuntimeAgree` (root), `TestCanFuseCrosstab_JoinsForceBuffered`.

Surface: `types/join.go`, `internal/processing/join.go`, `internal/service/join.go`, `internal/descriptor/join.go`, `internal/descriptor/capabilities_join.go`. See `skills/join-design.md`.

## Facet endpoints

`pulse.Facet(ctx, path, field)` simple distinct-values (categorical fast path through dict, numeric streams file). `pulse.FacetSchema(ctx, *FacetRequest)` rich multi-field — counts (sorted desc by count, ties asc by value), null tallies, Welford online numeric stats, optional `NumericPercentiles` (forces buffered per-field sort), optional `IncludeHistogram` with caller-supplied `HistogramRange` (single-pass), optional `DiscreteTopK` (`TruncatedAt` warning), optional `AdditiveFields` contribution counts, optional `FacetRequest.Overlays []*OverlaySpec` carrying the four FACET-host overlay kinds (`OVERLAY_INDEX_VS_POP` / `OVERLAY_ZSCORE_VS_POP` / `OVERLAY_CHISQ_VS_POP` / `OVERLAY_KS_VS_POP`).

Overlay dispatch runs at the buffered FacetSchema exit via `processing.ApplyOverlaysFacet`, attaches layers to `FacetResult.Overlays` in spec order, and recurses `FacetSchema` against `Ref.Population.Cohort` to materialise the per-spec population view (strips Filterers / Labels / Additive; cycle-safe). Streamability mixed: INDEX_VS_POP / ZSCORE_VS_POP are streamable per `types/overlay_streamability.go` but run at the same buffered exit since FacetSchema is structurally buffered today. Capability: `Manifest.Facet` carries `SupportsOverlays: true` + `SupportedOverlayKinds`. Predict: `descriptor.ValidateFacet` (calls `descriptor.ValidateFacetOverlays`). The Ref / Scope / Level contract is one rule on both sides, `overlayhost.FacetSpecRefusal` (U30 E7-S4; the runtime used to check only `Ref.Population.Cohort`). CLI `pulse api facet` falls back to simple shape unless rich flag set. **Resource limits (U19).** `FacetSchema` runs `descx.FacetLimitRefusal` right after the facet field-reference pass: a set `MaxEstimatedMemory` below `EstimateFacetMemory` (a streaming scan, one bucket per `Fields` + `AdditiveFields` entry, per-value state for a dictionary-less field — doubled under `numeric_percentiles`) refuses before the scan. The simple `Facet` runs the same pre-flight on its streamed (numeric) path over a one-field request before the iterator opens (U35 E7-S1); its categorical fast path reads no record and mints nothing, so it has none (`TestFacet_DictionaryPathSkipsMemoryPreflight`). `PredictFacet` reports `FacetLimitFindings` — a `possible` `MaxGroups` bound (`FacetGroupBound`: the largest faceted field's dictionary size, 2 for `packed_bool`, clamped by the header count; numeric fields mint none) and the `certain` memory estimate — on `FacetValidationResult.LimitFindings`; the pre-flight refuses with the first certain one (`TestLimits_PredictFacet_Findings`, `TestLimitsPredictRuntimeParity`). See `skills/facet-design.md` and `skills/overlay-system.md` (Host-arm wiring — the FACET bullet).
