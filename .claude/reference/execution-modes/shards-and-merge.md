# Execution modes — parallel shards, blocked merge, filter precompute, compile-once expressions

Per-topic slice of the execution-modes reference. Index (Mode index + section map): `.claude/reference/execution-modes.md` — load it first, then only the slice(s) your engine work touches.

## Parallel shards

`pulse.Options.ShardWorkers`, default `0` ⇒ `runtime.NumCPU()`. An explicit `1` forces serial. Both concurrency knobs (`ShardWorkers` here, `DecodeWorkers` under Parallel buffered Process) are orthogonal to each other and reject negatives at `pulse.New()` (relocated from CLAUDE.md "Build / Env" Knobs at U18 E1-S2). Bounded per-shard worker pool inside `Process` when cohort is a shard archive. Reducer engages only when every operator is mergeable per `processing.CanMergeRequestWithExtensions` (built-ins per type with non-decimal targets, extension aggregators per their `Mergeable` declaration; no windows/features/regressions/tests/two-pass; attributes must be row-local per `internal/mergegate` — `ATTR_SCALE_SCORE` / `ATTR_PROFILE_SIMILARITY` stay off because their `Components` / warning tallies are per run and the reducers do not fold them, #391). The per-row order is filter → row-local attributes → floor and `Run.NullRecords` tallies, on both reducers and the serial grouped path, so a primary field that is an attribute label is read after it lands. Non-mergeable falls through to serial `shardIter`. Associative+commutative byte-equal vs serial; Welford within ULP via Chan-Welford. Surface: `internal/service/shard_reduce.go`, `processing.MergeableAggregator`, `types.AggregationType.Mergeable()`. See `skills/cohort-schema-design.md` (Sharded) + `skills/cohort-sharding.md`.

**Decode and memory (matrix-extensions-hardening E8-S3).** `processOneShard` decodes each row into a FRESH positional `Record` (`recordBindingFor(schema, nil, nil).NewRecord()` + `ReadRecordReused`, the parallel-decode reducer's decode), not three maps and a converted record — ~3 allocations a row instead of ~58 at p = 50, same values, same bits (`TestShardParallel_DecodeAllocsPerRow`; the parity gates below). Memory on an archive is not the payload alone: the per-shard partials keep their own buckets until `mergeShardPartials` folds them into the first. **The archive itself is never resident (U51 E1-S1):** every service read path opens it through `archiveFile` (`internal/service/archive_open.go` — one handle, `concurrentReaderAt`, `encx.OpenArchive` parsing the central directory once per scan), and each shard is read through a buffered SectionReader at its data offset (`archiveFile.shardReader`, a forward-`Seek`ing window so a projected decode still skips); a deflated entry is refused `PULSE_ARCHIVE_CORRUPT` on the serial and parallel arm alike (`TestArchiveOpen_DeflatedShardRefused`), a Process reads the archive's bytes once (`TestArchiveOpen_ScanReadsByRandomAccess`), and open allocates O(shards) (`TestArchiveOpen_AllocsIndependentOfBytes`). `MaxEstimatedMemory` still charges the archive bytes × `fileCopyFactor` the old slurp needed (an over-count until E1-S2 re-pins the archive term) and the partials, plus ONE dictionary-bearing schema decode (the canonical entry). No shard's schema is decoded with its dictionaries: `Open`'s record-count peek (`Archive.PeekShardRecordCount`, E8-S4) and the scan (`shardIter.openShard`, `processOneShard`, E8-S5) both read each shard's block layout-only (`internal/encoding.ReadSchemaLayout`) — dictionaries and group entries read past, never allocated — because the canonical schema decodes every row (`TestShardScan_SkipsShardDictionaries`) (`.claude/reference/predict-inspect.md` (The memory estimate)).

**`Response.Components` is part of that parity, not an exception to it.** Both reducers share `shardPartial` / `mergeShardPartials` / `finalizeMergedPartial`, and `shardPartial` carries per-slot floor tallies (`aggFloor`, `processing.SlotFloor`; per bucket `groupFloors` on a grouped partial) and `processing.FilterPassCounters` alongside the operator state, all folded slot-wise on merge. The per-operator `Operator` map is read off the MERGED aggregator — the arms fold operator STATE, so no components-level merge exists or is needed, and the `Mergeable` / `Partial` / `None` classes need no second gate here because `CanMergeRequest` already refused anything whose state cannot fold. Emitted: `Aggregations` (grouped: cohort-wide slot floors + per-bucket `groups[]`, built by the shared grouped tail), `Filterers`, `Run`, and `Groupers`: each worker builds its own grouper instance, and those instances' live bucket state folds through `processing.MergeableGrouper` (implemented by exactly the `GroupType.Mergeable()` set), so the merged grouper's `Components()` is the serial one's. **The grouped arm has no emission tail of its own** — it hands the merged buckets and grouper to `processing.FinalizeGroupedStream`, the tail the serial streaming-grouped path uses (row order incl. include order, `Request.Sort`, Components, SERIES overlays), and keys records through `processing.GroupKeyer` (multi-key fan-out for `GROUP_SET_PER_ELEMENT`). A private copy of that tail used to drop `Sort`, `Overlays`, include order and `Groupers`, and refused `GROUP_SET_PER_ELEMENT` outright. `Run.ShardCount` is the archive's shard count on BOTH arms — the serial exit stamps it in `Service.Process` (`stampShardCount`) because the processing layer has no shard concept. Counting presence for the floor goes through `processing.FieldPresent`, never `Record.NumericValue`, or a set column reads as entirely null. **An empty merge is seeded, never counters-only (#215).** Every partition is built by one `newPartitionPartial` (tallies, matrices, ungrouped aggregators or grouped buckets + grouper instances); a decode segment with zero records never publishes, so when NO partition did, `finalizeMergedPartial` seeds the merge in place with exactly that zero-record state — the ungrouped arm then writes the zero-n `Data` row and one zero-n `Components.Aggregations` entry per slot, the grouped arm runs the shared tail over zero buckets (`Groupers` included) — the serial zero-record answer; it used to emit only `Run` / `Filterers` (gates `TestFinalizeMergedPartial_EmptyPartialMatchesSerial`, `TestDecodeWorkers_EmptyCohortMatchesSerial`, `TestShardWorkers_ZeroRecordShardsMatchSerial`). Parity gates: `TestShardWorkers_AggregationComponentsParity`, `TestShardWorkers_FiltererComponentsParity`, `TestDecodeWorkers_ComponentsParity`, `TestShardWorkers_ComponentsParity_GroupedAndFlatArchives` (whole `{data, components, overlays}` document, flat + grouped `0x02` archives), `TestDecodeWorkers_GroupedAnswersParity`, `TestMergeableGrouper_MergedComponentsEqualSerial`.

**Two or more groupers, streaming and buffered (U54 E1).** `processStreamingGrouped` keys each record through one `GroupKeyer` per slot and `CompositeKeySet.Expand` mints the per-record cartesian product; the buffered path (`composite_groups.go`) builds the same keys. Every grouper is driven once per record (a null at an earlier position does not skip later ones), so per-slot `Components.Groupers` entries and `groups[].group_key` tuples agree across arms; `GROUP_QUANTILE` / `GROUP_KMEANS` are fitted once over the whole filtered set under `params.fit` `"global"` (the default) and per outer-prefix bucket under `"within"` (Crosstab, "Data-dependent axis groupers"). Series overlays run per partition of the composite rows (U46; "Series partitions" below) — the U54 interim refusal is gone.

**Two or more groupers on both reducers (U54 E2-S1).** A partition holds EVERY `Request.Groups` slot, not `Groups[0]`'s: one fresh grouper instance and `GroupKeyer` per slot (`newPartitionGroupers`, `shardPartial.initGrouped`), per-grouper `assignments`, and — for two or more groupers — a `processing.CompositeKeySet`. `foldGroupedRow` keys a record exactly as `processStreamingGrouped` does: every grouper is driven once per record (ONCE-PER-RECORD, even after an earlier position's null key, so each grouper's live state is its own `Components.Groupers` entry), and `CompositeKeySet.Expand` mints the per-record cartesian product (nothing when any position is empty; a key holding `"\x00"` is refused `PROCESSING_GROUP` at intern time, on every arm). `mergeShardPartials` folds each slot's grouper state through its own `MergeGrouperState` and sums its assignment count, in partition order, and unions the key sets (a key's tuple is a function of the key); buckets merge key by key as before. The tail receives every slot plus the merged `KeySet`, so row order (each grouper's native order, outer → inner), the key columns (written from the tuple, never the parsed string), the per-slot `Components.Groupers`, `groups[].group_key` tuples and the grouped matrices' tuple keys + all-grouper header are the serial arms'. `MaxGroups` counts composite keys per partition and on the merged count. One grouper keeps the plain-key path. Gates: root `TestMultiGrouper_*` (the #422 table under ShardArchive — a 1-row and an empty shard — and ParallelDecode modes, each required to take its parallel arm), `TestMultiGrouper_BitExactAcrossWorkers` (ShardWorkers 1–4 × DecodeWorkers 1/2/3/7, weighted and unweighted: rows, Components and grouped matrices bitwise over count + merge-block slots; the floor's `sum_weights` / `n_eff` are plain Σ tallies, equal within 1e-12 relative on every grouper count).

**Resource limits on the grouped paths (U19).** `MaxGroups` is counted at every bucket mint — O(1) per NEW key, never per row — and a breach raises `PULSE_LIMIT_EXCEEDED` (`limits.Check`) with no partial result: the serial streaming-grouped mint (`processStreamingGrouped`), the buffered path once `Grouper.Group` returns (one check on the partition size), `GroupedMatrices.bucket` (built with the run's limits by `BuildGroupedMatrices`), each parallel partition's `foldGroupedRow`, and the MERGED key count in `mergeShardPartials` (every partition can sit under the limit while their union does not). `newProcessor` installs `Service.Limits()` through `Processor.SetLimits`; both parallel reducers bypass it, so `newShardPartial` takes the limits explicitly. A partition never holds more keys than the run, so a local trip is a sound early abort; the parallel `observed` is therefore the count AT BREACH (≥ configured + 1) and is not reproducible across worker counts — parity compares `{code, limit, configured}` only. Facet bounds each faceted field's distinct values the same way (rich categorical / boolean accumulators, base and additive; the simple facet's numeric stream) — the simple facet's categorical fast path returns the resident dictionary and mints nothing, so it is not counted. Gates: `TestMaxGroups_ProcessorPaths`, `TestMaxGroups_GroupedMatricesMint`, `TestMaxGroups_ParallelShardPartition`, `TestMaxGroups_ParallelShardRuns`, `TestMaxGroups_ParallelDecode`, `TestMaxGroups_GroupedMatrixRun`, `TestMaxGroups_PartitionMatricesCarryLimits`, `TestMaxGroups_Facet`, `TestMaxGroups_FacetBool`.

## Blocked merge (`processing.BlockMerger`)

The opt-in for a reducer whose answer must be BIT-identical under every concurrency knob, not merely within ULP. Surface: `internal/processing/block_merge.go`; the one built-in user is the U16 matrix slot (`MAT_*`, below — an extension `MAT_*` (U30) never opts in itself: it runs in that same slot with only the finalizer swapped, so it inherits the tree), and every other reducer keeps the `MergeOnline` path above untouched.

- **Positions.** Every record source stamps the row's merge-block position on the `Record` (`SetMergePosition(shard, shardStart, record)` → `MergeBlock() (BlockKey, bool)`; packed into the Record's padding, size stays 96 bytes). Blocks key by the GLOBAL record ordinal `shardStart + record`: the serial single-file iterator (`streamingIterator`, shard 0, start 0) and the parallel-decode workers (shard 0, start 0, `segment start + offset`); the serial archive iterator (`shardIter`) and the per-shard reducer (`processOneShard`) stamp the shard's archive index, its start (`shardStarts`: the record counts of the shards before it, from `ShardEntry.RecordCount`) and the in-shard index. `BlockKey{Block, Shard, Head}` with `Block = global / linalg.MergeBlockSize` (4096) and `Head` = the shard holds the block's first ordinal (always on a single file); keys order by block, then shard.
- **State.** A `BlockMerger` is an `OnlineAggregator` whose state is a `*BlockCoMoments` — one FRAGMENT per (block, shard) that saw a row. A head fragment holds a `linalg.CoMoment`, rows folded in record order; a fragment whose shard starts inside the block (at most the shard's first block, ≤ 4096 rows) buffers its rows instead. A record no source stamped (join output, a chain stage, a test harness) is refused `PROCESSING_INTERNAL` rather than guessed at.
- **Merge.** `mergeShardPartials` (both parallel arms, ungrouped slots and grouped buckets) moves the other partition's fragments in via `processing.MergeBlockMerger` → `BlockCoMoments.Absorb` — a disjoint union, so partition order cannot reach the bits; a key on both sides means a fragment was split across partitions and is `PROCESSING_INTERNAL`.
- **Tree.** At `Finalize` the reducer calls `BlockCoMoments.Tree`: each block's partial is its head fragment (or an empty accumulator) with the block's other fragments replayed on top in shard order — the block's sequential fold in ordinal order — then one `linalg.MergeTree` over the block partials in block order. A block no row reached has no entry (absence is data-determined); no blocks ⇒ an empty accumulator; a head that is not its block's first fragment is `PROCESSING_INTERNAL`. Serial, any `DecodeWorkers`, any `ShardWorkers` count and any shard split — a shard archive versus its single-file twin — therefore produce the same bits on every architecture (the kernels are FMA-free). `AGG_VEC_MEAN` / `AGG_VEC_SUM` / `AGG_VEC_SD` (Chan-combined Welford moments) key their per-element partials the same way (`aggregator_vector.go`, through `MergeOnline`'s disjoint union).
- **Matrix slots.** `Request.Matrices` state is not an aggregator: each partition (`shardPartial`, both arms) carries a `*processing.MatrixSlots` (`mats`, the `aggs` analogue, nil without matrices; a grouped partition carries per-bucket `*processing.GroupedMatrices` in `groupedMats` instead, fed per key by `foldGroupedRow`, merged key by key and rendered by the grouped tail in the final, `Request.Sort`-applied Data order — `.claude/reference/matrix-and-vectors.md`) built off the STAMPED request by `processing.BuildMatrixSlots`, folds every filter-passing row after the universal floor (`processOneShard` / the decode callback), merges in `mergeShardPartials` via `MatrixSlots.Merge` (slot-wise `MergeBlockMerger`, so the same disjoint union), and `finalizeMergedPartial` sets `Response.Matrices` from `MatrixSlots.Finalize` on every arm. The merge gate admits it: `mergegate.MergeRefusal` waives the at-least-one-aggregator rule for a request carrying matrices, and requires every `MatrixType.Mergeable()` (manifest `matrices[].mergeable`); a grouped request carrying matrices merges per bucket under the ordinary grouper rule. `ChainRefusal` still strips `matrices` before the rule. `Run.NullRecords` stays 0 for a matrix-only request on every arm (no aggregator or grouper names a primary field). Gate: `TestMatrixCovariance_WorkerInvariant` (`internal/service/matrix_merge_invariance_test.go`) — every real `MAT_*` registration (`MAT_COVARIANCE`, `MAT_CORRELATION`) under the same cohorts and knobs as the vehicle gate below, matrix-only and beside an aggregation, weighted and unweighted, bitwise over every cell and the determinant plus warnings and `Components.Run`; `TestMatrixOnly_RunComponents`.
- **Memory.** `limits.MergeBlocks` counts fragments (per shard, the global blocks its rows touch) and `limits.MergeBufferedRows` the rows non-head fragments keep (`vectors.Matrix.FragmentRowBytes` each); predict's `estimated_bytes` and the memory pre-flight add both.
- **Gate.** `TestCoMomentMergeTree_WorkerInvariant` (`internal/service/comoment_merge_tree_test.go`) drives a `_test.go`-only CoMoment reducer through the real dispatch (registered on `Service.SetExtensions`; no registry, manifest or skill entry): serial vs `DecodeWorkers` 2/3/7/8 on 102,400- and 105,177-record cohorts, serial vs `ShardWorkers` 2/3/8 on an 8-shard archive and vs its single-file twin (bitwise), listwise/pairwise × weighted/unweighted — bitwise over N, invalid-weight count, W, means and every pair's count, weight and M2. Unit gates: `TestBlockCoMoments_*`, `TestRecordMergePosition*`, `TestMergeBlocks`, `TestMergeBufferedRows`; end to end `TestVecAgg_BitExactAcrossWorkers` (uneven splits incl. 1-row and empty shards == the twin, `ShardWorkers` 1–4 × `DecodeWorkers` 1/2/3/7). **Extension `MAT_*` (U30 E1-S4):** `TestExtensionMatrix_WorkerInvariant` (root `extensions_matrix_invariance_test.go`) drives an operator registered through `Options.Extensions.MatrixOps` ONLY (no engine hook) that renders every raw co-moment figure (PairM2, pair counts and weights, means, N / W / NEff, the components entry): serial vs `DecodeWorkers` 2/3/7/8 on a 105,177-record file, an uneven 7-shard archive (1-row and empty shards, edges inside blocks) under `ShardWorkers` 1/2/3/8 (plus 3×3, 8×7) vs its single-file twin, listwise/pairwise × weighted/unweighted × grouped/ungrouped, each parallel run required to take its parallel arm (`observe.Hooks`); the `Streamable: false` tier stays serial under every knob and equals the co-moment tier's bits; predict's `streamable` / `mergeable` match the arm taken. Its falsification `TestExtensionMatrix_WorkerInvariantGateBites` shows a reordered block merge renders different bits under the gate's comparator.

## Filter precompute (grouped cohorts)

Over a parent-grouped (`0x02`) cohort a filter whose every input field is a member of ONE group has at most `entry_count` distinct answers, whatever the row count or order. `internal/processing/filter_precompute.go` evaluates it once per dictionary ENTRY into a two-bit-per-entry verdict table (unknown / fail / pass / per-row) and turns each row's verdict into a bit test on the row's entry index. On the effort's reference shape that is ~109K evaluations instead of ~1.4M. Derived at read time, never persisted; opt-out process-wide with `processing.SetFilterPrecompute(false)` (benchmarks / A-B only — it changes speed, never a result). Diagnostics: `processing.FilterPrecomputeStats()` (tables built, entry evaluations, table bytes, ineligible pairs) — only table builds and entry evaluations touch its atomics, never the per-row path.

**Seam.** The wrap is at the `FilterFunc`: `Processor.buildFilterFuncs` and `processing.BuildFilters` wrap each ELIGIBLE filterer (grouped build schema only; an ungrouped schema gets the builder's `FilterFunc` back unchanged, so a `0x01` cohort pays nothing). `applyFilterPass` is untouched, so `{n_in, n_out, n_null_input}` are the per-row counts by construction: `n_in` / `n_out` follow the verdict, and `n_null_input` still reads the record's own null state (`Record.IsNull`, now one name resolution instead of three). **The entry index** reaches the record through `encoding.GroupIndexRecord` (`SetGroupIndices(schema, idx)`), called by the grouped reuse decoder after every row on the full, plan, plain-sink and run-skip paths (`nil` for a plan that decodes nothing). `*processing.Record` stores the indices bit-exactly in the tail of `vals` past the set-mask words (`recordLayout.nGroups`; no allocation, none at all for an ungrouped schema) and reports them through `Record.GroupIndex(g)` only while valid: `ClearForRow` and `resetRun` — every schema-field mutation that is not a decode write — withdraw them, and indices addressing another schema than the record's own (by identity; the decoder passes the GROUPED schema, not its `Logical()` view) are refused. A feature or attribute rewriting a member's name therefore sends that row per-row, never to a stale verdict.

**Eligibility** (`precomputeInputs`, then per record schema `precomputeGroup`): every built-in filterer on its `Field`; `FILTER_EXPRESSION` when its AST's free identifiers are all fields and every call is pure — expr-lang built-ins except `now()`, the set built-ins, and `lookup()` only when every lookup table is a static `Rows` map. Embedder `ExprFunctions` (even one shadowing a built-in), `let` names, `$env` and off-schema columns disqualify. Extension filterers never qualify — a registration declares no purity and `FieldInputs` does not prove statelessness. Inputs must resolve to unique field names in ONE group: a group member mixed with a row field, or two groups, stays per-row (the verdict space is the product; there is no small table). **Evaluation is lazy**: an entry is evaluated the first time a row carrying it reaches the filter, so the work is the DISTINCT entries reached — never more than the per-row count, even behind a selective earlier slot. An entry whose evaluation ERRORS is marked per-row and re-evaluated on each of its rows, so an error surfaces on exactly the row the per-row path raises it on, and never when no such row gets there. Per-entry evaluation decodes only the filter's input members (`internal/encoding.NewGroupEntryDecoder(schema, g, fields)`), not the whole entry.

**Arms.** Routed: streaming Process (reuse record), buffered and projected Process (fresh record per row through `ReadRecordReusedWithPlan`), fused crosstab and buffered crosstab, parallel buffered Process (one `FilterFunc` set — and so one verdict table — per worker; bounded by workers × entries), Compose (per slot), ProcessChain stage 0, `FacetSchema`, and `FilterToFile` (its map decode forwards `RecordReader.GroupIndex` into `Record.SetGroupIndices`; `TestGroupedCohort_FilterToFilePrecompute`). Per-row fallback (correct, not precomputed): every other map-decode consumer — `Lookup`, the shard reducer, the projection-without-plan fallback — plus joined records (`Request.Joins`), ProcessChain stages ≥ 1 (synthesised ungrouped cohorts) and any extension filterer. Shard archives refuse grouped shards today; the tables are keyed by the record's schema pointer (the shard's own dictionary), so grouped shards need no change here beyond the decoder handing over that shard's schema. Gates: `TestFilterPrecompute_ParityEveryFilterer` (all built-in filterers, both reuse arms, verdicts + components vs per-row and vs `0x01`, evaluation count = distinct entries, ≥10x at 12x fanout), `TestGroupedCohort_FilterPrecomputeParity` (facade arms, exact entry-evaluation counts), `TestFilterPrecompute_ParallelDecode`, `TestGroupedDecode_ReportsGroupIndices`, `TestRecord_GroupIndexWithdrawnByEveryMutator`. Bench: `BenchmarkFilterPrecompute` (`internal/service/`).

## Before-filters attributes (`ATTR_PREVIOUS_STATE`)

A per-operator property, `prevstate.BeforeFilters(type)` (`internal/prevstate`), true for `ATTR_PREVIOUS_STATE` ONLY: the attribute runs over EVERY decoded record (after the pre-filter features) BEFORE the filter pass, so a date window keeps each subject's first in-window record with its TRUE previous state — the long panel's crosstab then equals the wide `state_t(k-1)` × `state_t(k)` one under the same window (`TestPreviousState_DateWindowKeepsFirstInWindowTransition`). Every other attribute (extensions included) still runs over the filter-passing records.

- **Runtime.** `Processor.filterThenAttributes` (`internal/processing/processor.go`) is the one buffered filter + attribute step, shared by `processRecords` (ungrouped / grouped / Compose slots / chain stage 0), the buffered crosstab and `DeriveRecords` (materialize): before-filters slots in declared order over every record, the filter pass, then every other slot over the survivors; warnings and `Components.Attributes` keep DECLARED slot order. A request with no such slot takes the historical path byte-identically. The attribute is buffered-only, so no streaming, fused-crosstab, parallel-reducer or shard-merge arm ever meets it. A buffered crosstab under `DecodeWorkers > 1` DOES take `ArmParallelDecode`: the records are decoded in parallel segments, then the attribute scores the full decoded set (`previous_state_modes_test.go`); only the parallel REDUCER (row-local merge) never meets it.
- **Expressions.** The field-reference walk (`fieldRefWalk.preFilter`, predict and runtime alike) declares each before-filters label as a derived column from the filter step on: an expression filter — and any expression, an `ATTR_FORMULA` declared earlier included — may read it (`prev != nil` drops first records). It reads BY STATE NAME, exactly as its state field does (`prev == "paid"`, `prev in [...]`, string operators; a null absent — the source field's nil rules): the dictionary-inheritance view types it (predict `exprenv.DerivedDecl` in `compileRefusal`; runtime `exprenv.DerivedFields` declared + its code lifted through `exprenv.Bind` in `newExprProgramKeyed`, the view reaching every expression site — request and fit_on filters, `ATTR_FORMULA`, `total()` arguments — as `Processor.keySchema` through `keysBinder`). A request without the attribute binds byte-identically (`TestPreviousState_ExpressionsReadStateNames`, `TestPreviousState_UpgradeFromFreeFilter`). A field-keyed filter naming the label stays `SERVICE_VALIDATION` unknown field.
- **Counts.** Filter Components `{n_in, n_out}` and `Run` judge the filter alone. The attribute's floor `{n, n_null}` and operator counts are over every record it scored (`n + n_null` = `Run.total_records`).
- **Predict.** `PredictResult.ComputedBeforeFilters` (`computed_before_filters`, `omitempty`) lists the before-filters labels in declared order, from the same rule. Limits: `MaxEstimatedMemory` already charges the buffered arm every decoded record (the estimate never sees filter selectivity), so the unfiltered buffer is what is judged (`TestPreviousState_LimitsJudgeUnfilteredBuffer`).

## Compile-once expressions (`FILTER_EXPRESSION`, `ATTR_FORMULA`)

Both compile their expr-lang program ONCE per build (`internal/processing/expr_program.go`), never per row. **Prototype**: every schema field declared with the Go type `Record.AllValues` gives it (`exprValueType` — float64; string for a dictionary categorical; `[]string` for a dictionary set; `Decimal128` / `uint64` / `SetMask` otherwise), so build-time type checking equals the old per-row check on a row with every field present — same program, same results, same `PROCESSING_RUNTIME` "compiling … expression" error, now raised by `BuildFilters` / `buildFilterFuncs` / the attribute build (`bindAttribute` → `prepare`) before any row. A name the schema cannot declare (feature output, earlier attribute label) DEFERS the compile to the first record, against prototype + that record — the old first-row env — then caches it. **Env**: per row, only the named fields (`Record.exprValue`, pinned to `AllValues` by `TestRecord_ExprValueMatchesAllValues`) in a pooled map; `$env`, a deferred compile, or a record already carrying its `AllValues` map take the whole map. **Null**: a null field is absent → reads as nil. Rows with every referenced field present run the typed program; a null-input row runs an untyped twin (every name `any`, compiled lazily once) so nil follows expr-lang's nil rules uniformly (`== nil` true, `==` false, `!=` true, `in` false, `??` substitutes; ordering / arithmetic / nil-rejecting functions error). `FILTER_EXPRESSION` reads a null-input evaluation error (or nil result) as UNKNOWN → row dropped; `ATTR_FORMULA` raises it ("evaluating formula expression"). `now()` still evaluates per row. **Concurrency**: `*vm.Program` is immutable and `expr.Run` builds a VM per call; the lazy compiles sit behind a mutex + atomic publish. Gates: `TestExprProgram_CompilesOncePerBuild` (`processing.ExprCompileCount` deltas independent of row count), `TestExprProgram_MatchesPerRowCompile` (per-row-compile oracle), `TestExprValueType_MatchesAllValues` (every field type × every decode path), `TestExprFilter_NullSemantics`, `TestExprProgram_ConcurrentRuns` (`-race`). Bench `BenchmarkExprCompileOnce` (95-field join fixture, 100K rows): filter pass ~8.7 µs → ~0.14 µs/row, end to end ~24 → ~2.1 µs/row (0x01), ~24 → ~1.1 (0x02).
