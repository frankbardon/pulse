# Execution modes — parallel shards, blocked merge

Per-topic slice of the execution-modes reference. Index (Mode index + section map): `.claude/reference/execution-modes.md` — load it first, then only the slice(s) your engine work touches.

## Parallel shards

`pulse.Options.ShardWorkers`, default `0` ⇒ `runtime.NumCPU()`. An explicit `1` forces serial. Both concurrency knobs (`ShardWorkers` here, `DecodeWorkers` under Parallel buffered Process) are orthogonal to each other and reject negatives at `pulse.New()` (relocated from CLAUDE.md "Build / Env" Knobs at U18 E1-S2). Bounded per-shard worker pool inside `Process` when cohort is a shard archive. Reducer engages only when every operator is mergeable per `processing.CanMergeRequestWithExtensions` (built-ins per type with non-decimal targets, extension aggregators per their `Mergeable` declaration; no windows/features/regressions/tests/two-pass; attributes must be row-local per `internal/mergegate` — a `total()` formula excepted when it runs two-phase (Two-phase `total()` below) — and the tally attributes, whose per-run `Components` / warning tallies the reducers fold (Tally attributes below)). The per-row order is filter → row-local attributes → floor and `Run.NullRecords` tallies, on both reducers and the serial grouped path, so a primary field that is an attribute label is read after it lands. Non-mergeable falls through to serial `shardIter`. Integer / sentinel reducers and the **binned reproducible sums** are byte-equal vs serial under any worker count or shard split; Welford (variance, stddev, `AGG_WELFORD`, shape moments, the weighted `m2_weighted` / `weighted_variance` components) within ULP via Chan-Welford — never bit-exact. Surface: `internal/service/shard_reduce.go`, `processing.MergeableAggregator`, `types.AggregationType.Mergeable()`. See `skills/cohort-schema-design.md` (Sharded) + `skills/cohort-sharding.md`.

**Decode and memory (matrix-extensions-hardening E8-S3).** `processOneShard` decodes each row into a FRESH positional `Record` (`shardRows.next`: `binding.NewRecord()` + `ReadRecordReusedWithPlan`, the parallel-decode reducer's decode), not three maps and a converted record — ~3 allocations a row instead of ~58 at p = 50, same values, same bits (`TestShardParallel_DecodeAllocsPerRow`; the parity gates below). **It projects (U51 E2-S2):** `processShardArchiveParallel` builds the projection ONCE per run (`shardDecodeFor` → `Service.decodeProjection`, the recipe the parallel-decode dispatcher shares — `NeededFields` → keep → `BuildDecodePlan`, gated by projection being on) and every worker reads it: the plan seeks past unretained fields, the record binding is projected (`recordBindingFor(schema, plan, keep)`), the plan stamp carries the retained count (`projected_fields`, `OperationResult.Projected`), parent-group indices still reach the record (`readGroupIndices`), and the defensive projection-without-plan map decode captures exact u64 words as `shardIter.openShard` does (`TestShardParallel_ProjectionTransparent` — flat and `0x02` archives, on vs off vs serial; `TestShardParallel_ProjectedDecodeAllocatesLess`; `TestExactU64_ShardParallelProjectionWithoutPlan`; `TestLogPlanDecisionDebug_ShardParallelProjected`). An anchor-opened shard streams its archive section through the same bounded window (`anchorSectionSize` in `streamingIterator.initFromFile`; `TestShardStream_AnchoredShardStreamsSection`), never `afero.ReadFile`. Memory on an archive is not the payload alone: each shard's partial keeps its own buckets until the incremental merge folds it (below: Incremental merge and group memory). **The archive itself is never resident (U51 E1-S1):** every service read path opens it through `archiveFile` (`internal/service/archive_open.go` — one handle, `concurrentReaderAt`, `encx.OpenArchive` parsing the central directory once per scan), and each shard is read through a buffered SectionReader at its data offset (`archiveFile.shardReader`, a forward-`Seek`ing window so a projected decode still skips); a deflated entry is refused `PULSE_ARCHIVE_CORRUPT` on the serial and parallel arm alike (`TestArchiveOpen_DeflatedShardRefused`), a Process reads the archive's bytes once (`TestArchiveOpen_ScanReadsByRandomAccess`), and open allocates O(shards) (`TestArchiveOpen_AllocsIndependentOfBytes`). `MaxEstimatedMemory` charges (U51 E1-S2) the LARGEST shard's records × stride × `fileCopyFactor` in place of the cohort's payload, 8 × the central-directory bytes (`encx.Archive.DirectoryBytes`) and the partials, plus ONE dictionary-bearing schema decode (the canonical entry); an anchored shard is charged as a single file. No shard's schema is decoded with its dictionaries: `Open`'s record-count peek (`Archive.PeekShardRecordCount`, E8-S4) and the scan (`shardIter.openShard`, `processOneShard`, E8-S5) both read each shard's block layout-only (`internal/encoding.ReadSchemaLayout`) — dictionaries and group entries read past, never allocated — because the canonical schema decodes every row (`TestShardScan_SkipsShardDictionaries`) (`.claude/reference/predict-inspect.md` (The memory estimate)).

**`Response.Components` is part of that parity, not an exception to it.** Both reducers share `shardPartial` / `mergeShardPartials` / `finalizeMergedPartial`, and `shardPartial` carries per-slot floor tallies (`aggFloor`, `processing.SlotFloor`; per bucket `groupFloors` on a grouped partial) and `processing.FilterPassCounters` alongside the operator state, all folded slot-wise on merge. The per-operator `Operator` map is read off the MERGED aggregator — the arms fold operator STATE, so no components-level merge exists or is needed, and the `Mergeable` / `Partial` / `None` classes need no second gate here because `CanMergeRequest` already refused anything whose state cannot fold. Emitted: `Aggregations` (grouped: cohort-wide slot floors + per-bucket `groups[]`, built by the shared grouped tail), `Filterers`, `Run`, and `Groupers`: each worker builds its own grouper instance, and those instances' live bucket state folds through `processing.MergeableGrouper` (implemented by exactly the `GroupType.Mergeable()` set), so the merged grouper's `Components()` is the serial one's. **The grouped arm has no emission tail of its own** — it hands the merged buckets and grouper to `processing.FinalizeGroupedStream`, the tail the serial streaming-grouped path uses (row order incl. include order, `Request.Sort`, Components, SERIES overlays), and keys records through `processing.GroupKeyer` (multi-key fan-out for `GROUP_SET_PER_ELEMENT`). A private copy of that tail used to drop `Sort`, `Overlays`, include order and `Groupers`, and refused `GROUP_SET_PER_ELEMENT` outright. `Run.ShardCount` is the archive's shard count on BOTH arms — the serial exit stamps it in `Service.Process` (`stampShardCount`) because the processing layer has no shard concept. Counting presence for the floor goes through `processing.FieldPresent`, never `Record.NumericValue`, or a set column reads as entirely null. **An empty merge is seeded, never counters-only (#215).** Every partition is built by one `newPartitionPartial` (tallies, matrices, ungrouped aggregators or grouped buckets + grouper instances); a decode segment with zero records never publishes, so when NO partition did, `finalizeMergedPartial` seeds the merge in place with exactly that zero-record state — the ungrouped arm then writes the zero-n `Data` row and one zero-n `Components.Aggregations` entry per slot, the grouped arm runs the shared tail over zero buckets (`Groupers` included) — the serial zero-record answer; it used to emit only `Run` / `Filterers` (gates `TestFinalizeMergedPartial_EmptyPartialMatchesSerial`, `TestDecodeWorkers_EmptyCohortMatchesSerial`, `TestShardWorkers_ZeroRecordShardsMatchSerial`). Parity gates: `TestShardWorkers_AggregationComponentsParity`, `TestShardWorkers_FiltererComponentsParity`, `TestDecodeWorkers_ComponentsParity`, `TestShardWorkers_ComponentsParity_GroupedAndFlatArchives` (whole `{data, components, overlays}` document, flat + grouped `0x02` archives), `TestDecodeWorkers_GroupedAnswersParity`, `TestMergeableGrouper_MergedComponentsEqualSerial`. `GROUP_ROUNDED` joined the set in U51 E3-S3 (counts sum, `low` last-write; root `TestBitExact_Heavy`'s `rounded_*` shapes, chain stages admit it too — `process_chain.mergeable_groupers` is the gate's list).

**Incremental merge and group memory (U51 E2-S4, #358).** The per-shard arm no longer holds one partial per SHARD until a final merge. `scanAndMergeShards` dispatches shard indices to the workers and folds each result through a `partialMerger` (`add`, the body `mergeShardPartials` keeps for the decode arm and tests) the moment shards 0..i are all done — partial i merges, then is dropped from `pending` and collected — so the merge runs on the caller's goroutine WHILE later shards scan (its time is in the `scan` phase; `reduce` is the finalize). The merge ORDER is still shard insertion order, the one-shot order, so every answer is byte-identical to the pre-change arm, Welford slots included, under any worker count (`TestGroupMemory_ManyShardsWorkerInvariant`, 40 shards × workers 2/3/5/8); row order never came from the merge (the grouped tail orders rows), so the grouped merge walks `p.groups` in map order and the partition keeps no key-order list. **Live partials are bounded by the window** `limits.ShardMergeWindow(workers)` = 2 × workers — under a set `MaxEstimatedMemory` shrunk to the largest window (≥ 1) whose whole-run estimate fits (`limits.ShardMergeWindowWithin`; `descx.ShardMergeWindow` computed with the pre-flight's inputs and passed to `scanAndMergeShards`; predict judges the same window's estimate, so a refusal fires only when one partial does not fit; U51 E5-S4, `TestGroupMemory_MergeWindowFitsBudget`, root `TestLimits_ShardMergeWindowShrinksToBudget`): shard j is dispatched only once j < next + window (next = the first unmerged shard), neither channel ever blocks (both sized to the window), and every dispatched shard reports exactly once (`scanShard` recovers a panic per shard), so the first error — a scan, a panic, a merged `MaxGroups` trip — cancels the rest and is returned after every dispatched shard reported. Gate `TestGroupMemory_LivePartialsBoundedByWindow` counts the partials still REACHABLE (weak pointers + GC at each merge, through the test-only `shardMergeHook`) on 40 shards: ≤ window (measured 1), where keeping them all leaves 39 alive. Predict charges the window (`descriptor.shardWindowPartitions`: the window's largest bucket bounds and largest record counts), parity in root `TestLimits_MaxEstimatedMemory_PredictCertainAndProcessRefuses` ("archive per-shard window"). **Per-group bytes.** A bucket is ONE map entry `map[string]*processing.GroupBucket{Aggs, Floors}` on every streaming-grouped arm (serial `processStreamingGrouped`, both reducers; `GroupedTail.Buckets`), minted by `processing.NewGroupBucket` with its floors shaped by `NewSlotFloorsLike` off the cohort-wide floors (the weight spec resolved once per run, not per bucket); `SlotFloor.weight` is a `*WeightFloor`, nil on an unweighted slot (the inline 128-byte binned floor was most of a bucket). `GroupFloorsOn` counts the floor switch (`WorkStats.GroupFloorBuilds`). Gated: `TestGroupMemory_PartitionBytesPerGroup` / `TestGroupMemory_MergedBytesPerGroup` — 800,000 keys, `AGG_COUNT` + `AGG_SUM` + `AGG_AVERAGE`, components on, live heap after GC ≤ 512 B/group (measured ~422; ~866 before; 126–215 B of it is the key, map slot and grouper tally, varying with the map's fill). The finalize output (Data rows, per-group Components) is NOT in that figure — ~2.6 KB a group at the run's peak — and the memory model charges it separately (`.claude/reference/predict-inspect.md` (The memory estimate)). The grouped tail CONSUMES the buckets (U51 E5-S12, #499): each is deleted once its row and per-group Components entry are written, so merged state and rows never peak together (`TestGroupMemory_FinalizeReleasesBuckets`); the estimate still charges both (a released bucket is garbage until the next GC).

**Two or more groupers, streaming and buffered (U54 E1).** `processStreamingGrouped` keys each record through one `GroupKeyer` per slot and `CompositeKeySet.Expand` mints the per-record cartesian product; the buffered path (`composite_groups.go`) builds the same keys. Every grouper is driven once per record (a null at an earlier position does not skip later ones), so per-slot `Components.Groupers` entries and `groups[].group_key` tuples agree across arms; `GROUP_QUANTILE` / `GROUP_KMEANS` are fitted once over the whole filtered set under `params.fit` `"global"` (the default) and per outer-prefix bucket under `"within"` (Crosstab, "Data-dependent axis groupers"). Series overlays run per partition of the composite rows (U46; "Series partitions" below) — the U54 interim refusal is gone.

**Two or more groupers on both reducers (U54 E2-S1).** A partition holds EVERY `Request.Groups` slot, not `Groups[0]`'s: one fresh grouper instance and `GroupKeyer` per slot (`newPartitionGroupers`, `shardPartial.initGrouped`), per-grouper `keyed` record counts (once per record, however many keys a fan-out grouper gives it), and — for two or more groupers — a `processing.CompositeKeySet`. `foldGroupedRow` keys a record exactly as `processStreamingGrouped` does: every grouper is driven once per record (ONCE-PER-RECORD, even after an earlier position's null key, so each grouper's live state is its own `Components.Groupers` entry), and `CompositeKeySet.Expand` mints the per-record cartesian product (nothing when any position is empty; a key holding `"\x00"` is refused `PROCESSING_GROUP` at intern time, on every arm). `mergeShardPartials` folds each slot's grouper state through its own `MergeGrouperState` and sums its keyed-record count, in partition order, and unions the key sets (a key's tuple is a function of the key); buckets merge key by key as before. The tail receives every slot plus the merged `KeySet`, so row order (each grouper's native order, outer → inner), the key columns (written from the tuple, never the parsed string), the per-slot `Components.Groupers`, `groups[].group_key` tuples and the grouped matrices' tuple keys + all-grouper header are the serial arms'. `MaxGroups` counts composite keys per partition and on the merged count. One grouper keeps the plain-key path. Gates: root `TestMultiGrouper_*` (the #422 table under ShardArchive — a 1-row and an empty shard — and ParallelDecode modes, each required to take its parallel arm), `TestMultiGrouperInvariance_{Archive,Heavy}` (the shared harness `internal/testutil/invariance`: ShardWorkers 1/2/3/8, DecodeWorkers 2/3/7/8, weighted and unweighted slots — the whole response bitwise over count + merge-block slots; `sum_weights` / `n_eff` are binned sums).

**Resource limits on the grouped paths (U19).** `MaxGroups` is counted at every bucket mint — O(1) per NEW key, never per row — and a breach raises `PULSE_LIMIT_EXCEEDED` (`limits.Check`) with no partial result: the serial streaming-grouped mint (`processStreamingGrouped`), the buffered path once `Grouper.Group` returns (one check on the partition size), `GroupedMatrices.bucket` (built with the run's limits by `BuildGroupedMatrices`), each parallel partition's `foldGroupedRow`, and the MERGED key count in `partialMerger.add` (every partition can sit under the limit while their union does not). `newProcessor` installs `Service.Limits()` through `Processor.SetLimits`; both parallel reducers bypass it, so `newShardPartial` takes the limits explicitly. A partition never holds more keys than the run, so a local trip is a sound early abort; the parallel `observed` is therefore the count AT BREACH (≥ configured + 1) and is not reproducible across worker counts — parity compares `{code, limit, configured}` only. Facet bounds each faceted field's distinct values the same way (rich categorical / boolean accumulators, base and additive; the simple facet's numeric stream) — the simple facet's categorical fast path returns the resident dictionary and mints nothing, so it is not counted. Gates: `TestMaxGroups_ProcessorPaths`, `TestMaxGroups_GroupedMatricesMint`, `TestMaxGroups_ParallelShardPartition`, `TestMaxGroups_ParallelShardRuns`, `TestMaxGroups_ParallelDecode`, `TestMaxGroups_GroupedMatrixRun`, `TestMaxGroups_PartitionMatricesCarryLimits`, `TestMaxGroups_Facet`, `TestMaxGroups_FacetBool`.

**Reproducible sums (U51 E2-S3, #357).** `AGG_SUM`, `AGG_AVERAGE` (binned Σ over the exact integer n), `AGG_RATIO`, the weighted Σw / Σw·x / Σw² (`weightedAggregator`: weighted `AGG_COUNT` / `AGG_SUM` / `AGG_AVERAGE` / `AGG_WEIGHTED_MEAN`), the `sum_weights` / `n_eff` floor (`WeightFloor`), the weighted counting aggregators (`aggregator_weighted_counts.go`), `AGG_DISTINCT_SUM` (binned at freeze; exact when each key has one value) and `ATTR_FORMULA` `total()` (`formula_total.go`) accumulate in `internal/reprosum.Sum` (ReproBLAS K=3/W=40 binned sum) on EVERY path — serial, streaming, buffered (`binnedSum`), fused crosstab, both reducers — and `MergeOnline` / `WeightFloor.Merge` merge the binned state, so the value is a function of the multiset of inputs: no order, partition or merge tree reaches the bits, on amd64 and arm64 alike (the kernel carries its own `float64(...)` FMA barriers; callers add none — a weighted product goes through `AddWeighted`). It is not correctly rounded (bound in the package doc); serial float-sum bits moved once at the switch. Welford state keeps its running Σw (`runW`) separate from the binned Σw; the weighted two-pass variance mean stays sequential so unit weights still reproduce the unweighted variance (`TestWeightedCore_UnityParity`). Gate: root `TestBitExact_*` (`internal/integration/bit_exact_test.go`) — non-dyadic mixed-magnitude rows, serial vs `DecodeWorkers` 2/3/7 vs `ShardWorkers` 1/2/3/8 over a hash-scattered 9-shard uneven archive, each parallel run required to take its arm; `reflect.DeepEqual` on Data and Components (Welford keys lifted and checked at 1e-12); also streaming vs buffered, the fused / buffered crosstab and `total()`. Bench: `BenchmarkGroupedSumScale` (`docs/internals/BENCHMARKS_BASELINE.md`).

**Two-phase `total()` (U51 E3-S1, #399).** A total-bearing `ATTR_FORMULA` is not row-local, yet both reducers run it when `mergegate.ParallelTotals` admits it: the request is ungrouped (no `Groups`, no `Crosstab`) and the formula sits in pre-pass layer 0 — no input reads, directly or through row-local slots, an earlier `total()` formula's label (the two-pass planner's rule over `vectors.AttributeInputNames` + `vectors.DefaultAttributeLabel`; an `ATTR_REG_PREDICT`, fit-referenced or extension slot depends on every earlier one, so the gate never admits what the planner would layer later). Phase 1 (`internal/service/totals_prepass.go`) is a parallel pre-pass over the same partitions — shards on the per-shard arm, the block-aligned segments on the decode arm — under its own projection (`processing.TotalsPrepassRequest`: filters, weights, zones, the row-local stages a `total()` argument reads and each `total()` formula reduced to its arguments — never a field only the formula's row expression or an aggregation reads; `TestTotalsPrepass_ProjectionNarrowsToTotalInputs`): each worker folds its filter-passing rows into a `processing.TotalsPrepass` (the layer-0 row-locals a `total()` argument reads, then each formula's `PrePass`), the workers' states merge through `MergeableTotals.PartialTotals` / `AbsorbTotals` (binned `reprosum` sums, integer counts — order-free, so the merged totals are the serial pre-pass bits) and `Publish` finalizes them. Phase 2 is the ordinary reduce: `buildRowLocalAttrSpecs` binds each partition's formula through `PublishedTotals.Bind` → `PublishTotals` before its first row (an unbound one refuses, never reads 0). Predict follows the shared gate (`ShardFanOut` / `DecodeFanOut`: `TestShardFanOut_PredictMatchesRuntime`, `TestDecodeFanOut_PredictMatchesRuntime`) and `PULSE_ADVISORY_EXTRA_PASS` stays one added scan. **The chain stays out:** `ChainRefusal` judges with `total()` admission off (a stage has no two-phase runtime), so every `total()` stage keeps `PULSE_CHAIN_NOT_MERGEABLE` with the row-local reason, runtime and validator alike (`TestChainGate_ValidatorMatchesRuntime`). Grouped, multi-layer and chain `total()` stay sequential / refused (v1.x). Gates: the bit-exactness family `TestBitExact_Archive` / `TestBitExact_Heavy` (DecodeWorkers 2/3/7/8, ShardWorkers 2/3/8 on a scattered nine-shard archive, each parallel cell required to fan out, == the serial bits; plain, weighted, filtered share-over-label and matrix-beside `formula_total*` shapes, the grouped and multi-layer ones pinned to their serial arm), `TestParallelTotals`, `TestTotalsPrepass_*`, `TestFormulaTotal_PartitionedRouting`.

**Tally attributes (U51 E3-S2, #456).** `ATTR_SCALE_SCORE`, a non-centroid `ATTR_PROFILE_SIMILARITY`, an `ATTR_VEC_DISTANCE` over a row-local metric and no centroid (`vectors.ComparisonRowLocal`: the metric — explicit or the vector kind's default — must resolve and not be fitted; `std_euclidean` / `mahalanobis`, `fit_on` or a bound `fit`, stay out) and an extension attribute declared `Mergeable` (`row_local`, `extend.MergeableAttribute`) keep a per-run tally — their `Components.Attributes` operator counts and the Response warnings those back (`PULSE_ATTR_SCALE_OUT_OF_RANGE`, `PULSE_VECTOR_REFERENCE_MISSING` with its smallest-ten unmatched keys, `PULSE_VECTOR_METRIC_DOMAIN` with its reasons). They implement `processing.MergeableAttributeTally` (`MergeTally(other RowLocalAttribute)`; the extension adapter forwards `extend.MergeableAttribute.MergeTally` with the partner unwrapped), so `mergegate` admits them — on both reducers AND chain stages (the shared `MergeRefusal`); the centroid forms stay two-pass and out. Each partition keeps its `rowLocalAttrSpec`s on `shardPartial.attrs` — the instance plus its `processing.AttributeFloor` (`{n, n_null}`, under `ComputePlan.Attributes`) — and `partialMerger.add` folds them slot by slot (`mergePartitionAttributes`: floors add, `processing.MergeAttributeTally` folds the tally; a `MetaAttribute` without a fold is `PROCESSING_INTERNAL`). `finalizeMergedPartial` then folds the merged slots into the run's ONE bound build (`boundAttributes`, which scores no row and is where fit warnings and the capture offer come from) and emits from it once, cohort-wide: the `Components.Attributes` entries (declared order) and every slot's warnings prepended in declared order — no per-partition warning ever reaches the response. A zero-row run reports the bound build's zero tallies, as serial does. Integer tallies, so the fold is exact in any order. An extension attribute emitting components (one rule, `attributeEmitsComponents`, feeds both merge-fact sources) without the declaration stays serial and chain-refused (`registryMergeFacts` / `snapshotMergeFacts`). Gates: `TestTallyMerge_*` (root: both arms ungrouped / grouped / zero-row == serial, chain stages runtime ≡ validator, predict fan-out ≡ runtime, the probe refusals), `TestShardWorkers_AttributeComponentsParity`, the `scale_score_*` rows of `TestShardWorkers_ComponentsParity_GroupedAndFlatArchives` / `TestDecodeWorkers_GroupedAnswersParity`, `TestProcessChainCapability_RowLocalAttributesMatchGate`, `TestExtensions_ComponentAttributesRuntimeMatchesSnapshot`, `TestMergeRefusal` (vec-distance rows).

**Attribute slots (U51 E5-S4).** A row-local attribute's output used to land in the per-record overflow map (`recordAux.ovVals`), allocated per row on every arm that mints a fresh record (both reducers, the serial buffered scan). `processing.BindRecords(schema, keep, extras...)` now gives each off-schema name in `extras` a positional float64 slot (value in the `vals` tail past the set-mask and group-index words, has/null bits in two planes past the schema slots'); `recordBindingFor(..., attributeLabels(req)...)` passes the request's labels on `shardDecodeFor`, the parallel-decode context, the totals pre-pass, both crosstab decode fan-outs and the serial iterators (`scanIterator.SetExtras`, from `applyProjection` / `applyCrosstabProjection`). An extra reads exactly as its overflow entry did (wide values stay in `ovWide`; schema names are never extras), and the list is a sizing hint only. Gates: `TestRecord_PositionalMatchesLegacyMapSemantics` (`+extras` bindings), `TestRecord_ExtraSlots*`, `TestAttributeSlots_*` (allocations a row flat from 1 to 13 attributes on every arm), `TestBitExact_RetentionShapeChain` (serial vs both reducers, slots on vs off, byte-identical).

**Grouped fan-out is cardinality-blind (U51 E3-S4).** A mergeable grouped request fans out whatever its key count; there is no cardinality admission. Measured (`BenchmarkGroupedSumScale`, `docs/internals/BENCHMARKS_BASELINE.md` "Grouped fan-out by cardinality"): value-keyed groupers (`GROUP_ROUNDED`, `GROUP_RANGE`) stop gaining once each partition is expected to mint keys for ≳ 70% of its rows (8 workers: 1.01× at share 0.74, ~2× the allocation), and predict cannot see their cardinality (it depends on values); dictionary-keyed ones (`GROUP_CATEGORY`) still gain 1.04–1.05× at share 0.92. A rule routing high-cardinality dictionary groupings serial was measured and dropped. The decode dispatch counts records from the file length less the header + schema bytes `Open` read (`openedRecordCount`; `Cohort.payloadOffset`), never a second schema decode (`TestOpenedRecordCount_NoSecondSchemaRead`).

## Blocked merge (`processing.BlockMerger`)

The opt-in for a reducer whose answer must be BIT-identical under every concurrency knob, not merely within ULP. Surface: `internal/processing/block_merge.go`; the one built-in user is the U16 matrix slot (`MAT_*`, below — an extension `MAT_*` (U30) never opts in itself: it runs in that same slot with only the finalizer swapped, so it inherits the tree), and every other reducer keeps the `MergeOnline` path above untouched.

- **Positions.** Every record source stamps the row's merge-block position on the `Record` (`SetMergePosition(shard, shardStart, record)` → `MergeBlock() (BlockKey, bool)`; packed into the Record's padding, size stays 96 bytes). Blocks key by the GLOBAL record ordinal `shardStart + record`: the serial single-file iterator (`streamingIterator`, shard 0, start 0) and the parallel-decode workers (shard 0, start 0, `segment start + offset`); the serial archive iterator (`shardIter`) and the per-shard reducer (`processOneShard`) stamp the shard's archive index, its start (`shardStarts`: the record counts of the shards before it, from `ShardEntry.RecordCount`) and the in-shard index. `BlockKey{Block, Shard, Head}` with `Block = global / linalg.MergeBlockSize` (4096) and `Head` = the shard holds the block's first ordinal (always on a single file); keys order by block, then shard.
- **State.** A `BlockMerger` is an `OnlineAggregator` whose state is a `*BlockCoMoments` — one FRAGMENT per (block, shard) that saw a row. A head fragment holds a `linalg.CoMoment`, rows folded in record order; a fragment whose shard starts inside the block (at most the shard's first block, ≤ 4096 rows) buffers its rows instead. A record no source stamped (join output, a chain stage, a test harness) is refused `PROCESSING_INTERNAL` rather than guessed at.
- **Merge.** `mergeShardPartials` (both parallel arms, ungrouped slots and grouped buckets) moves the other partition's fragments in via `processing.MergeBlockMerger` → `BlockCoMoments.Absorb` — a disjoint union, so partition order cannot reach the bits; a key on both sides means a fragment was split across partitions and is `PROCESSING_INTERNAL`.
- **Tree.** At `Finalize` the reducer calls `BlockCoMoments.Tree`: each block's partial is its head fragment (or an empty accumulator) with the block's other fragments replayed on top in shard order — the block's sequential fold in ordinal order — then one `linalg.MergeTree` over the block partials in block order. A block no row reached has no entry (absence is data-determined); no blocks ⇒ an empty accumulator; a head that is not its block's first fragment is `PROCESSING_INTERNAL`. Serial, any `DecodeWorkers`, any `ShardWorkers` count and any shard split — a shard archive versus its single-file twin — therefore produce the same bits on every architecture (the kernels are FMA-free). `AGG_VEC_MEAN` / `AGG_VEC_SUM` / `AGG_VEC_SD` (Chan-combined Welford moments) key their per-element partials the same way (`aggregator_vector.go`, through `MergeOnline`'s disjoint union).
- **Matrix slots.** `Request.Matrices` state is not an aggregator: each partition (`shardPartial`, both arms) carries a `*processing.MatrixSlots` (`mats`, the `aggs` analogue, nil without matrices; a grouped partition carries per-bucket `*processing.GroupedMatrices` in `groupedMats` instead, fed per key by `foldGroupedRow`, merged key by key and rendered by the grouped tail in the final, `Request.Sort`-applied Data order — `.claude/reference/matrix-and-vectors.md`) built off the STAMPED request by `processing.BuildMatrixSlots`, folds every filter-passing row after the universal floor (`processOneShard` / the decode callback), merges in `mergeShardPartials` via `MatrixSlots.Merge` (slot-wise `MergeBlockMerger`, so the same disjoint union), and `finalizeMergedPartial` sets `Response.Matrices` from `MatrixSlots.Finalize` on every arm.
