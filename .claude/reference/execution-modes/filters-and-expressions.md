# Execution modes — filter precompute, before-filters attributes, compile-once expressions

Per-topic slice of the execution-modes reference. Index (Mode index + section map): `.claude/reference/execution-modes.md` — load it first, then only the slice(s) your engine work touches. Split out of `execution-modes/shards-and-merge.md` at U51 E2-S4 (slice ceiling).

## Filter precompute (grouped cohorts)

Over a parent-grouped (`0x02`) cohort a filter whose every input field is a member of ONE group has at most `entry_count` distinct answers, whatever the row count or order. `internal/processing/filter_precompute.go` evaluates it once per dictionary ENTRY into a two-bit-per-entry verdict table (unknown / fail / pass / per-row) and turns each row's verdict into a bit test on the row's entry index. On the effort's reference shape that is ~109K evaluations instead of ~1.4M. Derived at read time, never persisted; opt-out process-wide with `processing.SetFilterPrecompute(false)` (benchmarks / A-B only — it changes speed, never a result). Diagnostics: `processing.FilterPrecomputeStats()` (tables built, entry evaluations, table bytes, ineligible pairs) — only table builds and entry evaluations touch its atomics, never the per-row path.

**Seam.** The wrap is at the `FilterFunc`: `Processor.buildFilterFuncs` and `processing.BuildFilters` wrap each ELIGIBLE filterer (grouped build schema only; an ungrouped schema gets the builder's `FilterFunc` back unchanged, so a `0x01` cohort pays nothing). `applyFilterPass` is untouched, so `{n_in, n_out, n_null_input}` are the per-row counts by construction: `n_in` / `n_out` follow the verdict, and `n_null_input` still reads the record's own null state (`Record.IsNull`, now one name resolution instead of three). **The entry index** reaches the record through `encoding.GroupIndexRecord` (`SetGroupIndices(schema, idx)`), called by the grouped reuse decoder after every row on the full, plan, plain-sink and run-skip paths (`nil` for a plan that decodes nothing). `*processing.Record` stores the indices bit-exactly in the tail of `vals` past the set-mask words (`recordLayout.nGroups`; no allocation, none at all for an ungrouped schema) and reports them through `Record.GroupIndex(g)` only while valid: `ClearForRow` and `resetRun` — every schema-field mutation that is not a decode write — withdraw them, and indices addressing another schema than the record's own (by identity; the decoder passes the GROUPED schema, not its `Logical()` view) are refused. A feature or attribute rewriting a member's name therefore sends that row per-row, never to a stale verdict.

**Eligibility** (`precomputeInputs`, then per record schema `precomputeGroup`): every built-in filterer on its `Field`; `FILTER_EXPRESSION` when its AST's free identifiers are all fields and every call is pure — expr-lang built-ins except `now()`, the set built-ins, and `lookup()` only when every lookup table is a static `Rows` map. Embedder `ExprFunctions` (even one shadowing a built-in), `let` names, `$env` and off-schema columns disqualify. Extension filterers never qualify — a registration declares no purity and `FieldInputs` does not prove statelessness. Inputs must resolve to unique field names in ONE group: a group member mixed with a row field, or two groups, stays per-row (the verdict space is the product; there is no small table). **Evaluation is lazy**: an entry is evaluated the first time a row carrying it reaches the filter, so the work is the DISTINCT entries reached — never more than the per-row count, even behind a selective earlier slot. An entry whose evaluation ERRORS is marked per-row and re-evaluated on each of its rows, so an error surfaces on exactly the row the per-row path raises it on, and never when no such row gets there. Per-entry evaluation decodes only the filter's input members (`internal/encoding.NewGroupEntryDecoder(schema, g, fields)`), not the whole entry.

**Arms.** Routed: streaming Process (reuse record), buffered and projected Process (fresh record per row through `ReadRecordReusedWithPlan`), fused crosstab and buffered crosstab, parallel buffered Process (one `FilterFunc` set — and so one verdict table — per worker; bounded by workers × entries), Compose (per slot), ProcessChain stage 0, `FacetSchema`, and `FilterToFile` (its map decode forwards `RecordReader.GroupIndex` into `Record.SetGroupIndices`; `TestGroupedCohort_FilterToFilePrecompute`). Per-row fallback (correct, not precomputed): every other map-decode consumer — `Lookup`, the shard reducer, the projection-without-plan fallback — plus joined records (`Request.Joins`), ProcessChain stages ≥ 1 (synthesised ungrouped cohorts) and any extension filterer. Shard archives refuse grouped shards today; the tables are keyed by the record's schema pointer (the shard's own dictionary), so grouped shards need no change here beyond the decoder handing over that shard's schema. Gates: `TestFilterPrecompute_ParityEveryFilterer` (all built-in filterers, both reuse arms, verdicts + components vs per-row and vs `0x01`, evaluation count = distinct entries, ≥10x at 12x fanout), `TestGroupedCohort_FilterPrecomputeParity` (facade arms, exact entry-evaluation counts), `TestFilterPrecompute_ParallelDecode`, `TestGroupedDecode_ReportsGroupIndices`, `TestRecord_GroupIndexWithdrawnByEveryMutator`. Bench: `BenchmarkFilterPrecompute` (`internal/service/`).

## Before-filters attributes (`ATTR_PREVIOUS_STATE`)

A per-operator property, `prevstate.BeforeFilters(type)` (`internal/prevstate`), true for `ATTR_PREVIOUS_STATE` ONLY: the attribute runs over EVERY decoded record (after the pre-filter features) BEFORE the filter pass, so a date window keeps each subject's first in-window record with its TRUE previous state — the long panel's crosstab then equals the wide `state_t(k-1)` × `state_t(k)` one under the same window (`TestPreviousState_DateWindowKeepsFirstInWindowTransition`). Every other attribute (extensions included) still runs over the filter-passing records.

- **Runtime.** `Processor.filterThenAttributes` (`internal/processing/processor.go`) is the one buffered filter + attribute step, shared by `processRecords` (ungrouped / grouped / Compose slots / chain stage 0), the buffered crosstab and `DeriveRecords` (materialize): before-filters slots in declared order over every record, the filter pass, then every other slot over the survivors; warnings and `Components.Attributes` keep DECLARED slot order. A request with no such slot takes the historical path byte-identically. The attribute is buffered-only, so no streaming, fused-crosstab, parallel-reducer or shard-merge arm ever meets it. A buffered crosstab under `DecodeWorkers > 1` DOES take `ArmParallelDecode`: the records are decoded in parallel segments, then the attribute scores the full decoded set (`previous_state_modes_test.go`); only the parallel REDUCER (row-local merge) never meets it.
- **Expressions.** The field-reference walk (`fieldRefWalk.preFilter`, predict and runtime alike) declares each before-filters label as a derived column from the filter step on: an expression filter — and any expression, an `ATTR_FORMULA` declared earlier included — may read it (`prev != nil` drops first records). It reads BY STATE NAME, exactly as its state field does (`prev == "paid"`, `prev in [...]`, string operators; a null absent — the source field's nil rules): the dictionary-inheritance view types it (predict `exprenv.DerivedDecl` in `compileRefusal`; runtime `exprenv.DerivedFields` declared + its code lifted through `exprenv.Bind` in `newExprProgramKeyed`, the view reaching every expression site — request and fit_on filters, `ATTR_FORMULA`, `total()` arguments — as `Processor.keySchema` through `keysBinder`). A request without the attribute binds byte-identically (`TestPreviousState_ExpressionsReadStateNames`, `TestPreviousState_UpgradeFromFreeFilter`). A field-keyed filter naming the label stays `SERVICE_VALIDATION` unknown field.
- **Counts.** Filter Components `{n_in, n_out}` and `Run` judge the filter alone. The attribute's floor `{n, n_null}` and operator counts are over every record it scored (`n + n_null` = `Run.total_records`).
- **Predict.** `PredictResult.ComputedBeforeFilters` (`computed_before_filters`, `omitempty`) lists the before-filters labels in declared order, from the same rule. Limits: `MaxEstimatedMemory` already charges the buffered arm every decoded record (the estimate never sees filter selectivity), so the unfiltered buffer is what is judged (`TestPreviousState_LimitsJudgeUnfilteredBuffer`).

## Compile-once expressions (`FILTER_EXPRESSION`, `ATTR_FORMULA`)

Both compile their expr-lang program ONCE per build (`internal/processing/expr_program.go`), never per row. **Prototype**: every schema field declared with the Go type `Record.AllValues` gives it (`exprValueType` — float64; string for a dictionary categorical; `[]string` for a dictionary set; `Decimal128` / `uint64` / `SetMask` otherwise), so build-time type checking equals the old per-row check on a row with every field present — same program, same results, same `PROCESSING_RUNTIME` "compiling … expression" error, now raised by `BuildFilters` / `buildFilterFuncs` / the attribute build (`bindAttribute` → `prepare`) before any row. A name the schema cannot declare (feature output, earlier attribute label) DEFERS the compile to the first record, against prototype + that record — the old first-row env — then caches it. **Env**: per row, only the named fields (`Record.exprValue`, pinned to `AllValues` by `TestRecord_ExprValueMatchesAllValues`) in a pooled map; `$env`, a deferred compile, or a record already carrying its `AllValues` map take the whole map. **Null**: a null field is absent → reads as nil. Rows with every referenced field present run the typed program; a null-input row runs an untyped twin (every name `any`, compiled lazily once) so nil follows expr-lang's nil rules uniformly (`== nil` true, `==` false, `!=` true, `in` false, `??` substitutes; ordering / arithmetic / nil-rejecting functions error). `FILTER_EXPRESSION` reads a null-input evaluation error (or nil result) as UNKNOWN → row dropped; `ATTR_FORMULA` raises it ("evaluating formula expression"). `now()` still evaluates per row. **Concurrency**: `*vm.Program` is immutable; evaluation takes a `vm.VM` from `exprVMPool` (`runPooled`, U51 E5-S4 — `expr.Run` built a VM and its stack per call, one allocation a row per expression; `VM.Run` resets its own state, so a pooled VM evaluates as a fresh one; `TestExprProgram_RunReusesVM`: a warm formula row allocates nothing), one goroutine per VM at a time; the lazy compiles sit behind a mutex + atomic publish. Gates: `TestExprProgram_CompilesOncePerBuild` (`processing.ExprCompileCount` deltas independent of row count), `TestExprProgram_MatchesPerRowCompile` (per-row-compile oracle), `TestExprValueType_MatchesAllValues` (every field type × every decode path), `TestExprFilter_NullSemantics`, `TestExprProgram_ConcurrentRuns` (`-race`). Bench `BenchmarkExprCompileOnce` (95-field join fixture, 100K rows): filter pass ~8.7 µs → ~0.14 µs/row, end to end ~24 → ~2.1 µs/row (0x01), ~24 → ~1.1 (0x02).
