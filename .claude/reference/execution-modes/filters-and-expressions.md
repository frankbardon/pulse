# Execution modes — filter precompute, before-filters attributes, post-window attributes, windows-first, compile-once expressions

Per-topic slice of the execution-modes reference. Index (Mode index + section map): `.claude/reference/execution-modes.md` — load it first, then only the slice(s) your engine work touches.

## Filter precompute (grouped cohorts)

Over a parent-grouped (`0x02`) cohort, a filter whose every input field is a member of ONE group has at most `entry_count` distinct answers, whatever the row count or order. `internal/processing/filter_precompute.go` evaluates it once per dictionary ENTRY into a two-bit-per-entry verdict table (unknown / fail / pass / per-row) and turns each row's verdict into a bit test on the row's entry index. Derived at read time, never persisted. `processing.SetFilterPrecompute(false)` turns it off process-wide (benchmarks / A-B only — it changes speed, never a result); `processing.FilterPrecomputeStats()` reports tables, evaluations and bytes without touching the per-row path.

**Seam.** The wrap is at the `FilterFunc`: each ELIGIBLE filterer is wrapped only on a grouped build schema (an ungrouped schema gets the builder's `FilterFunc` back unchanged, so a `0x01` cohort pays nothing). The filter pass itself is untouched, so `{n_in, n_out, n_null_input}` are the per-row counts by construction. **The entry index** reaches the record through `encoding.GroupIndexRecord` (`SetGroupIndices`), called by the grouped reuse decoder after every row. `Record.GroupIndex(g)` reports it only while valid: every schema-field mutation that is not a decode write withdraws it, and indices addressing another schema than the record's own (by identity) are refused. So a feature or attribute rewriting a member's name sends that row per-row, never to a stale verdict.

**Eligibility.** Every built-in filterer on its `Field`; `FILTER_EXPRESSION` when its free identifiers are all fields and every call is pure — expr-lang built-ins except `now()`, the set built-ins, `range_label()` (range tables are static), and `lookup()` only when every lookup table is a static `Rows` map. Embedder `ExprFunctions` (even one shadowing a built-in), `let` names, `$env` and off-schema columns disqualify. Extension filterers never qualify — a registration declares no purity. Inputs must resolve to unique field names in ONE group: a group member mixed with a row field, or two groups, stays per-row.

- **Evaluation is lazy:** an entry is evaluated the first time a row carrying it reaches the filter, so the work is the DISTINCT entries reached — never more than the per-row count.
- **An entry whose evaluation ERRORS is marked per-row** and re-evaluated on each of its rows, so an error surfaces on exactly the row the per-row path raises it on.
- Per-entry evaluation decodes only the filter's input members, not the whole entry.

**Arms.** Routed: streaming, buffered and projected Process, fused and buffered crosstab, parallel buffered Process (one verdict table per worker), Compose slots, ProcessChain stage 0, `FacetSchema`, and `FilterToFile`. Per-row fallback (correct, not precomputed): every other map-decode consumer (`Lookup`, the shard reducer, the projection-without-plan fallback), joined records, chain stages ≥ 1 (synthesised ungrouped cohorts) and any extension filterer. Tables are keyed by the record's schema pointer, so a grouped shard needs only its decoder to hand over that shard's schema. Pinned by `TestFilterPrecompute_ParityEveryFilterer` (verdicts and components vs per-row and vs `0x01`; evaluation count = distinct entries).

## Before-filters attributes (`ATTR_PREVIOUS_STATE`)

A per-operator property, `prevstate.BeforeFilters(type)`, true for `ATTR_PREVIOUS_STATE` ONLY: the attribute runs over EVERY decoded record (after the pre-filter features) BEFORE the filter pass, so a date window keeps each subject's first in-window record with its TRUE previous state — the long panel's crosstab then equals the wide `state_t(k-1)` × `state_t(k)` one under the same window. Every other attribute (extensions included) runs over the filter-passing records.

- **Runtime.** `Processor.filterThenAttributes` is the one buffered filter + attribute step (ungrouped, grouped, Compose slots, chain stage 0, the buffered crosstab and materialize): before-filters slots in declared order over every record, the filter pass, then every other slot over the survivors; warnings and `Components.Attributes` keep DECLARED slot order. A request with no such slot is byte-identical. The attribute is buffered-only, so no streaming, fused-crosstab, parallel-reducer or shard-merge arm meets it. A buffered crosstab under `DecodeWorkers > 1` does take parallel decode — segments decode in parallel, then the attribute scores the full decoded set.
- **Expressions.** The field-reference walk (predict and runtime alike) declares each before-filters label as a derived column from the filter step on, so an expression filter — and any expression, an earlier `ATTR_FORMULA` included — may read it (`prev != nil` drops first records). It reads BY STATE NAME, exactly as its state field does (`prev == "paid"`, `prev in [...]`; a null is absent): the dictionary-inheritance view types it at every expression site. A field-keyed filter naming the label stays a `SERVICE_VALIDATION` unknown field.
- **Counts.** Filter Components `{n_in, n_out}` and `Run` judge the filter alone. The attribute's floor `{n, n_null}` and operator counts are over every record it scored (`n + n_null` = `Run.total_records`).
- **Predict.** `PredictResult.ComputedBeforeFilters` (`computed_before_filters`, `omitempty`) lists the before-filters labels in declared order. `MaxEstimatedMemory` already charges the buffered arm every decoded record (the estimate never sees filter selectivity), so the unfiltered buffer is what is judged.

## Post-window attributes (transformed predictors)

Attributes run before windows. An attribute that reads a window label — directly, or through the label of an earlier post-window attribute — is WINDOW-DEPENDENT. One classification decides it, `vectors.PostWindowAttributes` (`internal/vectors/post_window.go`), read by the field-reference walk (predict and the runtime entry check) and by the engine's ordering, so the two never drift. Reads: an `ATTR_FORMULA`'s field + free identifiers; an `ATTR_REG_PREDICT` (or a `params.fit` fitted / residual / leverage attribute) the bound model's terms; any other slot `vectors.AttributeInputNames`. A window label equal to a schema field is no window-derived name. A request with no window or no attribute classifies to the zero plan without allocating.

- **Who moves.** A window-dependent ROW-LOCAL slot (`vectors.PostWindowEligible`: `ATTR_FORMULA` without `total()`, `ATTR_REG_PREDICT`) moves to the post-window phase when the windows run over the record rows (no groups, aggregations or crosstab — or windows-first, below). Any other window-dependent slot (a non-row-local type, a `total()` formula, a fit-referenced regression attribute, an extension attribute, or any slot outside that shape) is `PULSE_ATTRIBUTE_WINDOW_ORDER` `{attribute, field}`, whose message and fixups name both routes: windows-first, and materialize first.
- **Walk.** The moved slots are judged right after the windows, in declared order, so a sort key or a post-test may name them and a window may not. Their labels are visible to regressions; a test or a weight still may not read them.
- **Runtime.** After `applyWindows`, the window labels the moved slots read are copied onto the filtered records (`copyWindowMembers`; a non-numeric window value is `PROCESSING_CONFIG`), then the moved slots run over those records, writing the record (regressions, matrices and later slots read it) and the output row (a null leaves the cell absent). Warnings and `Components.Attributes` keep DECLARED slot order. A processor driven without the service re-raises the refusal. Windows already force buffered, so no streaming / merge arm meets the phase.
- **Byte identity.** The zero plan takes the historical code path at every site; `TestWindowPredictor_PostWindowPlanInertOverCorpus` holds the example corpus to it. Parity: `TestWindowPredictor_AttributeWindowOrderParity`.

## Windows-first

By default windows run AFTER the groups, aggregations and crosstab, over their output rows (a window over a grouped `AGG_SUM`), and over the record rows only when the request has none of the three. A request is WINDOWS-FIRST when it has groups, aggregations or a crosstab AND one of them reads a window output — an aggregation's `field` or column param, a grouper's `field`, a crosstab axis / cell / margin aggregation — directly or through a post-window-eligible attribute, transitively. Its windows then run first, over the filtered record rows, and the groups / aggregations / crosstab read the window and post-window values off the records. Skill: `skills/windows-first.md`.

- **One classifier.** `vectors.WindowsFirst(req, schema, c)` (`internal/vectors/windows_first.go`) over a `vectors.Classifier{Route, Cat, Ext}`. Everything that asks "do the windows run over the records?" reads it, through `PostWindowAttributes` or `vectors.WindowsOverRecords` — column resolution, matrix plans, projection, regressions, predict's streamability, Explain. Grep `WindowsOverRecords` before adding a site that needs the answer. A window label equal to a schema field or a named vector is no window output.
- **Extension `FieldInputs`.** `Classifier.Ext` makes an extension aggregator's or grouper's hook names count as its column reads, so a window label read only through one turns the mode on and is copied onto the records. Predict and runtime both hand the hook stand-in params and treat a panic as no declaration. Nil without hooks (zero cost).
- **One catalog.** Every site passes the bound-model catalog it holds in `Classifier.Cat`, so windows-first behaves the same whether a slot reads a window label directly or a bound model's terms do; regressions, holdouts and vector members then read the window labels as record columns too. Predict carries the loaded catalog on a copy of its options (never the caller's). `mergegate` passes none — it excludes every request with windows first. (Keep the catalog a function PARAMETER on the matrix resolver: a struct field leaks its callbacks to the heap, `TestObservabilityOffNoAllocs`.)
- **Walk.** In the mode the windows and post-window attributes are judged between the regressions and the groups, against the record columns; the groups, aggregations and crosstab then see every window and post-window label. A window reading an aggregation output label that is no record column is `PULSE_WINDOW_INVALID` `details.reason: "windows_first_reads_aggregate"` `{window_index, field}`. The output rows carry group keys and aggregation labels only, so a sort key or post-test naming a window label is refused. A window-label weight and a tier-1 test reading a window label stay refused.
- **Streamability.** Buffered on every shape (streaming refuses any window; `crosstabfuse.Decide` declines any window); predict's reason names windows-first and is appended ahead of the crosstab gate (`TestWindowsFirst_PredictStreamableMatchesRuntime`).
- **Crosstab windows nothing reads.** A crosstab writes no output row, so its windows run only windows-first. A crosstab window no axis, cell or margin aggregation reads (directly or through a post-window attribute) is `PULSE_WINDOW_INVALID` `details.reason: "crosstab_window_unread"` `{window_index}` (`vectors.CrosstabWindowRefusal`, walk and runtime alike) rather than being dropped silently.
- **Runtime.** After the filter and pre-window attribute pass and BEFORE any group, aggregation or crosstab cell, `Processor.windowsFirstPass` (`attribute_post_window.go`) runs the windows over scratch record rows (`partition_by` / `order_by` unchanged), copies onto the filtered records every window label something reads (`vectors.WindowsFirstReads`, first-read order; a non-numeric value `PROCESSING_CONFIG` `{field, value_type}`), then runs the post-window attributes. Ungrouped and grouped aggregation (per-bucket aggregations, tier-1 tests and Components) and the buffered crosstab then run over the window-carrying records. Every result equals the same request over a cohort carrying the window column, against the BUFFERED arm (a streamed twin folds `AGG_STDDEV` Welford-style, other bits). The response rows carry no window column.
- **Lagged categories.** A `WIN_LAG` / `WIN_LEAD` of a categorical lands on the records as its source dictionary's codes, which `GROUP_CATEGORY` (group or crosstab axis) keys by label. Any other read is `PULSE_FIELD_TYPE_UNSUPPORTED` `categorical_window_output` (`vectors.CategoricalWindowRefusal`); an extension window writing strings is the copy's `PROCESSING_CONFIG`.
- **Weights.** A window has no weighted form and no slot weight, so a request-level `weight` on any request with windows is `PROCESSING_CONFIG` `windows[i]: <WIN> has no weighted form and carries no slot weight; drop the request weight` (predict and runtime alike); an instance `DefaultWeight` is skipped on the window. A slot `weight` on an aggregation weighs the window column like any cohort column.
- **Byte identity.** Every name that turns the mode on was refused before (unknown field, or `PULSE_ATTRIBUTE_WINDOW_ORDER`), so no valid request changes meaning; the corpus test above holds every example to `WindowsFirst == false`.

## Compile-once expressions (`FILTER_EXPRESSION`, `ATTR_FORMULA`)

Both compile their expr-lang program ONCE per build (`internal/processing/expr_program.go`), never per row.

- **Prototype.** Every schema field is declared with the Go type `Record.AllValues` gives it (`exprValueType` — float64; string for a dictionary categorical; `[]string` for a dictionary set; `exprenv.U64` for a `u64`, below; `Decimal128` / `uint64` / `SetMask` otherwise), so build-time type checking equals a per-row check on a row with every field present, and the `PROCESSING_RUNTIME` "compiling … expression" error is raised before any row. A name the schema cannot declare (feature output, earlier attribute label) DEFERS the compile to the first record, then caches it.
- **Env.** Per row, only the named fields (`Record.exprValue`, pinned to `AllValues` by `TestRecord_ExprValueMatchesAllValues`) in a pooled map; `$env`, a deferred compile, or a record already carrying its `AllValues` map take the whole map. Projection decodes a constant-name `$env.f` member as `f` and widens to every field on a dynamic `$env` use.
- **Null.** A null field is absent → reads as nil. Rows with every referenced field present run the typed program; a null-input row runs an untyped twin (every name `any`, compiled lazily once) so nil follows expr-lang's nil rules uniformly (`== nil` true, `==` false, `!=` true, `in` false, `??` substitutes; ordering / arithmetic / nil-rejecting functions error). `FILTER_EXPRESSION` reads a null-input evaluation error (or nil result) as UNKNOWN → row dropped; `ATTR_FORMULA` raises it. `now()` still evaluates per row.
- **Concurrency.** `*vm.Program` is immutable; evaluation takes a pooled `vm.VM` (a warm formula row allocates nothing), one goroutine per VM at a time; lazy compiles sit behind a mutex + atomic publish. Pinned by `TestExprProgram_CompilesOncePerBuild`, `TestExprProgram_MatchesPerRowCompile` and `TestExprProgram_ConcurrentRuns` (`-race`).

**Request params.** `Request.Params` binds as compile-time CONSTANTS, never as an env name: a patcher registered FIRST rewrites each declared `params.<name>` / `params["<name>"]` into a constant of its normalized type (`exprenv.NormalizeParams`: an integer int64, else uint64, else float64; string; bool; a one-kind list), so the row env never carries params and a program is specific to its values — no stale program can serve another run. The run compiles through a per-request registry (`ExtensionRegistry.WithParams`), so every arm, pre-pass and overlay pass folds the same values, and a param read never defers the compile. `total()`'s patcher runs BEFORE the fold on both sides.

- Refusals live in the field-reference walk: `PULSE_PARAMS_INVALID` first, then per compile `PULSE_PARAMS_FIELD_COLLISION` (`params` is a column there) or `PULSE_PARAMS_UNDECLARED`. A bare `params` is never a parameter read.
- Between two params, or a param and a literal, expr-lang compares mixed integer kinds through `int`, so a uint64 param above 2^63 is exact for `==` / `!=` but not for ordering. A param against a `u64` field compares exactly (below).
- **Inheritance.** `ComposedRequest.Params` / `ChainRequest.Params` merge into every sub-request during normalization (each Compose slot after expansion, each fit request, each chain stage), the sub-request's own key winning, through ONE function per root (`descx.InheritComposeParams` / `InheritChainParams`) called by predict and runtime at the same point; the top-level block is validated first. Merged sub-requests are shallow copies, so the echo carries the merged params. A Compose-host `OVERLAY_FORMULA` reads the batch's top-level params.
- **Facet params.** `FacetRequest.Params` follows the same rules for the base and additive filterers, labels and overlays; the facet walk hands it to the synthetic Request so predict and the run refuse alike.

**Exact u64 fields.** A `u64` field binds as its stored word, `exprenv.U64`, as does a constant-name `$env.id` / `$env["id"]` / `$env?.id` read and a FORMULA ALIAS (an `ATTR_FORMULA` whose expression IS a bare u64 read; `id + 0` keeps the float echo). An expression using `$env` DYNAMICALLY keeps the echo for every u64, since those reads reach no patcher. Three patchers in `internal/exprenv/u64.go`:

1. a one-shot WRAP turns every U64-typed node into its float64 echo (expr-lang's checker does not count a named integer type as a number, so it runs before every other one-shot patcher) — except a `let` initializer that is a bare u64 read, so `let k = id; k == N` compares exactly;
2. a one-shot COMPARE rewrites an accepted `==` `!=` `<` `<=` `>` `>=` or `in` over a wrapped operand against a number or an `any` value (never a decimal) into an exact builtin; a non-number at run time takes the historical operator over the echo, same panic text;
3. a repeatable RETYPE, registered LAST, clears those calls' types after each pass so the final check re-judges their arguments.

**Unchanged:** every arithmetic / function / result type (always the echo), compile errors, nil rules. **Changed by design:** a comparison or `in` whose operands differ past 2^53 — `id == 9007199254740993` is false for id = 2^53, which the rounded echo called true. Predict declares the same type; the filter precompute's per-entry decode writes the word too, and a folded `params` read does not disqualify a filter from precompute. Pinned by `TestU64Expr_*` and `TestU64ParamsInvariance_Heavy` (DecodeWorkers ≡ 1).
