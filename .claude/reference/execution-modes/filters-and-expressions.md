# Execution modes — filter precompute, before-filters attributes, post-window attributes, windows-first, compile-once expressions

Per-topic slice of the execution-modes reference. Index (Mode index + section map): `.claude/reference/execution-modes.md` — load it first, then only the slice(s) your engine work touches. Split out of `execution-modes/shards-and-merge.md` at U51 E2-S4 (slice ceiling).

## Filter precompute (grouped cohorts)

Over a parent-grouped (`0x02`) cohort a filter whose every input field is a member of ONE group has at most `entry_count` distinct answers, whatever the row count or order. `internal/processing/filter_precompute.go` evaluates it once per dictionary ENTRY into a two-bit-per-entry verdict table (unknown / fail / pass / per-row) and turns each row's verdict into a bit test on the row's entry index. On the effort's reference shape that is ~109K evaluations instead of ~1.4M. Derived at read time, never persisted; opt-out process-wide with `processing.SetFilterPrecompute(false)` (benchmarks / A-B only — it changes speed, never a result). Diagnostics: `processing.FilterPrecomputeStats()` (tables built, entry evaluations, table bytes, ineligible pairs) — only table builds and entry evaluations touch its atomics, never the per-row path.

**Seam.** The wrap is at the `FilterFunc`: `Processor.buildFilterFuncs` and `processing.BuildFilters` wrap each ELIGIBLE filterer (grouped build schema only; an ungrouped schema gets the builder's `FilterFunc` back unchanged, so a `0x01` cohort pays nothing). `applyFilterPass` is untouched, so `{n_in, n_out, n_null_input}` are the per-row counts by construction: `n_in` / `n_out` follow the verdict, and `n_null_input` still reads the record's own null state (`Record.IsNull`, now one name resolution instead of three). **The entry index** reaches the record through `encoding.GroupIndexRecord` (`SetGroupIndices(schema, idx)`), called by the grouped reuse decoder after every row on the full, plan, plain-sink and run-skip paths (`nil` for a plan that decodes nothing). `*processing.Record` stores the indices bit-exactly in the tail of `vals` past the set-mask words (`recordLayout.nGroups`; no allocation, none at all for an ungrouped schema) and reports them through `Record.GroupIndex(g)` only while valid: `ClearForRow` and `resetRun` — every schema-field mutation that is not a decode write — withdraw them, and indices addressing another schema than the record's own (by identity; the decoder passes the GROUPED schema, not its `Logical()` view) are refused. A feature or attribute rewriting a member's name therefore sends that row per-row, never to a stale verdict.

**Eligibility** (`precomputeInputs`, then per record schema `precomputeGroup`): every built-in filterer on its `Field`; `FILTER_EXPRESSION` when its AST's free identifiers are all fields and every call is pure — expr-lang built-ins except `now()`, the set built-ins, and `lookup()` only when every lookup table is a static `Rows` map. Embedder `ExprFunctions` (even one shadowing a built-in), `let` names, `$env` and off-schema columns disqualify. Extension filterers never qualify — a registration declares no purity and `FieldInputs` does not prove statelessness. Inputs must resolve to unique field names in ONE group: a group member mixed with a row field, or two groups, stays per-row (the verdict space is the product; there is no small table). **Evaluation is lazy**: an entry is evaluated the first time a row carrying it reaches the filter, so the work is the DISTINCT entries reached — never more than the per-row count, even behind a selective earlier slot. An entry whose evaluation ERRORS is marked per-row and re-evaluated on each of its rows, so an error surfaces on exactly the row the per-row path raises it on, and never when no such row gets there. Per-entry evaluation decodes only the filter's input members (`internal/encoding.NewGroupEntryDecoder(schema, g, fields)`), not the whole entry.

**Arms.** Routed: streaming Process (reuse record), buffered and projected Process (fresh record per row through `ReadRecordReusedWithPlan`), fused crosstab and buffered crosstab, parallel buffered Process (one `FilterFunc` set — and so one verdict table — per worker; bounded by workers × entries), Compose (per slot), ProcessChain stage 0, `FacetSchema`, and `FilterToFile` (its map decode forwards `RecordReader.GroupIndex` into `Record.SetGroupIndices`; `TestGroupedCohort_FilterToFilePrecompute`). Per-row fallback (correct, not precomputed): every other map-decode consumer — `Lookup`, the shard reducer, the projection-without-plan fallback — plus joined records (`Request.Joins`), ProcessChain stages ≥ 1 (synthesised ungrouped cohorts) and any extension filterer. Shard archives refuse grouped shards today; the tables are keyed by the record's schema pointer (the shard's own dictionary), so grouped shards need no change here beyond the decoder handing over that shard's schema. Gates: `TestFilterPrecompute_ParityEveryFilterer` (all built-in filterers, both reuse arms, verdicts + components vs per-row and vs `0x01`, evaluation count = distinct entries, ≥10x at 12x fanout), `TestGroupedCohort_FilterPrecomputeParity` (facade arms, exact entry-evaluation counts), `TestFilterPrecompute_ParallelDecode`, `TestGroupedDecode_ReportsGroupIndices`, `TestRecord_GroupIndexWithdrawnByEveryMutator`. Bench: `BenchmarkFilterPrecompute` (`internal/service/`).

## Before-filters attributes (`ATTR_PREVIOUS_STATE`)

A per-operator property, `prevstate.BeforeFilters(type)` (`internal/prevstate`), true for `ATTR_PREVIOUS_STATE` ONLY: the attribute runs over EVERY decoded record (after the pre-filter features) BEFORE the filter pass, so a date window keeps each subject's first in-window record with its TRUE previous state — the long panel's crosstab then equals the wide `state_t(k-1)` × `state_t(k)` one under the same window (`TestPreviousState_DateWindowKeepsFirstInWindowTransition`). Every other attribute (extensions included) still runs over the filter-passing records.

- **Runtime.** `Processor.filterThenAttributes` (`internal/processing/processor.go`) is the one buffered filter + attribute step, shared by `processRecords` (ungrouped / grouped / Compose slots / chain stage 0), the buffered crosstab and `DeriveRecords` (materialize): before-filters slots in declared order over every record, the filter pass, then every other slot over the survivors; warnings and `Components.Attributes` keep DECLARED slot order. A request with no such slot takes the historical path byte-identically. The attribute is buffered-only, so no streaming, fused-crosstab, parallel-reducer or shard-merge arm ever meets it. A buffered crosstab under `DecodeWorkers > 1` DOES take `ArmParallelDecode`: the records are decoded in parallel segments, then the attribute scores the full decoded set (`previous_state_modes_test.go`); only the parallel REDUCER (row-local merge) never meets it.
- **Expressions.** The field-reference walk (`fieldRefWalk.preFilter`, predict and runtime alike) declares each before-filters label as a derived column from the filter step on: an expression filter — and any expression, an `ATTR_FORMULA` declared earlier included — may read it (`prev != nil` drops first records). It reads BY STATE NAME, exactly as its state field does (`prev == "paid"`, `prev in [...]`, string operators; a null absent — the source field's nil rules): the dictionary-inheritance view types it (predict `exprenv.DerivedDecl` in `compileRefusal`; runtime `exprenv.DerivedFields` declared + its code lifted through `exprenv.Bind` in `newExprProgramKeyed`, the view reaching every expression site — request and fit_on filters, `ATTR_FORMULA`, `total()` arguments — as `Processor.keySchema` through `keysBinder`). A request without the attribute binds byte-identically (`TestPreviousState_ExpressionsReadStateNames`, `TestPreviousState_UpgradeFromFreeFilter`). A field-keyed filter naming the label stays `SERVICE_VALIDATION` unknown field.
- **Counts.** Filter Components `{n_in, n_out}` and `Run` judge the filter alone. The attribute's floor `{n, n_null}` and operator counts are over every record it scored (`n + n_null` = `Run.total_records`).
- **Predict.** `PredictResult.ComputedBeforeFilters` (`computed_before_filters`, `omitempty`) lists the before-filters labels in declared order, from the same rule. Limits: `MaxEstimatedMemory` already charges the buffered arm every decoded record (the estimate never sees filter selectivity), so the unfiltered buffer is what is judged (`TestPreviousState_LimitsJudgeUnfilteredBuffer`).

## Post-window attributes (transformed predictors, U57)

Attributes run before windows. An attribute that reads a window label — directly, or through the label of an earlier post-window attribute — is WINDOW-DEPENDENT; one classification decides it, `vectors.PostWindowAttributes` (`internal/vectors/post_window.go`), read by the field-reference walk (predict and the runtime entry check) and by the engine's ordering, so the two never drift. Reads: an `ATTR_FORMULA`'s field + `exprident.Free` identifiers; an `ATTR_REG_PREDICT` (or a `params.fit` `ATTR_REG_FITTED` / `_RESIDUAL` / `_LEVERAGE`) the bound model's terms (`model.Catalog` — the runtime `Set`, predict's `FitCatalog`); any other slot `vectors.AttributeInputNames`. A window label equal to a schema field is no window-derived name. A request with no window or no attribute classifies to the zero plan without allocating.

- **Who moves.** A window-dependent ROW-LOCAL slot (`vectors.PostWindowEligible`: `ATTR_FORMULA` without `total()`, `ATTR_REG_PREDICT`) moves to the post-window phase when the windows run over the record rows (no groups, aggregations or crosstab, or windows-first — `PostWindow.WindowsFirst`, below). Any other window-dependent slot — a non-row-local type, a `total()` formula, a fit-referenced regression attribute, an extension attribute (its `FieldInputs` included), or ANY slot outside that shape — is `PULSE_ATTRIBUTE_WINDOW_ORDER` `{attribute, field}` (message and fixups name both routes: windows-first, and materialize first), judged before an extension feature's open column set admits the name.
- **Walk.** Step 3 skips the moved slots; step 5b judges them right after the windows, in declared order, exactly as step 3 would (columns: the record columns + every window label + earlier post-window labels), so a sort key or a post-test may name them and a window may not. Their labels are visible to regressions at step 4 (`fieldRefWalk.postLabels`, `checkRegression`); a test or a weight still may not read them.
- **Runtime.** `processRecords` / `DeriveRecords` with a non-zero plan run `filterThenAttributeSlots` (every non-moved slot as before), then after `applyWindows` the window labels the moved slots read are copied onto the filtered records (`copyWindowMembers`, consumer `attribute`, `derivedFloat` — the materialize route's conversion; a non-numeric window value is `PROCESSING_CONFIG`), then `applyPostWindowAttributes` runs them over those records, writing the record (regressions, matrices, later slots read it) and the record's output row (a null leaves the cell absent). Warnings and `Components.Attributes` keep DECLARED slot order (`mergeAttrSlots`). A processor driven without the service re-raises the refusal (`Processor.postWindowPlan`), the buffered crosstab included. Windows already force buffered, so no streaming / merge arm meets the phase and predict's streamability is unchanged.
- **Byte identity.** The zero plan takes the historical code path at every site; `TestWindowPredictor_PostWindowPlanInertOverCorpus` holds the example corpus to it. Gates: `TestWindowPredictor_AttributeWindowOrderParity` (predict ≡ runtime), `TestWindowPredictor_PostWindowOpenWalk` (FR-13), `TestWindowPredictor_PostWindowFormulaEqualsMaterializedColumn`, `TestWindowPredictor_PostWindowScoresWindowTermModel`.

## Windows-first (mmm-followups E4)

Historically windows run AFTER the groups, aggregations and crosstab, over their output rows (a window over a grouped `AGG_SUM`), and over the record rows only when the request has none of the three. A request is WINDOWS-FIRST when it has groups, aggregations or a crosstab AND one of them reads a window output: an aggregation's `field` or built-in column param (`vectors.AggregationParamFieldKeys`, moved from the descriptor's `aggParamFieldKeys`, which aliases it; `vectors.AggregationColumnReads`), a grouper's `field`, or a crosstab axis grouper / cell / margin aggregation names a window label — or the label of a post-window-eligible attribute that reads one, transitively. Its windows then run first, over the filtered record rows, and the groups / aggregations / crosstab read the window and post-window values off the records.

- **One classifier.** `vectors.WindowsFirst(req, schema, route, cat)` (`internal/vectors/windows_first.go`). Everything that asks "do the windows run over the records?" reads it: `PostWindowAttributes` (`PostWindow.WindowsFirst`, with the route and model catalog — who moves, `Refusal`), `vectors.WindowsOverRecords(req, schema, cat)` (record-row shape OR `WindowsFirst` over the same catalog — `ComputedColumns`, so `ResolveRequest`, every per-slot resolver, the matrix plans and projection; `RegressionWindowReads`; the walk's `checkRegression` / `checkHoldout` via `fieldRefWalk.overRecords`), `AttributeWindowOrderRefusal(req, windowsFirst, …)` (the why), predict's streamability, Explain (through `PostWindowAttributes`). A window label equal to a schema field or a named vector is no window output. An extension aggregator's `FieldInputs` are invisible to the static classification: a window label read only through one does not turn the mode on (unknown field) — still a limit after E4-S6: the catalog does not carry it, and closing it needs a SECOND input at every windows-first site, the extension `FieldInputs` hook (the runtime `ExtensionRegistry`, predict's `ExtensionsSnapshot.DeclaredFieldInputs`), which the extension-free classification and most of its callers (`ComputedColumns`, the vector resolvers) do not hold. Predict and the runtime refuse the read alike (unknown field); it is never silently dropped.
- **One catalog (E4-S6).** Every site passes the bound-model catalog it holds, so windows-first behaves the same whether a slot reads a window label directly or a bound model's terms do (an aggregation over an `ATTR_REG_PREDICT` label whose model reads a window): its regressions, holdouts and vector members read the window labels as record columns too. Engine: `Processor.catalog()` (the bound `model.Set`) into `ExprVectors`, `ResolveAttributeInputs` / `ResolveAggregationInputs`, the grouper / test resolvers, `resolveMatrixPlans` (`ResolveMatricesWith`'s catalog PARAMETER, grouped too — a `MatrixResolve` field would leak its callbacks to the heap, +3 allocations a predict, `TestObservabilityOffNoAllocs`) and `windowRecordColumns`; projection takes `NeededFieldsWithModels`' set; the service hands `catalogOf(model.SetFrom(ctx))` to the reducers and `LimitInputs.Models`. Predict: the walk's `models`; `PredictOptions.withModels` (a copy, never the caller's options) carries the loaded catalog to the vector echo, reference / length issues, limit estimates (`LimitInputs.Models`), p-value counts and `computeStreamable`; a Compose slot's catalog (`validateComposeSlots`) reaches its slot verdict and a chain stage's its limits. `mergegate` passes none — it excludes every request with windows first. An output-column listing (`AggregationOutputColumns`) reads no decision: `resolveListing` admits every window label, which resolves a valid request's vectors exactly as any catalog does. Before E4-S6 these sites were catalog-free and such a request was refused on both sides. Gates: `TestWindowsFirst_WindowsOverRecords` (vectors), `TestWindowsFirst_CatalogTriggeredPredictMatchesRuntime` (descriptor), `TestWindowsFirst_CatalogTriggeredRecordReaders` (processing: regression, holdout and matrix equal a stored-column twin).
- **Walk.** In the mode the windows and the post-window attributes (steps 5 / 5b) are judged between the regressions and the groups (step 4), against the record columns; the groups, aggregations and crosstab then see every window and post-window label. A window reading an aggregation output label (`types.AggregationLabelOf` over the aggregations and the crosstab cell / margin aggregations) that is no record column is `PULSE_WINDOW_INVALID` `details.reason: "windows_first_reads_aggregate"` `{window_index, field}` (fixup: drop the window-output read, or materialize first), judged before an extension feature's open column set. The output rows carry the group keys and aggregation labels only, so a sort key or post-test naming a window label is refused (a crosstab's sort still judges the record columns). Unchanged: a window-label weight (`checkWeights`, windows run after every weight resolves), a tier-1 test reading a window label.
- **Streamability.** Buffered on every shape (`processing.canStream` refuses any window; `crosstabfuse.Decide` declines any window); predict's reason names windows-first and is appended ahead of the crosstab gate, so a crosstab windows-first request is buffered too (`TestWindowsFirst_PredictStreamableMatchesRuntime`, which also checks `crosstab_fusable` against `processing.CanFuseCrosstab`).
- **Crosstab windows nothing reads (E4-S6).** On the historical order a window runs over the output rows — a grouped or aggregated request's, refused when they lack a name it reads — but a crosstab writes no output row, so its windows run only windows-first. A crosstab window no axis, cell or margin aggregation reads (directly or through a post-window attribute) is `PULSE_WINDOW_INVALID` `details.reason: "crosstab_window_unread"` `{window_index}` (`vectors.CrosstabWindowRefusal`: the walk — predict and the service entry check — and `RunCrosstab` alike); before, `RunCrosstab` dropped it silently. Predict still reports such a (refused) request buffered with `crosstab with windows runs via the buffered path`. Gates: `TestCrosstabWindowRefusal`, `TestCrosstab_UnreadWindowRefused`, `TestCrosstab_UnreadWindowPredictMatchesRuntime`.
- **Runtime (every shape, E4-S2 / E4-S3).** The engine reads the mode off `PostWindow.WindowsFirst` (`Processor.postWindowPlan`, the processor's bound models as catalog). After the filter and pre-window attribute pass (`filterThenAttributeSlots`) and BEFORE any group, aggregation or crosstab cell, `Processor.windowsFirstPass` (`attribute_post_window.go`) runs the windows over scratch record rows (`recordsToRows(filtered)`, `applyWindows`, no key orders — windows over records, `partition_by` / `order_by` unchanged), `copyWindowMembers` writes onto `filtered[i]` every window label a matrix, regression, post-window attribute or — consumer `aggregation` — an aggregation / grouper / crosstab axis / cell / margin aggregation reads (`vectors.WindowsFirstReads`, first-read order; `derivedFloat`, a non-numeric value `PROCESSING_CONFIG` `{field, value_type}`), then `applyPostWindowAttributes` runs with nil rows (the record carries the label). Callers: `processRecords` (ungrouped: `aggregateWithComponents`; grouped: `processGrouped` over the same records — per-bucket aggregations, tier-1 tests and Components exactly as over a cohort column; the post-aggregate window step and step 4b are skipped) and the buffered `RunCrosstab` (axes, cells, margins and axis Components partition the window-carrying records). Every result equals the same request over a cohort carrying the window column (`TestWindowsFirst_WindowColumnAggregatesAsCohortColumn`, `TestWindowsFirst_GroupedSumByDateBucket`, `TestWindowsFirst_CrosstabCellsByDateBucket`, against the BUFFERED arm — a streamed twin folds `AGG_STDDEV` Welford-style, other bits); the response rows are the aggregation / group / crosstab rows (no window column), Components in declared slot order. The streaming arms never see the mode (`canStream` refuses any window) and neither does the fused crosstab (`crosstabfuse.Decide` declines any window, `windows force buffered` — before E4-S3 it admitted one and the fused arm failed `PROCESSING_INTERNAL`), so predict's `streamable` / `crosstab_fusable` and the runtime agree on every shape. **Categorical sources:** grouping by a window label over a categorical field (e.g. `GROUP_CATEGORY` on a `WIN_LAG` of a category) is refused before any row, by predict and the engine alike, with `PULSE_FIELD_TYPE_UNSUPPORTED` `{type, slot, field_type}` — every built-in window refuses a categorical field (`internal/fieldaccept`), so no window yields a category label to key by; an extension window that writes strings is the `aggregation` copy's `PROCESSING_CONFIG` above. Gates: `TestWindowsFirst_AggregationEqualsSumOfRecordRows`, `TestWindowsFirst_GrouperOnWindowLabel`, `TestWindowsFirst_CrosstabAxisOnWindowLabel`, `TestWindowsFirst_PostWindowAttributeGroupedAndCrosstab`, `TestWindowsFirst_CategoryGroupOnCategoricalWindowRefused`, `TestWindowsFirst_CategoricalWindowGroupRefusedByPredict`, `TestWindowsFirst_PredictMatchesRuntime` / `TestWindowsFirst_ServiceGroupedAndCrosstab` (service), `TestWindowsFirst_ServiceSumsLaggedColumn`, `TestWindowsFirst_NonNumericWindowRefused`, `TestWindowsFirstReads`.
- **Weights.** A window is `weighting.ClassNotWeightable` with no slot weight, so a request-level `weight` on any request with windows — windows-first included — is `PROCESSING_CONFIG` `windows[i]: <WIN> has no weighted form and carries no slot weight; drop the request weight` (`ResolveWeights`, predict and runtime alike); an instance `DefaultWeight` is skipped on the window. A slot `weight` on an aggregation weighs the window column like any cohort column. Unchanged by the mode; the skill and the recipe say so.
- **Companions (E4-S5).** Skill `windows-first` (triggers, shapes, weights, refusals, predict plan), routed from `attribute-composition`, `window-design`, the `op-win-*` skills whose label a slot commonly aggregates, and `mmm-workflow`; examples `win_column_aggregate` (ungrouped) and `win_column_by_quarter` (grouped) in `internal/examples/windows/`; the contribution-by-quarter recipe is DOCS only (`docs/src/library/mmm.md`, no workflow test — operations are tested one at a time).
- **Byte identity.** Every name that turns the mode on was refused before (unknown field, or `PULSE_ATTRIBUTE_WINDOW_ORDER`), so no valid request changes meaning; `TestWindowPredictor_PostWindowPlanInertOverCorpus` holds every example request to `WindowsFirst == false`. Gates: `TestWindowsFirst_*` (vectors, descriptor, processing), `TestExplain_WindowsFirstAttributeOrder`, `TestAggregationColumnReads`.

## Compile-once expressions (`FILTER_EXPRESSION`, `ATTR_FORMULA`)

Both compile their expr-lang program ONCE per build (`internal/processing/expr_program.go`), never per row. **Prototype**: every schema field declared with the Go type `Record.AllValues` gives it (`exprValueType` — float64; string for a dictionary categorical; `[]string` for a dictionary set; `exprenv.U64` for a `u64` — see Exact u64 fields below; `Decimal128` / `uint64` / `SetMask` otherwise), so build-time type checking equals the old per-row check on a row with every field present — same program, same results, same `PROCESSING_RUNTIME` "compiling … expression" error, now raised by `BuildFilters` / `buildFilterFuncs` / the attribute build (`bindAttribute` → `prepare`) before any row. A name the schema cannot declare (feature output, earlier attribute label) DEFERS the compile to the first record, against prototype + that record — the old first-row env — then caches it. **Env**: per row, only the named fields (`Record.exprValue`, pinned to `AllValues` by `TestRecord_ExprValueMatchesAllValues`) in a pooled map; `$env`, a deferred compile, or a record already carrying its `AllValues` map take the whole map. **Null**: a null field is absent → reads as nil. Rows with every referenced field present run the typed program; a null-input row runs an untyped twin (every name `any`, compiled lazily once) so nil follows expr-lang's nil rules uniformly (`== nil` true, `==` false, `!=` true, `in` false, `??` substitutes; ordering / arithmetic / nil-rejecting functions error). `FILTER_EXPRESSION` reads a null-input evaluation error (or nil result) as UNKNOWN → row dropped; `ATTR_FORMULA` raises it ("evaluating formula expression"). `now()` still evaluates per row. **Concurrency**: `*vm.Program` is immutable; evaluation takes a `vm.VM` from `exprVMPool` (`runPooled`, U51 E5-S4 — `expr.Run` built a VM and its stack per call, one allocation a row per expression; `VM.Run` resets its own state, so a pooled VM evaluates as a fresh one; `TestExprProgram_RunReusesVM`: a warm formula row allocates nothing), one goroutine per VM at a time; the lazy compiles sit behind a mutex + atomic publish. Gates: `TestExprProgram_CompilesOncePerBuild` (`processing.ExprCompileCount` deltas independent of row count), `TestExprProgram_MatchesPerRowCompile` (per-row-compile oracle), `TestExprValueType_MatchesAllValues` (every field type × every decode path), `TestExprFilter_NullSemantics`, `TestExprProgram_ConcurrentRuns` (`-race`). Bench `BenchmarkExprCompileOnce` (95-field join fixture, 100K rows): filter pass ~8.7 µs → ~0.14 µs/row, end to end ~24 → ~2.1 µs/row (0x01), ~24 → ~1.1 (0x02).

**Request params (U58).** `Request.Params` binds as compile-time CONSTANTS, never as an env name: `exprenv.Bound.Params` registers a patcher FIRST in `Bound.Options` that rewrites each declared `params.<name>` / `params["<name>"]` into a constant node of its normalized type (`exprenv.NormalizeParams`: an integer int64, else uint64, else float64; string; bool; a one-kind list `[]int64` / `[]uint64` / `[]float64` / `[]string` / `[]bool`), so the row env never carries params and a program is specific to its values — no stale program can serve another run. The run compiles through a per-request registry (`ExtensionRegistry.WithParams`; `Service.forRequest` copies the Service only when the request declares params), so every arm, pre-pass and overlay pass folds the same values; `newExprProgramKeyed` drops a fully folded `params` from its free names, so a param read never defers the compile. total()'s patcher runs BEFORE the fold on both sides (it keys each call by its argument's source). Refusals live in the field-reference walk (both sides' entry check): `PULSE_PARAMS_INVALID` first, then per compile `PULSE_PARAMS_FIELD_COLLISION` (`params` is a column there — schema field, derived column, vector) or `PULSE_PARAMS_UNDECLARED`; OVERLAY_FORMULA's shared gate (`formulaident.RequestSpecRefusalWithParams`) raises the undeclared read. A bare `params` is never a parameter read: it reads the column, or fails as an unknown name. A param against a `u64` field compares exactly (below); between two params or a param and a literal, expr-lang compares mixed integer kinds through `int`, so a uint64 param above 2^63 is exact for `==` / `!=` but not for ordering. **Inheritance (U58 E3-S2).** `ComposedRequest.Params` / `ChainRequest.Params` merge into every sub-request during normalization — each Compose slot (sweep and banner slots: after `banner.ExpandCompose`), each Compose fit request, each chain stage (after the root slot gate) — a sub-request's own key winning, through ONE function per root (`descx.InheritComposeParams` / `InheritChainParams`) both predict and the runtime call at the same point; the top-level block is validated first (`PULSE_PARAMS_INVALID` at the root). The merged sub-requests are shallow copies (the caller's are never written), so the echo carries the merged params and the facade resolves a chain's `return` plans from `Service.ProcessChainResolved`'s stages. A Compose-host OVERLAY_FORMULA reads the batch's top-level params: `formulaident.ComposeRefusalWithParams` (predict and the dispatcher) refuses an undeclared read, and the fold compiles through `Service.composeExtensions`. **Facet params (expression-wires E2-S4).** `FacetRequest.Params` is a facet's own block, same rules: `Service.forFacet` (right after the slot gate) folds it for the base and additive filterers, labels and overlays; the facet walk (`ScopedFacetFieldRefRefusals*` / `FacetFieldRefRefusals` / `ValidateFacet`) hands it to the synthetic Request so predict and the run refuse alike. Gates: `TestParams_*`, `TestFacetParams_*`.

**Exact u64 fields (U58 E3-S1 fix).** A `u64` field binds as its stored word, `exprenv.U64` (`Record.exprU64`: the decoder's word when the record holds it for the value it holds now — `planeExact` and the echo equal — else the float64 echo, so a column a feature or attribute rewrote binds as before; an expression reading `$env` binds the echo too). Three patchers in `exprenv.Options` (`internal/exprenv/u64.go`): a one-shot WRAP turns every U64-typed node into `__pulse_u64(x)` → its float64 echo (expr-lang's checker does not count a named integer type as a number, so this runs before every other one-shot patcher, and `%` / `**` / the decimal patcher / the maths built-ins judge the echo exactly as the old float64 field); a one-shot COMPARE rewrites an ACCEPTED (bool-typed) `==` `!=` `<` `<=` `>` `>=` or `in` over a wrapped operand against a number or an `any` value (never a decimal) into an exact builtin (word vs int64 / uint64 param, integer literal, another u64 field, float — NaN unordered; a non-number at run time takes the historical operator over the echo, same panic text, same location); a repeatable RETYPE, registered LAST, clears those calls' types after each repeatable pass so the final check re-judges their arguments (`id == x + "a"` still fails to compile with the float64 message). The null-row twin declares a u64 as the recognisable `u64Operand` (`exprenv.Untyped`), the wrapper yields nil there. **Unchanged:** every arithmetic / function / result type (always the echo, bits included, at any magnitude), compile errors, nil rules. **Changed:** a comparison or `in` whose operands differ past 2^53 — `id == 9007199254740993` is now false for id = 2^53, which the rounded echo called true. Predict declares the same type through `exprenv.Prototype`. The filter precompute's per-entry decode writes the word too, and a `params.<name>` read no longer disqualifies a filter from precompute (`exprPureInputs` drops a folded `params`). Gates: `TestU64Expr_*` (exprenv, processing), `TestParams_U64FieldExactAcrossArms` (DecodeWorkers 1 ≡ 4), `TestParams_U64FieldPredictMatchesRuntime`, `TestParams_U64GroupMemberPrecompute`.
